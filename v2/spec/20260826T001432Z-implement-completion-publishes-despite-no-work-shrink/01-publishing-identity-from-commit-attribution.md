# Resolve publishing identity from commit attribution

## Problem

The completion tail also skips publication outright when no publishing identity resolves. `publicationAgent` is `lastResult.kind === "complete" ? (completionAgent ?? (isReviewLastStep ? (durableWriteAgent ?? completionStep?.agents[0]) : undefined)) : undefined`, and both the landing block and the whole commit/push/PR block (including the completion committer call itself) are gated on `publicationAgent !== undefined`. Outside a review-last workflow there is no fallback and no visible failure: the tail returns `complete` with nothing published — the committer is never even invoked.

This is the actual mechanism behind the 2026-08-23 strand on `20260823T000833Z-dismiss-run-durable-flag`, not the commit-count gate [subspec 00](./00-publish-branch-ahead-of-base.md) addresses: that run's final boundary attributed no `completionAgent`, the workflow was not review-last, `publicationAgent` resolved to `undefined`, and the entire publish path — including the committer call that would otherwise have produced a real `commitSha` — never ran.

The shape is reachable on base, not dead code: `prepareWorkflowStep` (`v2/src/execution/workflow-runner.ts`) reuses a durable `completed` row and re-emits `completionAgent` only when the row carries one (`completionAgent?.trim()`, stored as nullable `completion_agent`), and `runShrinkAfterImplementComplete` does the same for the hidden `~shrink` row. A re-dispatched implement whose `implement` and `implement~shrink` rows are already `completed` without attribution reaches the tail with `completionAgent === undefined` while its branch still carries the completed spec's commits.

This subspec is independent of subspec 00: its regression fixtures need a branch with real, pre-existing content ahead of base, which already resolves a `commitSha` under both the pre-fix and the 00-fixed committer gate (00's content check is a no-op wherever real content already differs from base). Either subspec can land first.

## Decision ledger

- The fallback identity is read from the branch's own `Jarvis-Agent` trailers via the existing `readBranchCommits` (`v2/src/execution/pr-attribution.ts`), newest attributed commit first; rules out attributing to the step's configured `agents[0]`, which quota fallback can make a different agent than the one that produced the commits.
- The fallback stays scoped inside the completion arm: `publicationAgent` is computed as `lastResult.kind === "complete" && boundaryAgent === undefined ? await branchCommitAgent(completionStep) : boundaryAgent`, where `boundaryAgent` is the existing `lastResult.kind === "complete" ? (...) : undefined` expression unchanged. Rules out appending the fallback to the resolved value outside that ternary, which would fire the git read on non-`complete` results too.
- The `boundaryAgent === undefined` check short-circuits the await, so the git read happens only on the unresolved-identity path within a completed run; rules out a probe on every completed workflow.
- A branch whose commits carry no `Jarvis-Agent` trailer resolves no identity and keeps the existing skip (and, for review-last, the existing visible failure); rules out synthesizing an author for commits Jarvis did not make.
- An unreadable branch log resolves to no identity rather than failing the run; rules out a diagnostic git read that can strand a completed spec.
- **The fallback is not scoped away from review-last in code, but is practically reachable only on non-review-last workflows.** `branchCommitAgent` fires whenever `boundaryAgent === undefined`, with no `isReviewLastStep` check of its own — so in the vanishingly rare case where review-last's own chain (`completionAgent`, `durableWriteAgent`, *and* `completionStep?.agents[0]`) is entirely unresolved, the fallback applies there too, narrowing rather than eliminating the `no completion agent available to attribute the publication commit` failure (`workflow-runner.ts:888-891`) to "boundary unresolved *and* the branch carries no `Jarvis-Agent` trailer either". A configured write step always has at least one agent, so that combination was already near-unreachable before this change and remains so — the fallback's real, practically-exercised surface is non-review-last (standalone and pipeline implement) workflows, where `boundaryAgent` is always `undefined` and `branchCommitAgent` is the only source of a resolved identity. No test asserts the review-last failure path is unreachable — there is nothing to pin for a combination that cannot be practically constructed.
- **Scope is this one call site.** Three other sites raise the same "no attributable agent" refusal shape (`:3082` plan-landing recovery, `:3554` populated-intent resume, `:4344` mutation-finalization replay); they keep pre-fix behavior — no commit-attribution fallback — deliberately, not by oversight. Deferred pipeline settlement now routes stages through resume, so a stage that lands on one of those three sites can still hit the old skip after this change ships; extending `branchCommitAgent` to them is a follow-up if that gap proves live in practice, not part of this subspec.
- **Re-publication of an already-settled spec is an accepted, documented limitation, not newly guarded against.** With identity now resolvable from commit history, a re-dispatch of a spec whose PR already merged can reach the publish path where pre-fix it silently stayed `complete`; the resulting `gh pr ready`/`gh pr merge` failure on an already-closed PR is `ready_flip_failed`, a terminal non-resumable outcome. This subspec does not add new "already-merged" detection — existing dispatch/resume guards are expected to prevent re-running a fully settled spec in normal operation, and hardening that boundary is a separate concern.
