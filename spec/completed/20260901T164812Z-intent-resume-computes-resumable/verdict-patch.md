Reviewing the implementation and resume-admission paths against the spec before issuing the verdict.
## Verdict — required outcomes

1. **Align `loop_finished.resumable` with post-settlement resume admission.** The spec requires projected `resumable` to agree with `resolveIntentFinalizationResumeContext`. Intent admission is row/state-based (`isReviewLandingRecoveryAttempt` plus populated `.jarvis-intent-stage/`), not terminal `loopOutcomeKind` alone. `settleIntentResumeFailure` always settles `invocation_failure` with `failureKind: "landing"` while emitting `invocation_failure` or `completion_commit_failed` on the log. A static set containing only `landing_failed` makes every real call to this function project `resumable: false`, including populated-stage paths (no completion agent, landing I/O error) where admission still succeeds. That inverts the original bug for those cases and violates the spec’s bidirectional contract.

2. **Restore the positive acceptance criterion.** AC #2 requires a test that `settleIntentResumeFailure` emits `loop_finished.resumable: true` for a resumable outcome. No such test exists; the only set member (`landing_failed`) never flows through this function. At least one exercised settlement path where post-settlement admission succeeds must assert `resumable: true`. The no-agent populated-stage test currently expects `false` and must be corrected once projection is fixed.

3. **Replace the partial agreement test with a settle-row agreement test.** AC #3 requires bidirectional alignment: every resumable kind is admitted, and no admitted post-settlement row is omitted. The current test only loops set members against pre-settlement seeds and hardcodes three `Set.has` checks; it never compares admission on the row *after* settlement to the emitted `loop_finished.resumable`. Add an intent-finalization analogue of the review-mutation settle-agreement test: drive `resumePopulatedIntentPublication` through `settleIntentResumeFailure`, then assert `loop_finished.resumable === resolveIntentFinalizationResumeContext(settledRun).ok` for both admissible and inadmissible outcomes.

4. **Make `INTENT_FINALIZATION_RESUMABLE_OUTCOME_KINDS` truthful or demote its role in settlement.** If the exported set remains, its membership and comment must match what governs settlement projection and must be enforced by the agreement test. A kind-only set that excludes `invocation_failure` cannot satisfy the spec while admission admits landing `invocation_failure` with a populated stage. Settlement should derive `resumable` from the same admission predicate (or an equivalent post-settlement check), not from a set that `settleIntentResumeFailure` never satisfies at runtime.

5. **Tighten the doc sentence.** The workflow-runner note should state that intent-finalization settlement projects `resumable` from admission alignment (same *pattern* as the review-mutation twin), not imply intent admission uses the same terminal-kind set predicate.

**Rationale:** The patch correctly fixes false-positive `resumable: true` for empty-stage `completion_commit_failed`, but it trades that for false-negative `resumable: false` on populated-stage `invocation_failure` where resume still works — directly contradicting spec decisions and AC #3. Checked acceptance criteria for the positive case and bidirectional agreement are not actually met. The actuator must close the admission-alignment gap before this spec can land.
