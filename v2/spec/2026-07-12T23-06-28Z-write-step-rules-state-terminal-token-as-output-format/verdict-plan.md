## Verdict — refinements required

The core change (reword the shared constant into an output-format rule; leave parsing alone) is right and correctly sized as one subspec. But the draft's factual claims about the parser, the prompt surfaces, and the test blast radius are wrong in ways that would produce a red suite and a misleading decision record. Refine as follows.

**1. Re-ground the decision record on the parser as it actually is.** `parseStepOutcomeToken` (`v2/src/execution/step-runner.ts`) is *lenient*, not strict: exact-match, then last bare-token line, then a global last-token-word scan anywhere in stdout. Two consequences the spec must absorb:
- The "keep the parser unchanged" decision stands, but its rationale cannot be "don't loosen the parser" — that risk is already live. State the real reason: the reword makes the lenient fallback tiers unnecessary; changing the parser is a separate concern.
- Drop the phrase "the parser's last-line preference." The preference is for the last *token-only line*. Pinning the final line to a bare token is still the correct wording — say it targets the explicit bare-token-line tier.

**2. Fix the problem statement's causal claim.** Prose containing a token word still parses (to a possibly wrong token); `invalid_token` only occurs when no token word appears at all. Either cite a real observed `invalid_token` step, or restate the problem as: the rule reads as an enum description, so agents don't reliably emit a bare final-line token, and the outcome is decided by lenient fallback or recorded `invalid_token`.

**3. Correct the prompt-surface inventory; AC 2 is factually wrong.** The three surfaces that render the constant are `plan.prompt.draft`, `intent.prompt.split`, and `write.execute` (the default write prompt — the spec never names it). Only the two shared builders (`shared/prompts/plan-draft.ts`, `intent-split.ts`) emit a `## Step completion` heading; `prompts/write/execute.md` interpolates a bare `<STEP_RULES>` with no such heading. AC 2 as written asserts a structure that doesn't exist on the default path and, for the two builders, is trivially true of any input string (they echo whatever they're passed). Replace it with a claim that is actually verifiable: that the call sites (`plan-workflow-steps.ts`, `intent-workflow-steps.ts`, `write-loop-input.ts`) pass `DEFAULT_WRITE_STEP_RULES` — a preservation claim, so per spec guidance cite the pinning tests rather than paraphrase.

**4. "Reaches every write prompt" is false and must be scoped honestly.** `patch.prompt.body` (implement) sets `stepRules: DEFAULT_WRITE_STEP_RULES` but declares no `STEP_RULES` placeholder, and `executeDefaultWrite` only wires `STEP_RULES` for `write.execute` — every other promptId renders from `promptPlaceholders`, which the implement step never populates. The implement step's step rules are dead text on the payload today; rewording the constant changes nothing there. That plumbing gap is a distinct defect and belongs in its own intent, not this wording change — but the spec must stop claiming coverage it doesn't have, and should name the gap explicitly as out of scope. Likewise scope out the daemon reattach path (`daemon.ts` reconstructs with `stepRules: ""`).

**5. State that the wording must be self-anchoring.** `daemon-revise` appends the operator prompt *after* the step rules, so section-relative phrasing ("end this section with…") is defeatable. The rule must anchor on the response ("the final line of your response must be…").

**6. Enumerate the full test blast radius and the required test scripts.** The literal is hardcoded in `v2/src/cli.test.ts` (two sites), `v2/src/tui/tui-daemon-client.test.ts`, `v2/src/execution/write.test.ts`, `v2/src/execution/write-loop-input.test.ts`, and as fixtures in `shared/prompts/plan-draft.test.ts` and `intent-split.test.ts`. AC 4 names only two of these; the rest land red. Because the change touches `shared/**`, the repo's scope rule requires `test:v1` + `test:v2` + `test:integration:v2` — the spec currently names no test scripts at all.

**7. Reconcile the docs, don't create a contradiction.** `v2/docs/prompts.md` documents the `## Step completion` suffix and `v2/docs/shared-step-runner.md` documents the lenient parser. A new strict-sounding contract in `write-behavior.md` must say both things explicitly — the *prompt* demands a bare final-line token; the *parser* tolerates less — in one durable home with cross-references, rather than asserting strictness the parser doesn't enforce. Note also that this changes existing v1-visible behavior only at the prompt level; confirm whether `v2/docs/v1-behaviors.md` needs a line.

No split required.
