## What went wrong, and why

**Four wrong conclusions, all from reading partial tool output instead of measuring.**

1. *Phantom red `main`.* Grepped `bun run check` output, saw findings, called it red. They were
   warnings — `noNonNullAssertion` is `warn`, and `noUnusedImports` doesn't fail either. Verified by
   reverting the fix and capturing the exit code: 0 both ways. Seed retracted, and the claim that
   "every implement run inherited a red gate" was false.
2. *False-green formatting.* The same grep pattern didn't match formatter errors, so a failing
   `check` read as green and #2165 went to CI red.
3. *"`bun run fix` had nothing to fix."* The sandbox silently blocks writes to
   `~/.jarvis/worktrees/`, so `--write` reported "no fixes applied" rather than failing.
4. *"Tests eat the iteration."* `test:v2` is 84 s. Iterations are long because the agent generates a
   lot of code, which was the operator's read from the start.

A fifth: the seed for per-iteration commits initially asked to *build* a feature that already exists
(`commitProgressIteration`, spec `20260724T211609Z`). The operator's PR-history check settled it —
PRs #2162 and #2164 each carry two same-headline commits.

**The P0's cost.** Roughly 4.5 hours across four attempts. Two were `iteration_timeout` on subspec
02. A verdict-salvage amendment made that subspec *larger*, which was an operator error.

per escalation *segment* rather than per rung instead of silently diverging from its own spec. All
three passed diff-derived mutation verification, runtime smoke, and a green gate.

## Facts worth keeping

- Actuator rungs are **head-only by design** (`resolveInvocationBindings`, spec

  Escalation on timeout goes to the next *agent*.
