### The land-a-slice pattern (new, and it is what closed #3122)

A multi-subspec spec that cannot finish inside one iteration budget **cannot converge by re-dispatch**. A re-run either resets the workspace (discarding completed subspecs) or is refused by the preserve-landed-criteria gate, which names the ticked files. Landing the completed subspecs to `main` clears the gate so the next dispatch routes to the first unfinished one. Used for the archive lane (#3360 → #3363, which is how #3122 actually closed), `modularize-daemon` [#3364], and `pipeline-resume-recover` [#3365]. ## This-session (2026-09-05 — a daemon outage, root-caused in three layers)

Operator-present. The session's asks were pipeline dogfooding and parallelization at every stage; most of it went to an outage that made the harness unusable machine-wide, and the fixes are the session's real output.

**The whole machine lost its daemon, and the harness was deleting its own socket.** `startIpcServer` ran `rmSync(socketPath, {force:true})` unconditionally before binding (dating to #729), so every daemon start — including the auto-start any `jarvis` command performs when it cannot reach one — unlinked the incumbent's directory entry. The incumbent keeps its bound inode and serves established connections, but `connect()` resolves by path, so every new client gets `ENOENT`: `daemon status` reads `stopped` for a healthy daemon and every run it owns becomes unobservable. It self-perpetuates, because each stranded command auto-starts another daemon that unlinks the socket again — 16 orphaned `daemon-entrypoint` processes and 242 logged `EPERM`s before it was understood. Fixed in three layers: [#3468] refuses to replace a live socket (connect probe; a probe *timeout* counts as live, since a saturated daemon is still serving), [#3469] stops classifying from `existsSync` because a denied `stat` false-negatives into deletion, and [#3471] — the one that actually closed it — unlinks only a **proven-stale** entry.

**The guard was defeated twice before it held, and both misses were the same mistake: trusting a signal that can false-negative into deletion.** Under the sandbox agent sessions run in, `connect()` to a *live* socket under `~/.jarvis` returns **ENOENT**, which #3469 classified as `absent` and removed. `absent` now removes nothing — the probe found nothing there, so unlinking can never be necessary, and it was the only route by which a live socket could be deleted. Generalizable: a guard that decides whether to destroy something must treat every inconclusive answer as "do not destroy", and `ENOENT` from a caller that cannot see the path is inconclusive, not authoritative.

**`daemon status` lied throughout, which is why the diagnosis took three attempts.** Two coupled defects ([#3473]): `startDaemon` wrote the pid file at spawn time, so a start that never bound overwrote a healthy daemon's pid with one that never served (observed: pid file `75064`, daemon actually serving `74393`); and `getDaemonStatus` short-circuited on that pid, reporting `stopped` regardless of whether the socket answered. The socket is the service, so it now decides, and the pid is gone from the signature. This is the [[terminal-state-honesty-invariant]] class on the lifecycle surface — a status derived from a proxy rather than from the thing itself — and it repeatedly pointed toward `kill -9` on a working machine.

**Diagnosis notes worth keeping.** `lsof -p <pid> | grep unix` showing a socket path that `stat` says does not exist is the signature of bound-then-unlinked, and it distinguishes this from every documented "daemon is dead" shape whose recovery is destructive. A live listening canary named `daemon-<16hex>.sock` surviving 90s is what ruled out a periodic reaper and pointed the search back at daemon startup. Both are cheap and were decisive; both are now in the runbook.

**A subagent found what three of my own passes missed.** I had ruled out the deletion site by reading the code, twice, and was reasoning about "contested keys" — a red herring; the key is simply the one every agent session's auto-start targets.
