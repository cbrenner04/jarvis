## Verdict

Required outcomes before this subspec's acceptance criteria can be considered met:

1. **`getCurrentBranch` (shared/git.ts) must be bounded on the shrink path.** `shrink.ts` calls this unconditionally on every shrink run (line 387) and its underlying `execFileSync` currently has no timeout. Acceptance criterion 2 ("every real git subprocess on this path runs under the same 30s failure window") is not met while this call site is unbounded. Since `shared/git.ts` is version-agnostic shared code used by other callers, do not change its exported signature/behavior globally — bound this call from the shrink path itself (e.g., a local bounded wrapper/helper used at the shrink call site) so shared callers are unaffected.

2. **The `git push` invoked via `pushCurrent` (v1/src/worktree.ts) must be bounded when reached from the commit-success path in `commitShrinkPass`.** `commitShrinkPass` bounds its own status/add/commit calls but then calls `pushCurrent`, whose internal `execFileSync("git", ["push", ...])` has no timeout. A stall here would hang the success/commit path past the promised 30s bound, violating the same acceptance criterion. Fix by bounding this git invocation (directly, or via an injectable bounded-exec path) without changing `pushCurrent`'s contract for other unrelated callers outside the shrink path.

3. **Test coverage must actually exercise both fixed call sites.** The current stalled-git test replaces `git` globally and hangs at the very first call (`rev-parse HEAD`), so `agent.calls` stays empty — it never advances far enough to reach `getCurrentBranch` or the commit/push path. Extend or add test case(s) so the suite drives execution past the initial HEAD read (e.g., a real HEAD read succeeds, then the stall is injected at the branch-read or push call site) to prove those two sites are bounded. Without this, a regression in either fixed call site would go undetected, undermining acceptance criterion 4 (the file must exercise the real stall behavior, not merely appear to based on an incomplete path).

**Rationale:** The spec's acceptance criteria state "every real git subprocess on this path runs under the same 30s failure window" and require the test to exercise the real stall behavior. Both unbounded call sites are unconditionally reachable on the shrink path (one always, one on success), so they fall inside the stated scope — this is not the deferred "sibling audit" or "shared helper for other suites" work explicitly ruled out of scope. Leaving them unbounded, or leaving them untested, means the acceptance criteria are not actually satisfied by the current implementation.
