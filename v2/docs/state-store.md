# State store

Durable state for v2 runs and execution history: SQLite at `~/.jarvis/state/v2.sqlite`.

`openStateStore(path?)` creates or opens the file and bootstraps the schema idempotently before any operation; tests pass a path override and write nothing under `~/.jarvis`. Fresh stores receive a baselined `CREATE` matching the current on-disk contract. Stores that already ran pre-squash migrations `004`–`030` upgrade once on open to that same shape via `031-baseline-squash` in `_migrations`; row load/save semantics are unchanged and no operator action is required.

## Concurrency & journal mode

The store opens SQLite with **WAL (Write-Ahead Logging)** journal mode and a 5-second busy timeout, enabling concurrent reader-vs-writer access on a single machine:

- **WAL mode** separates reads from writes: multiple readers can observe committed snapshots while a writer holds an uncommitted transaction (serialization points are commits, not transaction starts).
- **busy_timeout** causes writers to wait up to 5 seconds if a reader holds a lock, rather than failing instantly; this accommodates routine polling (daemon `listRuns`, TUI status checks) during active runs.
- **-wal** and **-shm** sidecar files: WAL requires two additional files alongside the main database (`-wal` for the write-ahead log, `-shm` for shared memory). These must reside on the same filesystem as the main database and be readable/writable by the process. Network filesystems (NFS, cloud drives) are unsupported; single-machine access is guaranteed only. See [On-disk maintenance](#on-disk-maintenance) for backup, purge, and hand-copy.

A failed WAL setup (e.g., restricted filesystems, old SQLite, or sandboxed environments) silently falls back to the default rollback journal; the store remains functional but with reduced concurrency (readers block writers and vice versa).

Overlapping workflows and routine TUI polling are safe against the store on one machine without additional locking or coordination.

## On-disk maintenance

Backup, purge, or hand-copy of the orchestration store must move or delete `v2.sqlite`, `v2.sqlite-wal`, and `v2.sqlite-shm` under `~/.jarvis/state/` together. Copying or removing only the main file can strand committed rows or leave a torn store. In-repo helpers `copyOrchestrationStore` and `removeOrchestrationStore` in [`state-store-on-disk.ts`](../src/persistence/state-store-on-disk.ts) apply the same rule for tests and tooling.

## Schema

- `runs` — orchestration identity, lifecycle, and checkpoint: `id`, `project`, `spec_ref`, `created_at`, `status` (`in-progress` | `completed` | `blocked` | `budget-soft-stopped` | `paused` | `failed` | `interrupted` | `killed` | `queued`), `attempt_count` (durable resume checkpoint), `worktree_path` (reconstructible pointer), `branch` (durable), `spec_path`, `step_id` (nullable, opaque workflow step identifier for multi-step resume tracking), nullable `workflow_snapshot` JSON (`{ invocationId, steps: [{ stepId, role }] }`) for workflow-backed runs, nullable `reconciled_at` (Unix epoch milliseconds when orphan reconciliation settled the run without an open `in-progress` attempt), nullable `finished_at` (Unix epoch milliseconds, stamped by `setRunStatus` on a terminal status write, by `commitGuardedKill` on the killed row, and by `commitTerminalRunSettlement` on terminal settlement; cleared to `NULL` when `setRunStatus` writes a non-terminal status), nullable `ready_gate_pgid` (process group id of the run's in-flight ready-gate test tree; `NULL` when no gate is in flight), nullable `dismissed_at` (Unix epoch ms) — an operator display mark, `NULL` when not dismissed, set only by `dismissRun` and cleared only by `undismissRun`, nullable `terminal_cause` TEXT (`WriteLoopOutcomeKind` string aligned with log `loopOutcomeKind`; `NULL` when unset or pre-migration), and nullable `terminal_failure_detail` TEXT (`InvocationFailureDetail` JSON; `NULL` when unset, cleared, corrupt, or pre-migration). Written via `setReadyGatePgid` by the ready-finalize gate and required-integration invocations (`v2/src/execution/ready-finalize.ts`, `v2/src/execution/write-loop.ts`): recorded at spawn and cleared on settlement (success or failure) in each invocation's own `finally`, so at most one of the two is ever set at a time.
- `attempts` — one row per step attempt: `id`, `run_id`, `attempt_number`, `started_at`, `status` (`in-progress` | `completed`), plus the durable outcome once committed: `outcome_kind` (`done` | `no-work` | `progress` | `blocked` | `contract_miss` | `invocation_failure` | `invalid_token`), `completed_at`, and nullable `invocation_failure_detail` JSON (`{ failureKind, bindingAttempts }`) on terminal binding-chain `invocation_failure` only.
- `pipelines` — one row per admitted pipeline: `id`, `name`, `created_at`, and an immutable `definition` JSON snapshot (the validated `PipelineDefinition` at admission time; later mutation of the caller's source object never affects the stored row). Nullable `context` JSON holds the immutable admitted `PipelineContext` snapshot (`{ cwd, configPath, seed?, seedPath?, targetDir?, projectRegistry? }`); `cwd` and `configPath` are required on admission; optional inline `seed` or admission-supplied `seedPath` (xor at admission; neither required; path resolution is not this layer's job). Ambiguous or dual-populated rows load as stored with no migrate-on-read. Pre-migration rows and admissions that omit context read back `context = null` — this layer never synthesizes admission input on load. Opaque `loadPipeline` / `mapPipelineRow` parse does not validate required fields; `loadPipelineContext` in [`state-store.ts`](../src/persistence/state-store.ts) validates `cwd` and `configPath` at consumption boundaries and returns `{ kind: "pipeline-context-loader", errors }` when stored JSON is incomplete — at execution (`runPipeline` / `continuePipeline`) that failure records `pipeline-context-loader` on the pending workflow stage's `failure_detail` and skips dispatch, without rejecting opaque parse at load time. Nullable `terminal_publication_failure` JSON records a durable terminal-action failure (`terminalAction`, normalized `PublicationFailure`, optional `prNumber`/`prUrl`); nullable `terminal_publication_succeeded_at` stamps successful settlement. `owner_identity` (nullable `<pid>:<process-start-epoch>` of the admitting process, stamped by `createPipeline`, same shape as `runs.owner_identity`) and `status` (`'active'` | `'interrupted'`; `'active'` at admission, `'interrupted'` set by `reconcilePipelines` — the only pipeline status this layer defines) back pipeline-restart reconciliation. Nullable `dismissed_at` (Unix epoch ms) is an operator display mark: `NULL` when not dismissed, set only by `dismissPipeline` and cleared only by `undismissPipeline`.
- `pipeline_stages` — one row per `(stage_id, branch_key)` within a pipeline, `UNIQUE (pipeline_id, stage_id, branch_key)`: `id`, `pipeline_id` (FK, `REFERENCES pipelines(id)`), `stage_id` (authored identifier), `branch_key` (`NOT NULL`; `"default"` at admission and for pre-migration rows), `position` (authored order, 0-based; branch siblings for the same authored stage share `position`), `status` (free-form string; this layer enforces persistence only, not a transition policy, except for the values `reconcilePipelines` depends on — `pending` is undispatched, `awaiting`/`approved`/`rejected` are decided approval states left untouched by restart reconciliation, `succeeded`/`failed`/`interrupted`/`skipped` are terminal or blocked-suffix rows left untouched by restart reconciliation, anything else is active; that same set — `succeeded` | `failed` | `interrupted` | `skipped` — is also the terminal set `updateStage` derives `ended_at` for, see below), nullable `workflow_invocation_id`, nullable `started_at`/`ended_at` (Unix epoch milliseconds), and nullable `artifact`/`failure_detail` JSON (schema-free envelopes, opaque to this layer). Lifecycle fields (`status`, `workflow_invocation_id`, `started_at`, `ended_at`, `artifact`, `failure_detail`) initialize at admission: `status` to `'pending'`, the rest to `NULL`. Approval rows use the same durable `id`, authored `stage_id`, and `branch_key` keys; conditional approval operations address rows by durable `id` only. Approval status vocabulary on those rows: `pending` (undispatched), `awaiting` (boundary reached, decision outstanding), `approved`, and `rejected`. Nullable `decided_at` (Unix epoch milliseconds) is the approval decision timestamp: `NULL` until decided, stamped only by `commitApprovalDecision`, and not settable through `StageLifecyclePatch`.
- `pipeline_stage_admission` — one row per in-flight durable dispatch claim keyed by `(pipeline_id, stage_id, branch_key)` with `PRIMARY KEY (pipeline_id, stage_id, branch_key)`: `pipeline_id` (FK, `REFERENCES pipelines(id)`), `stage_id`, `branch_key`, and `holder_identity` (`<pid>:<process-start-epoch>` of the claiming process at claim time). Distinct from in-memory `dispatchClaims` in `pipeline-execution.ts`, which coordinate fan-out sibling dispatch within one pipeline run; this table coordinates cross-continuation dispatch for the same stage row across overlapping `continuePipeline` callers.
- `operator_notification_deliveries` — delivery ledger for operator-notification sweep: `incident_id`, `transition`, `delivered_at` (Unix epoch ms), `PRIMARY KEY (incident_id, transition)`. Written only by the sweep; existing settlement writers are untouched.

The store enables `PRAGMA foreign_keys=ON` on its connection, so `pipeline_stages.pipeline_id → pipelines(id)` and `attempts.run_id → runs(id)` are enforced, not merely declared.

**Baseline bootstrap:** Fresh stores apply only the baselined `CREATE` in [`state-store.ts`](../src/persistence/state-store.ts) (orchestration tables at the current durable shape) and stamp `_migrations` with `031-baseline-squash`.

**Pre-squash upgrade:** Stores with any legacy `_migrations` id other than `031-baseline-squash` (the pre-squash `004`–`030` era) run `upgradeFromLegacyEra` once on open: idempotent `ADD COLUMN` / table-create / `pipeline_stages` branch-key rebuild to reach the baselined shape, then stamp `031-baseline-squash`. Partial-era files (migration chain interrupted) are covered. Row nullability, backfill behavior, and load/save semantics are unchanged from a fully migrated pre-squash store; no operator action on open. Subsequent opens are no-ops.

## API

Repository-style named ops keyed by durable IDs — no public SQL surface. Signatures: the `StateStore` interface in [`state-store.ts`](../src/persistence/state-store.ts).

- `createRun` — insert a run (`in-progress`, zero attempts); accepts optional `stepId` and optional `workflowSnapshot` for workflow-backed runs; returns its ID.
- `loadRun` / `findRunByProjectBranch` — read a run plus attempt history; the latter resolves the `(project, branch, stepId)` resume key (stepId optional for single-step) to the most recent run.
- `recordAttemptStart` — insert an `in-progress` attempt row.
- `commitCompletionBoundary` — the one transactional write: attempt completion, outcome classification, and run checkpoint (`attempt_count` + status) commit or roll back together. Idempotent: re-committing a finished boundary is a no-op, so recovery can never double-advance the checkpoint or duplicate an outcome. When `runStatus` is terminal and optional settlement evidence (`terminalCause`, `prNumber`/`prUrl`, `terminalFailureDetail`) is supplied, the run-row update routes through the same settlement writes as `commitTerminalRunSettlement` inside the boundary transaction (including `finished_at` and evidence columns); nonterminal boundaries and terminal boundaries without settlement evidence keep the legacy status-only run update.
- `setRunStatus` — status update outside a boundary. Current use: marking `budget-soft-stopped` when an invocation exits on budget after its last committed `progress` boundary. Stamps `finished_at` to `Date.now()` when the new status is terminal (`isTerminalRunStatus`), clears it to `NULL` otherwise — a resumed run carries no stale finish time.
- `commitGuardedKill` — legacy guarded helper: set `killed` unless the row is already boundary-terminal (`completed`, `blocked`, `failed`, `interrupted`); `paused` is not boundary-terminal. Stamps `finished_at` on the killed row. Daemon production kill no longer calls it; daemon admission precedes `commitTerminalRunSettlement`.
- `commitTerminalRunSettlement` — one transactional writer for terminal `runs.status`, `finished_at`, optional durable `terminalCause` (`WriteLoopOutcomeKind`, validated on write), optional `prNumber`/`prUrl`, and optional `terminalFailureDetail` (`InvocationFailureDetail` JSON). Accepts only `isTerminalRunStatus` values; nonterminal statuses refuse without mutation. Omitted optional evidence fields leave their columns unchanged; explicit `null` clears that column. `prNumber` and `prUrl` use independent per-field omitted-vs-null semantics (unlike `setPrEvidence`, which always writes both). Stamps `finished_at` to `Date.now()` inside the settlement transaction. Runs at least two in-transaction `UPDATE` statements (terminal `status`/`finished_at` first, then evidence columns) so `beforeSecondWrite` runs after the first statement; `beforeSecondWrite` is a test seam only. Daemon kill and restart reconciliation use it after daemon-owned admission and omit `terminalCause` and `terminalFailureDetail`. Execution-owned terminal run writers are `commitTerminalRunSettlement` and settlement-backed `commitCompletionBoundary` only (`terminalCause`, optional PR evidence, optional `terminalFailureDetail` on the boundary args); production `v2/src/execution/**` is guarded by `execution-terminal-settlement-guard.test.ts`. Daemon-owned kill/reconcile paths remain separate — see [`daemon-host.md`](./daemon-host.md).
- `dismissRun` / `undismissRun` — set or clear `dismissed_at`, an operator display mark unrelated to lifecycle; parity with the `dismissPipeline`/`undismissPipeline` pair. Both take a positional `runId` and return `RunDismissalOutcome`: `{ kind: "applied", runId }` or `{ kind: "refused", runId, reason: "run_not_found" }` (`RunDismissalRefusalReason`) for an unknown run id. `dismissRun` is a first-writer-wins idempotent stamp: re-dismissing an already-dismissed row leaves the original timestamp untouched. `undismissRun` unconditionally writes `NULL`; called on a never-dismissed run it is a no-op success (`applied`, `dismissedAt` stays `NULL`). Neither operation touches attempt rows, any other run's row, or the targeted run's lifecycle columns (`status`, `attempt_count`, `workflow_snapshot`, `finished_at`, `reconciled_at`, publication columns). The store never filters on `dismissed_at`: `listRuns`, `loadRun`, and `findRunByProjectBranch` return dismissed runs like any other, and `beginRunReconciliation` ignores the column, so a dismissed run keeps executing and keeps being reconciled. Nothing in the store clears `dismissed_at` on a lifecycle transition — a resumed or reconciled run stays dismissed. Dismissal never deletes the durable row. Default-excluding a dismissed run from a projection, and the terminal-retention interaction, are the daemon's concern, not this layer's.
- `forceKillOwnerAdmits` (async) — owner-liveness guard backing daemon `kill`'s `force` path: admits when the run's `owner_identity` is `NULL`, equals the calling store's own identity, or names a process `isOwnerAlive` reports dead; refuses a different still-live owner. Read-only — it does not itself write status; the daemon reloads durable status after this asynchronous check and synchronously calls `commitTerminalRunSettlement` only when the row remains non-terminal. A second internal consumer of `owner_identity` alongside `beginRunReconciliation`, deliberately not reusing that function's discriminant (which skips rows owned by the current process — exactly the row this guard exists to admit).
- `setReadyGatePgid` — record (or clear, with `null`) the process group id of the run's in-flight ready-gate test tree. A recorded id replaces any prior value on that run — one in-flight gate per run. Clearing writes `NULL` via its own branch rather than a shared bound-parameter update, so record and clear are independently testable. `null` means no gate is in flight. `listReadyGateSweepCandidates` selects every row with a non-null `ready_gate_pgid` and classifies owner liveness with the same `isOwnerAlive` probe as `beginRunReconciliation` / `forceKillOwnerAdmits`; daemon startup's `sweepOrphanReadyGateGroups` signals non-live groups (SIGTERM→SIGKILL on `-pgid`, swallowing `ESRCH`/`EPERM`), then clears the column. Dead-owner rows are signaled without recorded-at bounds; recycled-pgid false positives on those rows are accepted.
- `beginRunReconciliation` / `finishRunReconciliation` — restart admission and event bookkeeping, not terminal writers. `beginRunReconciliation` applies owner-liveness admission to orphan statuses, atomically sets `reconciliation_pending`, and stamps finish metadata (attempt `completed_at` when an `in-progress` attempt exists, otherwise run `reconciled_at`; no `commitCompletionBoundary`, `outcome_kind`, or `attempt_count` bump). It never writes `runs.status`. Existing pending rows are returned for crash-after-settlement/event retry without another timestamp. The daemon reloads each returned row, chooses `killed` or durable-review `interrupted`, preserves a boundary-terminal winner, and calls `commitTerminalRunSettlement`; `finishRunReconciliation` clears pending only after the owed `run_reconciled` event is persisted or suppressed.
- `createPipeline` — admit an already-validated `PipelineDefinition`: one `pipelines` row (`owner_identity` stamped with the calling process's identity, `status = 'active'`, optional immutable `context` JSON snapshot when supplied) plus one `pending` `pipeline_stages` row per authored stage with `branch_key = 'default'`, atomically (all-or-nothing; a mid-admission fault rolls back the pipeline and every stage). Returns the generated pipeline ID. Caller-side mutation of the source `context` object after admission does not alter the stored snapshot.
- `createPipelineStageBranch` — admit an additional `pending` row for one authored stage at fan-out: copies the default sibling's `position`, initializes lifecycle fields to admission defaults, and returns the new row's durable `id`. Refuses unknown `pipelineId`/`stageId` and duplicate `(pipelineId, stageId, branchKey)`.
- `loadPipeline` — read an admitted pipeline plus its stages ordered by stored `position` ascending, then `branch_key` ascending with `"default"` first among position ties; null when unknown. Every returned stage record exposes `decidedAt`.
- `listPipelines` — read every admitted pipeline, including persisted `active` and `interrupted` rows, exactly once with every associated stage row exactly once in stored position/branch order (row count may exceed authored stage count when branch rows exist). It returns every persisted pipeline and stage field without interpreting lifecycle metadata, including `decidedAt` on every stage record. An empty store returns `[]`. Pipeline ordering, filtering, retention, and snapshot consistency against concurrent writes are unspecified and deferred until a consumer needs them. The store never filters on `dismissed_at`: `listPipelines` returns dismissed pipelines exactly like undismissed ones, and `reconcilePipelines`/`claimPipelineContinuation` ignore the column entirely, so a dismissed pipeline keeps executing and keeps being reconciled. Nothing in the store clears `dismissed_at` on a lifecycle transition — a reopened or reconciled pipeline stays dismissed. Default-excluding a dismissed pipeline from a projection is the daemon's concern, not this layer's.
- `listIncidentCandidateRuns` — SQL-filtered run rows for notification incident derivation. Caller supplies `statuses` and `sinceMs`. A row is a candidate when its `status` is in `statuses` and either the status is non-terminal (`isTerminalRunStatus` is false), or `finished_at` is `NULL`, or `finished_at >= sinceMs`. Terminal rows with `finished_at` strictly before `sinceMs` are excluded. Non-terminal rows are candidates regardless of `finished_at`. Ordering matches `listRuns` (`created_at DESC, rowid DESC`).
- `listIncidentCandidatePipelines` — SQL-filtered pipelines for notification incident derivation. Caller supplies `sinceMs`. Each matching pipeline returns once with all stage rows in stored position/branch order, same shape as `listPipelines` elements. A pipeline is a candidate when any of the following holds in SQL (not via daemon `derivePipelineState`): (1) **non-terminal stage signal** — any stage row has `status` outside the stable set `succeeded` | `failed` | `interrupted` | `skipped` | `approved` | `rejected` (covers `pending`, `awaiting`, `running`, and other active shapes); (2) **settlement-pending publication** — admitted `definition` JSON has `terminalAction`, both `terminal_publication_succeeded_at` and `terminal_publication_failure` are null, and every `default`-branch stage is in the stable set; (3) **fan-out branch signal** — any non-`default` `branch_key` row has `status` in `pending` | `awaiting` | `running`; (4) **otherwise-terminal with recent settlement** — no stage fails (1)–(3), and settlement timestamp `COALESCE(MAX(stage ended_at/decided_at), terminal_publication_succeeded_at, created_at) >= sinceMs`. Conditions (1)–(3) ignore `sinceMs`; only otherwise-terminal pipelines age out by settlement timestamp.
- `updateStage` — apply a targeted lifecycle patch (`StageLifecyclePatch`: optional `status`, `workflowInvocationId`, `startedAt`, `endedAt`, `artifact`, `failureDetail`) to one stage row in place, keyed by `(pipelineId, stageId, branchKey)`; omitted `branchKey` defaults to `"default"`. Omitted fields, and fields explicitly passed as `undefined`, are unchanged; an explicit `null` clears a nullable field. `artifact`/`failureDetail` round-trip losslessly only for JSON-representable values (no `undefined`, functions, or cyclic structures). Rejects a patch with no defined fields and an unknown target. Modifies only the targeted row — the row's `id`, `pipelineId`, `stageId`, `branchKey`, and `position` and every sibling stage are untouched. A patch whose `status` is terminal (`succeeded` | `failed` | `interrupted` | `skipped`, see `isTerminalStageStatus`) and whose `endedAt` is not already a number derives `endedAt = Date.now()` at write time — an explicit `endedAt: null` alongside a terminal status does not survive; a caller-supplied numeric `endedAt` is preserved as given. `startedAt` is never synthesized, so a stage that failed before start stays terminal with `started_at` null. Non-terminal statuses and decided-approval statuses (`approved`, `rejected`) are unaffected. Exported helper `stageLifecyclePatchWithTerminalFinish` backs the derivation.
- `settleLinkedStagesFromEntryRun` — transactionally finds every `pipeline_stages` row whose `workflowInvocationId` equals the entry run id and whose status is still `running`, then computes the entry workflow's durable rollup with `isLive: false` from its fresh run row, persisted workflow snapshot, and `findRunsByInvocationId` siblings. A non-terminal rollup writes nothing. A terminal non-`completed` rollup writes `failed` with failure evidence projected from the entry row's status, `terminalCause`, `terminalFailureDetail`, and attempts. `completed` writes `succeeded` with `{ entryRunId, invocationId?, specPath, downstreamInputs?, prNumber?, prUrl? }`; an empty `specPath` instead writes the existing missing-spec failure, and the final workflow stage of a `ready` or `merge` pipeline requires both PR fields or writes `completion_publication_missing_pr_evidence`. Only `running` rows are conditional write targets, so replay never changes or retimes `succeeded`, `failed`, `interrupted`, or `skipped` rows. Daemon callers remain on the promise-backed settlement path until a follow-on intent migrates them; log-derived `requestedBase`/`resolvedBase` are not projected by this store operation.
- `commitApprovalBoundary` — conditionally mark one `kind: "approval"` row `pending` → `awaiting` by durable `PipelineStageRecord.id` (not authored `stageId`). Returns `ApprovalOperationOutcome`: `{ kind: "applied", stageRecordId }` or `{ kind: "refused", stageRecordId, reason }`. Refusal reasons: `stage_not_found`, `not_approval_stage` (workflow rows and non-approval authored stages), `status_not_pending` (already `awaiting`/`approved`/`rejected`, or a losing race). Refused writes leave every row unchanged. Leaves `decided_at` `NULL`.
- `commitApprovalDecision` — conditionally decide one `kind: "approval"` row `awaiting` → `approved` or `rejected` by the same durable `PipelineStageRecord.id`. First writer wins; duplicate, losing-race, wrong-row, non-awaiting, and invalid-decision requests return `kind: "refused"` with `status_not_awaiting` or `invalid_decision` and leave every row unchanged. Stamps `decided_at` to `Date.now()` in the same conditional write as the status transition; a refused write stamps nothing. Exported predicates `isApprovalAuthoredStage`, `approvalBoundaryAllowsStatus`, and `approvalDecisionAllowsStatus` back the kind and status guards.
- `claimPipelineContinuation` — atomically claim an `active` or reconciled-`interrupted` pipeline for continuation by the current process: sets `owner_identity` to the sweeping process and restores `status = 'active'`. Succeeds only when `priorOwnerIdentity` matches the durable row; first writer wins (`claim_lost` on a concurrent loser). Refusal reasons: `pipeline_not_found`, `not_active`, `stale_owner`, `claim_lost`.
- `claimPipelineStageAdmission` — atomically claim durable `pipeline_stage_admission` for one `(pipelineId, stageId, branchKey)`; omitted `branchKey` defaults to `"default"`. First writer wins (`claim_lost` on a concurrent loser); re-entrant for the current holder. Returns `{ kind: "applied" }` or `{ kind: "refused", reason: "claim_lost" }`. Distinct from in-memory `dispatchClaims`, which coordinate fan-out sibling dispatch within one run.
- `releasePipelineStageAdmission` — clear the caller's durable `pipeline_stage_admission` row when `holder_identity` matches the calling process. Idempotent when no row exists (`applied`). Refuses with `stale_holder` when another holder owns the row. Omitted `branchKey` defaults to `"default"`.
- `loadPipelineStageAdmission` — read durable `pipeline_stage_admission` for one `(pipelineId, stageId, branchKey)`; omitted `branchKey` defaults to `"default"`. Returns `{ kind: "absent" }` when no row exists (distinct from a refused claim) or `{ kind: "present", holderIdentity }` when held.
- `reopenFailedPipeline` — atomically reopen one failed continuation row and its contiguous skipped suffix in place as `pending`, clearing only prior-attempt lifecycle payloads (`workflow_invocation_id`, `started_at`, `ended_at`, `artifact`, `failure_detail`, `decided_at`) while preserving each row's durable `id`, `pipeline_id`, authored `stage_id`, and `position`. Optional `branchKey` scopes analysis and reopen to one named fan-out branch; omission and `branchKey: "default"` are an exact alias, retaining unscoped whole-pipeline analysis (including its multiple-failure refusal when a sibling branch also failed — this alias never narrows). For a non-default `branchKey`: the continuation boundary is the lowest durable position carrying both a `default` row and a row keyed to that `branchKey` (`stageId`s must match at that position); analysis covers the unique `default` rows strictly before the boundary (shared prefix) plus the unique `branchKey` rows at the boundary and every later durable position (its own continuation through the last durable position), excluding every `default` row at or after the boundary and every sibling branch's rows entirely. A missing, duplicated, `stageId`-misaligned, or incomplete named continuation refuses `malformed_continuation` without ever falling back to an unscoped or sibling-branch result; the resolved continuation then applies the same exactly-one-`failed`-row, `succeeded`/`approved`-predecessor, and `skipped`-suffix shape validation as the unscoped path. Valid shape requires exactly one `failed` row, only `succeeded`/`approved` predecessors, and a suffix of only `skipped` rows; multiple failures, no failure, or any other later status refuse without mutation. An untouched `approved` predecessor keeps its `decided_at`. Both the pre-transaction check and the in-transaction re-analysis resolve the identical `branchKey` scope, so a losing race or stale re-read refuses rather than reopening a partial or wrong-branch continuation. Returns `PipelineReopenOutcome`: `{ kind: "applied", stageRecordId }` (the failed row's durable `PipelineStageRecord.id`, not its authored `stageId`) or `{ kind: "refused", pipelineId, reason }`. Refusal reasons: `pipeline_not_found`, `no_failed_stage`, `multiple_failed_stages`, `malformed_continuation`, `reopen_lost` (concurrent loser on the failed row or any suffix row); an absent or non-failed named branch also refuses through this same reason vocabulary, with no reason pinned specifically to that case yet. Exported predicates `reopenPredecessorAllowsStatus`, `reopenSuffixAllowsStatus`, and `analyzeFailedPipelineReopenShape` (now accepting the same optional `branchKey`) back the shape guards.
- `commitTerminalPublicationFailure` — atomically record a terminal-publication failure on the pipeline row (`terminalAction`, normalized `PublicationFailure`, optional `prNumber`/`prUrl`) without mutating stage rows. Idempotent when a failure or success marker is already present.
- `commitTerminalPublicationSuccess` — atomically stamp `terminal_publication_succeeded_at` when terminal publication succeeds. Idempotent when already set or when a failure is recorded.
- `dismissPipeline` / `undismissPipeline` — set or clear `dismissed_at`, an operator display mark unrelated to lifecycle. Both return `PipelineDismissalOutcome`: `{ kind: "applied", pipelineId }` or `{ kind: "refused", pipelineId, reason: "pipeline_not_found" }` (`PipelineDismissalRefusalReason`) for an unknown pipeline id. `dismissPipeline` is a first-writer-wins idempotent stamp: re-dismissing an already-dismissed row leaves the original timestamp untouched. `undismissPipeline` unconditionally writes `NULL`; called on a never-dismissed pipeline it is a no-op success (`applied`, `dismissedAt` stays `NULL`). Neither operation touches stage rows, any other pipeline's row, or the targeted pipeline's other columns (`status`, `owner_identity`, `terminal_publication_failure`, `terminal_publication_succeeded_at`).
- `reconcilePipelines` (async) — restart sweep for pipelines, mirroring `beginRunReconciliation`'s ownership/liveness predicate but scoped to `pipelines.status = 'active'` rows: a pipeline is a settlement candidate only when `owner_identity` is `NULL` or names a different process no longer alive (`isOwnerAlive`). A pipeline owned by the sweeping process, or by any other live process, is untouched. Settlement — one transaction per sweep — sets the pipeline `status = 'interrupted'` and marks each of its stages currently outside `reconciliationStableStageStatus` (i.e. active) `interrupted` with `ended_at` set; every `pending`, decided approval, blocked-suffix (`skipped`), or already-terminal stage is left as-is. Idempotent: the `status = 'active'` scan excludes already-`interrupted` pipelines, so a re-sweep changes nothing and does not re-return their IDs. Returns the settled pipeline IDs. No pipeline log stream or pending-flag column exists yet (unlike `beginRunReconciliation`'s `run_reconciled`/`reconciliation_pending`) — deferred until a consumer needs one.
- `hasNotificationDelivery` / `tryRecordNotificationDelivery` / `releaseNotificationDelivery` — operator-notification delivery ledger keyed by `(incidentId, transition)`. `tryRecordNotificationDelivery` uses `INSERT OR IGNORE` and returns whether this caller won the race. `releaseNotificationDelivery` deletes a claim after a failed sink spawn so the next sweep can retry. Written only by the notification sweep; settlement paths are untouched.

The current `artifact` envelope is pointer-only: `{ entryRunId, invocationId?, specPath, downstreamInputs?, prNumber?, prUrl?, requestedBase?, resolvedBase? }`, never artifact file content. `settleLinkedStagesFromEntryRun` projects the durable fields through `pipeline-stage-settlement.ts`; the daemon path may additionally project log-derived base-retarget fields. `pipeline-stage-resolve` and `pipeline-execution` consume `downstreamInputs` for fan-out resolution and branch admission (see `daemon-host.md`).

`failureDetail` on `pipeline_stages` rows is JSON-opaque to the store; writers today use one of:

- `{ message: string }` — resolution failures, unexpected throws, and missing entry-run spec paths at settlement.
- `{ code: string, message: string }` — dispatch-time refusals (`worktree_claimed`, etc.).
- `{ reason, retryable, nextAction }` — composed operator errors from `composeRunOperatorError` when the entry run row is missing at settlement.
- The full operator-error object from `composeRunOperatorError` when the entry run row is present.

The pipeline-level `status` stores only restart-reconciliation state: `active` or `interrupted`. It does not describe execution progress — observation derives boundary state from stage rows even when the pipeline row still reads `interrupted` after reconcile. Callers derive overall pipeline state from durable pipeline and stage rows with `derivePipelineState` in `v2/src/daemon/pipeline-execution.ts`; the seven-state precedence walk, stage-satisfaction rules, terminality, and daemon observation contract live in [`daemon-host.md`](./daemon-host.md#pipeline-snapshots). `claimPipelineContinuation` restores a reconciled `interrupted` row to `active` when continuation claims ownership.

`skipped` rows (written when an earlier stage fails) are never themselves read as `failed` — they only distinguish "will never run" from "not yet reached". Restart reconciliation treats them as reconciliation-stable alongside decided approval and terminal rows, so a failed pipeline's blocked suffix survives daemon restart with each durable `id`, authored `stage_id`, and `skipped` status intact. See `daemon-host.md`'s "Ordered pipeline progression" for how the loop drives stages into these rows.

## Semantics

- A run's durable `status` must agree with its terminal log signal; harness guesses (`killed`, reconcile) never overwrite a boundary-terminal status committed by `commitCompletionBoundary`. A terminal `loop_finished` row must not combine `runStatus: "completed"` with `resumable: true`; surviving-mutation failures settle `failed` with `resumable: true` and matching operator `error` fields.

- Outcomes are deterministic classifications, not free-form payloads; the runner branches on them. No transcripts or cost streams — the store carries only what resume reads. Token/cost and per-invocation usage belong in the telemetry JSONL substrate, not here — see [`telemetry-capture.md`](telemetry-capture.md).
- Recovery derives from durable state only: the `(project, branch, stepId)` lookup, run status, and attempt/outcome history. A durable review-debate row has one attempt spanning its fixed cycles and roles; a restart stores `interrupted` without mid-cycle replay. `budget-soft-stopped` resumes with a fresh per-invocation budget; a terminal run status returns its stored result idempotently.
- Multi-step workflows use `stepId` to isolate per-step attempt history: each
  workflow step maintains its own durable `(project, branch, stepId)` run,
  allowing independent resume tracking, run ids, and attempt counts. In one
  successful two-step run, step one and step two keep separate attempt
  histories even if they complete in different numbers of attempts.
- Workflow-backed step runs also share one durable `workflow_snapshot`, so a daemon `list` row can render the authored step order, `stepId`, and `role` for not-yet-started and already-finished steps without scanning unrelated runs.
- Three durable finish sources record when a run stopped, each owned by a different write path: run `finished_at` (`setRunStatus`, `commitGuardedKill`, `commitTerminalRunSettlement`, and `commitCompletionBoundary` when it routes terminal `runStatus` through settlement), attempt `completed_at` (`commitCompletionBoundary`), and `reconciled_at` (orphan settlement). A run that only ever went terminal through `commitCompletionBoundary` without settlement evidence keeps `finished_at` null by design; its finish time lives on the attempt row.
- `beginRunReconciliation` (async) scopes admission to a run's admitting process, not merely its status: a non-terminal row is a candidate only when `owner_identity` is `NULL` or names a different process that is no longer alive (`isOwnerAlive`, an injectable `(identity) => Promise<boolean>` — alive iff the pid exists and its `ps -o lstart=`-derived start epoch matches the recorded one; an existing pid with an unreadable epoch counts as alive). A row owned by the sweeping process itself, or by any other live process, is never touched. `openStateStore(path?, { currentIdentity?, isOwnerAlive? })` overrides let tests simulate a prior incarnation and inject liveness. An `in-progress` attempt's non-boundary `completed_at` is intentional — max-`completedAt` readers are the intended consumers; boundary semantics still require `outcome_kind` or attempt status `completed`. When `reconciled_at` is set, prior attempt `completed_at` values may remain stale; raw max-attempt readers must not treat attempt `completed_at` as authoritative when `reconciled_at` is set (list/TUI precedence is owned by `list-row-step-honesty`). Idempotence is split across layers: pending prevents repeated admission stamps, and daemon terminal guards prevent repeated or concurrent sweeps from re-settling or re-timing an already terminal row.

See `v2-architecture.md` (**Runs & state**, **Persistence**, **Recovery**) for the broader design.
