## Headline: the P0 was reproduced live, twice, before it was fixed

`iteration-commits-missing-on-failed-runs` was diagnosed by the intent run reading the code, not by
guessing: `prepareWorkflowStep` and `buildCompletionStepWriteLoopInput` set `publishCompletion: false`
on **every** workflow step, and `commitProgressIteration` returned early on exactly that condition.
Per-iteration commits worked on runs that completed and never ran on runs that failed.

While the fix was in flight, the P1 idle-watchdog spec hit the 30-minute iteration wall **twice**,
each time leaving ~420 insertions across 17–18 files with **zero commits**. A third run
(`aggregate-test-cost`) died with 4 iterations of work uncommitted. That is three live reproductions
of the defect during the session that fixed it.

The plan also caught a hazard the seed did not name: with per-iteration commits on, the shrink step's
`git reset --mixed <sha>^` would unwind *past* the last iteration commit rather than to pre-implement
HEAD. Fixed by anchoring on a `headBefore` sample. A created-vs-reused HEAD discriminator was needed
too, because the completion committer returns a real `commitSha` (HEAD) even when it created nothing.

## Headline: a measurement deleted a planned optimization

The P1 seed asserted the test suite's wall clock was ~86% process spawn, extrapolated from the v2
slice. The measurement subspec was written to check that before changing the runner. It reported:

| measure | value |
| --- | --- |
| wall clock | 574.4 s |
| summed in-file execution | 573.2 s |
| residual (spawn + boot) | **1.2 s (0.2%)** |

Verified independently: `/usr/bin/time -p bun test <file>` gives `real 0.04` against bun's own
`43ms`. The "86%" came from one batched `bun test` invocation's single summary line, not from summing
per-file summaries — different quantities. **Batching processes would buy about one second.**

The agent that wrote it declined to conclude anything about a runner change from the number, and said
so in the doc. That restraint was correct and is why the follow-on was reframed rather than built on
a false premise.

The real lever was 574 s of genuine test execution running **serially** on an 18-core box. The intent
was rewritten around bounded concurrency (#2179) and implemented:

| run | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| result | pass | pass | pass | pass | pass |
| wall | 330 s | 327 s | 325 s | 321 s | 325 s |

**5/5 pass, 321–330 s, mean 326 s, against 697 s — 2.1×**, with zero load-dependent failures. Subspec
01's ≤320 s target was *not* met (every run 1–10 s above); it was a projection, and the measured
distribution superseded it rather than being re-rolled until a run dipped under.

## Review earned its keep

Stacking the final subspec on the prior branch put all four subspecs in one PR, so patch review saw
code its own per-subspec reviews had already passed. It found three real correctness defects:

1. `defaultSpawn` registered only `'close'`, so a spawn `ENOENT`/`EAGAIN` — exactly the pressure
   N-way fan-out introduces — left the promise pending forever, permanently consuming a pool worker
   with no diagnostic. `spawnSync` had folded these into a return value; the transport swap regressed
   it.
2. Every test injected a fake spawn, so the real transport, and subspec 00's central
   timeout-classification AC, were satisfied by construction rather than tested.
3. A `NaN` or fractional `JARVIS_TEST_CONCURRENCY` produced `Array.from({length: NaN})` → zero
   workers, zero results, `aggregateExitCode([]) === 0`: **a passing run that executed nothing.**

All fixed before merge. Note #3 is the same class as the gate-trust lesson below: a green signal that
means nothing.

## The sandbox is the dominant source of false diagnoses

Three times a sandboxed command returned empty and I read the emptiness as signal:

- `jarvis run list` inside a `Monitor` → zero live rows → "fleet idle" while three implements ran.
  Twice.
- `ps ax` inside a `Monitor` → no processes → "no agents running" while three `claude` agents were
  writing.

`Monitor` **always** runs sandboxed and cannot be opted out. Anything reading `~/.jarvis`, the daemon
socket, or `api.github.com` must run as a backgrounded `Bash` with the sandbox disabled. This belongs
in the runbook.

Related: `bun run check ... | tail` reports `tail`'s exit code. I read a green gate off that once and
had to re-run for an honest `TEST_EXIT=0`. The prior session logged four wrong conclusions from the
same pattern; it is still the highest-frequency self-inflicted error.

## Operator interrupt: the stall deadlock

Two rows sat `in-progress` + `live` with **zero** agent processes while `jarvis run log` hung on them.
`daemon stop` and `run kill` each refuse that state, so nothing jarvis-native could clear it. Recovery
was `kill -9` + `jarvis daemon start`; startup reconciliation settled both. This was the session's one
genuine operator interrupt, and it is `workflow-stall-is-observable-and-kill-reaps-it` — which was
blocked on the idle signal that shipped in #2178, so it is now unblocked.

It also compounds: reconciliation settles orphans to `killed`, and a terminal `killed` row
permanently fails cleanup's eligibility gate (#2182). **The normal recovery path manufactures the
thing that wedges cleanup.**
