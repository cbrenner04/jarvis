# Resume drives deferred settlement

## Problem

A stage wedged `running` with `failureDetail: { code: "settlement_deferred", reason: "entry_run_still_live" }` behind a now durably-terminal entry run has no operator verb on a live daemon. `resumePipeline` derives `running`, `resumeDeferredRefusalApplies` holds, and it refuses `pipeline_not_resumable` without touching the row; killing the entry run refuses `run_not_active` because it is already terminal. The daemon-start sweep (`recoverContinuablePipelines` + `hasRedrivableDeferredSettlement`, `v2/src/daemon/pipeline-execution.ts`) recovers this shape only on restart, so the only recovery on an already-up daemon is bouncing the process.

The settlement machinery is already in place: `redrivableDeferredSettlementEntryRunId` (`v2/src/daemon/pipeline-stage-dispatch.ts`) identifies the wedge from durable rows alone, and re-entering `continuePipeline` re-settles the row, dispatches the pending successor, and runs terminal publication. The gap is resume admission.

## Decision ledger

- Carve the exception inside the existing `resumeDeferredRefusalApplies` refusal branch rather than as a new pre-check ahead of it, matching how the sibling `resume*` predicates are already wired into that branch.
- Scope the exception to derived `running`; rules out admitting a derived-`interrupted` pipeline (any `interrupted` stage row wins in `derivePipelineState` regardless of a sibling wedge), which would turn resume into an implicit restart of a reconciled pipeline.
- The exception is a named exported predicate `resumeDrivesDeferredSettlement(store, derivedState, pipeline)` beside the sibling `resume*` predicates, with the derived-state check and the redrivable check on separate lines; rules out an inline conjunction whose two conditions cannot be mutated independently.
- Reuse `hasRedrivableDeferredSettlement`, passing a named `NO_RECONCILED_ENTRY_RUNS` empty set as its required third argument; the name documents why the set is empty here — resume runs on a live daemon, not a restart batch, so no run has been reconciled-this-start.
- Accepted risk, not resolved here: the IPC server (`v2/src/daemon/daemon.ts`) starts accepting requests before the restart sweep and `recoverReconciledRuns` finish. A resume landing in that narrow startup window also sees an empty reconciled set and can re-drive a stage whose entry-run reconciliation is independently about to run via the sweep — the same race the sweep's reconciled-set exclusion exists to prevent. This is an accepted, operator-triggered edge case; no guard or test covers it.
- Settlement runs through the existing `continueAfterAdmission` → `continuePipeline` path with no `branchKey`; rules out a bespoke settlement call that would skip the ownership claim, the ordered-walk successor dispatch, and terminal publication.
- No reopen on this path: the wedged row is `running`, not `failed`, so `reopenFailedPipeline` is not called; rules out reopening a row that never failed and losing its entry-run linkage.
- `handlePipelineResumeHandler` and the `pipeline resume` CLI are untouched — the outcome stays `{ kind: "resumed", pipelineId }` and continuation stays detached, so `resumed` still means admitted, not settled; rules out a synchronous-settlement RPC that would hold the client connection through the entry-run rewrite.
- Resume tests call `resumePipeline` without `detachContinuation` so settlement is awaited and assertable in-test; the detached RPC wrapper stays covered by its existing `daemon-pipeline-resume.test.ts` coverage.
- Hoist `RESTART_SWEEP_DEFINITION`, `deferredMarkerDetail`, `restartSweepEntrySnapshot`, and `restartSweepWait` from the `pipeline activation after restart` describe to module scope in `v2/src/daemon/pipeline-execution.test.ts` for reuse by the resume tests; rules out duplicate fixtures that would drift from the durable-rollup `wait` contract those helpers encode.
- Fan-out inherits the restart sweep's composition unscoped: a wedged stage row keeps a fan-out pipeline deriving `running` (the running-branch check precedes the actionable-awaiting check in the fan-out suffix/prefix tallies), so the unscoped `resumePipeline` verb is already the fan-out recovery path — no branch-scoped variant is added or needed.
- Re-entrancy is safe: admitting resume on a live daemon can re-walk stages of branches unrelated to the wedge, and two rapid resumes can both be admitted. Durable stage-admission claims and adopt-instead-of-redispatch for live-linked rows make this the same exposure the existing reopen and approve paths already carry. The terminal-publication window is unreachable at admission time because a redrivable wedge implies an unsatisfied `running` stage row.
