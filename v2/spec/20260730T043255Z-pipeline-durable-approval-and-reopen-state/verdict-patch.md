Verifying the critical composition issues against the implementation and spec acceptance criteria.
## Verdict — required outcomes

1. **Post-reconcile activation must work for eligible pipelines.** Subspec 07 requires that after restart reconciliation, an approved approval gate and an applied failed-pipeline reopen can each activate under one live owner and dispatch the eligible continuation. Today `reconcilePipelines` sets `pipelines.status = 'interrupted'`, while `isPipelineContinuable` and `claimPipelineContinuation` require `status === 'active'`. Neither `commitApprovalDecision` nor `reopenFailedPipeline` restores activatable pipeline status. The result: any pipeline that survives reconcile as `interrupted` — including approved gates and reopened failures — can never be claimed or dispatched. Continuation eligibility, ownership claim, and reopen must compose so that reconciled pipelines with a dispatchable stage shape (approved gate with pending successor, or reopened failed continuation) can be activated without client-supplied admission input.

2. **Regression tests must exercise the reconcile → activate path on a real store.** Subspecs 04 and 07 claim restart-safe production continuation and post-reconcile activation. Current activation tests use fakes that always keep `status: 'active'`, never call `reconcilePipelines`, and the reopened-pipeline activation case sets the failed row to `pending` via `updateStage` instead of `reopenFailedPipeline`. Add coverage that: runs `reconcilePipelines` on a real `StateStore`, applies `reopenFailedPipeline` or an approval decision as appropriate, then proves `recoverContinuablePipelines` / `continuePipeline` claims ownership and dispatches once with no second dispatch on duplicate claim.

3. **Pipeline observation must not permanently mask preserved approval semantics after reconcile.** Subspec 03 requires `derivePipelineState` to distinguish `awaiting`, `approved` continuation (`pending`), and `rejected`. After reconcile, `pipeline_list` / `pipeline_wait` report `interrupted` for pipelines whose stage rows still read `awaiting`, `approved`+pending successor, or `rejected`, because pipeline-level `interrupted` wins first. Observation semantics must align with preserved stage-level approval and continuation evidence documented in `daemon-host.md` and `state-store.md` — operators must be able to see the true boundary state, not only `interrupted`, for reconciled pipelines whose stage rows were left untouched.

4. **Admission without durable context must match subspec 01.** Subspec 01 AC states the negative case proves no `pipelineId` is returned when durable context is absent. The inversion test currently returns a truthy `pipelineId` with `context: null`. Behavior, test, and AC must agree: either refuse admission when context is not written in the admission transaction, or the checked AC must be narrowed to “context is not durably persisted” (prefer refusal — it matches the subspec decision to persist context before returning an ID).

5. **`reopenFailedPipeline` must return explicit refusal on suffix concurrent loss.** Subspec 06 requires every reopen attempt to return `applied` or `refused` with no silent mutation. A failed-row race returns `reopen_lost`; a suffix-row race throws inside the transaction. Suffix loss must also surface as an explicit refused outcome per the documented contract.

6. **Document the reconcile ↔ activation composition once fixed.** `daemon-host.md` describes activation after reconcile and reopen but does not state how `interrupted` pipeline status becomes runnable again. After fixing outcome 1, durable docs must state the pipeline-status transition that makes claim and dispatch legal for approved and reopened continuations.
