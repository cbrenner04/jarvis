## Verdict

**1. Fix false routing rationale (subspec 01).** The current rationale claims dropping the `.sandbox-unrunnable` infix routes the file into `test:v2`-style agent-runnable discovery. This is factually wrong: `test:shared` runs every file under `shared/` unconditionally regardless of filename, and there is no name-based test-discovery filter for `shared/`. Rewrite the rationale to state the marker is a human/reviewer signal, not a discovery mechanism — the file is renamed because it no longer spawns a real process, not because renaming changes what test command picks it up.

**2. Add an acceptance criterion covering existing call sites (subspec 00).** `shared/git.ts` is version-agnostic shared code with real consumers (multiple files under `v1/src/` and `v2/src/`). The "no behavior change for existing callers" claim currently lives only in the decision record, not in acceptance criteria, so it isn't verified. Add an AC requiring that existing call sites compile and run unmodified against the new default-runner signature (typecheck passing plus no required call-site edits), per the spec guidance's rule that behavior-preservation claims must cite verifiable AC coverage, not just be asserted in prose.

**3. Record the error-shape decision as an explicit deferral (subspec 00).** The thrown-error shape from the injected runner (plain `Error` vs. an `execFileSync`-mimicking object) is unspecified and has no current consumer that needs a specific shape. Add a one-line `Deferred to first consumer:` entry per the repo's deferral convention, naming the choice and noting it's pinned when a `gh`-parsing call site needs it — do not invent a contract nothing in this intent exercises.

**4. Add an AC blocking stray direct subprocess calls (subspec 00).** Add an acceptance criterion that `shared/git.ts` no longer imports `execFileSync`/`node:child_process` directly, so the boundary conversion is verifiable rather than just implied by the task checklist.

**5. Record the `SubprocessRunner` vs. `typeof execFileSync` divergence as a named decision (subspec 00).** The repo has an existing convention (`ci-checks.ts`, `commands/triage.ts`) of injecting `typeof execFileSync` directly rather than a bespoke interface. Per the ledger rule that a decision must name the plausible alternative it rules out, add a decision line stating the bespoke `SubprocessRunner` interface is chosen over the `typeof execFileSync` convention because it narrows the seam to the cmd/args/cwd/stdout shape this boundary (and future `gh` call sites) actually need, rather than leaking `execFileSync`'s full options/overload surface.

**6. State synchronous execution explicitly (subspec 00).** The decision bullet describing `SubprocessRunner` should state explicitly that the call is synchronous, matching today's `execFileSync` behavior, rather than leaving it implicit.

No other changes required. Subspec 02's conditional/audit shape is correct as-is for the intent's "decide whether real spawning is load-bearing" framing and needs no refinement.
