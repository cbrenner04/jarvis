# Verdict — Refinement Required

The spec targets a real bug with a correct remedy (mandatory tick) and a well-formed decision ledger, but it asserts several factually wrong or ambiguous things and must be refined before it ships. The following refinements are required. None expand scope; each tightens correctness of a claim the spec already makes.

## Required refinements

1. **Correct the fixture-staleness mechanism (highest priority).** The spec's decision frames bumping the rules-fragment revision as what "rules out shipping a stale snapshot." That is wrong. The rendered fixtures embed the rules **body text** verbatim; the rules-fragment revision number never appears in the rendered output. The fixtures go stale solely because the inlined body string changes — not because of any revision bump. The spec must:
   - State that the fixture filename key `@r3` is derived from the **rendered-prompt artifact's** revision, which **stays `3`**, and that the snapshot test's hardcoded `revision` assertion (the `"3"` literal) is **unchanged** by this spec.
   - Make clear the only real regeneration gate is the fixture **contents** (because the rules body text changed), and the two `@r3` fixture filenames are kept, not renamed.
   - Decouple the rules-fragment revision bump from the fixture rationale: if the bump is kept, justify it only as honest provenance for editing the fragment, never as the de-stale mechanism. (Note: nothing in the test enforces the fragment's revision, so the bump is optional; the spec must not imply otherwise.)
   - **Rationale:** As written, an implementer could plausibly bump the rendered-prompt artifact's revision to chase the `@r3` key, simultaneously breaking the hardcoded revision assertion and orphaning both fixture filenames. This is a live trap that produces a red suite; the spec must foreclose it.

2. **Pin a single, true path for the rules file.** The live file is `prompts/patch/rules.md`. The spec's Tasks use it correctly, but its Problem/framing prose and the index/intent carry a stale pre-move path (`v1/src/modes/patch/rules.md`) that no longer exists. Resolve to the one true path and drop the stale reference so Problem and Tasks do not contradict.

3. **Sharpen the Problem and acceptance criteria to name the actual failure condition.** The exit-4 no-progress failure occurs only when the subspec enters the iteration with acceptance criteria left `- [ ]` whose underlying work is already complete, which the agent re-verifies, declares "already done," and leaves unticked. A subspec already fully `[x]` on entry completes normally (the zero-unchecked path returns exit 0 with a PR). The spec's current "already satisfied on entry" phrasing conflates these two cases. Both the Problem statement and the relevant acceptance criterion must explicitly target the **unticked-`[ ]`-but-already-done** condition (re-verify, then tick), not a generic "already satisfied."
   - **Rationale:** The ambiguity will propagate into the rules text the agent authors; pinning the real condition is the highest-value clarity fix and directly serves the intent ("the case the current wording lets slip").

4. **Disambiguate the agent-owns-the-tick criterion from the existing index-checkbox sentence.** The rules file already contains a correct sentence stating the harness flips the **`index.md`** checkbox itself once all acceptance criteria are checked. The spec's "rules.md does not instruct the harness to tick" criterion is about **acceptance-criteria** ticking and must say so, explicitly leaving the index-checkbox sentence intact. Otherwise a literal-minded implementer may treat that sentence as a violation and remove it, regressing correct behavior.

5. **Resolve "add/extend" to "add" for the behavior doc.** `v2/docs/v1-behaviors.md` has no existing patch-rules tick-on-completion entry (the nearest entry documents checkbox-driven completion *measurement*, a different fact). The doc work is an **add**. Resolve the hedge to "add" and, per spec-guidance, ensure the new entry records the hardened rule (re-verify and tick already-satisfied criteria as a mandatory final step; agent owns the tick, harness never auto-ticks) with a `Sources:` citation to `prompts/patch/rules.md`. The Patch-mode completion cluster is the natural home.

6. **State the concrete revision target rather than "greater than its prior value."** A reviewer reading only final state cannot verify "greater than prior." If a fragment revision bump is retained (per refinement 1), name the explicit target value so the criterion is checkable from the final file alone.

7. **Pin edit placement to avoid a redundant ticking bullet.** The `## Iteration` block is deliberately terse and already contains a ticking line and a separate "stop when you have made meaningful progress" line. Add a Task constraint that the mandatory-tick requirement folds into / replaces the existing ticking-and-stop region rather than appending a new overlapping bullet. Do **not** dictate verbatim replacement prose — the rules file's clipped imperative style is best matched by the implementing agent; a placement/non-duplication constraint is the right altitude.
