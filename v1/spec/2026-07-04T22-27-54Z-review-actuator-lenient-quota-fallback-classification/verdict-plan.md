## Verdict

The draft's core decision (classify before branching, mirroring `shrink.ts`) is sound, but four precision gaps must be closed before implementation, since "classify before branching" is currently underspecified enough that a competent implementer could diverge from the actuator's existing behavior in observable ways.

1. **Fanout message selection must stay three-way, not collapse to two.** The spec must state explicitly that the fanout line selection branches on the *raw* result in three cases — native-quota+authFailure (auth-rotate message), native-quota (strict message), lenient-upgraded-error (lenient-fallback message) — mirroring `shrink.ts`'s exact branch. "Preserve raw-result details alongside the classified one" is too vague; without pinning the three-way split, an implementer could reuse the actuator's current two-way message branch and mislabel a lenient fallback with the strict-quota message.

2. **Enumerate which reads use classified vs. raw results.** Rather than "keep a reference to the original result," the spec must enumerate each existing `result.kind` read in the actuator (stderr-fanout gate, `isIdleTimeout`/`isQuota` computation, exit-code/telemetry-kind computation, terminal-throw message) and state which now reads the classified result and which still needs the raw one (only the fanout-message three-way split, per #1). Leaving this to implementer judgment risks inconsistent classification across the function.

3. **Cover the final-rung lenient-quota case explicitly.** Today a lenient-eligible error on the actuator's last rung falls through to the generic terminal-error throw with an error-shaped result. Once classified, it will carry `kind: "quota"` on the final rung too — the spec must state what message/exit code this terminal case produces (matching or intentionally diverging from `shrink.ts`'s dedicated exhausted-quota terminal branch) and add an explicit acceptance criterion plus regression test for it, distinct from the non-final-rung fallthrough test already specified.

4. **Pin classify-before-idle-timeout-check ordering as an explicit decision.** The spec must state that classification happens once per rung, and the quota branch (return/continue) is checked before `isIdleTimeout` is ever evaluated — matching `shrink.ts`'s ordering. This should be a stated decision, not left implicit, since the actuator's current code computes idle-timeout from stderr before any quota check exists, and getting the order wrong could misroute idle-timeout aborts or vice versa.

None of these expand scope beyond the intent — they are precision requirements on "classify before branching," not new behavior, and align with the spec-guidance principle that decisions should pin exact structure when structure is the contract for a harness subspec.
