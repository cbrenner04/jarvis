# Structural recovery brief

Phase tracker for the v2 structural recovery, from the 2026-08-29 code review of `v2/src`. **Standing document**: current priorities and operating rules only. Session narratives live in `reports/` (one per session since the reset); per-seed tracing lives in [`structural-recovery-seed-ledger.md`](./structural-recovery-seed-ledger.md). Rewritten 2026-09-05 (compaction) from the journal it had become.

## Why this phase, and where it stands

237 of 376 v2 code commits over the six weeks before the reset were fixes, clustered on a handful of structural seams — terminal state written on the happy path only, config assembled twice with one copy stale, settlement copied then redriven. The recovery's charter: five structural retirements that close whole classes — one dispatch front door, settlement derived from run rows, atomic terminal writes, the module splits, dead-export/test-seam gates.

**As of 2026-09-05 it is mostly working**: since 08-31, 11 of 79 `v2/src` commits were fixes (~14%, was 63%), zero reverts. Closed: front-door chain (#3226 et al.), both module splits (workflow-runner #3380/#3388/#3393, daemon #3364–#3394), mutation-gate P0 chain (4/4), watchdog trio, external-spec chain (#3122), notification-sweep CPU fix (73–98% → 4.6–15%), daemon socket/status honesty (#3468–#3473), CLI retirements (`write`, aliases, `TuiDaemonClient.start`). The remaining bug frontier is concentrated where the one unfinished retirement lives: **chained/linked-row settlement and resume** (the 09-02→09-05 issue wave: #3462/#3463/#3395, #3464, #3400, #3433), plus the external/`plan.commit:false` family mid-chain. 2026-09-06 landed the matcher head lane (#3514), the disposable-lane gates (#3512), and closed the importer-cap fuse (#3513); it also showed the seam is now mostly **operator-visible**: stage rollups disagreeing with durable run rows, and recovery verbs refusing on branches with undone work. The late 2026-09-06 session closed both dependent lanes (#3535, #3538) and the external chain (#3534, #3543), and shifted the frontier again: the remaining defects are no longer mostly *settlement* but **publication** — five distinct ways a lane that finished its work still could not publish, every one hand-salvaged. The keystone is that `iteration_timeout` has never been resumable for an implement lane, so none of those five could recover themselves. 2026-09-06 (operator session) closed two of that family — inventory [#3555](https://github.com/cbrenner04/jarvis/pull/3555) and socket reclaim [#3554](https://github.com/cbrenner04/jarvis/pull/3554) — and **corrected the keystone claim**: the inventory fix alone does not restore resume, because the full-suite AC is ticked last and consumes the iteration budget. It also established that the pipeline shape itself is sound (a single-lane `full-review` ran seed→ready end-to-end, both gates approved after review) and that **every remaining failure is in the implement stage**. The newest frontier is the verifier itself: it can hang forever on a mutant it generated, and when it does, no `run` verb can stop it. **2026-09-09 (hand-landed, 40 PRs):** the deadline pair ([#3648](https://github.com/cbrenner04/jarvis/pull/3648), [#3650](https://github.com/cbrenner04/jarvis/pull/3650)), gate-slot ownership ([#3647](https://github.com/cbrenner04/jarvis/pull/3647)), the notification cursor ([#3652](https://github.com/cbrenner04/jarvis/pull/3652)), `daemon stop` liveness ([#3655](https://github.com/cbrenner04/jarvis/pull/3655)), the dead-directive sweep ([#3654](https://github.com/cbrenner04/jarvis/pull/3654)), and an issue burn-down (#3372 precedence, #3029 mechanism 1, #3030, #3381 closed) all landed by hand; every one skipped the harness. Also learned: `jarvis cleanup` cannot archive a spec no run ever touched, so hand-landed specs need an archive PR ([[cleanup-archives-hand-landed-specs]]). **2026-09-09 (pipeline dogfood, 12 PRs):** four `full-review` pipelines driven seed→ready located the implement-stage failure precisely — [[chained-implement-cannot-tick-its-own-criteria]], a split between the spec tree the agent writes (implement worktree) and the one the criteria-ticked contract reads (`specReadRoot`, the plan worktree). Three lanes failed three different ways from that one cause; a standalone implement of the *same spec* completed end-to-end unattended twice ([#3692](https://github.com/cbrenner04/jarvis/pull/3692), [#3693](https://github.com/cbrenner04/jarvis/pull/3693)), which isolates the defect to the chained stage rather than to `implement`, the agents, or concurrency. Plan lanes cleared the contract gate **4/4 unaided** — the first session with no hand-collapsed plan. The session's second block then drove all six sibling ready-intents to `main`: **six standalone implements, five completing end-to-end unattended** (criteria ticked, gate green, draft→ready flipped, PR published, zero operator steps) — the same preset that failed 3/3 as a chained pipeline stage that morning, on the same specs and agent order. Also closed the verifier-orphan mode empirically ([#3691](https://github.com/cbrenner04/jarvis/pull/3691) + [#3706](https://github.com/cbrenner04/jarvis/pull/3706): 113/113, zero orphans, after two 20GB orphans had driven the machine into OS low-memory reaping), and diff review caught two defects the gates passed — a dead tie-break whose acceptance criterion claimed coverage of an unreachable branch, and a verb path that resolves a pipeline-id prefix and then sends the raw argument ([[pipeline-verb-path-discards-its-own-resolution]]). 35 PRs merged.

**Where it stands, 2026-09-11 (late).** **Publication is closed.** The defect that had hand-published seven implement lanes across two sessions was root-caused and fixed by hand ([#3794](https://github.com/cbrenner04/jarvis/pull/3794)): three composing mechanisms, no exception anywhere — `prepareWorkflowStep` forces `publishCompletion: false` so a workflow write step's row settles `completed` before the publication tail runs; `executeWorkflow` returned on a non-`complete` step result with no log and no store write; and the daemon discarded the returned `WorkflowResult`. There was never a throw, and the stage's `harness_failure` was only the fallthrough classifier for the row shape the first mechanism leaves. The fix settles the row at the point the outcome is known and **only when it still reads `completed`** — keying on the outcome kind instead breaks resume, because `budget-exhausted` and `paused` are deliberately non-terminal. Mechanism 1 is deliberately unchanged; holding the row `in-progress` across the tail would strand rows on any tail path that fails to settle.

The frontier moves to **parallelism economics**. Lane count and load are no longer the ceiling — five concurrent implements at load 11-17 produced zero watchdog kills and zero idle stalls, and the 45-minute paired timeouts did not reproduce. The ceiling is the single full-suite gate slot, and past it lanes settle `gate_invocation_refused` / resumable rather than timing out. But the refusal does not queue, nothing re-drives it, and it aborts *before* the iteration's checkpoint commit — so a lane refused four times produced zero commits and zero ticked criteria with a complete implementation uncommitted in its worktree. Seeded as [[gate-slot-refusal-is-a-resume-treadmill]]. Working number today: **2-3 concurrent implements**. Also this session: the plan lane failed 3/3 on one drafter drift (an orphaned renamed subspec beside the keeper — [[plan-draft-contract-miss-reprompts-before-blocking]]), and `pipeline recover` went 2/3 with a clean control that isolates [[recover-needs-no-predecessor-artifact]] to the resolver rather than the correction.

**Where it stands, 2026-09-11.** The last structural retirement — settlement derived from run rows — closed 2026-09-10 ([#3745](https://github.com/cbrenner04/jarvis/pull/3745)), so the charter's five are done. The frontier has moved off *settlement* entirely and onto two things the recovery did not originally name. First, **daemon identity**: the operator's question — why rotation is something an operator must think about at all — collapsed five open seeds, two issues, and 21 runbook references into one root cause, now the P0 row below. Second, **publication**: every implement lane that finished work on 2026-09-11 settled `completed` with a real commit, correct criteria, and no PR, no review row and no publication row — four for four, all hand-published. That is a violation of the documented completion-honesty contract (a `completed` implement implies confirmed PR evidence), not merely friction, and it is under active diagnosis rather than seeded. Also established this session: the plan-contract gate's "strict lexical patterns fail closed" class reached its sixth instance ([[artifact-count-treats-a-glob-as-an-artifact]] — a glob and the file exemplifying it counted as two artifacts), and `jarvis pipeline recover` is genuinely usable when its predecessor artifact resolves, having landed a hand-corrected plan tree and unblocked the daemon chain's head lane.

**2026-09-10 hand burn-down.** 15 ready-intents landed by hand in one session (PRs #3715–#3729); the four left are the settlement seam (in flight, above) and the operator-failure chain ([[settle-workflows-with-falsifiable-failures]] → [[serve-canonical-failures-from-daemon]] → [[render-operator-failures-consistently]]; the shared record exists in `shared/operator-failure-record.ts`, only the store consumes it). Lessons: (1) Bun mis-transpiles a local identifier named `declare` — calls silently no-op; (2) `state-store-wal-concurrency.test.ts` is a load flake (passes idle) and was the only red in three otherwise-green slices; (3) the dead-export gate immediately caught my own new modules' in-file-only exports, so demote as you go; (4) the reap intent's `daemon.ts:633-635` shrink literals and "gate-only sweep" claims were already stale — verify an intent's Problem paragraph against `main` before implementing it; (5) cleanup archive publication changed a contract ten e2e tests pinned in-checkout, and `gh` fixtures had to treat `cleanup/archive-*` as unmerged, as production `gh` would.

**Circuit-breaker (per-lane, per-gate).** If a lane (plan / implement / review) needs hand-intervention twice in a row on the same gate, stop routing that lane through Jarvis until the gate fix merges — hand-land the work instead. Re-open the lane only after one clean end-to-end run on the fixed gate. Mirrored in [operator-runbook.md § Circuit-breaker](../docs/operator-runbook.md#circuit-breaker-stop-routing-a-lane-that-keeps-failing-the-same-gate).

**Parallelization (measured 2026-09-06, refined again by the operator session).** The ceiling is **concurrent full-suite gate invocations**, not lane count and not load. Four concurrent implements ran at load 6-11 with zero watchdog false-kills and a saturation alarm at 18-22 that never fired in two hours — yet two lanes died at exactly **45m01s and 45m02s** with real work committed and only `bun run test:v2` unticked. Each subspec's final AC runs the whole suite inside the write step's iteration budget and nothing staggers that across lanes. Load average does not predict it; attribute by what each lane is doing. Hold at two concurrent implements until [[implement-gate-invocation-outlives-the-iteration-ceiling]] ships. Earlier measurement, still valid: Lane count is not the ceiling — seven concurrent lanes ran at load 6-21 with zero watchdog false-kills, and plans fan out freely (3 concurrent, 2 of 3 clean end-to-end unattended). The ceiling is **verification-phase overlap**: three implements reaching diff-derived verification together drove load to 48.8 and timed out all three at exactly 45.1 min, because each verifier spawns up to `MAX_CONCURRENT_VERIFIER_TEST_RUNS` (4) `bun test` subprocesses. Nothing staggers them; hold at two concurrent implements. A `shared/**` implement's gate still runs all six slices and cannot share the machine. And `ready_gate_out_of_scope` is worse than "manufactured by load" — `main` itself fails `bun run test:v2` on an idle machine with a *rotating* set of 30 s timeouts, all green in isolation ([[coscheduled-test-pair-strands-runs-terminally]]), so the base-ref probe can be truthfully right and still strand healthy work. Attribute by process family before believing any ceiling; never run local suites beside a live gate. Approve fan-out gates **simultaneously**, before any sibling plan consumes its ready-intent — the serial "head lane first, land, then resume" practice is what triggers [[fan-out-plan-resolution-is-all-or-nothing-across-lanes]] (corrected 2026-09-07; [[plan-bases-off-a-declared-prerequisite-branch]] + [[pipeline-fan-out-lanes-serial-chained-bases]] remain the structural answer for coupled lanes on independent bases). **Do not merge while lanes are live** — every lane branched pre-merge is stale-based and its review/repair steps rewrite files the merge landed.

**A green mutation `pass` is not evidence.** Four distinct vacuous passes in one session: 0 accepted/13 skipped (fixes uncommitted, so candidate positions were stale), 0/0 against a stale local `main`, 0/0 on a file with 348 changed lines that had yielded candidates minutes earlier, and one genuine 1/0. `kind` alone cannot distinguish a verifier that killed everything from one that evaluated nothing — read `acceptedSites`. The gate is also structurally blind to **argument-swap** defects, which is exactly the bug class [#3555](https://github.com/cbrenner04/jarvis/pull/3555) fixed. Commit before running it: verification is diff-derived against the base ref.

**A dirty guard in a wedged worktree may be the verifier's mutant, not agent work.** Restore only runs after the killing test returns, so a hung candidate leaves an inverted production guard on disk that reads exactly like agent-authored corruption. Check parentage of any hot `bun test` (`ps -o ppid=`) before concluding anything: daemon-parented is a live gate/verifier child, `launchd`-parented is a leaked orphan, and the recoveries differ.

**Land-a-slice.** A multi-subspec spec converges only with immediate re-dispatch after each merged slice, `cleanup --yes --abandon` between. Treating a merged slice as the finish line strands doc subspecs permanently.

**Guards that destroy.** A guard deciding whether to destroy or land something treats every inconclusive answer as "do not act" — `ENOENT` from a sandboxed caller is inconclusive, not authoritative (the socket outage), and a test that asserts a recorded field is not a test that the behavior happens (#3483's consumption bug).

**A `@mutate` annotation that does not kill is worse than none.** Two shipped inside ticked acceptance criteria on 2026-09-06 and both passed every mechanical gate: one where the mutant collapsed a result to `[]` while every assertion over it was `.not.toEqual` or emptiness-tolerant, and one where the annotated line was reachable only through a branch no fixture exercised. Verify a pin by deleting the line it names, not by reading it.

**Planning was corrupting its own drafts, and it reached other projects (2026-09-08).** Three consecutive plan lanes needed hand-collapsing before the cause was found: `normalizePlanDraftSpecDir` re-split every authored draft by a hardcoded jarvis surface taxonomy, copying the parent body into each child. The agents' content was sound every time. Retired in [#3628](https://github.com/cbrenner04/jarvis/pull/3628). Two lessons survive it. First, **a mechanical post-hoc rewrite of agent output is a defect surface** — the split was redundant with the draft prompt's one-surface-per-bullet rule and with the review roles, which already split oversized subspecs correctly, and it was the only one of the three that damaged anything. Second, **jarvis-shaped machinery applied to every registered project leaks**: the taxonomy's patterns are ordinary software vocabulary and were already half-firing on a SwiftUI app. Check any shared-path feature for that shape before assuming it is jarvis-only. Same class as #3426.

**Plans invent precision.** A criterion naming a test that does not exist passes review and blocks ticking later; verify named tests exist at plan review, and prefer discovery scripts over hand manifests (the #3442 narrowing).
