The plan step writes criteria asserting *the feature works*. The gate requires *every changed guard
pinned in both directions*. Nothing bridges them, so an implementer who satisfies the written
criteria has done what was asked and still fails. Recovery each time was the operator hand-adding
the missing criterion — nine times.

Two sub-patterns, both worth knowing:

- **Naming one guard gets exactly that guard covered.** Three specs stalled a second time on the
  *same guard shape one layer up* (`write-loop` → `ready-finalize`; `stale-dispatch` →
  `daemon-lifecycle` → `daemon-entrypoint`). Pointwise naming loses to a large diff.
- **Optional-field spreads need key-absence assertions.** Inverting `x === undefined ? {} : {x}`
  yields a *present-but-undefined key*, which a value assertion cannot distinguish from absence.

Seed: `plan-specs-omit-both-direction-guard-coverage` (#1928). It explicitly rules out weakening the
gate, which has been correct in every observed case.

## Concurrency finding

Running **7 implements concurrently** was comfortable: load average ~4, 4 `codex` + 4 `bun`, total
CPU well under saturation. The "throttle to 1–2 implement runs" folklore did not hold on this
machine — the measurement tooling cost more than the extra runs did. Fan-out is limited by the
*daemon revision guard*, not CPU: any merge touching `v2/src/**` makes the daemon stale, and a stale
daemon cannot bounce while runs are live, so dispatch serializes behind a fully idle fleet.
