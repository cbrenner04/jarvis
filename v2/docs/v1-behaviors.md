# v1+v2 behavior parity catalog

This document inventories user-observable v1 behavior and records each v2 parity decision — preserve, change, or drop — plus v2-only divergences. Entries reflect the state when each parity call was made; v2 source and `v2/docs/` are authoritative for current v2 behavior.

## Overview and scope

### v2 workflow CLI names

The primary workflow commands are `intent`, `plan`, and `implement`. All accept
`--review-passes <n>` and `--review-behavior debate|light`. For `intent`, omitted
`--review-passes` defaults to one light pass; `--review-passes 0` opts out (v2
consolidation — prior bare `intent` was split-only). For `plan`, omitted or zero
passes omit review. For `implement`, omitted
`--review-passes` defaults to one debate pass; `--review-passes 0` opts out.
Legacy `intent-reviewed`, `plan-reviewed`, and
`plan-reviewed-light` aliases remain accepted. `intent-reviewed` delegates to
`intent` with identical defaults (one light pass); it differs only in CLI alias
injection and a migration hint. `plan-reviewed` and `plan-reviewed-light` inject
one debate or one light pass respectively when review flags are omitted. Explicit
review flags override alias defaults. Invalid values fail with usage before daemon contact.

- This catalog describes behavior as shipped today under `v1/`, with v1 invoked via `jarvis1` in CLI usage and help text. Sources: `v1/src/cli.ts`
- The `jarvis1` rename has landed, so this file intentionally records the renamed `jarvis1` behavior as the migration baseline for v2 review. Sources: `v1/src/cli.ts`, `v1/spec/completed/2026-05-22T04-09-01Z-v1-behavior-catalog/00-skeleton-commands-and-project-resolution.md`
- Source files under `v1/src/` are treated as authority for behavior; docs are used to cross-check operator workflow expectations and terminology. Sources: `v1/src/cli.ts`, `v1/docs/run-loop.md`, `v1/docs/spec-guidance.md`
- Behavior entries in this catalog stay as short bullets ending with `Sources:` citations; `[uncertain]` is reserved for cases where source evidence cannot support a stronger claim. Sources: `v1/spec/completed/2026-05-22T04-09-01Z-v1-behavior-catalog/00-skeleton-commands-and-project-resolution.md`

- v2 daemon restart reconciliation kills orphaned non-terminal runs before IPC, then automatically resumes reconciled snapshot-backed write runs after IPC opens. Recovery retains run ID, workflow snapshot, worktree, and branch and logs `run_recovery`; admission failures become `failed` without blocking other rows, while snapshot-less rows remain `killed` / `unsupported_resume_context`. Kill and reconcile never overwrite boundary-terminal status (`completed`, `blocked`, `failed`), and `run_reconciled` events emit only for pending rows currently `killed`. Sources: `v2/src/daemon/daemon.ts`, `v2/src/persistence/state-store.ts`
- v2 `jarvis daemon stop` refuses when durable runs are non-terminal, reports every blocker ID, and leaves shutdown side effects untouched; `--force` bypasses only this guard. Sources: `v2/src/daemon/daemon-lifecycle.ts`, `v2/src/cli.ts`
- **[v2 additive]** v2 daemon shutdown is no longer limited to RPC `shutdown`, SIGTERM, and SIGINT. The IPC `supersede` RPC closes admission (rejects new `start` and `resume` with `daemon_superseded` before any claim or row creation), while observation and steering commands (`list`, `wait`, `health`, `status`, `pause`, `kill`) continue serving for in-flight runs. The retiring daemon exits automatically at idle (when no active runs remain), completing owned runs under the same daemon. Queued runs are not promoted after supersession. **[v2 additive]** When a new daemon starts, it automatically sends `supersede` to every other digest-keyed daemon socket in `JARVIS_HOME`, enumerated as `daemon-<key>.sock` files (best-effort, non-blocking, fire-and-forget). A peer that cannot be reached or errors does not block startup or prevent other peers from being superseded. The new daemon starts serving immediately — startup does not wait for peers to retire. This allows seamless daemon upgrades after executable tree rebuilds without manual intervention. Sources: `v2/src/daemon/daemon.ts`, `v2/docs/daemon-host.md`, `v2/docs/write-behavior.md`, `v2/docs/operator-runbook.md`
- **[v2-only]** `jarvis daemon status` reports the daemon's startup Git revision alongside the invoking CLI's current revision, but marks the daemon `stale` only when executable-tree digests differ (`v2/src/**`, `shared/**`, and repo manifests): `running loaded=<revision> current=<revision>` (exit 0) when the daemon is alive and digests match (even if HEAD differs after a docs-only merge); `stale loaded=<revision> current=<revision>` (exit 1) when alive but the executable tree changed since daemon startup; `stopped` (exit 1) when daemon process dead or socket unreachable. v1 `jarvis daemon status` reports only `running` or `stopped`; the v2 revision reporting is a v2-only enhancement. Sources: `v2/src/daemon/daemon.ts` (capture), `shared/executable-tree.ts` (digest), `v2/src/daemon/daemon-lifecycle.ts` (comparison), `v2/src/commands/daemon.ts` (output formatting), `v2/docs/write-behavior.md`, `v2/docs/daemon-host.md`
- **[v2-only]** v2 mutating dispatch (`run start`, `run resume`, `run workflow`) auto-starts the keyed daemon at the invoking digest's socket/PID/log paths when the connect fails, treating a lost start race (`DaemonAlreadyRunningError`) as reuse; read-only commands still report a missing daemon. No revision guard or auto-bounce mechanism: dispatch to a daemon at any revision/digest succeeds without stopping or restarting. v1 has no daemon and no such pre-start requirement to remove; v2 previously failed dispatch until the operator ran `jarvis daemon start`. Sources: `v2/src/cli/stale-dispatch.ts`, `v2/docs/write-behavior.md`

## Commands and modes

### Command surface

- The shipped top-level subcommands are `run`, `init`, `config`, `log-server`, `cleanup`, `triage`, `review-feedback`, `runbook`, `plan`, `intent`, `prompt`, `prices`, and `help` (including `-h`/`--help` aliases to help output). Sources: `v1/src/cli.ts`

- **[v2 additive]** `jarvis help` writes the registry-backed top-level command overview as `name<TAB>summary` lines and exits 0. The same registry owns v2 dispatch, command usage, and unknown-command names; invalid help operands/options print `usage: jarvis help` to stderr and exit 1. Sources: `v2/src/cli.ts`
- **[v2 behavior change]** A v2 unknown top-level command writes `unknown command: <command>` to stderr, then `did you mean <name>?` only for one registry name within Levenshtein distance 2, and finishes with `run \`jarvis help\` for available commands`; it writes nothing to stdout and exits 1. Sources:`v2/src/cli.ts`

- **v2 cleanup parity delta:** v2's shared archival policy derives completeness only from linked (or single-file) non-human-only acceptance criteria, rejects vacuous specs, and fails closed on open-PR or materialized-worktree ownership uncertainty. It moves the whole artifact into its existing home's `completed/` directory and prunes a same-named ready-intent only on byte identity with `intent.md`, rolling back the move on prune failure. Durable run rows remain untouched. Sources: `v2/src/commands/cleanup-artifacts.ts`, `shared/spec-parser.ts`

- **v2 cleanup retirement archival:** after `git worktree remove`, v2 resolves the spec's configured home and timestamped directory identity across durable workflow and ad-hoc run rows, then archives eligible completed artifacts in that same cleanup invocation. `--dry-run` previews the worktree, archive destination, and byte-proven ready-intent prune. Failed retirement leaves artifacts untouched; incomplete specs, open matching PRs, and other materialized owners remain at the root with stdout refusal reasons. Sources: `v2/src/commands/cleanup.ts`, `v2/src/commands/cleanup-artifacts.ts`
- **v2 cleanup stranded archival:** every cleanup also scans immediate open directories in each registered `v2/spec/` home, excluding `completed/`, `seeds/`, and `ready-intents/`, even with no removable worktree. Ownership is keyed to the durable implementation branch: only same-project managed worktrees on that branch own a spec; primary checkouts and resolved unrelated branches do not. Ownership is rechecked before archival, and unresolved or detached same-project managed worktrees fail closed. It applies the same complete/open-PR and proven-intent transaction policy, previews candidates and refusal reasons in `--dry-run`, and does not alter durable run rows. Sources: `v2/src/commands/cleanup.ts`, `v2/src/commands/cleanup-artifacts.ts`
- **[v2 additive] Cleanup daemon socket reaping:** every cleanup also enumerates and reaps dead daemon sockets under `~/.jarvis/daemon-*.sock`. Each socket is probed with a connect attempt: sockets whose probe receives `ECONNREFUSED` or `ENOENT` (indicating no listener bound) are classified dead and removed; all other probe results (connection succeeds, timeout, permission error, unexpected error) preserve the socket and are reported. This allows cleanup to safely run while overlapping keyed daemons are live: each socket is classified independently, and only sockets whose daemons have exited are removed. If the jarvis home cannot be enumerated, no sockets are removed in that cleanup run. Sources: `v2/src/commands/daemon.ts`, `v2/src/commands/cleanup.ts`
- **[v2 additive] Cleanup confirmation:** `jarvis cleanup --yes` (or `-y`) applies the normal retirement plan without prompting, including `--abandon <name>`; absent the flag, non-TTY stdin continues to assume no and makes no changes. Interactive `[y/N]` remains the default. Sources: `v2/src/commands/cleanup-cli.ts`
- The CLI dispatcher admits `--agent` for `intent` (`AGENT_FLAG_SUBCOMMANDS` includes `"intent"`); previously it was rejected with `intent: --agent is not supported` before reaching intent's own `--agent` parser. Sources: `v1/src/cli.ts`
- Every subcommand recognizes `--help` and `-h` flags and prints command-specific help text, then exits 0 without running the command or forwarding the flag downstream. For pass-through commands (`prompt`, `prices`), the `--help`/`-h` flag takes precedence over prompt text or prices subcommand, never forwarded as data. Commands without dedicated help usage strings fall back to the global usage. Sources: `v1/src/cli.ts`
- Unknown subcommands exit non-zero and print usage, while parse-time argument errors also print usage with a command-specific error prefix. Sources: `v1/src/cli.ts`
- `review-feedback` requires a non-empty `<worktree-name>` and exits with usage when omitted, while `triage` accepts an optional worktree argument and otherwise runs a no-arg listing mode. Sources: `v1/src/cli.ts`, `v1/src/commands/triage.ts`
- `prices` is a two-operation command surface (`show` and `edit`) rather than one flat action, and missing/unknown prices subcommands print command-specific usage. Sources: `v1/src/commands/prices.ts`, `v1/src/commands/prices-show.ts`, `v1/src/commands/prices-edit.ts`
- `cleanup` exposes `--dry-run` and `--abandon` modes and requires execution from inside a registered project or it exits with a targeted registration error. Default mode removes merged worktrees (force-retiring even when porcelain is non-empty or unpushed commits exist via `git worktree remove --force`, with no dirty skip line; not-merged worktrees silently skip at the merge gate and stay absent from preview; `isMergedPr` inspection failure keeps silent skip), deletes the local branch, and archives the completed spec to the `completed/` directory of the spec's located home: for `commit: true`, the in-repo home (`v1/spec`, `v2/spec`, or the configured `targetDir`); for `commit: false`, the external home `~/.jarvis/specs/<project-safe-id>/`. External archival is a plain rename with no git commit, and it also prunes `ready-intents/<branch-slug>.md` best-effort. For plan branches, both homes support a timestamp-stripped fallback from `<plan-name>` to timestamped directories using either the v1 dashed format `YYYY-MM-DDTHH-mm-ssZ-<plan-name>` or the v2 compact format `YYYYMMDDTHHmmssZ-<plan-name>`. When no home resolves the spec, the missing-source error names the expected home path. Archival is gated on the resolved archive spec name (`resolveSpecArchiveSource`): spec complete (finalize completion semantics shared with triage `--mark-ready`: every non-human-only acceptance criterion across all linked subspecs, or the sole spec file, checked; index routing checkboxes do not gate completion; vacuous-complete treated as incomplete when an in-flight owner exists; plan `--merge` may land with unchecked subspec AC and does not satisfy archival completeness), zero open PRs from `findMatchingOpenPrs` (multi-match or `gh` failure skips with logged reason, exit `0`), and no other live `.worktree/<spec-name>/` besides the one removed; skip lines go to stdout, merged worktree removal still runs, guards apply to both `commit:true` and `commit:false`, `--abandon` never archives, `--dry-run` unchanged (guards run only after confirmed removal). `--abandon` instead selects non-merged worktrees with no open ready PR, skips merged/ready/multi-open-PR cases, closes one matching draft PR best-effort, force-removes the worktree, deletes local and remote branches, and leaves the source spec untouched for re-run. With `--abandon <worktree-name>`, only `.worktree/<worktree-name>/` is resolved: stdout preview is `Worktree to remove:` then `<worktree-path> (<branch>)` with optional `(plan)` for `plan/*` branches before confirmation or `--dry-run` exit; unknown worktrees stderr `unknown worktree: <name>` exit `1`; merged PR stderr `cannot abandon <worktree-name>: branch <branch> PR is merged` exit `1`; ready/non-draft PR stderr `unsafe PR state for branch <branch>: matching open PR #<n> is not draft` exit `1`; multiple open PRs stderr `unsafe PR state for branch <branch>: multiple open PRs match; refusing abandon` exit `1`; PR inspection failure stderr `failed to inspect PR state for branch <branch>: <message>` exit `1`; branch resolution failure stderr `cannot abandon <worktree-name>: could not determine branch` exit `1`; live `.jarvis.lock` stderr `worktree is in use by process <pid> (started at <timestamp>)` exit `9` (stale locks ignored); scoped `--dry-run` lists only the named target; declining confirmation prints `cancelled` exit `0`; retire failure stderr `failed to remove <branch>: <message>` exit `1`; global `--abandon` without a name keeps the existing scan/skip/preview behavior. Beyond the removed-worktree's own spec, every non-abandon `commit:true` run also runs a root-archival pass (`findArchivableRootSpecs`): it scans `<targetDir>` root (not the `v1/spec`/`v2/spec` fallback homes, and never `completed/`) for other directories resolving to an `index.md` or sole `.md` file, applies the same `checkArchivePreconditions` (complete, ≤1 open PR, no live `.worktree/<spec-name>/`) with `removedWorktreeDir: ""`, and archives each survivor via `archiveResolvedSpec`/`commitArchivedSpecMove` — one commit per candidate. This runs even when zero worktrees were removed (the prior `no merged worktrees to remove` early return no longer skips it) and is unaffected by `candidateHomes`. `jarvis1 cleanup <spec-name>` without `--abandon` scopes this pass to the one matching root dir (CLI no longer requires `--abandon` for a positional argument); `--dry-run` lists candidates under a `Root specs to archive:` heading and archives nothing; `commit:false` and `--abandon` runs skip the pass entirely. Sources: `v1/src/cli.ts`, `v1/src/commands/cleanup.ts`, `v1/src/commands/triage.ts`, `v1/src/pr.ts`, `v1/src/worktree.ts`, `v1/src/worktree-lock.ts`
- `jarvis1 runbook add [--section <heading>] [--issue-url <url>] <entry>` appends a learning to the project's `OPERATOR_RUNBOOK.md` file. Entry text is required and must not be empty or whitespace-only. The `--section` flag (case-insensitive, heading text without `##`) routes the entry to `Known gotchas` (default), `Gate blind spots`, or `Cross-repo coordination`; unknown sections exit 1 and list valid options. The `--issue-url` flag appends an optional jarvis issue URL, formatting the entry as `- <entry> ([jarvis issue](<url>))`; an empty `--issue-url` value exits 1 with usage. The entry is appended as a new list item at the end of the target section, preserving all other content. Running two commands appends two distinct items with no overwrites. A missing `OPERATOR_RUNBOOK.md` exits 1 directing the operator to `jarvis1 init`. Running outside a registered project exits 1 with a registration error. Bare `jarvis1 runbook` and `jarvis1 runbook <unknown-action>` exit 1 and print `runbook` usage. Sources: `v1/src/cli.ts`, `v1/src/commands/runbook.ts`

### Triage command and session-end verdict

- `jarvis1 triage` with no argument (no-arg form) lists valid worktrees from both `<repo>/.worktree/` (`v1`) and the registered project's `~/.jarvis/worktrees/<project-key>/` home (`v2`) in one summary table (HOME, NAME, DIRTY, AHEAD/BEHIND, PR, SPEC columns). Jarvis-owned nested names remain home-relative (for example `plan/<name>`); duplicate names remain distinct via HOME. The session-end verdict identifies each outstanding row's home and retains the same dirty, ahead/behind, PR, spec-progress, landed, and draft classification for either home. Sources: `v1/src/commands/triage.ts`
- A worktree is classified as landed when ALL of the following are true: (1) PR state is MERGED, (2) worktree tree is clean (no staged, unstaged, or untracked file changes), and (3) no unpushed commits exist (the worktree is fully synchronized with its remote tracking branch). When a post-merge upstream deletion occurs (PR merged, remote branch deleted), the no-unpushed check is satisfied (deleted upstream = merged-and-cleaned = landed). Sources: `v1/src/commands/triage.ts`
- A worktree is classified as outstanding in all other cases, including: PR is OPEN/CLOSED/DRAFT, tree has any dirty state, unpushed commits exist, PR-state query fails, or the worktree is a plan worktree (`.worktree/plan-*`). A PR-state query failure is classified as outstanding (safe direction), never as landed. Sources: `v1/src/commands/triage.ts`
- The session-end verdict emits one of two outcomes: (1) `all work landed` when every worktree is landed, or (2) `outstanding work` header followed by one named line per outstanding worktree, listing its name, PR state (OPEN/CLOSED/MERGED/none), draft-vs-ready status, and GitHub's merge-blocking gate state. Draft status is reported as `(draft)` appended to the PR state line; ready (non-draft) PRs emit no draft marker. Gate state is reported as `[<mergeStateStatus>]` (e.g. `[CLEAN]`, `[BLOCKED]`) when available; when the gate query fails, no PR exists, or no checks are reported, gate state is reported as `[unavailable]`. Gate state is enriched only on outstanding entries; landed worktrees do not incur a gate-state query. Sources: `v1/src/commands/triage.ts`
- Named form (`jarvis1 triage <worktree-name>`) performs no verdict and issues no landed-vs-outstanding classification; it remains a diagnostic drill-down only. Sources: `v1/src/commands/triage.ts`
- Named triage **Suggested next moves** may suggest scoped `jarvis1 cleanup --abandon <worktree-name>` (never global abandon). Eligibility matches `checkScopedAbandonPreflight` (exists, no live lock, branch resolves, PR guards) and requires `prState ≠ unknown` — uncertain PR state never suggests scoped abandon. Rule 4: `modified`/`mixed`/`untracked-only` + `MERGED` → `Discard: jarvis1 cleanup` (no stash prerequisite). Rule 6: eligible dirty incomplete → `Discard:` uses scoped abandon; resume retained. Rule 7: `clean` + incomplete + `CLOSED`/`none` + eligible → `Retire this worktree:` scoped abandon only. `clean` + incomplete + `DRAFT`/`OPEN` stays fallback. Advisory only. Sources: `v1/src/commands/triage.ts`, `v1/src/scoped-abandon-preflight.ts`
- Named form with `--mark-ready` flag (`jarvis1 triage <worktree-name> --mark-ready`) finalizes a complete worktree: commits outstanding dirty changes (`git add -A`, message `chore: complete-but-dirty commit`, trailer `Jarvis-Agent: completion-ready`), pushes via `commitAndPushFinalizeDirtyWorktree` (`git push -u` when no upstream on paths that actually push — dirty finalize, or clean tree when `computeUnpushed` > 0; clean tree with `origin` but no upstream and `computeUnpushed` === 0 skips push, so local commits are not auto-pushed), opens a draft PR when absent (`ensureDraftPr`), runs the completion ready gate once (on `full`: `bun run fix` → commit-if-dirty → strict verify, honoring `readyCommand` for verification), and on green marks the PR ready (exit 0). Pre-ready fix/commit/push/post-commit-dirty (and green-over-dirty) failures in this triage path exit `1` with no retry loop. Also serves stuck-red exit 10 recovery when the operator verifies the gate should pass. Completeness is judged on **non-human-only acceptance criteria** read from each linked subspec (or a single-file spec) in the working tree — not the index linked-checkbox — so exit-6 trees with uncommitted criteria ticks still finalize. A worktree whose only unchecked criteria are human-only (`(Manual)`, `visual inspection only`, `no automated guard`) finalizes. Genuinely incomplete runs (any unchecked non-human-only AC) are refused **before any side effect** as re-runs (`jarvis1 run`, not finalize). Pre-checks after completeness: (a) behind-base refusal when the branch does not contain its base (PR `baseRefName` when a PR exists, else default base via `getBaseBranch`) — stderr `behind base, resolve then re-invoke`, exit non-zero, no commit/push/PR open/gate/ready flip; PR-path `gh pr view` or fetch failure soft-fails to proceed (parity with draft→ready guard); no-PR-path fetch/ancestor git errors soft-fail to proceed; (b) if a PR exists, it must be DRAFT (already-ready/merged/closed rejected); (c) absent PR skips the draft guard and opens one after commit/push. Spec path resolution: if `.active-spec-path` marker is present it is used as-is (unreadable, empty, or invalid marker exits with error); if absent, the spec is derived from the worktree's branch name by searching `plan.targetDir`, then `v1/spec`, then `v2/spec` — within each home, a direct branch-name match takes priority over a timestamp-stripped `plan/<name>` match; a matched directory resolves to `index.md` when present, otherwise to the single `.md` file in that directory (zero or multiple `.md` files without an `index.md` refuse with error); a branch with no matching spec refuses with a clear error before any side effect. Live-run lock refused. Push failure after finalize commit exits non-zero with commit intact (no PR open, no gate). Still-dirty after finalize commit exits non-zero (PR left draft if one existed). On gate failure the PR stays draft and exit is non-zero. The `readyCommand` per-project override is honored. Sources: `v1/src/commands/triage.ts`, `v1/src/git/base-current.ts`, `v1/src/cli.ts`, `v1/docs/run-loop.md`, `v1/docs/operator-runbook.md`
- For `--merge`, the worktree lock check follows the resolved home: v1-home worktrees use `<worktree>/.jarvis.lock`, while v2-home worktrees use `~/.jarvis/worktree-locks/<project>/<branch>/.jarvis.lock`; stale-lock liveness remains unchanged. Source: `v1/src/commands/triage.ts`
- `--merge` resolves a target to an absolute local worktree path across both homes: the v1 `<repo>/.worktree/` home and, when the repo is registered, `~/.jarvis/worktrees/<project-key>/` with branch-nested directories. Direct directories are checked before PR-reference and spec-path forms; PR references (`#N`, URL, bare `N`) and spec paths use the same branch/marker/basename/plan-slug matching in both homes. For plan branches in the Jarvis-owned home, v2 spec directories using the compact timestamp format `YYYYMMDDTHHmmssZ-<name>` are recognized alongside v1 dashed-format timestamps. A match in both homes is refused as an `unknown worktree` ambiguity listing both paths. An unregistered repo searches only the v1 home. This path-valued resolution is used by `--merge` and drill-down; `--mark-ready` and listing remain v1-home-only. Sources: `v1/src/commands/resolve-merge-target.ts`, `v1/src/commands/triage.ts`
- `--merge` accepts a resolved worktree with no `.active-spec-path` marker and no branch-derived spec (seed, report, intent, or docs PRs): it still runs the local ready gate, waits for green CI, and admin-squash-merges only afterward. A resolved spec retains its normal completeness guard, except the existing `plan/*` merge exception; missing or malformed markers still refuse without fallback. Sources: `v1/src/commands/triage.ts`
- `--merge` usage errors: `jarvis1 triage --merge` without a target exits with a usage error (matching `--mark-ready` preconditions except `--merge` accepts spec path and PR reference forms). Combining `--merge` and `--mark-ready` together exits with a usage error (mutual exclusivity). Sources: `v1/src/cli.ts`

### Patch-mode run workflow

- `jarvis1 run` accepts `--max-iterations`, `--review-passes`, `--tier`, `--agent`, `--repo`, `--cwd`, and `--resume-review` around a required `<spec-path>`. `--max-iterations` and `--review-passes` validate numeric bounds; `--tier` accepts only lowercase `trivial`, `standard`, or `hard`; invalid values exit `1` before agent spawn with accepted-value guidance. Repeatable `--agent` overrides in-memory `modes.patch.agentOrder` for that invocation (persisted config unchanged). `--resume-review` re-enters the post-completion review phase on an already-complete spec and enforces four preflight guards: review enabled (`modes.review.passes > 0`), effective `git: true`, implementation PR/remote branch exists, and spec has zero unchecked tasks; guard failures exit `1` with distinct error messages before agent spawn. Sources: `v1/src/cli.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`, `v1/docs/agents.md`
- Default implementation runs are index-routed: the harness selects one unchecked linked subspec per agent iteration via `getActiveLinkedSubspecPath` and injects that subspec's path and body into the implementation prompt; agents execute the injected subspec rather than routing from `index.md`. Sources: `v1/src/modes/patch/completion.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/prompt.ts`, `prompts/patch/instructions.md`, `prompts/patch/rules.md`, `v1/docs/spec-guidance.md`, `v1/docs/run-loop.md`
- **[v2 additive]** The v2 implement workflow routes iterations to linked subspecs via `resolveActiveLinkedSubspec` (v2/src/execution/linked-subspec-routing.ts) — the same index-routing model as v1. On multi-subspec `index.md` input, v2 materializes and validates the managed worktree before routing; a failure returns daemon start code `worktree_materialization_failed` with the managed path and underlying cause, before a run row or agent invocation. The first unchecked link is then resolved, its path becomes the completion artifact, and its body is injected into the prompt. Routing state is protected: agent-authored index-checkbox changes are detected, restored, and rejected as `implement.index_routing_mutated` without advancing; agent edits to the active subspec's criteria are allowed. Harness-only advancement checks non-human-only criteria only; unchecked human-only criteria do not block progress. After the final link advances, shrink runs once (terminal shrink timing). Direct subspec input fails as `implement.requires_index`; empty/already-complete indexes return complete without work. Invalid linked paths fail with named kind diagnostics before agent invocation: `implement.malformed_link`, `implement.link_missing`, `implement.link_unreadable`, `implement.link_out_of_tree`. v2's implement write step sources `REPO_GUIDANCE` from `AGENTS.md`/`CLAUDE.md` at the worktree root (same as v1 `readRepoGuidance`); `SIBLINGS_BLOCK` and `TIMEOUT_CHECKPOINT_CONTEXT` resolve to empty strings. **[v2 breaking change]** The CLI passes unresolved implement launch values to `buildImplementWorkflowSteps`, which resolves the cwd-visible spec through the registered source root, then rejects it before daemon contact or worktree creation unless its resolved project-relative path exists in `--base`. The resulting spec/artifact paths are relative to the eventual worktree. `--artifact` is ignored for `index.md` specs (the spec is the artifact) and required for non-index specs. Workflow-started implement cannot be paused/resumed/killed live because the step executes atomically within its timeout. Relative to v1's `jarvis1 run`, this changes required flags, path validation, project resolution, and live-control semantics. ### Patch-mode transient transport error retry

V2 completion publication and draft→ready flip now use a separate shared positive transport classifier: three total attempts with a flat 1000 ms backoff, normalized command evidence in notices and durable terminal errors, and no retry for unknown or permanent failures. This does not change v1 patch-mode retry behavior below.

- Transient transport errors (connection reset, broken pipe, HTTP 502/503/504, etc.) are retried transparently within `runAgent` (`src/agents/spawn.ts`) at the spawn layer before callers see a result. Detection is via `isTransientSignal` (`src/agents/quota.ts`) on non-zero exits only (`exitCode === 0` always returns false). Retries are bounded to a fixed cap of **3 re-attempts (4 total spawns)** with escalating backoff (`[1s, 2s, 4s]` delay before re-attempts 1/2/3) and no agent advancement. If all attempts fail, the final error is returned as `kind: "error"` for normal mode-layer fallback/termination handling. The classifier applies the shared transport patterns to every agent and adds opencode-only guarded HTTP 500 matching, including best-effort `UnknownError`+`500` wording, so opencode server-side 500s ride the same retry loop without widening git/gh retry behavior. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/quota.ts`, `v1/docs/quota-signals.md`, `v1/docs/agent-cli-failure-pipeline.md`
- An aborted invocation (timeout via `opts.signal`, iteration timeout, run timeout, or SIGINT) is never retried; the abort result is returned immediately. Per-iteration timeouts (idle, iteration, run) accrue across all retry attempts; the whole-iteration budget is not reset between spawns. Sources: `v1/src/agents/spawn.ts`
- Each transient re-attempt fires an optional `onTransientRetry` callback (added to `AgentRunOptions`) allowing modes to emit operator-facing diagnostics. Patch wires it to emit `transient transport error (exit N); retrying same agent (attempt A/CAP)` via harness stderr for operator visibility; this phrase shares no substring with quota strings (`quota exhausted; falling back` / `probable quota-like error`). Sources: `src/quota-harness-messages.ts` (`harnessTransientRetryLine`), `v1/src/modes/patch/iteration.ts` (`onTransientRetry` callback), `v1/src/agents/spawn.ts`
- Patch's `onSpawned` callback is made re-entry-safe for retry scenarios: any prior `descendantPollHandle` interval is cleared before assigning the new one (preventing leaked intervals on dead pids), and `watchdogPgid` is repointed to the live child. Sources: `v1/src/modes/patch/iteration.ts`

- **Patch edited-unticked iterations emit usage-bearing invocation rows** (new): a patch iteration that edits files but checks no new acceptance criteria now emits an invocation row with `exit_reason: "edited-unticked"` (on loop-back, below the retry bound) or `"dirty-worktree"` (on terminal exit 6), carrying `usage`, `usage_source`, `cost_usd`, `cost_source`, and `last_output_age_ms`. These rows are `kind: "ok"`, so they count as completed patch iterations in the run summary. This ensures every agent invocation that runs is visible in cost sheets. A run whose only iteration exits 6 now leaves a non-empty `runs.jsonl` with a harness `run_terminal` row. Sources: `v1/src/modes/patch/iteration.ts`, `v1/docs/run-loop.md`
- Review passes and verdict-actuator invocations use the same `DescendantTracker` orphan reaping as patch mode: track on spawn + interval, take a final snapshot after stopping the interval and before reap, then reap in each invocation's `finally`. The patch tracker is idle during review; overlap would be benign anyway because tracking is per-PID and identity-guarded. Reap failures are swallowed and never affect review outcome or exit code. Sources: `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/reap.ts`, `v1/docs/run-loop.md#orphan-process-reaping`

### Patch-mode completion `ready` gate

- Built-in script split: `bun run fix` is the default built-in autofix entrypoint (overridable per-project via `fixCommand`) and expands to `bun run check:fix:unsafe` in the jarvis repo. Built-in `bun run ready` is verification-only: **`full`** runs `install` when required → `check` → `typecheck` → aggregate `test` with one serial retry on genuine parallel failure when unscoped → `lint:md`; **`fast`** remains `typecheck` → aggregate `test` (or scoped per-surface steps when `JARVIS_READY_TEST_SCOPE` is set). The built-in full tier never invokes `check:fix`, `check:fix:unsafe`, or any other `:fix` script inside verification. Per-project `readyCommand` overrides replace the **verification** command only; per-project `fixCommand` overrides replace autofix on **`full`** gates. Sources: `package.json`, `scripts/ready.ts`, `v1/src/ready-gate.ts`, `v1/docs/run-loop.md`
- After implementation is complete (zero unchecked boxes) and `git: true`, a completion-stage `ready` gate runs before shrink and review phases when at least one implementation iteration completed. The gate always runs the built-in **`full`** tier harness-side via `runReadyAndCommit` (zero agent tokens). The completion-transition gate resolves the repo default branch via `getBaseBranch` and passes it as `baseBranch`, so the verification test step is scoped by changed path (`classifyChangedPaths`) like CI — `v1/**`-only diffs run `test:v1` + `test:integration:v1`, docs/spec-only diffs drop the test step, `shared/**` or unresolved merge-base still runs full; omitting `baseBranch` (plan mode, `auto-integrate-base.ts`) preserves unscoped aggregate `bun run test`. On **`full`** the order is: (1) run the project's `fixCommand` when set, else built-in `bun run fix` (skipped when the resolved package-manager script is absent from root `package.json`); (2) if porcelain is non-empty after fix, commit it (default message `chore: apply pre-ready check:fix`, preserving the per-call-site `Jarvis-Agent` agentLabel trailer) and push **before** verification; (3) run strict verification (`bun run ready`, or the project's `readyCommand` if set) against the committed tree; (4) if verification is green and porcelain is non-empty, commit it (default message `chore: apply post-ready verification output`, preserving the per-call-site `Jarvis-Agent` agentLabel trailer) and push — no second verification pass (CI is the backstop); (5) if porcelain remains non-empty after the post-verification commit attempt (or commit/push fails), the gate aborts (exit `6` class) before `gh pr ready`. The autofix and verification `execFileSync` calls are each bounded by `iterationTimeoutMs` (10 min default); timeout failures reuse `FixCommandError`/`ReadyCommandError` with `<cmd> exceeded <timeoutMs>ms budget (gate: <agentLabel>)`. **Operator migration:** prior behavior on `full` was immediate `ReadyVerificationDirtyError` on green verification with non-empty porcelain (no commit attempt); that contract is deliberately replaced — green+dirty now auto-commits harness-owned churn at step (4), and `ReadyVerificationDirtyError` is reserved for residual still-dirty porcelain after a successful post-verification commit (message parallels pre-ready still-dirty: commit succeeded, worktree still dirty, inspect unexpected changes). **`fast`** is unchanged: it runs neither autofix, the fix-commit/push, the post-verification commit, nor post-verification porcelain enforcement. The gate is skipped when `git: false` or when no implementation iterations ran. Sources: `v1/src/modes/patch/run.ts`, `v1/src/ready-gate.ts`, `v1/docs/run-loop.md`
- Completion gate exit classification: `runCompletionReadyGate` invokes the shared **`full`** gate exactly once. A red verification (`ReadyCommandError`) exits `10` with terminal `ready-gate-failed`; it has no retry, agent invocation, reset, force-push, discard, readiness promotion, or successful-completion telemetry. Fix, commit, push, timeout, and residual-dirty failures retain their operational exit-`6` routing. Green records the clean post-gate HEAD and proceeds to shrink → review → `maybeMarkReady`. Sources: `v1/src/modes/patch/completion-pipeline.ts`, `v1/src/modes/patch/run.ts`, `v1/src/ready-gate.ts`
- Post-completion gates share `selectReadyTier(recordedGreen)`: when HEAD and porcelain match the recorded green carrier, shrink pre-gate, review baseline, and `maybeMarkReady` (completion-transition and review final) each invoke `runReadyAndCommit` with **`fast`** or skip local `ready` when the recorded-green predicate allows it; when the tree changed or no green was recorded, they use **`full`** and refresh the carrier on green. Each of these six patch-mode gate call sites (completion transition, review baseline, review final, pre-shrink, `maybeMarkReady`, triage `--mark-ready` / `--merge`) resolves `baseBranch` via `getBaseBranch` and scopes the verification test step by changed path via `classifyChangedPaths` (falling back to full when merge-base can't be resolved); review baseline and final share one resolved `baseBranch` but reclassify independently at each gate. Scoped per-surface test steps (`test:v1`, `test:v2`, …) run without the serial-retry-on-flake safety net the unscoped `bun run test` step has — a behavior regression traded for scoping. CI's own scoping is unchanged. Before any patch-mode draft→ready flip, the helper resolves the PR's actual base ref, best-effort fetches `origin/<base>`, and runs `git merge-base --is-ancestor origin/<base> HEAD`; exit `0` proceeds, exit `1` blocks the flip with a stderr message and leaves the PR draft, and base-resolution/fetch failures soft-fail open to proceed — except at `patch-complete` (`maybeMarkReady` with `autoIntegrateBase: true`) and review-final behind-base, which merge `origin/<base>` when porcelain is clean, run a post-merge **`full`** gate, push, then `gh pr ready` (reversing guard-before-gate at those sites); merge conflict, dirty pre-merge porcelain, or post-merge gate failure restores pre-merge `HEAD` locally and emits the same blocked stderr. Plan-mode draft→ready stays unscoped (no `baseBranch`). Per-iteration `maybeMarkReady` on no-shrink/no-review completion defers to `patch-complete` only (no double auto-integrate). On the common path (green completion, no-op shrink, review makes no commits), exactly one **`full`** ready runs total. **`--resume-review`** has no in-run carrier: review baseline and final each use **`full`**. Sources: `v1/src/ready-gate.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/pr.ts`, `v1/src/commands/triage.ts`, `v1/src/git/base-current.ts`, `v1/src/git/auto-integrate-base.ts`, `scripts/ci-test-scope.ts`, `v1/docs/run-loop.md`
- Per-project `readyCommand` override: a project config entry `readyCommand: "<cmd>"` (validated non-empty, non-whitespace-only string at `loadConfig`) replaces the **verification** command at patch-mode gate sites — completion transition, pre-shrink, review baseline, review final, and `maybeMarkReady`. The command is resolved once from `preflight.cfg.projects[preflight.project.key]?.readyCommand` and threaded to every patch gate call. It is tokenized on whitespace and run via `execFileSync` (no shell). The `JARVIS_READY_TIER` env var is set unchanged; when `baseBranch` is wired, `JARVIS_READY_TEST_SCOPE` carries the scoped script list (or `""` for docs-only). When unset, patch gates fall back to `bun run ready`. The override is verification-only: on **`full`** the harness runs `fixCommand` (or built-in `bun run fix`) and the pre-ready commit-if-dirty step before the override, then the post-verification commit-if-dirty step after green verification when porcelain is non-empty; residual still-dirty porcelain after that commit aborts (exit `6` class) with no second harness fix pass. Mutating `readyCommand` outputs (coverage threshold auto-update, snapshot regen, etc.) are harness-owned committable churn on `full`. Plan-mode verification stays on built-in `bun run ready` without `baseBranch` scoping; plan threads `fixCommand` only. Sources: `v1/src/config.ts`, `v1/src/ready-gate.ts`, `v1/src/modes/patch/completion-pipeline.ts`, `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/pr.ts`, `v1/src/modes/plan/pr.ts`, `v1/docs/config.md`
- Per-project `fixCommand` override: a project config entry `fixCommand: "<cmd>"` replaces autofix on every **`full`**-tier ready gate — completion transition, pre-shrink, review baseline and final, `maybeMarkReady`, triage `--mark-ready` / `--merge`, and plan-mode draft→ready. Resolved from the registered project whose `root` matches the gate cwd (patch: once from `preflight.cfg.projects[preflight.project.key]`; triage/plan: root match). Tokenized on whitespace, `execFileSync` (no shell). When unset, autofix falls back to `bun run fix`. For package-manager-shaped commands, absent root `package.json` scripts skip autofix without `FixCommandError`; commit-if-dirty and verification still run. Non-PM-shaped commands always execute. Sources: `v1/src/config.ts`, `v1/src/ready-gate.ts`, `v1/src/commands/triage.ts`, `v1/docs/config.md`
- Legacy `readyGateRetryBound`: a saved non-negative integer remains loadable solely for compatibility, emits a deprecation warning, is ignored, and is omitted when config is written. It does not cause completion retries. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- Ready gate test-step serial retry: when the unscoped `bun run test` step fails with a genuine process exit code (not signal-derived or timeout), the gate runs the test suite serially (`bun test` without `--parallel`) exactly once before declaring the test step failed. If the serial run passes, the gate treats the test step as green and continues to remaining commands; if the serial run fails, the gate exits with the serial failure code. Scoped per-surface steps (`test:v1`, `test:v2`, …) invoked via `JARVIS_READY_TEST_SCOPE` do not get serial retry. Non-test steps (`install`, `check`, `typecheck`, `lint:md`) exit immediately on failure with no serial retry. Signal exits (SIGINT/SIGTERM, codes 130/143) and timeout exits (code 124) do not trigger serial retry — only genuine test-process failures do. This mirrors operator manual recovery from parallel-load flakes. Serial re-run accounts within the gate's deadline: if it exceeds the remaining budget, it is killed and the gate exits non-zero (fail-closed). Sources: `scripts/ready.ts` (`runReady`, `isGenuineTestFailure`, `isTestStep`), `v1/test/ready-script.sandbox-unrunnable.test.ts`
- Blocker-validation suite-run serial retry: the base-ref test runner (`runBaseRefTests`, `v1/src/modes/patch/base-ref-test-runner.ts`) and snapshot-update retest runner (`runSnapshotUpdateRetest`, `v1/src/modes/patch/snapshot-update-retest-runner.ts`) each apply test-invocation-only serial retry on suite failure (non-zero `bun run test` exit), mirroring the ready gate's recovery pattern. When the parallel invocation exits non-zero, each runner re-runs `bun test` (no `--parallel`, same discovery, no path/filter args) exactly once in the same execution context (base-ref in the throwaway worktree before cleanup; snapshot in the agent working dir). If the serial run passes, the test is treated as green; if the serial run fails, the runner returns non-green. Non-test steps (git setup in base-ref, update-snapshots command in snapshot runner) exit immediately on failure with no serial retry. Each runner emits three stderr lines on parallel failure: a retry-starting line, a recovered line on parallel-red → serial-green, and a serial-still-failed line on parallel-red → serial-red. Runners accept an optional `runCommandFn` injectable parameter for test-invocation seaming (default: execFileSync). Sources: `v1/src/modes/patch/base-ref-test-runner.ts`, `v1/src/modes/patch/snapshot-update-retest-runner.ts`, `v1/test/base-ref-test-runner.test.ts`, `v1/test/snapshot-update-retest-runner.test.ts`
- Agent guidance serial retry (mid-work): `prompts/patch/rules.md` instructs agents, when `bun run test` fails during implementation iterations, to re-run the suite once serially (`bun test` without `--parallel`) before treating the failure as real or appending a `## Blocker`. Only a serially-reproducing failure grounds a blocker or stops the run; single parallel-load flakes are treated as non-deterministic noise and are recovered from without blocking. This mirrors the ready gate and blocker-validation harness-side serial retry, extending operator-like recovery logic to agent-executed test invocations mid-work. Guidance also instructs agents to skip `bun run test` when the iteration changed nothing under tested paths (no source files, test files, prompt fragments, or fixtures — only human-facing prose), avoiding flake exposure on docs-only subspecs with zero signal. Sources: `prompts/patch/rules.md` (revision 8), `v1/src/modes/patch/prompt.ts`, `v1/docs/spec-guidance.md`

### Patch-mode post-completion shrink

- After implementation is complete (zero unchecked boxes), a clean worktree, and `git: true`, shrink runs when the run completed at least one implementation iteration and `modes.patch.shrink` is not configured to `"off"`. Shrink is skipped when `git: false`, when no implementation iterations ran, or when `modes.patch.shrink` is set to `"off"`. When shrink or review will run, per-subspec completion defers `maybeMarkReady` to the post-completion phases. Order: shrink (if enabled) → review (when configured) → `maybeMarkReady`. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- Shrink flow: pre-shrink gate uses `selectReadyTier` — **`fast`** when HEAD and porcelain match the recorded green carrier, **`full`** otherwise (refresh on green; failure logs warning, skips shrink) → walks `reviewActuator` order (fallback to `modes.patch.agentOrder`) with per-rung fresh idle watchdog and `iterationTimeoutMs` arms; each rung invokes `patch.prompt.shrink` + `global.terse` (not `patch.rules`). Quota exhaustion advances to the next rung (full-list walk; final-rung quota exhausted reverts and discards silently). Idle-output stall (`kind: "error"` with `aborted: idle-timeout` stderr) escalates to the next rung when one remains (`shrink: <agent>: idle timeout; escalating to next agent`, `watchdog-idle-timeout-fallback` telemetry, partial edits from stalled rung retained in worktree, no exit-code elevation); terminal idle reverts to pre-shrink HEAD and throws `ShrinkTerminalError` (run exit `8`, review skipped). `iterationTimeoutMs` wall-clock abort and other non-idle invocation failures revert and discard silently without elevating exit code. Post-success path: spec-tree revert, out-of-scope revert, then detect surviving file changes. When no surviving changes remain, the phase exits early without contract validation and produces no commit. When changes survive, contract validation requires `bun run test` pass, no deleted scoped `*.test.ts`, no AC checkbox regression (a criterion checked pre-shrink must remain checked); contract miss discards all shrink changes without elevating run exit code. Single `shrink:` commit with attribution and PR footer refresh is produced only when changes survive contract validation. Sources: `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/completion-pipeline.ts`, `v1/src/ready-gate.ts`, `prompts/patch/shrink.md`
- `reviewActuator` is the sole actuator-tiering lever for review actuator and shrink. Sources: `v1/docs/config.md`, `v1/docs/agents.md`
- The `modes.patch.shrink` config field (string enum `"off" | "agent"`, default `"agent"`) controls whether the shrink phase runs. `"agent"` keeps the existing agent-shrink behavior; `"off"` skips the entire phase (no pre-shrink gate fires, no telemetry row is emitted). Invalid values fail config validation with a named error naming the field. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- Shrink scope is the accumulated set of non-spec paths touched during implementation iterations; edits outside that set are reverted post-invocation. Prompt carries a branch change summary for orientation, run-scoped unified diff (allowlisted files only in `RUN_SCOPED_DIFF`), and an explicit allowlist — never a full-branch unified diff. Sources: `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/prompt.ts`, `prompts/patch/shrink.md`
- **Zero-output detection guard** (new): when an implementation-phase agent invocation completes with zero observed stdout and zero stderr bytes, patch mode emits a named harness diagnostic `zero agent output observed from <agent>; check agent binding` on stderr and stamps `zero_agent_output: true` on every telemetry record written during that iteration (both non-terminal invocation and terminal run rows). The flag is omitted (not `false`) when output was observed. The guard is a visibility signal only — no change to exit codes, escalation ladder, or iteration outcome. It fires regardless of the iteration's kind (`ok`, `error`, `quota`, `timeout`); it does not fire when the agent process never spawned (missing binary, spawn-layer error). The end-of-run summary notes zero-output occurrences per agent in the notes section: `N iteration(s) under <agent> produced zero observed output (stdout + stderr); check agent binding and environment.` Operators read `zero_agent_output: true` in telemetry to distinguish "no output" from "idle" or "quota" in timeout records where `last_output_age_ms: null`. Sources: `v1/src/quota-harness-messages.ts` (constant + function), `v1/src/telemetry.ts` (`TelemetryRecord.zero_agent_output`), `v1/src/modes/patch/iteration.ts` (detection + telemetry stamping), `v1/src/run-summary.ts` (summary note), `v1/docs/quota-signals.md` (full semantics)
- Telemetry records shrink with `patch_phase: "shrink"`; shrink is excluded from `patchIterationsCompletedForSummary` and run-summary `isImplementationAttempt` counts (like review). Sources: `v1/src/telemetry.ts`, `v1/src/modes/patch/run.ts`, `v1/src/run-summary.ts`

### Dependency installation on commit

- When a commit (subspec, WIP-progress, WIP-blocker) touches `package.json` or `bun.lock`, the harness detects the change and installs dependencies outside the agent sandbox with network access. Detection is via `git diff HEAD~1 HEAD --name-only` for changed files. The install runs only when `git: true` (in git-enabled patch mode). Sources: `v1/src/modes/patch/dep-install.ts`, `v1/src/modes/patch/iteration.ts`, `v1/docs/worktrees-and-commits.md`
- **Symlink promotion**: when `node_modules` is a symlink (the default in fresh worktrees), the harness removes the symlink before running `installCommand`, allowing the install to create a real directory. On resume, the worktree-creation logic (`createWorktreeSymlinks`) skips recreating the `node_modules` symlink if a real directory already exists, preserving the promoted state. Sources: `v1/src/worktree.ts` (`createWorktreeSymlinks`), `v1/src/modes/patch/dep-install.ts`, `v1/docs/worktrees-and-commits.md`
- **Install command**: the per-project `installCommand` config (default `bun install`) runs via shell (`sh -c`) in the worktree directory. Sources: `v1/src/config.ts`, `v1/src/modes/patch/dep-install.ts`, `v1/docs/config.md`
- **Lockfile commit**: if the install regenerates `package.json` or `bun.lock`, the harness commits those changes with message `harness: regenerate lockfile after dep install` and Jarvis-Agent trailer before the ready gate runs. This ensures the PR never ships with uncommitted lockfile changes. Sources: `v1/src/modes/patch/dep-install.ts`, `v1/docs/worktrees-and-commits.md`
- **Failure handling**: install failures are logged loudly to stderr with `[dep-install]` prefix but do not halt the run. Lockfile-commit failures are also logged but do not halt the run. The next iteration's typecheck and ready gate may fail if the dependency is missing. This is not a self-healing path — manual resolution is required. Sources: `v1/src/modes/patch/iteration.ts` (`maybeInstallDeps`), `v1/docs/run-loop.md`
- Install runs after subspec completion, WIP-progress, and WIP-blocker commits. Sources: `v1/src/modes/patch/iteration.ts` (lines with `maybeInstallDeps` calls)
- **Patch rules: agents no longer stop on new dependencies**: The patch rules (`prompts/patch/rules.md`, revision 8) instruct agents to edit `package.json`/lockfile, record the decision in spec, and continue when adding a dependency. Agents no longer halt on dep additions; the harness manages all installs post-iteration. In-sandbox install failures are expected (network blocked in sandbox, write blocked through symlink) and are not grounds for appending a `## Blocker`. Sources: `prompts/patch/rules.md` (revision 8), `v1/docs/run-loop.md`
- **Patch rules: human-only criteria are operator-verified (revision 8)**: The patch rules instruct agents that acceptance criteria flagged as human-only (`(Manual)`, "visual inspection only", "no automated guard") are operator-verified: implement them, run the automated gate, leave them unchecked, and do not attempt in-sandbox visual verification (no dev-server port bind). Agents do not append a `## Blocker` for human-only criteria. This reduces blocker churn from spec conditions the agent cannot verify in-sandbox. Sources: `prompts/patch/rules.md` (revision 8), `v1/docs/run-loop.md`
- **Patch rules: agents leave committing to Jarvis (revision 8)**: The patch rules (`prompts/patch/rules.md`, revision 8) instruct agents not to run `git commit` or otherwise create commits, stating "Jarvis owns staging and committing." This prevents agents from interleaving self-owned commits with Jarvis completion commits and raising blast radius. Sources: `prompts/patch/rules.md` (revision 8), `v1/docs/worktrees-and-commits.md`
- **Patch rules: tests must inject config fixtures for machine/user-config resolution (revision 10)**: The patch rules (`prompts/patch/rules.md`, revision 10) require that tests reaching machine/user-config resolution (e.g., `resolveMachineProfile`, `loadWorkflowSteps` without an injected profile) must inject an explicit config fixture and mocked profile, never reading the ambient machine config from `~/.jarvis`. This ensures test hermiticity: tests pass in CI and remain machine-independent. Tests with ambient config reads fail locally when profiles differ but pass on the operator's machine, creating CI-only failures; using explicit fixtures and mocked profiles prevents this divergence. Sources: `prompts/patch/rules.md` (revision 10), `v1/docs/run-loop.md`

### Git and loop-only runs

- Effective `git` resolves per-run from the top-level `git` flag overlaid by the resolved project's `projects.<key>.git` override; `--repo`/`--cwd` and ad-hoc resolution all funnel through the same effective value. Sources: `v1/src/config.ts` (`effectiveGit`), `v1/src/modes/patch/run.ts`
- When effective `git` is `false`, patch mode runs "loop-only": no worktree is created, the agent's `cwd` is the resolved project root (or `--cwd <dir>` when supplied), and no per-subspec commit, push, draft-PR open, or ready-on-complete occurs. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- In loop-only mode completion is purely "zero unchecked boxes": the clean-tree requirement and exit `6` do not apply, and `worktreeSymlinks` is ignored. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- **No-commit re-run auto-reset (updated)**: When a run with untracked mutations is incomplete (interrupted, killed, or blocked), acceptance-criteria checkboxes ticked and blockers appended during that run persist in the spec. On re-run of that incomplete spec, jarvis automatically reverts these stale mutations before agent invocation: AC ticked in the prior incomplete run are un-ticked, and any `## Blocker` appended is stripped. Mutations are untracked when `git: false` (no commits) OR when the spec file is external to the agent working tree (git cannot revert it). The recorded delta (newly-checked AC keys + appended blocker text) is persisted in jarvis-owned state (`~/.jarvis/no-commit-deltas/…`) during the incomplete run and cleared when a re-run completes the spec successfully. Pre-attempt AC checkboxes (authored before any run) remain ticked through reset, preserving operator work. This eliminates manual hand-reverting of checkboxes and blockers before retrying a no-commit or external-spec run. - On committed `--resume`/`--resume-draft`, if `.worktree/plan-<name>` is missing, jarvis best-effort fetches and auto-recreates it from local `plan/<name>` or `origin/plan/<name>` (logging recreate source), but it still enforces the later `origin` presence check and still fails with the original missing-worktree error when neither local nor remote branch exists. Sources: `v1/src/commands/plan.ts`, `v1/src/worktree.ts`
- Plan `commit: false` mode writes spec output to Jarvis-owned external spec roots and emits absolute-path next-step commands for later `jarvis1 run` execution instead of creating git commits, pushes, or PR transitions. Effective `git: false` is treated the same way: no plan worktree, branch, push, PR, or revert path. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/spec-paths.ts`, `v1/docs/plan-mode.md`
- On fresh `git: false` plan runs, name-collision checks come only from the external spec root; existing repo `spec/…`, `.worktree/plan-…`, and `plan/…` branch names do not rename the external spec. In git-disabled review, reviewer temp artifacts and reviewer-edit cleanup also stay in the external spec directory and avoid repo `git` cleanup calls. Sources: `v1/src/modes/plan/run.ts`, `v1/src/modes/plan/review.ts`, `v1/docs/plan-mode.md`
- Plan `commit: false` mode prints `Intent: <absolute-path-to-intent.md>` to stdout immediately after the external `intent.md` is written and before any later draft or review phase can fail. This ensures the operator retains the external intent artifact path even if a later phase fails. Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`
- Plan mode enforces a write boundary before each draft/review commit: agent writes must stay within the active spec directory. On a boundary violation in commit mode, commit-mode plans revert the offending paths, append a boundary `## Blocker`, commit a `plan: blocker`, and exit `1`. For no-commit plans, the external spec-root check is removed, including the dropped rogue-sibling detection; no external-storage boundary guard remains, allowing concurrent no-commit plans to coexist without spurious violations. When effective `git` is `true`, jarvis still checks the target checkout for stray `spec/`-prefixed writes via `assertTargetRepoPlanBoundary` (detects only `spec/` paths in the live checkout; does not cover external-storage escapes). When effective `git` is `false`, the target-repo `git status` boundary probe is also skipped entirely. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/boundary.ts`, `v1/docs/plan-mode.md`
- Plan `commit: false` mode preserves the named external spec directory and its `intent.md` on all later-phase failures (draft/review generic error, quota, model config, validation, boundary violation, blocker, interrupt): failure output prints a `Spec preserved at` breadcrumb naming the directory path so operators can inspect the artifact. The only exception is pre-`intent.md` write failure — in that case the abandoned spec directory is removed and no breadcrumb is printed (the operator has not yet received an `Intent:` path). Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`

### Intent mode

- `jarvis1 intent` is a separate mode entrypoint with its own parser, usage text, and handler; `--help` exits `0` with intent-specific usage while parse errors print targeted `intent:` messages. Repeatable `--agent` overrides in-memory `modes.plan.agentOrder` for intent-split actuation only. Sources: `v1/src/cli.ts`, `v1/src/commands/intent.ts`
- Intent mode supports both committed and no-commit routing based on `modes.plan.commit`. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- Fresh intent mode requires exactly one seed. The positional argument is treated as a file only when the path exists; otherwise it is treated as inline text. The file-seed input directory depends on the commit mode: under `commit: true`, file seeds must live under `<targetDir>/seeds/`; under `commit: false`, file seeds must live under `~/.jarvis/specs/<project-safe-id>/seeds/`. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- Intent mode uses the same plan-root resolution as plan mode. Per-run `--target-dir <dir>` overrides project/global `plan.targetDir` (same precedence and validation as plan: relative paths only, no absolute paths, no `..` traversal). Committed runs write authored intents to `<targetDir>/ready-intents/` in the target repo; no-commit runs write to an external Jarvis-managed directory `~/.jarvis/specs/<project-safe-id>/ready-intents/`. In no-commit mode, `--target-dir` no longer affects the seed-input directory validation (seeds are validated against the external home regardless of `--target-dir`). Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- Running intent mode splits one seed into N behavior-level intents, writes only `<name>.md` files under `ready-intents/`, and enforces (with deterministic repair) matching `name:` frontmatter, a heading on the first non-blank body line (after frontmatter), and a `## Prerequisites` section in each file: missing or mismatched `name:` is rewritten to the filename slug; missing `## Prerequisites` is appended as an empty section; exact `## Prerequisites` headings are normalized to one blank line before and after; malformed `## Prerequisites` bodies (non-bullet text) remain hard errors. Non-empty prerequisites are required to be one bullet line per prerequisite behavior. Body heading enforcement: if the first non-blank body line is already a `#` heading, it is left untouched; if it matches `name: <slug>` (the repaired slug value), it is replaced with `# <Title>` derived from the slug (kebab-case split on `-`, each word capitalized, joined with spaces); if the body has neither heading nor a duplicate `name:` line, the derived `# <Title>` is prepended. Emitted files are fixed in-TypeScript for MD012 (consecutive blank lines) by trimming before `## Prerequisites` append and MD018 (space-in-heading) by keeping issue references off line-start; all staged files then receive a `markdownlint --fix` pass using the harness-pinned binary and config (cwd anchored to prevent target-repo config override), applying autofix only and never failing on residual violations. Spawn failure or missing binary warns but continues with the in-TypeScript-repaired content. Never writes spec `index.md` files or numbered subspecs. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- A single-behavior seed is valid and still runs the full flow, emitting exactly one authored intent. Sources: `v1/src/commands/intent.ts`, `v1/test/intent-command.sandbox-unrunnable.test.ts`
- Intent-name collisions are hard errors: if `<targetDir>/ready-intents/<name>.md` (committed) or external `ready-intents/<name>.md` (no-commit) already exists, the run aborts without overwriting files and without opening a PR. Sources: `v1/src/commands/intent.ts`, `v1/test/intent-command.sandbox-unrunnable.test.ts`
- Splitter output is staged, mechanically repaired (`name:` frontmatter and `## Prerequisites`), and validated before move/commit. Structural errors (bad filenames, duplicates, malformed prerequisites, no files) abort without partial `ready-intents/` writes or a PR. Sources: `v1/src/commands/intent.ts`, `v1/src/modes/plan/intent-split.ts`, `v1/test/intent-command.sandbox-unrunnable.test.ts`
- Intent mode uses `modes.plan.agentOrder` (config default) for the splitter step, with per-invocation `--agent` overriding that ladder for intent-split only: `quota` and `model_config` fall through to the next configured agent (rotation stderr uses `intent: <agent>: …; falling back`); terminal exhaustion on all-quota exits `2` with the shared all-agents-exhausted wording, and all-`model_config` without `ok` exits `3` with `intent: model configuration error`. Sources: `v1/src/commands/intent.ts`, `v1/src/modes/plan/intent-split.ts`, `v1/test/intent-command.sandbox-unrunnable.test.ts`
- Successful file-seed fan-out consumes its seed: committed mode deletes the mapped worktree copy before the split commit, while no-commit mode deletes it after every ready-intent lands. Inline seeds have no deletion target; failed, missing, external, or symlink-escaped inputs remain. Sources: `v1/src/commands/intent.ts`, `shared/publication-input-consumption.ts`, `v1/test/intent-command.test.ts`
- **Committed mode (`commit: true`):** Successful runs create a dedicated `intent/<name>` branch and `.worktree/intent-<name>` worktree, commit the `ready-intents/` split, open or update a draft PR for operator review, and flip the PR ready immediately after push without waiting for local gates, base freshness checks, or remote checks. `gh pr ready` failures warn but do not fail the intent run. Sources: `v1/src/commands/intent.ts`, `v1/src/worktree.ts`, `v1/src/pr.ts`, `v1/src/modes/plan/pr.ts`, `v1/docs/intent-mode.md`
- **No-commit mode (`commit: false`):** Successful runs write authored intents to the external Jarvis-owned directory, skip worktree/branch/commit/push/PR operations, and print absolute-path `jarvis1 plan --repo <project> <path>` next-step commands for each emitted intent. The splitter runs with `--add-dir` access to a temporary external staging directory. This mode enables intent splitting in isolated setups (non-git project roots or `git: false` configurations). Fallback to cursor/opencode agents writes no files and fails validation since they do not honor `--add-dir` (inherited `--add-dir` limitation; fix out of scope). Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`, `v1/test/intent-command.sandbox-unrunnable.test.ts`

### Plan-mode flow matrix

Which phases actually run in a single invocation depends on the entry mode and the resolved `commit` flag. This consolidates the prose bullets above. Fresh plan flows require a ready-intent (`<targetDir>/ready-intents/<name>.md`) and skip intent authoring phases entirely:

| Entry mode | `commit` | Phases that run in one invocation | Stop / handoff |
| --- | --- | --- | --- |
| ready-intent (file arg) | `true` | copy `intent.md` -> draft -> `plan: draft` -> review -> PR handoff | exits `0`; operator merges PR then runs `jarvis1 run` on the generated spec |
| ready-intent (file arg) | `false` | copy `intent.md` -> draft -> review (into external spec root) | exits `0`; prints `jarvis1 run <indexPath>` next step |

Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`, `v1/docs/plan-mode.md`

- `--resume-draft` is rejected with guidance to use `jarvis1 plan <ready-intent>` for fresh work or `jarvis1 plan --resume <index.md>` for post-draft review. Sources: `v1/src/commands/plan.ts`
- `commit: true` plans run under a `plan/<name>` branch and `.worktree/plan-<name>` worktree where `<name>` is derived from the ready-intent frontmatter `name:`. Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`

### Prompt mode

- `jarvis1 prompt` is a single-pass one-shot agent invocation mode controlled by a required `<text>` positional argument and optional `--repo`, `--agent`, and `--model` flags; `--cwd` is explicitly rejected as an error (prompt mode requires git). Sources: `v1/src/cli.ts`, `v1/src/modes/prompt/run.ts`
- `--agent` on `jarvis1 prompt` pins the primary agent (first in effective list, config suffix deduped). Model: `--agent <name>:<model>` → `--model` → config row → agent default; colon wins over `--model`. Unknown/malformed values exit before worktree creation; other subcommands reject the flag. `run`, `plan`, and `prompt` all accept per-run `--agent`; seed `per-run-agent-override-flag` tracks remaining cross-mode override work beyond those surfaces. Sources: `v1/src/cli.ts`, `v1/src/parse-agent-flag.ts`, `v1/src/modes/prompt/run.ts`, `v1/docs/agents.md`
- Prompt-mode preflight gates include: `git: true` requirement (exit `1`), project registration (exit `1`), and GitHub CLI auth (`gh auth status`, exit `1`). Sources: `v1/src/modes/prompt/run.ts`
- Prompt mode uses `modes.prompt.agentOrder` for agent iteration; if `modes.prompt` is not defined in config, it defaults to a structuredClone of `modes.patch.agentOrder` at load time. Sources: `v1/src/config.ts`, `v1/src/modes/prompt/run.ts`
- Worktree creation names follow pattern `.worktree/<timestamp>-prompt-<nonce>/` on branch `<timestamp>-prompt-<nonce>` (UTC ISO8601 timestamp, 6-character random nonce suffix); the worktree is always created in the project root. Sources: `v1/src/modes/prompt/run.ts` (`iso8601DateTime`, `generateNonce`, `createPromptWorktree`)
- Prompt mode is strictly single-pass with per-agent fallback on the effective agent list (`modes.prompt.agentOrder`, or pinned-first when `--agent` is set); `quota` and `model_config` advance, generic `error` and timeout halt immediately. Exit 2 when every attempted agent returned quota; exit 3 on other chain exhaustion. Per-entry model drives invocation and telemetry `configured_model`. Sources: `v1/src/modes/prompt/run.ts`
- Prompt output handling differs by diff state: **no-diff** — agent's stdout is printed first, then a summary block (with usage/cost/duration) and an outcome line stating "No changes were made." are emitted to stdout, and the run exits `0` without any git/PR operations. **diffs present** — the prompt text is committed and a PR opened, then a summary block and an outcome line containing the PR URL are emitted to stdout. Sources: `v1/src/modes/prompt/run.ts`
- When diffs exist, prompt mode commits with subject = first non-empty line of prompt text (ellipsized to ~72 chars), body = full prompt text + `Jarvis-Agent: <label>` trailer, then pushes and opens a draft PR with the prompt text as body + attribution footer. The PR URL is captured from `gh pr create` stdout and included in the outcome line. Sources: `v1/src/modes/prompt/run.ts`
- Prompt PR body is static (operator input only in the PR title/description): `<prompt-text>\n\n---\n\n🤖 Generated with [Claude Code](https://claude.com/claude-code)`. Sources: `v1/src/modes/prompt/run.ts`
- Prompt telemetry is written with namespace `<project-key>:prompt` (matching patch mode's `<project-key>:run` and plan mode's plan naming), mode field `"prompt"`, and one terminal row per command (intermediate fallback attempts are stderr-only). On both success termini (no-diff and diff), telemetry is enriched with `usage`/`usage_source`/`cost_usd`/`cost_source` fields extracted from the agent result via `extractUsageAndCost`, and written before the summary renders. Terminal exit reasons include `success`, `all-agents-quota`, `agent-failure`, `watchdog-iteration-timeout`, and others matching patch-mode taxonomy. Chain exhaustion without success (mixed `model_config`/`quota`, all-`model_config`, or generic error) records `telemetryKind: "error"` and `exitReason: "agent-failure"`; all-quota exhaustion records `telemetryKind: "quota"` and `exitReason: "all-agents-quota"`. Sources: `v1/src/modes/prompt/run.ts` (`appendTelemetryLine`)
- Prompt mode exit codes mirror patch mode: `0` success, `1` error, `2` quota exhausted, `3` agent/model hard failure, `8` timeout, `9` worktree lock busy. Sources: `v1/src/modes/prompt/run.ts`
- Prompt mode always acquires and releases `.jarvis.lock` for the created worktree (failing with exit `9` if the lock is held by a live process), matching patch-mode lock semantics. Sources: `v1/src/modes/prompt/run.ts`, `v1/src/worktree-lock.ts`
- Prompt-mode invocations use the same `DescendantTracker` orphan reaping per fallback attempt: each attempt gets its own tracker, polls on spawn + interval while the agent runs, takes a final snapshot before reap, and reaps in that attempt's `finally`. Reap failures are swallowed and never affect the prompt exit code or reason. Sources: `v1/src/modes/prompt/run.ts`, `v1/src/modes/patch/reap.ts`, `v1/docs/run-loop.md`

## Spec authoring and implementation workflows

- New implementation specs are expected to be authored as index-routed trees (`index.md` + numbered subspec files) with checklist links from index into atomic subspec documents. Sources: `v1/docs/spec-guidance.md`
- The documented workflow requires spec-first sequencing: create a spec PR, merge spec files to `main`, and only then start implementation runs against that merged spec. Sources: `v1/docs/spec-guidance.md`
- `jarvis1 plan` can generate spec trees, but generated specs follow the same merge-first rule before `jarvis1 run` implementation work begins. Sources: `v1/docs/spec-guidance.md`, `v1/docs/workflows.md`
- External plan output (`modes.plan.commit: false`) produces Jarvis-owned spec trees written to a configured external spec root directory (not inside the target repo) with a required `repo:` binding so later `jarvis1 run` invocations can resolve the target checkout. Sources: `v1/src/modes/plan/spec-paths.ts`, `v1/docs/spec-guidance.md`, `v1/docs/config.md`
- For v2 phase-led execution (`v2/spec/v2-meta-index.md`), operator input should be a build brief sourced from the chosen phase line and matching `v2/docs/v2-build-order.md` section; `jarvis1 plan` is the drafting step, `jarvis1 run` is the implementation step, and phase completion is merged `v2/src` code rather than generated intent/spec artifacts. Sources: `v2/spec/v2-meta-index.md`, `v2/docs/v2-build-order.md`, `v1/docs/spec-guidance.md`

### Config storage and bootstrap

- Jarvis stores state under `~/.jarvis/` with `config.json`, and configuration is auto-bootstrapped on first run rather than requiring manual initialization. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- The config defaults to schema version 2 with mode-specific agent order blocks (`modes.patch.agentOrder` and `modes.plan.agentOrder`) and project registry storage under `projects`. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- The config exposes behavior knobs beyond agent order (quota policy, timeouts, log server, telemetry, git toggle, worktree symlinks); see the [Configuration field reference](#configuration-field-reference) below for the full enumeration and defaults. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- Each registered project may declare `siblings`: absolute paths passed to the agent as additional readable directories alongside the spec. Patch preflight errors with exit `1` if a configured sibling does not exist. Sources: `v1/src/config.ts`, `v1/src/modes/patch/run.ts`
- Invalid config structure is rejected with file-specific validation errors instead of partial best-effort reads. Sources: `v1/src/config.ts`
- `jarvis1 init` only registers repos under `~/Work` by deriving the project key from the path relative to that root, and it records `origin` only when `git remote get-url origin` yields a non-empty value. The runbook is not overwritten on re-run; byte-for-byte idempotence is preserved. The runbook includes a static known-gotchas section with jarvis-issue URLs and fixed section headings so references remain stable. Sources: `v1/src/commands/init.ts`, `v1/src/runbook-generator.ts`

### v2 additive: named workflow presets

- v2 write loops enforce machine config `iterationTimeoutMs` (default `600000` ms) from `iteration_started`, even before agent spawn. Timeout commits the attempt as `iteration_timeout`, marks the run failed, emits one terminal `loop_finished`, and suppresses late settle, throw, or abort effects. Sources: `v2/src/execution/write-loop.ts`, `v2/src/config/machine-config-loader.ts`

- `jarvis run workflow <name> [flags]` selects a CLI builder by name; `implement`, `intent`, `intent-reviewed`, and `plan` are registered. Missing or unknown names print `usage: jarvis run workflow <implement|intent|intent-reviewed|plan> [flags]` and exit `1` before daemon connection. The `implement` launch preserves its `--branch`, `--base`, `--spec`, and `--artifact` parser; `intent`/`intent-reviewed` use `(--seed <path> | --seed-text <text>) [--target-dir <dir>]`; `plan` uses `--ready-intent <path> [--target-dir <dir>]`. All builders validate their inputs and exit `1` pre-daemon before bad state reaches the daemon. After successful daemon `start`, the CLI blocks on a daemon `wait` request for the workflow run ID and mirrors the run's exit code: `0` on success, `3` on `runStatus: failed`, `4` on `runStatus: killed`, `5` on `runStatus: budget-soft-stopped`, or the mapped `loopOutcomeKind` code if present. Stdout carries the run ID line followed by the wait completion JSON line. Sources: `v2/src/cli.ts`, `v2/src/execution/plan-workflow-steps.ts`, `v2/docs/workflow-runner.md`, `v2/docs/write-behavior.md`

- **[v2 additive]** Daemon `wait` and `list` roll workflow entry status across snapshot steps marked durable: write, human, reviewed-intent review, and review-debate rows participate. Plan debate review has a separate durable list/TUI row keyed by its authored `stepId`; live detail retains the current debate role, while completed, failed, and daemon-reconciled interrupted rows survive restart. Ordinary review remains non-durable. Missing durability metadata is legacy-durable, so a missing legacy row remains `killed`. Sources: `v2/src/daemon/workflow-run-status-rollup.ts`, `v2/src/daemon/workflow-list-snapshot.ts`, `v2/src/execution/workflow-runner.ts`

- **[v2 additive]** Implement preset accepts one authored write step plus an appended review step by default (one debate pass when `reviewPasses` is omitted). Other resolver-supported presets (`write-write`, `intent`, `plan`) retain exact authored-write cardinalities at `resolveWorkflowPreset` time — `intent` and `plan` builders append review steps after preset resolution, so runtime workflow length can exceed preset step count. The write step is pinned to `behavior: "write"`, `role: "implement"`, and `promptId: "patch.prompt.body"`. Omitted or positive `reviewPasses` load one review step after terminal shrink in the implement worktree; explicit `0` or `--review-passes 0` omits review (v2 previously defaulted omitted flags to zero passes). `--review-behavior debate|light` (default `debate`, overridable per project via `projects.<key>.implement.reviewBehavior`) selects `review-debate` (four-role debate, `stepId: "implement-review"`, `verdict-patch.md`) or `review` (critic-actuator light patch review, same step id and verdict path). Sources: `v2/src/execution/workflow-runner.ts`, `v2/src/execution/implement-workflow-steps.ts`, `v2/docs/workflow-runner.md`
- **[v2 additive]** `loadWorkflowSteps` loads authored `write | review | review-debate` steps from machine config. A review receives the shared model config and configured order for fixed `critic` and `actuator` roles; a review-debate receives them for fixed `adversary`, `advocate`, `adjudicator`, and `actuator` roles. Missing bindings are aggregated before execution. Human steps are not loader inputs. Sources: `v2/src/execution/workflow-loader.ts`, `v2/src/execution/workflow-runner.ts`, `v2/docs/workflow-runner.md`
- **[v2 additive]** Daemon-run intent, plan, and implement reviews retain serializable profile policy and domain through JSON transport, then rehydrate executable renderers immediately before light or debate dispatch. Sources: `v2/src/execution/review-profile-registry.ts`, `v2/src/execution/workflow-runner.ts`, `v2/src/daemon/daemon-workflow-start.test.ts`
- **[v2 behavior change]** Intent workflow builders (`buildIntentWorkflowSteps` and delegating `buildReviewedIntentWorkflowSteps`) send authored split and review sources through one `loadWorkflowSteps` call, forwarding injected machine configuration. They resolve the `intent` preset from loaded write steps only, append review when passes are positive (one light pass by default), and return loader errors unchanged as `{ ok: false, error }`; zero review passes remains split-only. Sources: `v2/src/execution/intent-workflow-steps.ts`, `v2/src/execution/workflow-loader.ts`, `v2/docs/workflow-runner.md`
- **[v2 behavior change]** Reviewed-intent critic and actuator invocations, verdict handling, boundary enforcement/restoration, staging, landing, and enabled commit/push/draft-PR publication run in the split step's resolved external workspace; unrelated dirty files in the operator checkout are untouched. Review success is checkpointed before landing. A landing failure returns resumable `invocation_failure` with persisted `failureKind: "landing"`; resume retries landing without re-running review. Git-disabled runs land locally and perform no Git or GitHub operation. Sources: `v2/src/execution/intent-workflow-steps.ts`, `v2/src/execution/workflow-runner.ts`, `v2/src/execution/review-intent-enforcement.ts`

| `logServerBind` | `127.0.0.1:4310` | Bind address for `jarvis1 log-server`. |

- Validation is strict: unknown top-level/project/plan keys, non-absolute or duplicate project roots, empty model strings, unknown agent names, and priced-but-unknown models are all rejected with file-specific errors. Sources: `v1/src/config.ts`

### Repository resolution order and matching

- Target-repo resolution order is `--repo` first, then spec `repo:` value, then spec-path-inside-registered-project, then ad-hoc parent walk for a `.git` checkout root, then unresolved prompt/error signaling. Sources: `v1/src/resolve-project.ts`, `v1/src/repo.ts`, `v1/docs/run-loop.md`
- For both `--repo` and non-absolute `repo:` values, matching first checks exact registered project key and then loose URL/slug equivalence via normalized `host/owner/repo` comparison. Sources: `v1/src/resolve-project.ts`, `v1/src/repo-url.ts`
- Legacy absolute-path `repo:` values are honored only as exact matches to a registered project root; non-matching absolute paths fall through to location-based resolution. Sources: `v1/src/resolve-project.ts`, `v1/docs/spec-guidance.md`, `v1/docs/run-loop.md`
- Unresolvable `repo:` values (relative paths like `./project` and non-slug barewords like `jarvis`) are deferred to location-based resolution steps: spec-path-inside-registered-project and ad-hoc parent walk. If either location-based step succeeds, the run proceeds against that resolution and the unresolvable line is silently ignored. Only when both location-based steps fail does the resolution surface the unknown-repo error, naming the unresolvable value and the list of registered projects. Sources: `v1/src/resolve-project.ts`, `v1/docs/run-loop.md`, `v1/docs/spec-guidance.md`
- URL normalization intentionally lowercases host/owner/repo, strips protocol/user/trailing `.git`, interprets bare `owner/repo` as GitHub, and drops extra URL path segments when comparing loose matches. Sources: `v1/src/repo-url.ts`

### Ambiguity handling and operator prompts

- Multiple registered matches for `--repo` or spec `repo:` produce an explicit ambiguous result with candidate set rather than picking one silently. Sources: `v1/src/resolve-project.ts`
- In interactive mode, disambiguation prompts let operators choose by 1-based index or exact project key, with `q`/blank treated as cancellation. Sources: `v1/src/disambiguation-prompt.ts`
- In non-TTY mode, disambiguation does not prompt and instead emits candidates plus a rerun hint using `--repo <name>`. Sources: `v1/src/disambiguation-prompt.ts`

Sources: `v1/src/modes/patch/run.ts`, `v1/src/commands/plan.ts`, `v1/src/agents/quota.ts`

### Adapter-specific behavior

- `claude` runs `claude -p --permission-mode acceptEdits --output-format stream-json --verbose`, pipes the prompt on stdin, forwards `--add-dir` entries, and parses the terminal stream-json `result` event into displayed text, usage, and cost when present. Stream-json events arrive during the iteration so the idle-output watchdog observes Claude liveness the way it does for codex and opencode. On exit `0`, it first checks stdout for a verified quota error envelope (`is_error: true`, `api_error_status: 429`, quota message in `result`); when matched, it returns `kind: "quota"` with the full stdout JSON preserved in `stderr` diagnostics instead of parsing success fields. Sources: `v1/src/agents/claude.ts`, `v1/src/agents/claude-json.ts`, `v1/docs/agents.md`
- `codex` runs `codex exec --color never --sandbox workspace-write -c approval_policy="on-request"` with stdin prompt piping, appends a per-invocation marker to the prompt, and derives usage by correlating changed `~/.codex/sessions/*.jsonl` files; ambiguous or missing correlation is reported as unavailable instead of guessed. Codex `input_tokens` is normalized to fresh-only (cached-input subtracted) before costing to match the disjoint-bucket convention that `computeCost` assumes. Sources: `v1/src/agents/codex.ts`, `v1/src/agents/codex-session.ts`, `v1/docs/agents.md`
- `cursor` runs `cursor agent -p --output-format text --force --workspace <cwd> <prompt>`, and successful runs estimate token usage from prompt+stdout rather than CLI-reported counters. Sources: `v1/src/agents/cursor.ts`, `v1/src/agents/cursor-tokens.ts`, `v1/docs/agents.md`
- `opencode` runs `opencode run --dir <cwd> --model <provider/model> --format json <prompt>`, parses JSONL event output, uses summed `step_finish` token/cost fields when present, and falls back to estimator warnings when no clean `step_finish` data exists. Sources: `v1/src/agents/opencode.ts`, `v1/src/agents/token-estimation.ts`, `v1/docs/agents.md`

### Quota detection and fallback semantics

- Spawn classification order is **transient → auth → quota → model_config** in decreasing priority; only non-zero exits can classify as auth/quota/model-config at the shared spawn layer. Transient signals (connection reset, broken pipe, HTTP 502/503/504) stay as `kind: "error"` to enable same-agent retry. Durable credential/auth signals (refresh token revoked, re-authenticate required, log out and sign in) classify as `kind: "quota"` with an optional `authFailure: true` marker. Dual strict-quota + model-config → `quota`. The Claude adapter may reclassify exit-`0` stdout JSON into `kind: "quota"` before accepting `ok`. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/quota.ts`, `v1/src/agents/claude.ts`, `v1/src/agents/claude-json.ts`, `v1/docs/quota-signals.md`
- Credential/auth failure classification is durable-phrasing-driven and agent-scoped: Codex matches "refresh token revoked", "log out and sign in", and "re-authenticate" signals; Claude and Cursor patterns are deferred to the first real sample. Bare `401`/`unauthorized` one-off blips are not matched (treated as transient-eligible errors). Auth signals route through the existing quota fallback and rotation path (exit 2 on exhaustion), distinguished by the `authFailure` marker for later consumer notes. Sources: `v1/src/agents/quota.ts`, `v1/docs/quota-signals.md`
- Quota and model-configuration classification is regex-driven per adapter, with shared base model-config patterns and extra adapter-specific additions for Opencode provider-local failures. Sources: `v1/src/agents/quota.ts`, `v1/docs/quota-signals.md`
- `quotaFallback: "lenient"` can upgrade `kind: "error"` into `kind: "quota"` only when the caller-provided guard allows it; patch mode passes that guard only for no-progress iterations, preventing weak quota upgrades after observable repo progress. Sources: `v1/src/agents/quota.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/quota-signals.md`
- Quota rotation and exhaustion stderr strings are shared constants: strict fallback uses `quota exhausted; falling back`, lenient upgraded fallback uses `probable quota-like error (exit N); falling back`, and terminal exhaustion uses `all agents quota-exhausted` (plan prefixes with `plan:` and may append phase suffixes). When a quota-classified result carries an `authFailure: true` marker, an operator-visible note `<agent> auth failed; re-authenticate and retry` is emitted on stderr at all rotation emit points (patch iteration, shrink, review, prompt, plan) instead of quota fallback phrasing, naming the agent needing re-authentication. The note is distinct from quota strings for operator grep-ability. Sources: `v1/src/quota-harness-messages.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/review.ts`, `v1/src/modes/prompt/run.ts`, `v1/src/modes/plan/emit-plan-quota-stderr.ts`, `v1/src/commands/plan.ts`, `v1/docs/quota-signals.md`

### Patch invocation architecture

- Patch mode's per-iteration loop retains its own advancement semantics (head agent per iteration, with fallback on quota exhaustion). Starting with the shared-binding migration, patch now uses separable v1-owned binding methods for spawn and classification, distinct from the plan binding's coupled `invoke` method.
- The patch binding factory (`createPatchInvocationBinding`) exposes `spawn` and `classify` methods. `spawn` runs the agent with watchdog integration (onSpawned, lastOutputAtMs, abortKillGraceMs). `classify` applies quota fallback with a caller-supplied guard thunk (computed after the iteration body completes).
- The patch iteration loop calls `binding.spawn()` to run the agent, then executes the iteration body (checking acceptance criteria, detecting file edits, etc.), then calls `binding.classify(result, noIterationProgress)` with a guard computed from the iteration results.
- Patch implementation iterations keep their own loop and do not use the shared executor (`executeWithQuotaFallback`). Review/shrink may use the shared executor for their inner ladders; patch iteration telemetry, stderr messages (quota fallback and exhaustion), and exit codes remain unchanged.
- The separable spawn/classify seam exists to serve paths (review, shrink) that need custom logic between spawn and classification; patch is the primary consumer driving that separation. Sources: `v1/src/modes/patch/patch-invocation-binding.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/agents.md`

### Abort and process lifecycle

- All adapters execute via a shared spawn wrapper that launches the CLI in a detached process group, normalizes env with `PWD=<agent cwd>` and no `OLDPWD`, and buffers stdout/stderr until stream close + process close before final classification. Sources: `v1/src/agents/spawn.ts`, `v1/docs/agents.md`
- Patch-mode Ctrl-C handling aborts the current iteration controller and surfaces `interrupted`; agent subprocess abort handling then sends `SIGTERM` to the process group first and escalates to `SIGKILL` after a grace timeout. Sources: `v1/src/modes/patch/run.ts`, `v1/src/agents/spawn.ts`
- Aborted agent runs resolve as `kind: "error"` with `exitCode: -1` and `stderr` prefixed `aborted: <reason>`, so aborts are operator-visible as explicit harness-side failures rather than silent termination. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/types.ts`
- Patch mode enforces two timeouts that both surface as exit `8`: a per-iteration timeout (`iterationTimeoutMs`, default 10 minutes) and an optional whole-run timeout (`runTimeoutMs`). On iteration timeout a watchdog `SIGTERM`s the agent process group and escalates to `SIGKILL` after a grace period (5s), in addition to aborting the iteration controller; telemetry distinguishes `watchdog-iteration-timeout` from `iteration-timeout` and records the watchdog pgid plus stall diagnostics (`last_output_age_ms`, `watchdog_descendants_alive`) snapshotted at watchdog fire. Timeout terminal rows carry `record_role: "run_terminal"` and `active_subspec_path`; three trailing consecutive timeout rows for the same active subspec append a blocker recommending that the subspec be split. The first terminal row for another subspec or any non-iteration-timeout terminal result resets the streak. The timeout run still exits `8`; telemetry disabled via `telemetryPath: null` disables the split signal. Sources: `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/iteration.ts`, `v1/src/agents/spawn.ts`
- On the `aborted: iteration-timeout` path specifically (not idle- or run-timeout), `git: true` non-external-spec runs commit any staged worktree changes (tracked edits and new untracked files) as a `WIP: checkpoint (iteration-timeout)` commit before returning exit `8`, so uncommitted agent edits aren't lost to the next iteration; a no-op when nothing is staged. Commit failure is logged to stderr and does not change the exit code. Sources: `v1/src/modes/patch/{iteration,subspec}.ts`
- An optional idle-output watchdog (`idleOutputTimeoutMs`, default `90000`) aborts agent-spawning phases if the agent produces neither stdout/stderr **nor file-system activity** for the configured span. Applies to patch-mode phases (iteration, review debate/actuator, shrink) and plan-mode phases (draft, review debate/actuator, verdict-actuator). Liveness is `max(lastOutputAt, lastFileActivityAt, armedAt)`; the watchdog fires only when this effective last-activity time exceeds `idleOutputTimeoutMs`. File activity is the most-recent mtime in the agent working tree (excluding `.git/` internal changes); scan occurs only on the cheap path (both output and file activity already stale). Writes to gitignored paths count as file activity. Whichever timeout fires first (idle or wall-clock) aborts the phase. **Patch implementation** idle abort escalates through `activeAgents` when fallback rungs remain (`watchdog-idle-timeout-fallback` telemetry); terminal exit `8` with `watchdog-idle-timeout` only on the final rung (fix-up iterations do not escalate). **Review actuator** idle abort escalates through `reviewActuator` ladder when fallback rungs remain (`review:`-prefixed stderr, same fallback telemetry); terminal idle exit `11`. **Shrink** idle abort escalates through `reviewActuator` ladder when fallback rungs remain (`shrink:`-prefixed stderr, same fallback telemetry); terminal idle exit `8`. Review debate, plan, and prompt phases keep terminal idle abort with no cascade. `iterationTimeoutMs` wall-clock abort stays terminal with no ladder advance (including review actuator and shrink). Idle abort is **not** classified as quota. Idle abort behavior mirrors wall-clock timeout: when pgid is known, a `[watchdog]` line is logged and the process group is killed; when pgid is unavailable, telemetry still records stall fields. Sources: `v1/src/modes/patch/{iteration,review,shrink}.ts`, `v1/src/modes/plan/{draft,review,verdict-actuator}.ts`, `v1/src/modes/patch/idle-watchdog.ts`, `v1/docs/run-loop.md`
- [v2 divergence] **Invocation liveness** — v1: one global `idleOutputTimeoutMs` + parallel `iterationTimeoutMs` (10 min), with `max(output idle, file idle)` and ladder escalation; v2 shared invocation now has caller-supplied stdout/stderr-only `idleOutputMs` stall detection, disabled by default, with no mtime signal or stall cascade. Profiles, workspace/marker signals, and stall-driven binding advance remain deferred. Sources: `v1/src/modes/patch/{iteration,review,shrink}.ts`, `shared/invocation/{agents,execute}.ts`, `v2/docs/invocation-liveness.md`
- On normal agent completion with exit code `0` and no abort reason, the harness best-effort reaps in-group stragglers via `process.kill(-pgid, "SIGKILL")` from a `child.on("exit")` handler. **Deadlock rationale**: the reap runs on `exit` rather than on the close branch because `close` fires only after stdout/stderr stream teardown; a straggler that inherited the agent's stdio pipes holds them open indefinitely, preventing teardown and causing settlement (which waits for stream end) to deadlock. The `exit` event fires independent of pipe state, so killing the group closes inherited pipes and allows settlement to proceed. The reap is non-fatal: a kill error (including `ESRCH` on a clean close where the agent left no descendant) is swallowed and does not affect the settled result kind or exit code. Reaping is POSIX-only (it relies on `-pgid` for process-group targeting). Only in-group descendants are targeted; a process that left the agent's group (e.g., started its own session) is out of scope and is not killed. Reaping does not run when `code !== 0`, on the error-settle, quota, model-config, or `child.on("error")` paths; abort and timeout paths have their own group-kill logic. Sources: `v1/src/agents/spawn.ts`, `v1/docs/run-loop.md`
- Agent descendants that leave the agent's process group (e.g. via `POSIX::setsid()`) and re-parent to init (PPID=1) escape the in-group straggler reap above. macOS does not expose process environments to an unprivileged `ps`, so Jarvis tracks these orphans by PID instead of an env marker: while an agent runs, it samples the process table on a fixed interval and records every descendant PID (transitive `ppid`, plus processes sharing the agent's `pgid`), capturing escapees while their lineage is intact. At iteration end (settle, abort, timeout) and at finalize (SIGINT and direct `process.exit`) it SIGKILLs recorded descendants that are still alive, skipping any PID whose start time (`lstart`) changed to avoid killing a recycled PID, and never the harness's own process. Reaping is best-effort and non-fatal; it reads only `pid`/`ppid`/`pgid`/start time, so no process environments or arguments are logged or stored. Sources: `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/reap.ts`, `v1/docs/run-loop.md#orphan-process-reaping`

## Git/GitHub behavior

### Worktrees and locks

- Patch runs derive the worktree directory and branch name from the parent directory name of the resolved spec path, and create/reuse `.worktree/<spec-name>` plus branch `<spec-name>` (including recreating a missing local branch from `origin/<spec-name>` when available). Sources: `v1/src/worktree.ts`
- If `jarvis1 run` is invoked from inside a checkout already on branch `<spec-name>`, worktree creation is skipped and the current checkout is reused as the agent working directory. Sources: `v1/src/worktree.ts`
- New branch+worktree creation resolves the base branch through `gh repo view --json defaultBranchRef` (`getBaseBranch`) when needed, then cuts from `origin/<base>` when that remote-tracking ref resolves locally and falls back to the local base branch name when it does not; this applies to patch `ensureWorktree` and managed `createManagedWorktree` (plan/intent/prompt). Failures to `git fetch origin` are tolerated and do not stop worktree setup. Sources: `v1/src/worktree.ts` (`ensureWorktree`, `createManagedWorktree`), `v1/src/gh.ts`
- Plan mode uses a separate namespace: `.worktree/plan-<name>` on branch `plan/<name>`, with an explicit hard error when the plan worktree path already exists. Sources: `v1/src/worktree.ts`
- `review-feedback` auto-materializes a missing `.worktree/<worktree-name>` when `git: true`, creating the worktree from `origin/<worktree-name>` if remote-only or from the existing local branch otherwise; if neither exists it errors `no local or remote branch named <name>; cannot create worktree`. With `git: false` the legacy `unknown worktree "<name>"` error is preserved. Plan worktrees (`plan-*`) are rejected before this check. Sources: `v1/src/commands/review-feedback.ts`, `v1/src/worktree.ts`
- Patch and review-feedback flows serialize per-worktree execution with `.jarvis.lock`; if an existing lock PID is still alive, the command exits with code `9` and stderr `worktree is in use by process <pid> (started at <timestamp>)`. Sources: `v1/src/worktree-lock.ts`, `v1/src/modes/patch/run.ts`, `v1/src/commands/review-feedback.ts`
- Stale lock recovery is automatic: when a lock file exists but its PID is dead, jarvis replaces the lock with the current process and records a harness log line about recovering a stale lock. Sources: `v1/src/worktree-lock.ts`, `v1/src/modes/patch/run.ts`
- `.jarvis.lock` exclusion is enforced best-effort through worktree-local `info/exclude` so normal `git add -A` commit paths do not stage lock files. Sources: `v1/src/worktree-lock.ts`
- Git-backed patch preflight writes `.active-spec-path` in the patch worktree root after resolving the active spec path for the agent prompt. In-repo specs record the worktree-local copied spec path; external specs record the external absolute spec path. Re-runs rewrite the marker when the resolved value changes. The marker is excluded through worktree-local `info/exclude`, so tracked ignore files stay unchanged and normal `git add -A` paths do not stage it. Effective `git:false` runs and worktree-skipped preflight paths do not write the marker. Sources: `v1/src/modes/patch/preflight.ts`, `v1/src/commands/triage.ts`
- Patch-mode run teardown always attempts to release `.jarvis.lock` for the active worktree once preflight marked it as acquired. Sources: `v1/src/modes/patch/run.ts`, `v1/src/worktree-lock.ts`

### Review-feedback command

- `jarvis1 review-feedback <worktree-name>` collects actionable open PR review comments (unresolved inline threads and top-level comments) and, when any exist, runs the patch-mode agent loop with `renderReviewPrompt`, commits `address PR review comments` on dirty worktree, pushes, and exits `0`. Open review comments take priority over CI state — when any actionable comment exists, red CI does not switch to the CI-failure prompt or `address failing CI checks` commit subject. Sources: `v1/src/commands/review-feedback.ts`, `v1/src/review-feedback.ts`
- When no open review comments exist, `review-feedback` performs one HEAD-sha commit check-runs fetch (`git rev-parse HEAD` + paginated `gh api repos/{owner}/{repo}/commits/{sha}/check-runs` via `fetchCommitCheckRunsForSha`), adapts with `adaptCheckRunsToCiStates`, and classifies with `classifyCiChecks` on the same payload. Fetch `{ ok: false }` (gh API error, unresolvable `origin`, JSON/parse failure, pagination abort) exits `1` with the surfaced reason on stderr and does not print `no open review comments`. Successful fetch with zero check-runs, or classification `green` or `pending`, exits `0` with stdout line body `jarvis1 review-feedback: no open review comments` (trailing newline) and does not spawn an agent. Classification `red` runs `collectFailingCiContext` on the same fetch payload (no second gh call), `renderCiFailurePrompt`, the same patch-mode agent/quota/commit/push loop as the comment path, commit subject `address failing CI checks`, stdout `jarvis1 review-feedback: collected <N> failing CI checks for PR #<n>` then `jarvis1 review-feedback: review prompt prepared (<chars> chars)` before the agent, and on success the same tail line `jarvis1 review-feedback: committed and pushed review feedback updates via <agent>`. CI excerpts are bounded per check (2048-byte tail cap on combined `output.summary` + `output.text`). A clean worktree after the CI agent exits `1` with `agent run completed with no file changes; no commit created`. Sources: `v1/src/commands/review-feedback.ts`, `v1/src/ci-checks.ts`, `v1/src/review-feedback.ts`
- `review-feedback` CI state is HEAD commit check-runs; `triage --merge` polls branch-scoped `gh pr checks` — shared `classifyCiChecks` vocabulary does not guarantee cross-command alignment when sources diverge. Sources: `v1/src/ci-checks.ts`, `v1/src/commands/triage.ts`

### Branches and commits

- Patch subspec completion commits are created by jarvis (not agent git automation) with subject equal to subspec H1, body first line `Spec: <relative subspec path>`, and embedded `## Acceptance criteria` section body copied from the subspec file. Sources: `v1/src/modes/patch/subspec.ts`
- Completing a subspec also flips the corresponding linked checklist entry in that subspec directory's `index.md` from `[ ]` to `[x]` before commit creation. Sources: `v1/src/modes/patch/subspec.ts`
- Completion, progress, and blocker per-subspec commit paths all no-op on a clean tree after `git add -A` rather than failing the run; completion still writes the index checkbox before the clean-tree check, so a real `[ ]`→`[x]` flip still commits normally. Sources: `v1/src/modes/patch/subspec.ts`
- Progress and blocker iterations are committed as `WIP:` subjects with `Spec: <relative subspec path>` in the body, and blocker variants append a `## Blocker` section in commit message content. Sources: `v1/src/modes/patch/subspec.ts`
- All harness-authored commit shapes append `Jarvis-Agent: <label>` trailer when the agent label is non-empty; empty labels omit the trailer line entirely. Sources: `v1/src/commit-trailer.ts`, `v1/src/modes/patch/subspec.ts`, `v1/src/modes/patch/pr.ts`
- Push behavior is two-phase: first branch push uses `git push -u origin <current-branch>` and later pushes use plain `git push` once upstream tracking exists. Sources: `v1/src/worktree.ts`, `v1/src/modes/patch/run.ts`

### PR and GitHub CLI mediation

## v2 Parity: Completion publication (push and draft PR)

### Publication title resolution

v2 ports v1 `getIndexTitle` at the shared publication boundary: index H1, then
index parent basename, or non-index file basename. Unlike v1's unchecked read,
an unreadable index is an intentional v2 publication failure naming title
resolution and the spec path. Explicit intent titles remain authoritative.

- **v2-ported with async contract change:** push, draft PR ensure, post-PR body refresh with attribution footer, ready gate (`bun run ready`), and draft→ready flip (`gh pr ready`). v2 collapses work into one completion commit (v1 uses per-subspec commits for attribution). Each push/PR command executes inside the publication retry boundary and preserves operation, exit code, and labelled output tails on failure. Failed completion publication marks its owning row failed while retaining resume eligibility; ready finalization runs only after confirmed PR evidence and a successful publication. Sources: `v2/docs/write-behavior.md`, `v2/src/execution/completion-publisher.ts`, `v2/src/execution/workflow-runner.ts`.

### Publication evidence gate

- **v2 additive:** After all publication operations succeed (push, PR, body refresh), a final gate verifies publication evidence: if `pushSha` is present but `prNumber` is absent, the completion surfaces as retryable `completion_commit_failed` (not `complete`), and ready finalization is skipped. This ensures a reported completion always implies confirmed PR evidence, preventing silent publication gaps where code is pushed but no PR exists or was found. Sources: `v2/src/execution/write-loop.ts`, `v2/src/execution/publication-retry.ts`, `v2/docs/write-behavior.md`, `v2/docs/operator-runbook.md`.

## v2 Additive: Fresh dispatch for new run rows

- **v2 additive behavior:** `WorkflowRunnerInput.freshDispatch` is an optional boolean field (default `false`/absent). When set to `true`, the workflow runner suppresses reuse of completed runs from prior invocations and mints a new `invocationId` for the workflow snapshot, forcing new run rows for each step on the first touch in that execution. Within a single execution, subsequent touches of the same `stepId` (e.g., in a linked-implement loop or shrink step) reuse the run row created during that execution, avoiding duplicate rows. This enables operators to request a fresh execution of an already-completed workflow without manually managing prior-run state. When `freshDispatch` is absent or `false`, the normal resume-step-idempotence contract applies: prior `completed` runs are reused idempotently and invocationId is inherited from the prior run's snapshot. The fresh-dispatch decision reaches `prepareRun` in `write-loop.ts` (not just `prepareWorkflowStep` in the runner), so the enforcement is comprehensive across both layers. Non-terminal prior runs (`in-progress`, `paused`, `budget-soft-stopped`, `awaiting-human`, `revising`) are untouched. Sources: `v2/src/execution/workflow-runner.ts`, `v2/src/execution/write-loop.ts`, `v2/docs/workflow-runner.md`.

## v2 Parity: Completion commit subject and idempotency

- **v2 behavior change:** v2 completion commits derive their subject from the resolved spec title (the spec `index.md` H1 heading when readable and non-empty, falling back to the spec directory basename), rather than using the fixed literal `jarvis: complete run`. The `Spec: <specPath>` and `Jarvis-Agent: <agent>` trailers are preserved in the message body. Idempotency — recognizing a prior completion commit when the tree is unchanged — switches from matching the fixed subject to checking for the presence of a `Jarvis-Agent:` trailer in the HEAD message. This enables `git log --oneline` to show a human-readable subject per-run while preserving the idempotency contract through the trailer. Sources: `v2/src/execution/completion-commit.ts`, `v2/docs/write-behavior.md`.
