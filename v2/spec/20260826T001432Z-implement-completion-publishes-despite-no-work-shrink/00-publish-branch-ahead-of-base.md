# Publish a branch carrying unpublished commits

## Problem

`executeWorkflow`'s completion publication tail (`v2/src/execution/workflow-runner.ts`) gates the whole push + `gh pr create --draft` chain on `if (published.commitSha !== undefined)`. That gate is not decisive today: the tail calls the completion committer with `forceDistinctCommit: true`, and `shouldReuseHeadWithoutNewCommit` (`v2/src/execution/completion-commit.ts`) is `indexTree === headTree && !forceDistinctCommit` — with force `true` it never short-circuits, so the committer always falls through to `commit-tree` and returns a defined `commitSha`, even over a perfectly clean worktree with nothing new to say. The only way that committer returns no `commitSha` is the missing-`.git` early return in `createCompletionCommitter`. So on any readable Git worktree, `published.commitSha !== undefined` is already true for every completed workflow — including one whose branch has no content difference from its resolved base at all. The tail commits an empty marker and pushes it as a draft PR.

This is **not** what produced the 2026-08-23 strand on `20260823T000833Z-dismiss-run-durable-flag` (that run's `publicationAgent` resolved to `undefined`, so the committer was never called — see [subspec 01](./01-publishing-identity-from-commit-attribution.md)). It is a separate, adjacent defect this subspec targets: a completed workflow whose branch carries no real content ahead of base still gets an empty commit pushed and a draft PR opened for nothing. And the converse the intent asks for — "a run with no commits against a clean worktree neither pushes nor opens a PR" — is not current behavior either; `forceDistinctCommit` manufactures a commit and publishes it regardless.

## Decision ledger

- The decisive signal is content, not a raw commit count: because the tail's own forced commit means HEAD is always at least one commit ahead of base by the time any check could run, `git rev-list --count <baseRef>..HEAD` is never zero after the committer runs and is not the right predicate — checking it *before* the committer runs (or before the existing `preImplementResetAnchor` rewind that un-commits this run's own per-iteration progress so the tail can re-commit it as one clean commit) wrongly reads "nothing to publish" for the ordinary case where this run's own work is the only thing ahead of base. Rules out both a pre-commit and a naive post-commit `rev-list` gate.
- Publication is instead keyed on whether the tail's own completion commit differs in file content from `baseRef` — `git diff --name-only <baseRef> <publishedCommitSha>` is non-empty — evaluated *after* the committer call (so it reflects the final, post-rewind, post-force-commit state, independent of whether `preImplementResetAnchor` fired). Rules out duplicating the committer's own diff/status plumbing to predict the outcome before committing.
- When that diff is empty, the tail rolls the just-created marker commit back (`git reset --mixed` to the HEAD captured immediately before the committer call) and treats the boundary exactly as the existing no-`commitSha` path would: no `stamped.commitSha`, no `emitWorkBoundaryRecorded`, no push, no PR, no ready-gate/verification chain. Rules out leaving a dangling unpushed, unrecorded local commit that could confuse a later resume or a human inspecting the worktree, and rules out inventing a new terminal-record shape — the "nothing happened" record already exists and this reuses it.
- The existing no-`commitSha` dirty-named-paths block (`completion_commit_failed` when `getUncommittedPaths`/`remainingStagedIntentPaths` still name something) is untouched and still runs first, ahead of the new check, for the true missing-`.git` case. Rules out folding the two checks together.
- The new diff read only ever runs when `published.commitSha !== undefined`, which the committer only returns after it has itself confirmed `.git` exists (`createCompletionCommitter`'s own `existsSync` early return). The check therefore never runs against a non-Git directory and needs no separate repo-presence guard of its own — rules out a `git rev-list`-style probe that would run unconditionally and could ascend into an unrelated enclosing repo when the worktree path is not one.
- A failed or unparseable diff read (the worktree is not a Git repo, the base ref is unresolvable) resolves to "no publishable content" rather than failing the run, mirroring the no-throw contract the existing `countFilesChanged` helper already has for an empty `diff-tree` result. Rules out a diagnostic git read that can strand a completed spec.
- `baseRef` is resolved exactly as the tail already resolves it (`completionStep.worktree.baseRef`); a base ref that has moved since the branch was created can make the diff see content this run did not itself produce — that is the existing, accepted meaning of "ahead of base" used everywhere else in this file, not a new risk introduced here.
- The gate lives in the shared completion tail every workflow shape traverses (implement, intent, plan, review-last), not a write-role-implement conditional; coverage includes one non-implement shape so the change is proven repo-wide, not implement-only.
- A publication admitted by this gate runs the whole finalization chain (body refresh, ready gate, mutation verification, runtime smoke, draft→ready flip) exactly as any other publication; rules out a push-and-PR-only shortcut that would ship an ungated PR.
