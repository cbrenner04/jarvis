## Verdict

Three required outcomes, all confirmed directly in the code:

1. **Promoted runs must retain working bindings.** `start` normalizes `params.input` into live bindings (with `invoke` functions) before persisting it as `queuedInput` via `JSON.stringify` (functions are dropped silently). `promoteQueuedRun` passes the deserialized value straight into `spawnWriteLoop` with no re-normalization. Any promoted run currently gets bindings stripped of `invoke` and will fail at execution time. This must be fixed so a promoted run's bindings are fully functional, not just structurally present — either by re-deriving/re-normalizing bindings at promotion time from serializable inputs, or by persisting only what's needed to reconstruct them and rebuilding at promotion. This is required to satisfy the spec's core promise that a queued run can be spawned later "without the original caller's process still being alive" (subspec 01) — a promotion that produces a broken run doesn't meet that bar.

2. **`worktree_claimed` must reject a `start` for a key already claimed by a live run, even when memory is tight.** In the current `start` handler, the live-registry claim check (`_registry.isClaimed(key)`) only runs on the branch reached when memory headroom is available; the queuing branch checks only for an existing queued row, not for a live claim. This means a `start` for a key already owned by a running run, arriving while memory is briefly below the watermark, gets queued instead of rejected. This directly violates the accepted, checked-off criterion in subspec 01 ("a `start` call for a `(project, branch)` key already claimed — whether by a live run or an existing queued run — is rejected `worktree_claimed`"). The live-claim check must be evaluated before or independent of the memory-headroom branch so both claim sources (live registry and durable queued row) are always checked prior to queuing.

3. **`settleDelayMs` must not be silently discarded when `minFreeGb` is absent.** `validateMachineConfigMemory` parses and validates `settleDelayMs` up front, but if `minFreeGb` is missing it returns `undefined` for the whole result, discarding an explicitly configured `settleDelayMs`. Callers then silently fall back to the hardcoded default even though the user set a value. This is a least-surprise/config-correctness defect: a validated, explicit setting should never be dropped without at least being honored or the loader documenting that it's ignored in that combination. Fix by returning the validated `settleDelayMs` alongside `minFreeGb: undefined` (adjusting the return type and its consumers accordingly), or by treating an explicit `settleDelayMs` without `minFreeGb` as intentional and surfacing it consistently — pick one and make behavior match it, rather than leaving the value silently lost.
