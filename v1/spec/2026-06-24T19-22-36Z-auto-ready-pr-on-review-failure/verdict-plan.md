## Verdict

The spec's direction holds — auto-ready on a gate-green, review-incomplete tree is sound and matches the intent. But several decisions over-claim or rest on untested cruxes. Required refinements:

1. **Resolve the contradiction between "don't re-run quality work" and "ready-failure is a non-fatal warning."** The chosen auto-ready mechanism (`maybeMarkReady` / ready-gate tier selection) only readies without re-running when the tree is *unchanged* since the recorded green sha. Review routinely commits fix-ups, so the review-incomplete tree is typically *ahead* of that sha → the gate re-runs. The spec currently asserts both "must not require re-running quality work" and "ready failure leaves the PR draft," which cannot both hold on a review-moved tree. Reword so the precedence is explicit: an unchanged tree readies directly; a review-moved tree re-runs the gate and, on red, leaves the PR draft with a warning. Do **not** adopt a gate-bypass that readies on a stale green record — readying a PR whose live tree is unverified-red is a worse outcome than a draft, and contradicts the intent's "readied on the strength of the green gate."

2. **Add the missing acceptance criterion for the review-moved tree.** This is the crux case the whole spec turns on, yet no AC exercises it. Add coverage: review commits fix-ups, then fails → on the resulting tree, green readies the PR; red emits a warning and leaves it draft. Per spec guidance, behavior-preserving paths should cite the pinning behavior rather than paraphrase.

3. **Drop the git-disabled decision and its AC.** The review phase only runs when git is enabled, so a review exit `11` cannot occur with git disabled — that path is unreachable and tests dead code. Keep the no-PR variant, which *is* reachable (the ready step throws when no PR exists for the branch).

4. **Split the two cited review-failure tests rather than treating them as equivalent.** The quota → review-incomplete (gate-green) case fits the new behavior cleanly. The review-commit-*push*-failure case is a different state (commits exist locally but not on the remote PR); auto-readying there may re-attempt the push, re-hit the failure, or ready a branch whose remote is stale. Reason about each separately and confirm the push-failure run is one auto-ready should even attempt.

5. **Replace line-number anchors with symbolic references** (function/symbol/test names). The cited lines have already drifted (the review-incomplete early `return` is not at the cited `:550`), and the repo convention is to cite symbols, not lines.

Non-blocking / optional: the "already ready → no throw" claim is substantiated by the existing idempotent `gh pr ready` handling (already-ready/not-a-draft stderr resolves as success), and the "blocker `7` / interrupt `130` still leave draft" claim is correct because those codes are *returned* by review exit mapping, not thrown — so they bypass the auto-ready path by construction. Both are fine as-is; a one-line spec note ("returned, not thrown") and a cheap assertion on the corrected operator message would add clarity but are not required.

**Rationale:** The defects are concentrated in over-claimed prose (Decision 1), a dead path (git-disabled), and one untested crux (the review-moved tree) — not in the spec's scope or direction. Resolving the precedence and adding the moved-tree AC make the spec's central behavior verifiable instead of asserted; dropping the dead path and splitting the test reasoning prevent the implementation from chasing unreachable or conflated states.
