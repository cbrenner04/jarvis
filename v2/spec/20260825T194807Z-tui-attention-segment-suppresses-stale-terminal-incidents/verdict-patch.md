## Verdict — required outcomes

**1. The projection's own contract documentation must match the two numbers this spec changed.**
`AttentionProjection.total` is now the *post-recency-filter, pre-cap* surfaced count, and `overflow` is now the count of dropped **failure** rows only (gates are never dropped). The doc comments on those two fields still describe pre-change semantics ("Total actionable incidents before the cap", "Rows dropped by the cap"), which is precisely the contract subspec 00 and 01 rewrote. Same for `monitorLeftPaneAttentionRows`' jsdoc ("heading, up to six capped rows") and the `monitorSelectableNodeIds` parenthetical ("projection.rows is already capped") — after 01 only the failure suffix is capped; the surrounding claim (overflow is never selectable) is still true, the justification is not. Outcome: every comment in `v2/src/tui/tui-attention-rows.ts` and `v2/src/tui/tui-monitor-lines.ts` that states cap/total/overflow semantics reads correctly for gates-uncapped, failures-capped, post-recency-filter behavior. This is the one place a reader learns the contract, and it currently misstates it.

Do **not** rename `ATTENTION_ROW_CAP` — ratified acceptance-criterion mutation directives quote it literally, and renaming churns spec text for cosmetic gain.

**2. `v2/src/tui/tui-entry.test.tsx` attention fixtures must sit inside the recency window, not past it.**
`TERMINAL_LIST_FINISH_MS = 9_000_000_000_000` against the entry frame clock `WORKFLOW_FILTER_NOW_MS = 1_700_000_000_000`, and the rebased stage `endedAt` values (`1_700_000_00X_000`) are likewise ahead of that clock. Those rows therefore survive the filter only through the deliberate "future-dated incident from clock skew still surfaces" escape hatch, not through the window. Subspec 00's acceptance criterion asserts these suites stay green with *within-window* behavior unchanged; as written they never exercise the window at all, so a future regression in the window comparison would leave them green. Outcome: attention fixtures in that file are dated relative to the frame clock as recent-past incidents, and the suite still passes.

**3. Pin that a suppressed-everything state reserves no left-pane height by comparison, not by a hardcoded constant.**
The new assertion in `v2/src/tui/tui-monitor-lines.test.ts` hardcodes `smallLayout.paneHeight - 1` where its own comment promises "matches the zero-incident case exactly." Outcome: assert against the tree-row count of an equivalent zero-incident state so the pin cannot drift from what it claims.

**4. Add a pin for a gate set alone exceeding pane height.**
01's ledger explicitly accepts that an uncapped gate group can shrink the tree viewport to its zero floor and let Ink clip the segment prefix. That accepted consequence is currently only covered indirectly by the pre-existing never-negative budget test. Outcome: a test shows that with more gates than the pane can hold, the tree budget floors at zero (never negative) and every gate stays in the selectable set. Low cost, and it pins the one behavior the split cap newly makes reachable.

## Explicitly not required

- **Aging out or capping `rejected-gate` rows.** A decided rejected gate has no in-segment action and is now exempt from both the recency window and the cap, so it is the one incident kind whose bound got looser. That is a genuine design concern, but the intent and both subspec ledgers ratify it verbatim ("awaiting **or rejected** gates are surfaced regardless of age"; gate rows exempt from the cap), and an acceptance criterion pins it. Do not change it here — it belongs in a follow-up intent.
- **Gate ordering placing rejected gates ahead of the current awaiting gate**, and undated awaiting gates sorting after dated gates. Both are ledger-directed or retained pre-existing behavior; selectability — 01's actual guarantee — now holds unconditionally.
- **A selection-repair path for an incident that ages out under a live selection.** The refresh loop already drops `selectedNodeId` when it is absent from the selectable set computed at the refresh tick's clock, and null selection restarts navigation at the list ends. That check is clock-driven, so a window crossing repairs identically to a resolved incident; the inert window is at most one refresh interval.
- **Unifying the keystroke-time clock with the painted-frame clock.** The render path already holds one clock per frame, which is the invariant the ledger names. The residual skew can only ignore one keypress on a row that just went stale, and self-heals on the next refresh.
