# 00 - Resume one failed pipeline branch

## Problem

`resumePipeline` gates every admission on `derivePipelineState`, which aggregates fan-out branches. A pipeline with one failed branch and one sibling at an awaiting gate derives `awaiting-approval`, so resume claims ownership and returns without reopening or dispatching the failed branch — the branch-scoped `reopenFailedPipeline` scope landed in the state store has no orchestration caller.

## Decision ledger

- Branch scope arrives as optional `branchKey` on `resumePipeline`'s existing `options` argument; the `pipeline_resume` RPC and CLI keep their current parameters this slice. Rules out a second exported resume entry point and premature wire plumbing.
- Deferred to first consumer: how an operator names the branch over IPC/CLI. Pinned now so a later slice doesn't re-litigate it: the eventual `pipeline_resume` wire parameter is spelled `branchKey`, matching this slice's option name.
- `branchKey: "default"` aliases omission exactly, matching `reopenFailedPipeline`. Rules out treating `"default"` as a named branch, which would refuse on every fan-out pipeline whose pre-split rows are `default`-keyed. A downstream input literally named `default` therefore produces a permanently unaddressable branch key via branch-scoped resume (it always resolves to the unscoped path) — accepted as a pre-existing collision inherited from `reopenFailedPipeline`'s own aliasing, out of scope to rename or namespace this slice.
- A named `branchKey` skips aggregate `derivePipelineState` admission entirely, not only the reported `awaiting-approval` shape — running, rejected, deferred, and terminal aggregate outcomes never gate branch admission either. Refusing on a busy or rejected sibling would reinstate exactly the sibling veto this intent rules out, and concurrent per-branch continuation is already the established shape on the approval path. This is safe: a named branch that is itself live has no `failed` row, so branch admission refuses `branch_not_resumable` before any reopen regardless of aggregate state — liveness on the named branch is caught by branch admission itself, not by the aggregate check it bypasses.
- Branch admission derives its boundary the way `reopenFailedPipeline` does — the lowest position carrying both a default row and a `branchKey`-named row — rather than `findFanOutSplit`'s succeeded-split position, so admission and reopen agree on one boundary. Precondition: from that boundary through the branch's terminal row, every scanned position carries a `branchKey`-named row; production fan-out satisfies this by construction (a branch row at every post-split position, gate included). A scan position lacking the branch's row (half-applied admission) is indistinguishable from the branch never existing and refuses `branch_not_found` the same way — durable rows, not `findFanOutSplit`-derived branch-key enumeration, are the source of truth for "does this branch exist."
- Within that boundary, admission scans in order: absent branch, then a reachable undecided or rejected approval gate at or before the branch's failed row, then absence of a `failed` row. Rules out selecting an arbitrary failed sibling and rules out reopening past the branch's own gate.
- Branch-scoped refusals, each carrying `branchKey`: `branch_not_found` (unknown key; also covers an empty/whitespace key, a pipeline with no fan-out split, and a scan-boundary gap — none can match a durable row, so all reuse this reason rather than adding validation-only codes), `branch_awaiting_approval` (also carries the blocking gate's `stageId`), `branch_rejected` (a rejected gate on the named branch; also carries the gate's `stageId`), `branch_not_resumable` (no replayable `failed` row; also carries the branch's current stage status, e.g. `running`, so a live branch reads distinctly from one that never failed). Propagated `reopenFailedPipeline` reasons carry `branchKey` too. Rules out reusing `pipeline_not_resumable`, which cannot tell an operator which branch refused or why.
- An admitted branch calls `reopenFailedPipeline({ pipelineId, branchKey })` then `continuePipeline(pipelineId, deps, branchKey)` through the existing post-admission closure, so `detachContinuation` behaves identically. `branchKey` scopes which branch's suffix continuation dispatches — continuation still walks the shared default prefix from the start and still performs terminal-publication settlement exactly as unscoped continuation does; settlement on a branch-resumed pipeline is not pinned by a new test this slice, it inherits existing unscoped continuation-settlement coverage. Rules out unscoped reopen followed by scoped continuation, which refuses `multiple_failed_stages` whenever a sibling branch also failed, and rules out reading this as a fully branch-isolated continuation pass.
- A branch already reopened but not yet continued (no `failed` row, reachable `pending` successor) refuses `branch_not_resumable`. This window is inherited from the unscoped path — reopen precedes the continuation claim there too, so an in-process continuation refusal after a successful reopen can strand a branch this way; branch-scoped rescue of that stranded shape is out of slice (today's `resumeReopenedPendingContinuation` rescue does not fire on fan-out shapes either). Rules out porting that rescue to branch scope this slice.
- Refusal payloads carry `branchKey`; the success payload does not gain one this slice, since the caller already supplied it and the unscoped success shape stays unchanged. Rules out widening the success contract speculatively.
- Durable documentation lands in `v2/docs/daemon-host.md` § Pipeline stage-scoped resume, not the intent's `v2/docs/workflow-runner.md`; that file's Resume contract covers workflow-runner steps and never describes pipeline resume. Rules out splitting one behavior's contract across two homes.

## Task checklist

- Add optional `branchKey` to `resumePipeline`'s options in `v2/src/daemon/pipeline-execution.ts`, aliasing `"default"` to omission on one stable binding line, and route a named scope past aggregate derived-state admission entirely (running, rejected, deferred, and terminal outcomes included).
- Add branch admission that derives its boundary the way `reopenFailedPipeline` does (lowest position with both a default and a `branchKey` row) and resolves the named branch's suffix rows, refusing absent branches (including empty/whitespace keys, no-split pipelines, and boundary gaps), the branch's own reachable undecided or rejected gate, and branches without a replayable `failed` row, each before any reopen or dispatch.
- Extend the resume refusal type with `branch_not_found`, `branch_awaiting_approval`, `branch_rejected`, `branch_not_resumable`, their `branchKey`/`stageId`/status detail, leaving unscoped refusal payloads unchanged.
- Dispatch an admitted branch through `reopenFailedPipeline({ pipelineId, branchKey })` and `continuePipeline(pipelineId, deps, branchKey)` via the existing post-admission closure.
- Author a production-shaped fan-out fixture (branch rows, gate included, at every post-split position) and add branch-scoped reopen/dispatch, refusal (unknown key, empty/whitespace key, no-split pipeline, own awaiting gate, own rejected gate, no replayable failure, running siblings, rejected siblings), and `default`-alias coverage in `v2/src/daemon/pipeline-execution.test.ts`; the existing two-stage `setupFanOutAlphaLiveLinked` helper leaves its gate default-keyed and pending and cannot express these cases, so do not reuse it for this scenario.
- Add in-body `// @mutate` directives on stable, unique production lines for the keystone and every added branch-routing, branch-selection, and refusal guard (including the rejected-gate guard).
- Update the durable daemon-host resume contract, including the corrected § Pipeline approval decisions claim, and the v1-behaviors catalog, including correcting the stale sole-entry-point/fixed-refusal-set bullet.

## Implementer notes

- Bind the resolved scope once as a unique line (for example `const branchScope = options.branchKey === DEFAULT_PIPELINE_STAGE_BRANCH_KEY ? undefined : options.branchKey;`) and use it for routing, reopen, and continuation so the keystone directive is stable.
- Reuse `findFanOutSplit` only to detect a pipeline with no fan-out split (refuse `branch_not_found`); derive the branch's admission boundary the same way `reopenFailedPipeline` derives its reopen boundary, and reuse `suffixStagesForBranch`, `branchSuffixPredecessorsSatisfied`, and `isAuthoredStageSatisfied` for branch admission rather than adding parallel walkers.
- Author a production-shaped fan-out fixture — branch rows, including the gate, at every post-split position — for these tests; the existing `setupFanOutAlphaLiveLinked` two-stage helper leaves its gate row default-keyed and pending and cannot express a branch-keyed awaiting or rejected gate, so do not reuse it for this scenario. `FAN_OUT_PIPELINE_DEFINITION` and `instrumentDispatchLog` remain fine as a base to extend. Keep mutation directives on real production guards and add no test-only inversion hooks.
