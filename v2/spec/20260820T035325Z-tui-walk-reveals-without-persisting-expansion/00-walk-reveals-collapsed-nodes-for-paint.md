# Walk reveals collapsed nodes for paint

## Problem

`selectNextRun` in `v2/src/tui/tui-entry.tsx` adds the selected collapsed pipeline/stage/branch id to `expandedPipelineNodeIds` so ↓/`j` can descend into it. That write survives the walk: an operator scrolling past collapsed work expands every node walked through and explodes the tree. Navigation must not carry that side effect — reveal-for-paint already exists in `buildMonitorPipelineTree`'s effective-expansion union of `expandedPipelineNodeIds` and `resolveSelectedAncestors`.

## Decisions

- `selectNextRun` computes a local `revealState` — a distinct binding, not `provisionalState` (already used by the neighboring `revealSelectedAttentionTarget`) — that adds the selected expandable node to `expandedPipelineNodeIds`, and feeds it to `monitorSelectableNodeIds` only to recompute the selectable-id list. `revealState` is never passed to `setState` or `setSelection`.
- Invariant: every `setState` call remaining in `selectNextRun` commits the untouched committed `state` (the local binding is never reassigned), mirroring `selectPreviousRun`'s `setState(currentState)` in its no-selection-match branch. This closes both existing `setState` sites in the function — the removed expand-branch commit and the `selectedIndex < 0` / `activeId !== null` branch — so neither can ship the persist-on-walk bug.
- Ancestors of the new selection paint only through `resolveSelectedAncestors` — rules out a second transient expanded-id store beside the durable one.
- The explicit `setState({ ...state, steeringFeedback: null })` the old expand branch performed is dropped, not replaced. Every reachable path that actually changes `selectedNodeId` goes through `setSelection`, which unconditionally clears `steeringFeedback`; the two paths that don't call `setSelection` (`ids.length === 0` return, and the exhausted-walk `next === activeId` no-op) change nothing, so neither owes a clear. The `selectedIndex < 0`/`activeId !== null` branch's `setState(state)` also changes nothing (state is untouched), so it owes no clear either.
- `e` and the dock `expand`/`collapse` verbs stay the only writers of `expandedPipelineNodeIds`; a node they expand must stay expanded through and past a walk over it.
- `selectPreviousRun` keeps deriving ids from the committed state (unchanged). Because reveal-for-paint tracks the current selection's ancestors, not `expandedPipelineNodeIds`, ↑ only re-reveals a subtree while selection sits inside it: the first ↑ step out of a walk-revealed node retraces exactly (its parent is still ancestor-revealed), but the next ↑ step — once the selection itself is a top-level, non-descended-into node — sees no revealed descendants and moves through top-level rows only. ↓ and ↑ stop being exact inverses across more than one subtree boundary — rules out mirroring the provisional rule into ↑ (out of scope) and rules out keeping the walk-time expansion write to preserve the old retrace symmetry. One existing walk test encodes the old full-symmetry invariant and must be retitled and rewritten to this shape; a second, single-subtree walk test stays symmetric as-is because it never leaves the one subtree it descends into.
