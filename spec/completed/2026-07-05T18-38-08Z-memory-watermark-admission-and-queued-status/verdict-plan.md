## Verdict

Six refinements required, all confirmed against current code.

1. **Extend the count-guard removal to `resume` and `revise`.** `resumeHandler` and `reviseAwaitingHuman` both currently hard-reject with `run_in_progress` on `activeRuns.size > 0`, the same guard subspec 01 removes only from `start`. Left alone, these two paths still contradict the new "more than one run can be in flight" premise. Subspec 01 must scope the guard removal to all three call sites (their live-run's own ownership stays protected via the existing worktree-claim check, so removing the count guard is safe there for the same reason it's safe in `start`).

2. **Make the "queued run exclusively claims its key" decision actually true.** Ownership claiming currently only happens inside the spawn path, which a queued (non-spawning) `start` never reaches. Subspec 01 asserts queued runs hold their `(project, branch)` claim, but nothing establishes that claim at queue time. The spec must specify how a queued run's key is protected against a conflicting concurrent `start` — either by claiming/releasing the registry entry across the queued lifetime, or by replacing the "exclusively claims" language with an explicit query-based conflict check against durable queued rows. Pick one and state it as a decision.

3. **Correct the promotion hook-site description for `paused`.** The pause transition is recorded in the write-loop execution path, not in the daemon file the current decision text implies. Subspec 02's decision/task text must accurately name where each promotion-triggering transition (terminal outcomes vs. pause) is actually recorded, so the task checklist targets the right call sites.

4. **Anchor promotion to run-exit cleanup, not scattered `setRunStatus` calls.** The spec should specify promotion is triggered from the single place where a run's resources (active-run tracking and ownership claim) are actually released on every exit path (success, failure, kill, abort) rather than fanning promotion checks across multiple status-setting call sites. This is a more reliable and minimal integration point and should replace the current "wherever setRunStatus records terminal/paused" framing.

5. **Scope the task checklist to cover the persistence-layer change queued rows require.** The run-creation insert path currently hardcodes the `in-progress` status rather than accepting it as a parameter. Subspec 01's task checklist must explicitly include modifying (or adding an alternate path to) run creation so a `queued` status can be persisted, rather than assuming the existing creation signature already supports arbitrary status values.

6. **Close the idle-queue promotion gap.** As scoped, a queued run has no promotion path when no other run is live to trigger an exit-based check (exactly the scenario the queued state exists for: a `start` that queues when memory is briefly tight and nothing else is running). The spec must address this without violating the no-polling constraint — e.g., by re-checking headroom immediately at the moment of queuing (in case memory already recovered) and/or by explicitly stating the accepted scope boundary for idle-queue promotion latency. This must be resolved as an explicit decision, not left implicit.

Rationale: findings 1, 2, and 6 are correctness gaps that make the spec's own stated decisions untrue or unreachable in practice (contradicts the intent's "queued runs are admitted in order" once other runs can coexist, and the explicit ownership-claim decision). Findings 3–5 are factual/scope corrections needed so the task checklist and acceptance criteria target real code paths, per spec guidance's requirement that decisions and checklists be accurate and implementable.
