# 00 - Dedupe merged pipeline snapshots by pipelineId

## Problem

`mergePipelineSnapshots` (`v2/src/tui/tui-monitor-lines.ts:469`) concatenates every discovered socket's `pipelines` array with no dedup. During the transient two-daemon window (old daemon draining, new daemon admitting, same run store) both sockets return the same pipelines, so each pipeline paints twice under the *same* tree-node id, including stage/branch node ids (`${pipelineId}:${stageId}:${branchKey}`, `tui-monitor-pipeline-tree.ts:104`): 21 pipelines rendered as 42 rows on 2026-08-10, and the duplicated ids in `monitorSelectableNodeIds` trapped `j`/`k` on the top pair. `mergeRunLists` (`v2/src/daemon/merge-run-lists.ts`) already dedupes runs by `runId`; snapshot merging must mirror that.

Two downstream per-id dedups already sit on top of the current concatenation and both go stale once merge-level dedup lands: `pipelineObservationBuckets` (`:275-291`) collapses to one bucket per `pipelineId` via `awaitingGate > running > failed > done` precedence, and `canonicalPipelineSnapshots` (`tui-attention-rows.ts:60-73`) does first-snapshot-per-id-wins. Both must be retired in favor of the merge-level winner, not left as dead redundant passes.

`pipelineSnapshotsBySocketPath` is spread forward every refresh tick and never evicted (`tui-entry.tsx:623-624,652-654`), so a socket that disappears keeps its last-good snapshot in state indefinitely. Left alone, a "finished beats unfinished" collision rule would let a vanished, draining daemon's last-observed terminal snapshot outrank a still-live daemon's running one — worse than the duplicate-row bug being fixed. This must be closed by eviction (below), not by the collision rule alone.

## Decisions

- Dedupe inside `mergePipelineSnapshots`; the tree builder and `monitorSelectableNodeIds` consume the deduped list unchanged — rules out patching duplication downstream in tree/selection code.
- Key is `pipelineId`, one snapshot per id — rules out concatenation that double-counts a pipeline served by two sockets.
- Before merging, `tui-entry.tsx`'s refresh loop evicts any retained `pipelineSnapshotsBySocketPath` key whose socket path is no longer in the live `clients` map (post-`updateConnections()`) before spreading the prior tick's snapshots forward, so a socket that disappears drops out of every future merge instead of lingering with a stale terminal snapshot. Same-tick RPC failure for a still-connected socket keeps retaining its last-good snapshot (`tui-entry.tsx:652-654`, unchanged) — only full disconnection evicts. Considered mirroring `mergeRunLists`' per-row `isLive` precedence (`merge-run-lists.ts:15`) directly inside the collision rule instead; ruled out because `mergePipelineSnapshots` only receives the socket-keyed snapshot record, and giving it per-snapshot liveness would mean threading a new parameter/state field through every consumer and test fixture for the same guarantee eviction already gives at the one place liveness is known.
- Collision winner among the (now always-live) candidates for one id, in order: finished (`finishedAtMs !== null`) beats unfinished; then greater count of stages with non-null `endedAt`; then earlier sorted socket path. This is a total order, so the fold is order-independent for three or more colliding snapshots; two snapshots that are both finished (differing `finishedAtMs`) fall through the same `endedAt`-count/socket-path tiebreak with no special case. Rules out first-encounter-wins, which is stale and nondeterministic while two daemons momentarily disagree.
- `endedAt` is the stage-terminal marker already read by `pipelineStageRollupRow`/`stageDetailRows` — rules out inventing a separate progress field.
- Emission order is sorted socket-path iteration, each id at its first-appearance position even when a later socket's snapshot wins — rules out a reorder that churns unrelated row-ordering tests.
- Implement as a positional `merged: PipelineSnapshot[]` array plus `indexByPipelineId: Map<string, number>`, not a `Map<string, PipelineSnapshot>` values-map, so the never-seen-pipelineId guard is one line (`if (existingIndex === undefined) { ... push ... }`); a single-line revert of that guard to always-push reproduces literal pre-fix concatenation and is this subspec's keystone anchor.
- The merge-level winner becomes the single canonical per-id rule for every consumer. `pipelineObservationBuckets` classifies each already-unique merged snapshot directly into its bucket and counts — no candidate/current bucket-precedence comparison. `canonicalPipelineSnapshots` in `tui-attention-rows.ts` is deleted; `buildAttentionRows` calls `mergePipelineSnapshots` directly. This changes dock-count and attention-row output for a colliding pipeline id versus today's bucket-precedence behavior (see task checklist for the retired/replacement tests).
- Owner/display skew from `buildPipelineOwners` (`tui-entry.tsx:341-353`, first-wins in sorted socket order, independent of which snapshot renders) predates this change and both daemons sit over the same run store — unchanged, out of scope.
