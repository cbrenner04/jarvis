## Bugs found this session

### 1. `run resume` on a killed or failed run can never work — seeded, #1553

`resumeHandler` (`v2/src/daemon/daemon.ts:969`) builds the write-loop input as `bindings: []`, `stepRules: ""`, `expectedArtifactPath: ""`, with a comment conceding the reconstruction was never written. Every such resume dies `no_binding` in **32 ms** with zero agent invocations — while the RPC answers `{ok: true}`, the CLI prints `resumed <id>`, and `run list` advertises the row as `resumable` with remediation **`fix_config`**, pointing at a config that is fine. Observed live on two runs.

`resumePausedRun`, ninety lines above, already reconstructs bindings correctly from the `WorkflowSnapshot` — which exists for exactly this purpose.

### 2. A daemon restart kills every in-flight run — seeded, #1553

And the harness *requires* a restart after merging any v2 change (stale code snapshot). So landing a v2 fix destroys concurrent work. Observed: a merge-triggered bounce reconciled two implement runs to `killed`/`daemon_restart` mid-write-step; their agent work was left uncommitted and its tokens lost. Composes with (1): the prescribed recovery is resume, and resume cannot work.

### 3. A second RPC on one IPC client always failed — fixed in #1558, seeded #1561

`request()` created an `RpcTransport` per call and closed it in `finally`. `RpcTransport.close()` calls `client.close()`, which is `socket.destroy()`. **Every RPC destroyed the connection it was handed.** Invisible while every CLI path issued exactly one RPC per `withRunClient` — which was true of every path, until `run workflow` began chaining `start` → `wait`. Against a real daemon it would have printed the run id and then died `IPC connection lost`, exit 1, **on every invocation**.

The 16 red `cli.test.ts` tests were correct, and I very nearly dismissed them as stale fixtures. The seed is for the coverage hole: nothing asserts that two sequential RPCs on one client both succeed.

### 4. v1 and v2 read agent order from different config keys — seeded, #1557

v1 uses `modes.<mode>.agentOrder`; **v2 uses the flat top-level `agents` array** (`v2/src/cli.ts:236` → `loadMachineConfig`). Moving codex to the front of every `modes.*.agentOrder` — the documented lever — changed v1 and **nothing about v2**. Four subsequent v2 runs still invoked claude. I first misdiagnosed this as daemon config staleness; it is not. v2 resolves the order CLI-side, immediately and correctly, from a key nobody thinks to edit.

### 5. The spec path is never validated in the worktree that consumes it — seeded, #1557

`--spec` resolves against the operator's cwd, and that repo-relative path is re-resolved inside the run's own worktree. A cwd inside another git worktree produced a path that **passed preflight** (it really exists from the project root) and then failed `harness_failure` at the routing read — after a full agent write step. Cost: **7m52s and the tokens**, for a bad argument.

### 6. `lint:md` lints one file in all of v2 — seeded, #1553

`.markdownlint-cli2.jsonc` globs `v2/docs/onboarding.md` and nothing else under v2. All of `v2/docs/**` and `v2/spec/**` is unlinted — so the now-full-tier v2 ready gate (#1539) runs `lint:md` over a surface it does not cover. Every v2 workflow artifact lands in that blind spot.

### 7. Codex records no cost and no usage, silently — seeded here

All 11 codex invocations: `cost_usd: null`, `cost_source: "unavailable"`, every usage field null, and **`warnings: null`**. `shared/invocation/agents.ts` has three explicit "codex usage unavailable" warnings for the known failure modes and **none of them fired** — so the scrape is producing `unavailable` on a path with no diagnostic at all. The cost sheet reads **$12.73 claude / $0.00 codex**, which makes codex look free. It is not. This matters now: codex is being trialled as an implement primary, and a codex-primary session cannot be costed at all.

### Seed correction

`workflow-output-ignores-the-seeds-target-dir` claimed `grep -rn "target-dir" v2/src` returned no hits and that v2 has no such flag. **False** — it is fully wired for `intent`/`plan` and their reviewed variants (`v2/src/cli.ts:87–94, 865, 919, 895/903/949`). The misrouted artifacts came from the operator not passing the flag. The seed's decision still holds (the *default* must derive from the input path), but a planner reading it would have re-implemented an existing flag. Corrected in #1553.

### Runbook correction — #1559

The v2 runbook said *"`blocked` is inspect-and-resume, not terminal"* and told operators to resume. `run resume` refuses a blocked run outright, and `run list` already reports it `resumable: false` / `inspect_spec`. The harness was right; the doc was wrong. Also documented the daemon-restart trap, the agent-order key divergence, and the `--spec` cwd trap.

### 8. An acceptance criterion the agent cannot satisfy strands the run — seeded here

I launched `ready-gate-fails-on-any-red-test-file` as the **live end-to-end verification of #1560**. It never reached the gate. The agent did the work, ticked 4 of 5 criteria, wrote real tests — and then honestly blocked on the fifth:

```md
- [ ] The reproduction … is captured in the PR body: the tree/edit used, `bun run ready` output, …
```

The agent cannot write a PR body. **The harness owns publication.** The criterion is unsatisfiable by construction, so the run could only ever end `blocked`. Its own blocker says so: *"PR-body reproduction evidence remains to be added; GitHub API access failed in this session."*

This is the mirror of `acceptance-criteria-require-a-failing-test` (#1546, shipped): that one made criteria *demand evidence*; this is criteria demanding evidence the agent **cannot produce**. The plan preset wrote this spec earlier in the same session, so the two must be fixed coherently or plan agents will keep trading one failure for the other.
