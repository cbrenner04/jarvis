## Verdict — two required fixes

Both issues are narrow, isolated, and follow directly from the spec's own stated principles. Neither requires touching the predicate, migration, or test logic.

1. **Liveness probe must not treat "signal blocked" as "process dead."** The pid-liveness check (`state-store.ts` ~L288-292) collapses every `process.kill(pid, 0)` failure — including `EPERM`, which means the pid *exists* but the probe lacks permission to signal it — into "dead." The spec explicitly requires the opposite bias when a check can't be answered cleanly: the epoch-unreadable case is defined to fail toward "alive" because "failing to reconcile a dead process's run is recoverable; killing a live one is not." The same reasoning applies here. **Required outcome:** the liveness check must distinguish "no such process" (`ESRCH`, or equivalent confirmation the pid doesn't exist) from any other probe failure, and treat any non-confirmed-dead result as alive, consistent with the epoch-unreadable rule already in the spec.

2. **Module-init identity capture must not be able to hang indefinitely.** `CURRENT_OWNER_IDENTITY` is computed via an untimed top-level `await` that shells out to `ps` at module load, and the subprocess helper it uses has no timeout support. This is a new failure mode introduced by this change's own design choice (capturing identity once at module init): a hung or missing `ps` now blocks module load for every consumer of `state-store.ts`, including the non-daemon owners (`jarvis write`, workflow runner) the spec itself calls out. **Required outcome:** the `ps` probe used to compute the current process's owner identity must be bounded by a timeout, so a stalled or missing `ps` cannot indefinitely block state-store initialization.

No other concerns — predicate scoping (identity mismatch AND recorded-owner-not-alive), the transactional TOCTOU guard, the migration, and the reworked reconciliation tests are correct per the spec's decisions and acceptance criteria.
