# Verdict — Required Refinements

The advocate concedes the substance of the critique; the upheld findings below are correct against the code and must be resolved in refinement. The slice's green-path-only scope, in-process record, and tree-keyed-reuse boundary are sound and must be preserved — none of these refinements expand that boundary.

## Blockers (spec must resolve)

1. **Stop claiming reuse at the review final gate.** The review final gate runs after the debate cycles, which commit `review: actuator` and per-role changes whenever review does anything — so its tree is almost always advanced and it re-runs `ready` regardless. The spec currently lists this gate as a reuse beneficiary, overstating the saving. Refine the Behavior section and the affected acceptance criterion to state that the review final gate participates in the same tree check but in practice re-runs because its tree is advanced; reuse there applies only in the degenerate no-op-review case. Do not count it among the gates the slice eliminates on the common path.

2. **Pin the zero-implementation-iteration completion path.** When a run reaches completion with no implementation iterations (the checklist was already empty on entry), shrink and review are skipped and the lone `maybeMarkReady` runs standalone — there is no "tick that empties the checklist," and there is no redundancy to remove. The spec's completion-transition framing never names this path. State explicitly whether the completion gate runs there; the consistent answer is to bound it by the same "at least one implementation iteration" guard the other post-completion phases use, leaving that path unchanged. Add an acceptance criterion fixing this boundary alongside the existing `git: false` one.

3. **Name both `maybeMarkReady` call sites and pin the gate's order relative to each.** There are two: an in-iteration call on the completing iteration (guarded so it fires only when neither shrink nor review will run) and the one inside the completion routine. "Run `runReadyAndCommit` once at the completion transition … before shrink/review/`maybeMarkReady`" is ambiguous across these two sites and, on the path where the in-iteration call fires first, a gate placed later cannot dedupe it. The spec must identify both sites and specify how the completion gate and the recorded result coordinate with each so the in-iteration path also reuses rather than double-runs. This also resolves the objection that "(or its `git: true` completion path)" is an under-specified placement — that is internal placement the spec must pin now, not a legitimate first-consumer deferral.

4. **Key reuse on the post-`check:fix`-commit HEAD, and test the check:fix→shrink path.** The completion gate's `runReadyAndCommit` may create and push a `check:fix` commit, advancing HEAD before the worktree settles clean. If the recorded key is taken before that commit, the immediately-following shrink pre-gate sees a changed tree and re-runs, defeating the slice on the very path it targets. State that the green result is recorded after `runReadyAndCommit` returns and the worktree is clean, keyed on the resulting (post-commit) HEAD. Add an acceptance criterion: when the completion gate itself lands a `check:fix` commit, the next gate still reuses (tree unchanged since the post-commit record) rather than re-running.

5. **Make red catch-and-continue explicit and resolve the red-path double-run.** The completion routine has no `ready` call today; introducing one that may throw (red) and then "fall through to existing post-completion behavior" requires catching that throw and continuing — new control flow. The acceptance criterion "no behavior change on the red path" is imprecise: downstream gates are unchanged, but the completion gate's own red handling is new, and a red completion gate followed by a downstream red gate pays two red `ready` runs where today there is one. Refine to (a) state the red completion gate is caught, records nothing, and falls through, clarifying that "no behavior change" means downstream gates only; and (b) either eliminate the red-path regression (e.g. record the red verdict keyed to the same tree so a downstream gate reuses it and stays at one run) or explicitly acknowledge the doubled red run as a known consequence. Asserting unchanged red behavior while doubling the red run is not acceptable. Keep red loop-back semantics out of scope either way.

6. **Reconcile the "two-plus" baseline with the real common path and the default disagreement.** The first acceptance criterion ("down from two-plus") is not measurable as written: on the named common path with review configured, three gates run today (shrink pre-gate, review baseline, review final), and `maybeMarkReady` does not run on that path; the Problem section says "two full suite runs" while the Behavior section lists four gates. Compounding this, the configured default for review passes and the value documented in `v1/docs/run-loop.md` (and the figure in `v2/docs/v1-behaviors.md`) disagree. State the exact baseline for each named common path so the count is verifiable (given finding 1, the honest default-review saving removes the shrink pre-gate and review-baseline runs while the review-final run remains), and have the documentation updates correct the default-passes figure rather than inherit the inconsistency.
