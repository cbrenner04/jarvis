Required refinements to `00-render-and-filter-pipeline-list.md`:

1. **Existing default-JSON list tests are modified, not preserved.** `v2/src/commands/pipeline.test.ts` tests `live list returns within 500ms while reporting a non-terminal derived state` and `two-branch list stdout shows distinguishable branchKey values and per-branch statuses` (plus the "prints one minified JSON snapshot" / empty-array list tests) run bare `pipeline list` and `JSON.parse` stdout; they cannot stay green once the human default lands. Reword the "stays green" AC to state that the 500ms test is updated (pass `--json` or assert the human row) while preserving the single non-blocking `pipeline_list` request and the 500ms bound, and note that the other default-JSON list tests are rewritten to `--json` or human assertions. As written the AC strands the run.

2. **Pin the absent-`--since` cutoff value.** The filter mutation directive `"return pipeline.createdAt >= cutoff && (state === undefined || pipeline.state === state);"` presumes `cutoff` is always numeric. Add a Decision that an absent `--since` uses a numeric sentinel cutoff (e.g. `-Infinity`/`0`) so the directive target exists exactly once and is not hollowed by a `cutoff === undefined ||` implementation.

3. **Remove or concretize the unbounded `list guard inversions fail` criterion.** "Every added or modified guard not covered by the named checkpoints" is unenumerable and cannot be verified under the one-linked-directive-per-criterion contract (guidance: mutation-checkpoint criteria name a test title and a single `@mutate` directive). Either delete it (the named filter/JSON/incompatible-flags/empty-selection checkpoints plus keystone already satisfy guard-inversion guidance) or replace it with one or two concrete checkpoints, each with its own test title and explicit single-line `@mutate` string.

4. **Give the keystone a concrete, unique directive.** The keystone criterion currently describes the mutation in prose ("replaces the unique default human-render stdout statement with `JSON.stringify(snapshot)`"). `pipeline.ts` already contains `io.stdout(\`${JSON.stringify(snapshot)}\n\`)` on the JSON path, so the replacement can collide with the JSON branch, and if human rendering lives in a helper `snapshot` may be out of scope (compile error, not a red test). Specify a single-line `// @mutate v2/src/commands/pipeline.ts "<unique human-render stdout statement>" -> "<baseline JSON stdout>"` anchored on the human-render statement with `snapshot` in scope; keep the canonical `` `pinFile` — `pinTitle`; Keystone checkpoint: `` suffix.

5. **Light wording fixes.** (a) The parity AC should require adding a `["pipeline","list"]` entry to `PARITY_PATHS` and the corresponding parse-options constant in `v2/src/cli/help-flags-parity.ts`, since `parserAcceptedLongFlags` throws for unknown paths and parity is otherwise unverifiable. (b) Drop the claim that `--since` uses "the existing" `run list` grammar / that rows "match the existing `run list` row convention" as parity: `run list` also accepts numeric epochs and reports `invalid_since` on stderr, whereas this spec rules out epochs and routes all parse failures to `PIPELINE_LIST_USAGE` — state the decisions on their own terms. (c) Note that extra positionals moving from `PIPELINE_USAGE` to `PIPELINE_LIST_USAGE` is a deliberate change.
