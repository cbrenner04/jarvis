# Verdict — `2026-06-17T20-28-18Z-completion-ready-gate`

The spec's direction and slicing are sound and match the code: run `ready` once at the completion transition, record a green result keyed to tree state, and have the post-completion gates reuse it on an unchanged tree. The gaps are precision gaps in the load-bearing seam — where the recorded result lives, how it threads into three differently-typed gates, how the "exactly once" claim is counted, and how the reuse-skip preserves the existing clean-worktree guarantee. The following refinements are required.

## Required refinements

**R1 — Name the carrier for the recorded green result.** The three consumers (shrink pre-gate, review baseline, `maybeMarkReady`) are all invoked from inside the single completion-transition function, and each takes a distinct options shape. The spec must state where the recorded result is held and how it reaches each gate (e.g. an orchestrator-local value passed as a new field on each gate's options), and whether a gate that re-runs `ready` updates that value in place or returns a refreshed one. "Thread it into the three gates" is too vague for the spec's central seam. *Why: `01`'s reuse chain depends entirely on this carrier; leaving it as prose forces the implementer to invent the contract the spec exists to pin.*

**R2 — Disambiguate the two `maybeMarkReady` call sites and the completion gate's ordering relative to them.** There are two `maybeMarkReady` invocations: one in the completion-transition function (the review-skipped branch), and a separate per-iteration early-ready that fires when neither shrink nor review will run — and that per-iteration site executes *before* the completion gate is reached. The spec names "the review-skipped `maybeMarkReady`" without disambiguating these. It must state which invocation is in scope, where the new completion gate orders relative to the per-iteration site, and whether that per-iteration site is in scope, excluded, or must also consult the recorded result. *Why: silence here yields either a double `ready` run or a missed reuse on the zero-shrink/zero-review path — the exact redundancy the intent removes.*

**R3 — Pin the common-path baseline so "exactly once" is checkable.** Review and `maybeMarkReady` are mutually exclusive (`if/else if`), so *which* post-completion gates run depends on the resolved review-pass count. `01`'s criterion "`bun run ready` runs exactly once across the completion transition and all post-completion gates" is only well-defined once a configuration is fixed. The spec must pin the common-path baseline it is asserting against (which gates are reached under it) so the count is verifiable. *Why: an acceptance criterion that depends on unstated config is not independently testable, violating the atomic/testable subspec contract.*

**R4 — Resolve the "one ready per completed spec" contradiction with the always-on review final gate.** `01` correctly carves the review **final** gate (the `ready` immediately before the draft→ready flip) out of reuse — it stays unconditional. But the final gate is itself a post-completion gate that runs `ready`, so on the default review path the true count is two (completion gate + review final), not one. `01`'s "exactly once across all post-completion gates" criterion and its final-gate carve-out contradict each other. The spec must reword so the *reusable* gates collapse to one while the unconditional final gate is explicitly excluded from that accounting. *Why: an internally contradictory acceptance criterion cannot be satisfied as written.*

**R5 — Link the `maybeMarkReady` reuse-skip to the clean-worktree (exit-6) guarantee.** Today `maybeMarkReady` runs the ready-and-commit path — which re-checks porcelain, commits any `check:fix`, and throws if still dirty — *immediately before* `gh pr ready`; the documented exit-6 invariant ("worktree guaranteed clean before `gh pr ready`") rests on that re-check. Skipping it on reuse is safe only if the reuse predicate's clean-worktree half re-verifies cleanliness at that moment. The spec must state that the predicate's clean-worktree check is what upholds the pre-`gh pr ready` cleanliness guarantee in place of the skipped re-check, and must document this as a behavior change near the exit-6 description. *Why: dropping the re-check without naming what replaces the guarantee is an unstated weakening of an operator-facing invariant.*

**R6 — Make the reuse predicate's two-part composition a checkable criterion.** `00` defers the "unchanged tree" predicate to `01`; `01`'s prose defines it as HEAD-equality **and** clean worktree, but no acceptance criterion asserts both halves. A gate that reused on sha-equality alone would pass every listed criterion yet defeat the whole point of keying on tree state rather than a boolean. Add a criterion that pins the two-part predicate. *Why: the predicate's clean-worktree half is the safeguard against stale reuse; an untested half is an untested safeguard.*

**R7 — Add a criterion for `check:fix`-moves-HEAD chaining.** `01` covers a `shrink:` commit forcing a re-run but has no criterion for a `check:fix` commit (from the completion gate or any re-running gate) moving HEAD and forcing the *next* gate to re-run and refresh the recorded result. Since the entire rationale for keying on sha (rather than a boolean) is that `check:fix` mutates the tree, this is the more decision-relevant case and needs its own criterion. *Why: the spec's stated decision is only verified for the `shrink:` path, not the `check:fix` path it explicitly motivates.*

**R8 — Distinguish the no-op-shrink sub-cases in the counting criterion.** The shrink phase early-returns on an empty allowlist *before* its pre-gate, yet the orchestrator's "shrink runs" guard checks only that an implementation iteration occurred, not allowlist size. So "no-op shrink" conflates two paths: shrink agent ran with no diff (pre-gate executes, reuses) versus shrink bailed on empty allowlist (pre-gate never executes, contributes zero `ready` runs). The common-path counting criterion must say which it means, or the "exactly once" accounting is ambiguous. *Why: the reuse count differs between these paths; an ambiguous criterion cannot adjudicate either.*

**R9 — Own `00`-alone's transient extra `ready` run; do not claim net-neutral wall-clock for `00` in isolation.** After `00` lands alone, the completion gate runs `ready` and the still-unchanged shrink/review gates also run it — a temporary increase (not a reduction) in the exact wall-clock metric the intent targets, plus recorded state that nothing reads until `01`. The slicing is acceptable (the base slice is green and outcome-preserving), but the spec's "ships independently / additive" framing must acknowledge the transient extra run, or state that `00` and `01` are expected to land together. *Why: the project's deferral guidance treats state recorded ahead of its first consumer as a warning sign to answer head-on, not gloss; the spec should not imply `00` alone improves the metric it temporarily worsens.*

**R10 — State the documentation partition between `00` and `01`.** Both subspecs edit `v1/docs/run-loop.md` and `v2/docs/v1-behaviors.md` in overlapping regions (the completion/review/post-completion-shrink clusters). The documentation standard requires exactly one durable home per behavior with no duplication. The spec should state the split — `00` adds the new completion-gate behavior; `01` edits the shrink and review entries to record reuse — so two implementers do not both rewrite the same lines. *Why: without a stated partition, the two subspecs risk duplicating or clobbering each other's doc edits, violating the single-home rule.*

## Minor (fold in if cheap; not blocking)

**R11 — Note that capture happens after `runReadyAndCommit` returns and inside the completion-transition function.** `runReadyAndCommit` returns no value, so the recorded HEAD sha is read via a separate `git rev-parse` *after* the call (and after its internal `check:fix` commit). And the "at most once per run" property holds because the capture lives inside the completion-transition function (which early-returns when boxes remain), not in the per-iteration caller. `00` nearly pins both already ("after `spec complete`, before the phases"); one explicit line each removes residual ambiguity.

**R12 — One line on reuse/`skipGates` composition.** Each in-scope gate already has a test seam that bypasses its `ready` call; the reuse check must compose with that bypass (when a gate is skipped, the reuse decision is moot). A single sentence suffices — enumerating every seam is implementation detail the spec is right to omit.

Defining "tree changed" as HEAD-moved **or** dirty **or** no-result-recorded is the conservative, correctness-preserving definition of "is the recorded green still valid for this tree"; it is exercised behavior (reuse-validity), not invented precision. Keep it.
