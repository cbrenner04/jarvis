## Verdict

Several adversary findings are upheld. The spec's core remedy (`git: false` ⇒ force loop-only/no-commit, overriding `plan.commit`) is sound, but its narrative precision, coverage, and symbol accuracy need tightening before it is implementable. Required refinements:

1. **Correct the Problem narrative to match the evidence (upheld).** The intent's symptoms — a created `.worktree/plan-<name>`, a `plan/<name>` branch, a `git push` with no upstream, and a `git checkout -- spec/` revert — are all reachable only on the **commit-mode** path; the revert in particular fires only under `if (commit)`. The draft's Problem section instead pins the failure on `assertTargetRepoPlanBoundary` running `git status` (the commit===false path), which the runtime evidence contradicts. Rewrite the Problem so it states the observed path is commit-mode and that the load-bearing remedy — forcing `commit = false` once the project resolves to `git: false` — is what neutralizes the worktree/branch/push/revert. Keep skipping the `git status` target-repo boundary check as a secondary guard for the commit=false reading, but stop presenting it as the established mechanism. Phrase AC1–AC3 so they hold regardless of which `commit` value reproduction reveals (key them on "resolved to `git: false`," as most already do). *Rationale: a spec whose Problem section misidentifies the firing code path can mislead the implementer into a fix that addresses the wrong call site.*

2. **Cover the review-phase boundary call site (upheld — strongest finding).** The same `commit ? assertPlanWriteBoundary : assertTargetRepoPlanBoundary` structure, with its own revert and `git checkout`/`git clean` cleanup, exists in the review phase, not just the draft phase. A git-disabled run that survives draft and enters multi-pass review hits the identical false-positive and stray git calls. As scoped, the spec names only the draft call site, so an implementer editing one location ships a fix that regresses on review. Add a decision and an acceptance criterion ensuring the `git: false` ⇒ loop-only behavior holds across **both** the draft and the multi-pass review phases (e.g., an AC exercising a git-disabled run that enters review). *Rationale: atomic-but-complete — the subspec's contract is "plan honors `git: false`," and leaving one boundary call site unguarded violates that contract.*

3. **Pin the resume path to the same override (upheld).** Resume resolution chooses external-vs-worktree spec location from its own `commit` read, independent of the fresh-run resolution. The "reuse the commit===false path" decision implicitly assumes resume applies the same `effectiveGit` override but never states it; without it, `--resume` of a `git: false` spec mis-resolves. Add a decision that the `git: false` ⇒ `commit = false` override applies at resume resolution as well.

4. **Fix the `effectiveGit` argument (upheld).** The helper takes a project *key* (string), not a `Project` object — passing the object yields an undefined lookup that silently falls back to the global `git` value and masks the per-project `git: false`, defeating the fix. The decision text must call it with the project key. This is a harness spec where symbol precision is the contract; the implementer will copy the decision verbatim.

5. **Note the summary `spec:` path is out of scope (minor).** The `spec/<name>/index.md` summary line is the existing shape for *all* no-commit runs, not a `git: false`-specific symptom; changing it is broader behavior. Add a one-line out-of-scope note to preempt re-litigation. Not a required AC.

6. **Record the worktree-`.git` mechanism in the reproduce task (minor).** The report's root is a git worktree, where `.git` is a file, so an `existsSync(.git)` short-circuit does not catch it — which is why the gate must key on `effectiveGit`, not `.git` presence. Capturing this in the reproduce step documents why the fix gates where it does.

Not upheld: the claim that the cwd-scoped external-spec-dir check could itself false-positive — that check never invokes git, so it has no analogous failure mode; and the intent's phantom `cleanupNoCommitTempSpec` reference is an intent-level artifact the spec already redirected, with no spec-level residue beyond finding #2.
