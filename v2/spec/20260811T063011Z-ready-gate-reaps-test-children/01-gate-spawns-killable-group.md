# 01 - Gate and required-integration invocations spawn in a killable group bound to run termination

Module boundary: execution (`v2/src/execution/ready-finalize.ts`, `v2/src/execution/write-loop.ts`).

`createDefaultRunReadyGate` calls `runner.runAsync("bun", ["run", "ready"], worktreePath, { maxBuffer, env })` with no `signal` and no `processGroup`, and `createDefaultRunRequiredIntegration` passes even less. Terminating a run (kill, abandon, iteration timeout, or settlement after daemon loss) unwinds the harness while the gate's `bun test` tree keeps running — observed surviving for days and starving the machine. This subspec binds both invocations to the run's termination signal in process-group mode, and makes sure a kill mid-gate never enters agent repair. Recording the spawned group id on the run row is `02`.

## Decisions

- Call-time signature, not construction-time closures: `ReadyGate` (exported) and `RequiredIntegrationRunner` (module-private) both widen from `(worktreePath, x) => Promise<void>` to `(worktreePath, x, options?: { signal?: AbortSignal }) => Promise<void>`. `createDefaultRunReadyGate`/`createDefaultRunRequiredIntegration` read `options?.signal` and pass it straight through to `runner.runAsync(..., { signal, processGroup: {} })`. `ReadyFinalizeInput` gains `signal?: AbortSignal`, and the finalizer returned by `createReadyFinalizer` passes `input.signal` as the third argument to both invocations. This is bounded: it touches the two default-gate bodies, the two function types, and `ReadyFinalizeInput` — not every seam mock, since the added parameter is optional and existing mocks in `ready-finalize.test.ts` that ignore a third argument keep compiling.
- The run's existing termination `AbortSignal` is the binding, not a new controller. `WriteLoopInput = WriteExecuteInput & {...}` and `WriteExecuteInput.signal?: AbortSignal` (`v2/src/execution/write.ts`) is the signal the daemon's per-run `abortController` fires on kill/abandon. It is **not** reachable from `runReadyFinalizer` today: that function takes `seams: CompletionPublicationSeams`, a `Pick<WriteLoopInput, "completionPublisher" | "readyFinalizer" | "skipReadyFinalization">`. Widen the pick with `"signal"` (all-optional, so the object-literal caller in `v2/src/daemon/pipeline-stage-resolve.test.ts` and every `publishCompletionArtifacts(args, ...)` call that already passes a full `WriteLoopInput` keep compiling), and have `runReadyFinalizer` spread `seams.signal` into the `finalInput` it builds for `readyFinalizer(finalInput)`. No new field on `WriteLoopInput`.
- Group mode's `maxBuffer` is not honored: `shared/subprocess.ts`'s `runGroupMode` path buffers stdout/stderr unbounded regardless of `maxBuffer`, unlike the default `execFile` path. This subspec accepts unbounded output capture for both invocations rather than extending group mode with a cap — gate output volume is bounded in practice by the test suite's own output, and the shared runner's capture behavior is out of this subspec's module boundary. `maxBuffer` is dropped from both calls; the preservation criterion pins command, args, cwd, and `env`.
- Abort-vs-failure is distinguished in `publishWithReadyRepair`, not in the gate's catch. When the group is killed by the run signal the child closes on a signal, the runner rejects with `AsyncSubprocessError`, and the gate wraps it into `ReadyGateError` exactly as it does today — that stays: the outcome kind remains `ready_gate_failed`, which is accurate (the gate process did die). Rethrowing unwrapped instead would be worse: `buildFinalizationErrorResponse` maps any non-`ReadyGateError` to `ready_flip_failed`, misattributing a kill to the flip. What must not happen is repair: `publishWithReadyRepair` gains one guard immediately after `classifyReadyGatePublishFailure`, before `loadPersistedRepairAllowset`, the autofix `commitRepairAndRepublish`, and `runReadyGateRepairLoop`: `if (isActiveReadyGateFailure(outcome) && args.signal?.aborted) return buildReadyRepairPublishResult(outcome, iterationsConsumed)` — the same "not an active failure" return shape a timed-out gate takes, so no agent iteration is spent against a terminated worktree. Terminal status is unchanged by this subspec: the write-loop caller of `publishWithReadyRepair` already routes any returned failure through `if (args.signal?.aborted) return finishLoop(args, runId, "progress", publication.iterationsConsumed, true)`.
- Scope is the spawn options, the repair short-circuit, and the reap regression: test selection, `JARVIS_READY_TEST_SCOPE` derivation, gate error wrapping, and repair behavior for genuine (non-abort) failures are untouched.

## Task checklist

- [ ] Widen `ReadyGate` and `RequiredIntegrationRunner` with an optional third `{ signal?: AbortSignal }` parameter; widen `ReadyFinalizeInput` with `signal?: AbortSignal`; thread `input.signal` from the returned finalizer into both invocations.
- [ ] Pass `signal` and `processGroup: {}` in both `createDefaultRunReadyGate` and `createDefaultRunRequiredIntegration`, keeping command, args, cwd, and `env` unchanged; drop `maxBuffer` from both calls.
- [ ] Add `"signal"` to the `CompletionPublicationSeams` pick; spread `seams.signal` from `runReadyFinalizer` (`write-loop.ts`) into the `finalInput` passed to the finalizer.
- [ ] Add the `isActiveReadyGateFailure(outcome) && args.signal?.aborted` short-circuit in `publishWithReadyRepair` immediately after gate-failure classification, before the repair-allowset/autofix/repair-loop path.
- [ ] New integration regression `v2/src/execution/write-loop-ready-gate-reap.sandbox-unrunnable.test.ts`: drive a run to a gate that spawns a real, long-lived child process group, abort the run's signal, and assert the group is gone.
- [ ] Unit tests in `v2/src/execution/ready-finalize.test.ts` asserting the spawn options (`signal`, `processGroup`, no `maxBuffer`) for both invocations.
- [ ] Unit test in `v2/src/execution/write-loop.test.ts` asserting that an aborted signal short-circuits `publishWithReadyRepair` before any autofix or repair iteration runs.

## Acceptance criteria

- [ ] Terminating a run whose ready gate is mid-flight leaves no surviving test descendant: a new `v2/src/execution/write-loop-ready-gate-reap.sandbox-unrunnable.test.ts` drives a run to a gate spawning a real process group, aborts the run signal, and polls `process.kill(-pgid, 0)` until it throws `ESRCH` (bounded deadline, not a single immediate check, so the SIGTERM→SIGKILL escalation has room to complete) — it fails against the pre-fix code, where the group survives past the deadline. The fixture's child ignores SIGTERM (or sleeps past the grace window) so the assertion actually exercises the SIGKILL escalation rather than passing on a lucky SIGTERM exit.
- [ ] The gate and the required-integration invocation each spawn in group mode bound to the run's termination signal, asserted from the spawn options captured by a mock `AsyncSubprocessRunner` for both invocations in `v2/src/execution/ready-finalize.test.ts`.
- [ ] A gate that completes normally is unaffected: the existing `v2/src/execution/ready-finalize.test.ts` `createReadyFinalizer` tests stay green, including `runs the ready gate then flips the draft PR on green`, `overrides inherited JARVIS_READY_TIER=fast with full in the gate's child env`, `carries the ready gate command, exit code, and combined output`, and `runs required integration scope after ready gate and before flip`.
- [ ] A gate killed by an aborted run signal never enters agent repair: a new test in `v2/src/execution/write-loop.test.ts` — `an aborted signal short-circuits ready-gate repair without spending an iteration` — drives `publishWithReadyRepair` with `args.signal` already aborted and a `readyFinalizer` seam that rejects with a non-timed-out `ReadyGateError`, and asserts the result is a `ready_gate_failed` failure with `iterationsConsumed` unchanged and no autofix commit or repair iteration attempted (the agent runner is never invoked); it fails against the pre-fix code, which treats the rejection as an active gate failure and enters the autofix/repair path.
- [ ] Dropping the run signal turns the binding assertion red: replacing the gate's `signal` option with `undefined` leaves the gate unbound from run termination. `v2/src/execution/ready-finalize.test.ts` — `spawns the ready gate in group mode bound to the run signal`; Mutation checkpoint: the captured spawn options no longer carry the run's signal.
- [ ] Dropping the required-integration invocation's binding turns its own assertion red, independent of the gate's. `v2/src/execution/ready-finalize.test.ts` — `spawns required integration in group mode bound to the run signal`; Mutation checkpoint: replacing the required-integration invocation's `signal` option with `undefined` leaves that spawn unbound while the gate's spawn (previous checkpoint) stays bound.
- [ ] Reverting the gate's spawn options to baseline (`{ maxBuffer, env }` — no `signal`, no `processGroup`) turns the reap regression red. `v2/src/execution/write-loop-ready-gate-reap.sandbox-unrunnable.test.ts` — `terminating a run mid-gate kills the ready gate process group`; Keystone checkpoint: a surviving revert means the group-mode spawn is inert.
- [ ] `bun run typecheck`, `bun run test:v2`, and `bun run test:integration:v2` pass.
