VERDICT — Required refinements:

1. **Scope of root-archival pass (global vs. scoped invocation)**: The spec must state whether `jarvis1 cleanup <spec-name>` (scoped to one spec) runs the root-archival pass, not just the default global invocation. The intent's motivating scenario — a stranded, already-merged spec at root with no worktree — is plausibly exactly what an operator would target with a scoped cleanup call. Leaving this undecided means implementers will guess divergently on observable command behavior.

2. **`checkArchivePreconditions`/`archiveResolvedSpec` sentinel behavior must be verified, not assumed**: The decision to pass `removedWorktreeDir: ""` as a sentinel asserts specific behavior of existing functions without citing how those functions actually consume that parameter. Per this repo's "cite the test, don't paraphrase" principle (spec guidance's refactor-AC rule, extended here to reused-behavior claims), the spec must ground this in the actual function signature/logic — either confirm an empty-string sentinel is safe against the real implementation, or specify a proper optional/undefined parameter if the signature doesn't cleanly support the sentinel approach.

3. **Cross-subspec completeness-walk behavior must be confirmed, not assumed**: The spec's core correctness claim — that a root-archival candidate is judged complete by walking AC across all linked subspecs (not by reading a possibly-stale index checklist) — rests entirely on unverified assumptions about `checkArchivePreconditions`'s actual implementation. Since this is the load-bearing correctness guarantee of the whole pass, the spec must cite the real completeness-check logic (or its existing tests) rather than asserting reuse "unmodified" solves it by default.

4. **Multi-candidate commit granularity must be pinned**: When more than one root spec is archivable in a single run, the spec must state whether each candidate is committed individually or batched into one commit. This is an observable git-history difference with no stated default, and is untested. Per-candidate commits (matching `commitArchivedSpecMove`'s existing per-spec pattern) is the natural choice and should be the stated decision, with a corresponding test.

5. **PR-matching logic should be named, not left to inference**: The spec says preconditions/PR-matching are "reused... shared with `triage --mark-ready`," which is a legitimate way to avoid respecifying matching semantics, but should name the actual function/logic being reused so a reviewer unfamiliar with the removal-loop code isn't left to infer it.

6. **Idempotency on repeated runs should be an explicit test**: The spec implies idempotency (root scan excludes `completed/`), but this new steady-state, run-over-run behavior should be stated as an explicit test case (an already-archived candidate is not rescanned/re-archived on a later run), not left implicit.

Not required: doc-updates-as-AC-gating and performance/rate-limit exposure are out of scope — neither is mandated by this repo's spec conventions, and the latter is an existing property of reused logic, not new surface. Partial-run rollback and hand-ticked-but-never-run AC risk are pre-existing/self-resolving concerns (once #4 is pinned) and need at most a one-line acknowledgment, not new mechanism — leave to refiner's discretion, not a required refinement.
