# Walk the persisted-expansion tree only

## Problem

`selectNextRun` in `v2/src/tui/tui-entry.tsx` builds a throwaway `revealState` (`v2/src/tui/tui-entry.tsx:1044`) that adds the selected collapsed pipeline/stage/branch to `expandedPipelineNodeIds` purely to widen the selectable-id list, so `j`/↓ descends into a node the operator never expanded. `selectPreviousRun` walks the committed state, so the two directions disagree: down enters a subtree, up leaves it and never re-enters. Navigation should walk the currently painted tree — the persisted `expandedPipelineNodeIds` plus whatever selection has already ancestor-revealed via `resolveSelectedAncestors` — without ever widening it itself: a collapsed expandable node is one stop, and only `e`/`expand`/`collapse` write expansion. (Selection-driven reveal is unaffected by this change — see Decisions.)

## Decisions

- Delete the reveal branch outright instead of mirroring it into `selectPreviousRun` — rules out restoring symmetry by making ↑ auto-reveal too.
- `selectNextRun` keeps its `const nowMs = nowMsFn();` / `const state = currentState;` locals and derives ids once as `const ids = monitorSelectableNodeIds(state, nowMs);` — rules out collapsing the body onto `selectPreviousRun`'s `monitorSelectableNodeIds(currentState, nowMsFn())` form, which would leave the keystone anchor non-unique in the file.
- Keep `resolveSelectedAncestors` paint-time ancestor reveal and `revealSelectedAttentionTarget` — rules out reading "no auto-expansion" as also stripping reveal from Enter and `selectNode`. This also means the selectable-id list is *not* limited to `expandedPipelineNodeIds` alone: a subtree already ancestor-revealed by the current selection stays walkable by `j`/`k` (it's already painted). The fix only removes navigation's own power to widen that set.
- Retarget the two deleted `@mutate` directives onto surviving lines rather than dropping them — the "walking writes no expansion" negative case still needs a live guard once the `revealState` anchor is gone.
- Rewrite the two descend-asserting tests to the new expectation instead of deleting them; both stay collapsed-**pipeline** cases (the `pipe-multi` one is not redundant busywork — its two-run stage proves the whole subtree, not just the first stage, stays unpainted). A collapsed **stage** cannot exhibit this bug via `j` at all, so it gets no dedicated test: a stage always paints one representative run row regardless of its own expansion (`e` toggles representative vs. full constituents), so the item immediately after a collapsed stage is already painted either way; and the instant a run is selected, `resolveSelectedAncestors` legitimately ancestor-reveals that stage's full constituents for painting (the deliberate, unaffected reveal-on-select path) — producing identical ids whether or not the removed branch ever ran. A collapsed **branch** has no such fallback (its children are stages, painted all-or-nothing exactly like a pipeline's), so the bug is genuinely observable there. Repurpose the "walking past a revealed pipeline…" test — whose multi-step loop degenerates to a single hop once a collapsed pipeline shows zero children from the first step, duplicating the `pipe-multi` case — into a collapsed-branch test instead of a second collapsed-pipeline one.

  const nowMs = nowMsFn();
  const state = currentState;
  const ids = monitorSelectableNodeIds(state, nowMs);
  if (ids.length === 0) return;
  const activeId = state.selectedNodeId;
  const selectedIndex = activeId === null ? -1 : ids.indexOf(activeId);

}
