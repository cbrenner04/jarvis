# Verdict

The spec's core mechanism is sound (jarvis-driven deterministic deletion of the deterministically-resolved ready-intent path, in-memory copy feeding `intent.md`, scope to `commit: true`). But two findings make it unsafe or self-defeating as worded, plus several pinning gaps. The following refinements are required.

## Required refinements

1. **Pin the deletion placement to avoid the write-boundary check (must fix).** As worded, the deletion window ("after `intent.md` is written, before the draft commit's `git add -A`") spans plan mode's write-boundary enforcement, which scans `git status` and reverts any change whose path falls outside the spec directory — including a deletion under `ready-intents/`. An implementer following the current wording literally would have their deletion reverted and the run aborted with a spurious blocker, defeating the feature. The spec must constrain the deletion to occur **after the boundary check passes and before the draft commit is created**, so the deletion is never seen (and reverted) by the boundary enforcement. State this as the load-bearing placement decision, ruling out the inferior alternative of widening the boundary's allowed-path set.

2. **Require containment of the derived deletion path (must fix — safety).** Ready-intent validation only checks that the parent directory basename is `ready-intents`; it does not constrain the path to within the project root. An absolute ready-intent path located outside the repo (with a `ready-intents/` parent) would yield a `../`-escaping relative path that, joined onto the worktree, resolves *outside* the worktree — potentially mutating the operator's live checkout, contradicting the spec's own "the operator's main checkout is never touched." A bare existence guard does not catch this, since the escaped target may exist. The spec must require that the derived deletion target be rejected (no deletion staged, run proceeds) unless it resolves **within the worktree**, not merely that it exists.

3. **Reframe the "source not present" case to base-branch state (F3/Decision 5/AC #5).** Ready-intents are normally committed and merged before a plan run, so the source is typically present in the worktree's base. The genuine "not present" case is an **authored-but-unmerged** ready-intent (not committed into the branch's base), not an out-of-repo path. Tie Decision 5 and its acceptance criterion to that base-branch condition so the criterion is deterministically producible in a test, rather than the ambiguous "not present in the worktree checkout."

4. **Add an acceptance criterion that pins the F1 contract.** The existing AC ("the committed tree no longer contains the file") would also pass if the deletion were reverted and re-added in a separate commit — it cannot detect the boundary-revert regression. Add a criterion asserting the deletion **survives the write-boundary check and lands in the same `plan: draft` commit that carries the spec tree, with no spurious blocker** — i.e., not reverted, not a separate commit.

5. **Record the blocked-draft / abandoned-branch behavior as an explicit decision (F2).** When a blocker is appended after the boundary check (e.g., prereq/draft blocker), the deletion rides with the committed draft and merges correctly once the operator resolves the blocker. If the branch is instead abandoned, the deletion lives only on that branch and `main`'s `ready-intents/` is untouched, leaving the intent re-consumable. This is the correct fallback. State it as a one-line decision so it reads as intended behavior, not an oversight.

6. **Name the `commit: false` accumulation as an accepted gap (F5).** The spec correctly leaves the source in place under `commit: false` (live checkout, no PR to carry a deletion). Add one sentence stating the consequence — consumed no-commit ready-intents are never cleaned by any path — as a known, accepted product gap, so the scope boundary reads as a decision rather than an omission.

7. **Clarify resume consistency under the corrected placement (F7, minor).** With deletion moved to just before the draft commit, a run that fails before committing never stages the deletion; resume rebuilds from the branch and has no deletion logic. Since no spec ships in those failure modes, consistency holds. One clarifying sentence in Decision 6 should reflect that the deletion is durable only once the draft commit exists.

## Rationale

Findings 1 and 2 are correctness/safety blockers: the intent requires the deletion to actually land in the spec PR and explicitly forbids touching the operator's checkout — the current wording violates both. Findings 3–7 close pinning gaps so the spec's decisions and acceptance criteria fully constrain the deterministic, non-agent-discretion behavior the intent demands ("same ready-intent in, same removal out"), and so the criteria can detect the very regression Finding 1 describes. All findings are within the intent's stated scope; none over-reach. No other changes required — the `v1-behaviors.md` update is correctly included as mandated for a behavior change.
