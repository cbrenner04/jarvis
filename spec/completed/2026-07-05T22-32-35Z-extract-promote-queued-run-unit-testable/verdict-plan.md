## Verdict: Required Refinements

1. **Settle-delay state shape must be a decision.** The suppression deadline (`promotionsSuppressedUntil` in current code) is mutated across calls — a bare numeric parameter can't carry that mutation back to the caller. The spec must state explicitly how the extracted function threads this state in and out (e.g., a mutable ref object, or the function returns the updated deadline for the caller to store). Without this, "explicit parameters" is ambiguous on the one piece of state that isn't a simple snapshot.

2. **The wiring between `spawnWriteLoop` and the extracted function must be named as a decision.** Today `spawnWriteLoop`'s completion callback calls `promoteQueuedRun`, which in turn calls `spawnWriteLoop` again — a circular relationship. The spec currently only says `spawnWriteLoop` is a caller-supplied callback param, but doesn't say what reusable piece (e.g., a single closure built once in `createRunControlHandlers` that binds store/registry/check/settle-state and is handed to both the RPC handlers and `spawnWriteLoop`'s finally block) resolves the circularity. This needs to be a stated decision, not left implicit — otherwise the extraction's shape is underspecified at exactly the point where behavior preservation is riskiest.

3. **Task checklist must classify every existing test, not describe categories.** `daemon-queue-promotion.test.ts` has 7 tests; the current checklist speaks in categories ("pure promotion-ordering tests," "genuine RPC-wiring test") without confirming each test maps cleanly to one bucket. At least one test (the already-running/untouched-run case) isn't clearly classified either way, and the claimed-key-skip test relies on a live registry claim obtained via a real `spawnWriteLoop` round trip — converting it to a pure unit call requires manually seeding a registry claim, which is more than a mechanical rename and should be acknowledged as such. The spec should either enumerate the disposition of each test or make clear the conversion may require adapting individual tests' setup, not just relocating call sites.

4. **Drop or rescope the settle-delay-suppression test claim.** No existing test in the file actually asserts that a promotion was withheld because it fell inside the settle-delay window (the 100_000ms-delay test only proves an unrelated already-running run is undisturbed). The spec's checklist implies such a test exists to convert; it should instead either explicitly note this coverage gap and scope a new test for it, or drop the claim so the acceptance criteria don't imply test coverage that doesn't exist.

5. **Pin the extraction location.** "`v2/src/daemon/daemon.ts` (or a co-located module)" is an open choice with no clear reason to defer — per this repo's guidance to prefer concrete decisions over invented ambiguity, and since a same-file extraction is simplest and avoids new import surface for tests/docs, the spec should commit to one location rather than leaving both options live.

These five refinements are necessary because the spec's core claim — a pure, behavior-preserving extraction — is currently underspecified on the exact mechanics (mutable state threading, circular wiring) that determine whether the extraction actually preserves behavior, and the test-conversion plan overstates what's mechanical versus what requires real rewrite or new coverage.
