## Verdict: Required refinements

**01-tail-stream-direct-invocation.md**

1. **Specify handler-resolution mechanics for every test, not just the abort case.** The subspec's only worked example is the abort test. It must state the general rule for how `tailHandler(...)` is expected to resolve in each test shape: which tests never call `follow()` (and thus resolve immediately, needing no abort), and which do call `follow()` and therefore need an explicit termination path (abort via a per-test `AbortController`, or an equivalent). Without this, the implementer has to reverse-engineer control flow for every existing test case. This is required by the intent's demand to preserve behavior faithfully, not just make tests pass.

2. **Resolve the coverage question for "pending wait does not block other RPCs on the same connection" analog in the tail-stream file (and confirm for the wait-completion file) explicitly, not implicitly.** If a proposed rewrite of a transport-concurrency test ends up asserting the same property as another existing/rewritten test (e.g., duplicating a "two calls resolve independently" case), the spec must say so explicitly and justify it as an accepted, named coverage change — per the intent's explicit "no thinning behavior coverage" constraint and the spec-guidance rule that behavior changes/removals must be deliberate, not accidental. Silently presenting a near-duplicate rewrite as coverage-preserving is not acceptable; the spec must either name a distinct property the rewrite still asserts, or explicitly flag the loss and why it's acceptable.

3. **State the `AbortController`/`AbortSignal` construction convention once, as a shared decision.** Both subspecs call handler functions requiring a `signal` argument (`handlers.list`, `handlers.wait`, `tailHandler`). The spec must state a single, consistent convention — e.g., "each call site constructs its own `new AbortController()` and passes `.signal`; only abort-focused tests invoke `.abort()`" — applied uniformly, rather than leaving it to be inferred from one worked example. This also fixes the inconsistency where `handlers.list` is shown without the required `signal` parameter while `handlers.wait` is shown with one.

4. **Tighten the acceptance criteria beyond a raw test-count match.** "Same number of test cases, 0 skipped" does not guard against a rewritten test silently asserting a different (weaker or duplicate) property than the one it replaces, which finding 2 above shows is a real risk here. The AC should require that the specific preserved behaviors (fanout/independent resolution, single-waiter abort detachment, non-blocking dispatch or its justified replacement, `onClose` fires exactly once after expected `onData` calls) are each still asserted somewhere in the converted file — not just that the count is unchanged.

5. **Document the no-`follow()` resolution path as a one-line decision**, so the common-case tests (using `expectTailClosesWithoutData` or similar, with no `follow()` invocation) aren't left to be inferred solely from the harder abort-focused example.

Rationale: these gaps all trace back to the intent's explicit "no thinning behavior coverage" constraint and the spec-guidance principle that behavior-preserving conversions must cite/verify the specific behavior preserved rather than paraphrase or assume it. Findings 3 and 5 are small but load-bearing enough to block a correct first implementation attempt without back-and-forth.
