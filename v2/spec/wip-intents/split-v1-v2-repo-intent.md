name: split-v1-v2-repo
---

Split the repo into top-level `v1/` and `v2/` directories so that v1 keeps running unchanged while v2 is built alongside it. This is step 1 of the v2 rewrite — see `v2-vision.md` (sibling of this file) for the broader context, principles, and architectural constraints.

Goal: after this change, running `jarvis` (and every CLI subcommand) behaves identically to today, but all of v1's source, tests, specs, prompts, and v1-specific tooling live under `v1/`. A sibling `v2/` directory exists with its own `spec/` (containing this intent and the vision doc, migrated as part of this change) and room for src/test to land later. The repo root holds the single package and repo-wide glue: CI workflows, root README, root `.gitignore`, the one root `package.json`, the one root `bun.lock`, the shared `node_modules`, repo-wide tool config (biome, base tsconfig), and the root `bin/jarvis` shim needed for existing installs to keep resolving.

Model: one package, two source trees. A single root `package.json` / `bun.lock` / `node_modules` for the whole repo — NOT Bun workspaces and NOT a per-version `package.json`. v1 and v2 are separate TypeScript projects (separate source trees), not separate packages.

What needs to happen, at a high level:

- Move `src/`, `test/`, `spec/`, and any other v1-only directories/files into `v1/`.
- Create `v2/` with at least `v2/spec/wip-intents/` populated by migrating this file and the other `v2-*` files into it. No v2 source code yet.
- Keep the `jarvis` CLI entrypoint working from the repo root unchanged — binary name, subcommands, flags, stdout/stderr, exit codes all identical. Keep the root package `bin` field pointing at `bin/jarvis`, and update that shim to run the v1 CLI explicitly (for example `../v1/src/cli.ts` instead of `../src/cli.ts`). Existing symlinks to `bin/jarvis` must keep working.
- Keep a single root `package.json`. Do not introduce Bun workspaces or a per-version `package.json`. Preserve the familiar root command surface: `bun run typecheck`, `bun test`, `bun run check`, and `bun run ready` still work and validate v1 after the move. 
- Keep `bun.lock` and `node_modules` at the repo root as the single shared dependency tree. No v1-local or v2-local lockfile. Accepted consequence by design: v1 and v2 share one resolved version of every dependency.
- Make v1 its own TypeScript project: add `v1/tsconfig.json` extending a shared root `tsconfig.base.json`, scoped to v1 source. This is what enforces "pretty separate" — once v2 lands, separate tsconfig projects mean v1 and v2 cannot import each other's modules. Root owns repo-wide config (biome, base tsconfig) and the delegating scripts.
- CI and GitHub workflows continue to pass against v1 from its new location. Prefer path/script updates over workflow redesign; if workflows already call root scripts, keep that contract.
- This change is purely structural. No behavior changes, no deletions of "probably unused" code, no renames.

Implementation shape:

- Do the relocation as a single big-bang structural move. This repo is currently personal-use only so staged directory moves would add overhead without reducing meaningful risk.
- The verification bar is the existing gate plus a small manual CLI smoke test: `bun run typecheck`, `bun test`, `bun run check`, `bun run ready`, `bin/jarvis help`, and one harmless config/read-only subcommand.

## Refine turn 1

- The draft should make the migration inventory explicit instead of leaving "any other v1-only directories/files" open-ended. The current root also contains `scripts/`, `data/`, `docs/`, `bin/`, `biome.json`, `bunfig.toml`, `CODEOWNERS`, and `README.md`; the spec should classify each as root-owned glue, v1-owned content that moves under `v1/`, or intentionally shared top-level material.
- The current repo does not have `spec/tmp-d8bfcc86/v2-vision.md`; the long-lived v2 docs currently live under `spec/wip-intents/`. The draft should resolve that mismatch explicitly by naming the exact source paths that move into `v2/spec/wip-intents/` and by stating what remains in `v1/spec/` versus what becomes v2 planning material.
- Root command compatibility likely requires thin root delegators rather than keeping implementation at the root. Today `package.json` scripts and `bin/jarvis` point at root `src/` and root `scripts/`; after the move, the spec should preserve the same root command names while allowing those entrypoints to dispatch into `v1/` code.
- The TypeScript split needs a clear contract for the root config. Today there is only one root `tsconfig.json` including `src/**/*.ts` and `test/**/*.ts`; after the move, the spec should require a shared root `tsconfig.base.json`, a `v1/tsconfig.json`, and a root `typecheck` entry that still validates only v1 in this step rather than accidentally introducing a composite-build redesign.
- Treat non-TS runtime assets as part of the structural move, not incidental cleanup. Files like `src/modes/patch/rules.md` and the plan-mode prompt markdown under `src/modes/plan/prompts/` are behavior-bearing v1 assets and should move with the v1 engine so prompt loading and tests stay path-correct without changing behavior.

## Refine turn 2

- Make the inventory concrete enough that the draft can express it as an allowlist, not a vibe. Based on the current root, `src/`, `test/`, `data/`, `docs/`, and `scripts/` are v1-owned and should move under `v1/`; `bin/jarvis`, `.github/`, `.gitignore`, `README.md`, `package.json`, `bun.lock`, `bunfig.toml`, `biome.json`, `CODEOWNERS`, and the shared `node_modules/` stay root-owned; `AGENTS.md` should stay at the repo root and be treated as repo-level guidance that may need wording updates for the split.
- The draft should explicitly call out the current root entrypoints that must be repointed after the move, not just the obvious `bin` shim. Today `package.json` has `"module": "src/index.ts"`, `"start": "bun run src/index.ts"`, `"typecheck": "tsc --noEmit"`, `"ready": "bun scripts/ready.ts"`, and `"install-opencode-permissions": "bun run scripts/install-opencode-permissions.ts"`; the post-move contract should preserve the root command names while making them dispatch into `v1/` paths, and it should say whether any thin root helper files remain or whether the root scripts call `v1/...` directly.
- Treat the two current files under `scripts/` as v1 implementation, not repo glue. `scripts/ready.ts` and `scripts/install-opencode-permissions.ts` are behavior-bearing runtime tooling for the existing product and should move to `v1/scripts/`; if the root keeps any delegator scripts at all, they should be new thin shims rather than the current implementation continuing to live at the root.
- Resolve the spec migration with exact source and destination paths. The current v2 planning material is `spec/tmp-d8bfcc86/intent.md` plus the root files `spec/wip-intents/v2-vision.md`, `spec/wip-intents/v2.txt`, `spec/wip-intents/v2-catalog.txt`, `spec/wip-intents/v2-prompts.txt`, and `spec/wip-intents/v2-rename-binary.txt`; the draft should name where each lands under `v2/spec/wip-intents/` and should state that non-v2 planning/history such as `spec/completed/**`, `spec/wip-intents/web-interface.txt`, `spec/wip-intents/draft-pr-flip-to-ready-plan.txt`, and `spec/wip-intents/still-cant run-non-git-dirs.txt` remain with v1 under `v1/spec/`.
- The TypeScript/root-config contract should avoid accidental widening. A safe draft requirement is: root `tsconfig.base.json` holds shared compiler options only, `v1/tsconfig.json` owns the v1 `include` globs, and the root `typecheck` script must target `v1/tsconfig.json` explicitly rather than relying on a root `tsconfig.json` that might later sweep in `v2/`. If the draft keeps a root `tsconfig.json`, it should describe it as a non-authoritative wrapper and forbid it from becoming a second source tree config.
- The draft should classify prompt and fixture assets as first-class moved content. In addition to `src/modes/patch/rules.md` and `src/modes/plan/prompts/*.md`, the current test fixtures under `test/fixtures/**` and helpers under `test/helpers/**` are part of the v1 engine and should move with the v1 tests so imports and runtime file reads remain internal to `v1/`.
- CI can stay structurally identical if the root script contract stays intact. The current `.github/workflows/ci.yml` already does `bun install --frozen-lockfile`, `bun run typecheck`, `bun run test`, and `bun run check`; the draft should prefer preserving that file shape and updating only the root script targets instead of relocating workflow logic into version-specific paths.

## Refine turn 3

- The draft should pin the current root launcher behavior, not just the file path. `bin/jarvis` currently resolves symlinks before dispatching into `src/cli.ts`; after the split it should keep that symlink-safe wrapper logic intact and only change the final target to `v1/src/cli.ts`, so existing PATH symlinks keep behaving exactly the same.
- Root entrypoint ownership should be stated as a compatibility layer, not an implementation home. `package.json` remains the only package manifest and keeps the existing command names, but `module`, `start`, `typecheck`, `test`, `ready`, and `install-opencode-permissions` should either point directly at `v1/...` or at new root shims whose only job is forwarding into `v1/`. The draft should explicitly forbid leaving the real implementation in root `src/` or root `scripts/` after the migration.
- Scope the root lint/format contract carefully. Because `bun run check` currently runs Biome on `.`, the draft should say whether `v2/` starts as documentation/spec-only content that already satisfies the existing root formatter/linter rules. This avoids an accidental gap where empty or placeholder v2 files make the unchanged root `check` surface fail despite the migration being described as behavior-preserving.
- The v1 spec move should be described as a full-tree relocation, not only active specs. The current `spec/` root contains `completed/`, `wip-intents/`, and this plan directory `tmp-d8bfcc86/`; the draft should say that all non-v2 planning/history moves under `v1/spec/`, with the named v2 planning files carved out into `v2/spec/wip-intents/`, so there is no ambiguity about whether legacy completed specs remain at the repo root.
- Call out the root README and AGENTS updates as structural documentation work, not optional cleanup. They should explain the new top-level layout, clarify that `jarvis` still executes v1 from root-owned entrypoints, and point future v2 planning/implementation work at `v2/` without changing the current user-facing CLI contract.
- The draft should preserve the "no behavior change" rule for runtime file loading by naming path-sensitive assets beyond TypeScript sources. That includes `data/prices.json`, `docs/**/*.md` that are read or referenced by commands/tests, and all prompt/rules markdown under `src/modes/**`; the migration should update path resolution only as needed to keep those reads internal to `v1/` and externally unchanged.
