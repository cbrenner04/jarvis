## Verdict — required outcomes

1. **Failed branch rematerialization must not permanently disable durable fallback.** When recovery recreates the recorded `worktreePath` from `prior.branch`, a partial or invalid directory at that path must not cause later resolution to treat the worktree as present and fall back to worktree-first refusal. After rematerialization failure, a retry of `pipeline resume` or stage resolution must still be able to reach admission-base binding, branch rematerialization, or the `never landed` refusal — not be stuck on `not found in prior worktree` / `expected index at … in prior worktree` because `existsSync(prior.worktreePath)` is true on a non-checkout husk. This closes a wedge introduced by resolution-time `mkdir` + `git worktree add` without failure cleanup or husk detection; it is required for the spec’s recover-after-worktree-removal contract.

2. **Durable-root resolution docs must match runtime order and precedence.** `v2/docs/pipeline-execution.md` and `v2/docs/v1-behaviors.md` currently describe walking durable roots as “prior stage branch, then pipeline admission `context.cwd`.” Runtime checks admission filesystem presence first, then branch git presence with rematerialization. Update both docs so operator-facing prose matches that order and states that when both roots carry the path, admission `context.cwd` wins. Doc updates were an explicit acceptance criterion; misstated walk order is a contract bug even though binding behavior is correct.

No other changes are required to satisfy this spec’s checked acceptance criteria. Gaps called out but not required here: full `ensureExternalWorktree` parity (node_modules symlink, locks, remote-branch handling), extra unit tests for implement admission-base fallback / directory-shaped artifacts / fan-out with absent worktree, resume admission-base-only coverage, and `intent.md` checkbox hygiene.
