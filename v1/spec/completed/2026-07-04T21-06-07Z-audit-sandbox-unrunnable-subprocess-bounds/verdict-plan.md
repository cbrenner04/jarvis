## Verdict: Required Refinements

**1. Correct false test-coverage claims (subspecs 01 and 02).**
The Problem sections assert `run.sandbox-unrunnable.test.ts` currently "exercises" the `pr.ts`/`completion-pipeline.ts`/`preflight.ts`/`dep-install.ts`/`base-ref-test-runner.ts` paths with real subprocesses. This is factually wrong — that suite is watchdog-scoped via `FakeAgent` and has no references to these modules or to `force-with-lease`. The spec must instead state plainly that these git call sites currently have **no** stall-regression coverage, and that subspecs 01/02 are *adding* new coverage, not extending existing coverage. This changes the nature of the task checklist items: they should not presuppose `run.sandbox-unrunnable.test.ts` (or any single named file) as the landing spot. Let each subspec's task checklist choose the right home for its new stall test — the existing suite if the call site is genuinely reachable there, otherwise a smaller targeted test (e.g., a focused unit-level stall test invoking the function directly with a `git` shim on `PATH`). Per the intent's own escape hatch ("prove the remaining call sites are already bounded"), it's acceptable for a call site to get only the bound plus no dedicated stall test, as long as the doc update records that reasoning.

**2. Extend hang-fixture tracking to whichever file actually receives the new stall test (subspec 01).**
Subspec 00 correctly adds `beginHangFixtureTracking`/`reapActiveHangFixtures` to `subspec.sandbox-unrunnable.test.ts` because it lacks that tracking today. Subspec 01 must apply the same treatment: if its `completion-pipeline.ts`/`pr.ts` stall test is decided (per refinement #1) to land in `pr.sandbox-unrunnable.test.ts` — which today only has `mkdtempSync`/`rmSync`, no hang-fixture tracking — the subspec must add the tracking pair there too, mirroring subspec 00's decision. This must be reflected as an explicit decision/task item, not left implicit.

**3. Add an explicit fallback for stall-test placement, as a decision line, not just a task-checklist detail.**
Following from #1, each of subspecs 01 and 02 needs a stated decision covering what happens if wiring a real-subprocess stall test through an existing suite proves impractical for a given call site (e.g., because the call site isn't reachable from that suite's harness). The fallback options — a smaller targeted unit test with a `git` shim, or bounding-only with a documented rationale and no dedicated stall test — must be named as a decision so the acceptance criteria and doc updates aren't blocked on an assumption that turns out false during implementation.

**Not required:** the finding about `completion-pipeline.ts`'s force-with-lease call being in-process/synchronous rather than forked was checked and is moot — the spec's helper application is already scoped to `execFileSync("git", ...)` call sites by construction, so no additional decision is needed there. The `gh`-unbounded residual note (already present in subspec 01) is adequate as a docs-only note; a linked follow-up issue is optional polish, not a required refinement.
