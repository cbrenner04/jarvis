# 00 - Daemon claims a draining predecessor's pipeline before approve/reject/resume/recover

## Problem

`pipeline_approve`, `pipeline_reject`, `pipeline_resume`, and `pipeline_recover` each self-refuse with `daemon_superseded` whenever `ctx.retiring` is true (`daemon-pipeline-handlers.ts`), and each dispatches any resulting successor stage through this process's own `pipelineExecutionDeps()`/`admitWorkflowStart` when it does run. A draining direct predecessor is always `ctx.retiring`, so forwarding these four verbs to it for execution (as `wait`/`pause`/`kill` are forwarded in `daemon-stable-run-routing.ts`) would either bounce off its own refusal or, if that guard were bypassed, let the outgoing generation admit new work — both violate the handoff invariant that only the incoming generation admits work. Meanwhile the incoming generation's local `pipeline_owner` witness is `not_owner` for a pipeline the predecessor still (alive) owns, so it cannot adopt via the existing dead-owner path (`adoptOrphanedPipeline` refuses whenever `isOwnerAliveProbe` reports the recorded owner alive). Neither `applyPipelineApprovalDecision` nor `resumePipeline` checks `ownerIdentity` at all today — the only reason a wrong generation cannot currently act on a pipeline is that the CLI pre-flight resolves the right socket before connecting, a check [01](./01-cli-pipeline-verbs-stable-address-only.md) removes. No RPC is ever forwarded to the predecessor for these four verbs; instead the stable endpoint gains its first ownership gate for them, durably moving ownership to itself first via the existing `claimPipelineContinuation` CAS, then running the unmodified local handler. An already-dispatched stage's entry run keeps settling under whichever generation's process is actually driving it, unaffected by this spec (existing settlement machinery in `pipeline-execution.md`); this claim only governs what admits the *next* stage.

## Decisions

- No verb RPC is forwarded to the predecessor for these four verbs; the predecessor's approve/reject/resume/recover handlers are never invoked by this mechanism (they stay behind their own `ctx.retiring` refusal, untouched) — rules out forwarding-and-executing on the predecessor, which would let the outgoing generation dispatch a successor stage.
- New wiring lives beside `createStableRunHandlers` in `daemon-stable-run-routing.ts` and wraps these four handlers on the stable endpoint only; private endpoints keep the unwrapped local handlers — rules out re-triggering the claim from the predecessor's own private endpoint.
- Claim sequence per request: read the pipeline row's own `ownerIdentity` locally (already loaded to answer `pipeline_owner`); if it is this generation, or `adoptOrphanedPipeline`'s existing dead-owner check succeeds, proceed with the existing unmodified local handler as today. Otherwise, when a direct predecessor is configured, query `pipeline_owner` on `predecessorSocketPath`; only when it answers `{kind: "owner", ownerIdentity}` matching the row's own recorded `ownerIdentity` does the incoming generation call `store.claimPipelineContinuation({ pipelineId, priorOwnerIdentity: ownerIdentity })` (existing CAS primitive, no store change) directly — never `adoptOrphanedPipeline`, whose liveness gate exists for the dead-owner case — rules out stealing ownership from a live daemon this generation never confirmed is its own direct predecessor (e.g. a grandpredecessor two handoffs back, unreachable at `predecessorSocketPath`).
- Claim `applied` runs the verb's existing local handler unchanged: ownership is now stamped to this generation before the handler's own `dispatchPipelineStage`/`claimPipelineStageAdmission` call, so any successor stage this decision unblocks is admitted by the incoming generation through its own `pipelineExecutionDeps()` — this is the entire single-admitter mechanism; no predecessor code path runs, so there is nothing to admit twice.
- Claim `refused` (`stale_owner`/`claim_lost` — ownership moved between the confirming read and the claim write) re-runs the local owner decision once (re-read `pipeline_owner`'s own logic: now-dead-and-adoptable, now-ours, or still genuinely elsewhere) rather than surfacing the stale predecessor answer — rules out returning a refusal based on a read that raced a concurrent claim.
- Predecessor unreachable while queried (connect/timeout/`RpcError`) refuses with the existing `pipeline_no_live_owner` identifier as an `RpcError`, reusing `PIPELINE_UNREACHABLE_OWNER_RECOVERY`'s text; never treated as dead — rules out mis-adopting from a merely-slow or momentarily-unreachable predecessor that `isOwnerAliveProbe` still reports alive.
- Predecessor answers anything but a matching `owner` (`not_owner`, `not_found`, or a different `ownerIdentity`) keeps the same `pipeline_no_live_owner` refusal; no claim is attempted — this also means the fan-out `pipeline_owner_conflict` detection the CLI used to perform across every discovered socket is dropped for these four verbs: only the local store and the one configured direct predecessor are consulted, consistent with `pipeline_owner`'s own dead-owner adoption, which already assumes a single predecessor chain rather than fanning out.
- Genuinely ownerless pipelines (no predecessor configured, or the row has never had a live claimant) get the same `pipeline_no_live_owner` refusal, computed daemon-side here instead of CLI-side as today (the CLI no longer resolves ownership before connecting — see [01](./01-cli-pipeline-verbs-stable-address-only.md)); no predecessor socket is queried when there is nothing to ask.

## Acceptance criteria

- [x] A test in `v2/src/daemon/daemon-stable-run-routing.test.ts` proves each of `pipeline_approve`, `pipeline_reject`, `pipeline_resume`, `pipeline_recover` sent to the stable endpoint for a pipeline whose live stage is owned by an alive, draining direct predecessor succeeds (not `daemon_superseded`, not `pipeline_no_live_owner`); it fails against the pre-fix code, where the stable endpoint answers `pipeline_no_live_owner` locally and the predecessor itself would answer `daemon_superseded` if dialed directly.
- [x] A concurrency test drives one pipeline whose currently-dispatched stage keeps settling under the draining predecessor's own process (untouched, existing settlement) while two concurrent decision-verb calls at the stable endpoint race to claim ownership and dispatch its successor stage; it proves exactly one claim wins (citing `claimPipelineContinuation`'s existing CAS-loss path — `state-store.test.ts`, `claim_lost`/`stale_owner`, already reachable today for concurrent claimants — as the mechanism the losing call re-resolves against) and that the successor stage is dispatched exactly once, by the incoming generation only. Raw duplicate stage dispatch is already excluded by the pre-existing `claimPipelineStageAdmission` durable lock regardless of this subspec; what this test adds is that the new ownership-claim race resolves to a single winner rather than two callers both believing they hold the pipeline.
- [x] A test proves predecessor unreachability during the confirming `pipeline_owner` query (while the recorded owner is still alive per `isOwnerAliveProbe`) returns the `pipeline_no_live_owner` refusal and never adopts.
- [x] A test proves a genuinely ownerless pipeline with no predecessor configured still receives the `pipeline_no_live_owner` refusal from the stable endpoint with no predecessor socket connected at all (assert via a connect spy/fake that records zero calls), reusing the `not_owner`-for-a-live-foreign-owner semantics already pinned in `daemon-pipeline-owner.test.ts`. A second test proves the same refusal when a predecessor is configured but answers a mismatched or non-`owner` witness, with exactly one predecessor query made and no claim attempted.
- [x] `bun run typecheck`, `bun run test:v2`, and `bun run test:integration:v2` pass.

## Documentation updates

- `v2/docs/daemon-host.md` — the claim-then-execute mechanism for the four decision verbs on the stable endpoint; `pipeline_owner`'s own RPC shape is unchanged.
- `v2/docs/pipeline-execution.md` — single-admitter guarantee reusing `claimPipelineContinuation`, and that decision verbs are never forwarded to the predecessor.
- `v2/docs/v1-behaviors.md` — the existing "resolve owning socket, then issue RPC there" behavior for approve/reject/resume/recover no longer applies; record what replaces it.
- `v2/docs/operator-runbook.md` — the pipeline control-verb refusal paragraph (`pipeline_owner_conflict`/`pipeline_no_live_owner` text) no longer describes a cross-socket fan-out for these four verbs.
