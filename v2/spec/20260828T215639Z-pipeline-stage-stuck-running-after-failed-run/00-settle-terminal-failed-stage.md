# Settle terminal failed stage and recover

## Problem

When a pipeline workflow stage's dispatched run reaches terminal `failed` — for example `invocation_failure` / `quota_exhausted` — the stage row can stay `running` with `workflowInvocationId` pointing at that failed run and no `failureDetail`, so the pipeline derives `running` and is unrecoverable: `pipeline resume` refuses `pipeline_not_resumable`, `pipeline recover` does not apply, and killing the already-terminal run does not change the stage row. Observed 2026-08-23 on `full-review` pipeline `96830216` (implement run `5d3cb6e8`).

This is distinct from the existing deferred-settlement path: `running` rows whose `failureDetail.code` is `settlement_deferred` already redrive via `redrivableDeferredSettlementEntryRunId` / `hasRedrivableDeferredSettlement` when the linked run later terminals (`pipeline-execution.test.ts` restart-sweep tests). The wedge here is `running` with `workflowInvocationId` pointing at an entry run whose sibling-step rollup is terminally `failed` and **no** deferred marker because out-of-band settlement never ran — commonly `dispatchPipelineStage`'s catch path returning while the admitted entry run was still live, without recording `settlement_deferred`. In-band dispatch settlement when a run terminally fails is already covered on base; this subspec pins the out-of-band no-marker wedge (reconciliation and resume admission), matching intent AC #1's failing surface.

## Decision ledger

- A terminally `failed` linked entry run must settle its `running` stage row `failed` with composed operator `failureDetail`, so the pipeline derives `failed` and admits `pipeline resume` reopen; rules out leaving the stage `running` after its only run has terminally failed.
- Add `unsettledTerminalStageEntryRunId(store, record)` beside `redrivableDeferredSettlementEntryRunId` in `pipeline-stage-dispatch.ts`: bail unless `record?.status === "running"`; bail if `failureDetail` carries `settlement_deferred`/`entry_run_still_live` (deferred rows stay on the existing predicate); derive `linkedEntryRunId` via `settlementLinkedEntryRunId` and bail if absent; bail if `isLiveEntryRun(store, linkedEntryRunId)`; bail unless `rollupWorkflowRunStatus` over the linked entry run (same contract as restart-sweep `wait` / `adoptAndSettlePipelineStage`) is terminally non-success — at minimum `failed`; return `linkedEntryRunId` only on that rollup-`failed` wedge; rules out redriving merely because the entry row is non-live (rollup-`completed` without marker stays untouched per `restart sweep leaves a running stage without a deferred marker untouched`); rules out folding the marker check into `redrivableDeferredSettlementEntryRunId` and losing the deferred-only guard the restart sweep's reconciled-set exclusion depends on.
- Widen `hasRedrivableDeferredSettlement` to admit a pipeline when **either** predicate resolves on any stage row: resolve `deferredEntryRunId` and `unsettledEntryRunId` per stage, take `redrivableEntryRunId = deferredEntryRunId ?? unsettledEntryRunId`, then apply `if (reconciledEntryRunIds.has(redrivableEntryRunId)) return false;` on its own independently mutable line before returning true; rules out a second startup sweep or periodic timer.
- Re-settlement for both predicates continues through `continuePipeline` → adopt/settle (`adoptAndSettlePipelineStage` / `applyEntryRunSettlement`); rules out a bespoke force-settle writer or a separate operator verb.
- Extend `resumeDrivesDeferredSettlement` (or rename to a neutral exported name if the body widens) so derived-`running` resume admission ORs the unsettled predicate through the same `hasRedrivableDeferredSettlement` widening; rules out resume staying `pipeline_not_resumable` while the wedge row is still `running`.
- After reconciliation or resume admission settles the stage `failed`, unscoped `resumePipeline` follows the existing `resumeFailedRequiresReopen` → `reopenFailedPipeline` → `continueAfterAdmission` path; rules out a permanent `pipeline_not_resumable` once the row is durably `failed`.
- On `dispatchPipelineStage` catch early-return when `admittedEntryRunId` is still live, record the same `settlement_deferred`/`entry_run_still_live` `failureDetail` `applyEntryRunSettlement` uses for a non-`completed` rollup over a live run; rules out new bare `running`+linkage rows with no marker when wait/rethrow interrupted settlement (historical no-marker rows still need the new predicate).
- Preserve the reconciled-this-start exclusion from `20260825T220908Z-daemon-start-reconciles-deferred-pipeline-settlement`: an entry run id in `reconciledEntryRunIds` is not redriven by either predicate; rules out failing a stage out from under `recoverReconciledRuns`.
- `isLiveEntryRun` guards both predicates against genuinely live linked entry runs; the unsettled predicate additionally requires rollup-`failed` (not merely non-live); rules out terminalizing a stage whose linked entry run is genuinely still live (reachable on base via `restart sweep leaves a deferred stage whose entry run is still live untouched` and `pipeline-stage-dispatch.test.ts` `non-success settlement declines to terminalize a still-live entry run`).
- Restart/resume tests drive `wait` through `rollupWorkflowRunStatus` over seeded sibling step-run rows (same contract as existing restart-sweep fixtures); rules out trusting the entry row's `status` field in isolation.
- A no-marker `running` row whose linked entry run rollup is `completed` is never redriven by the unsettled predicate; rules out mis-settling the completed wedge `20260825T220908Z-daemon-start-reconciles-deferred-pipeline-settlement` deliberately left untouched.
