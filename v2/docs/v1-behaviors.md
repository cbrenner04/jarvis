# v1 behavior catalog for v2 parity review

This document inventories user-observable v1 behavior so v2 can explicitly preserve, change, or drop each item.

## Overview and scope

- This catalog describes behavior as shipped today under `v1/`, with v1 invoked via `jarvis1` in CLI usage and help text. Sources: `v1/src/cli.ts`
- The `jarvis1` rename has landed, so this file intentionally records the renamed `jarvis1` behavior as the migration baseline for v2 review. Sources: `v1/src/cli.ts`, `v1/spec/completed/2026-05-22T04-09-01Z-v1-behavior-catalog/00-skeleton-commands-and-project-resolution.md`
- Source files under `v1/src/` are treated as authority for behavior; docs are used to cross-check operator workflow expectations and terminology. Sources: `v1/src/cli.ts`, `v1/docs/run-loop.md`, `v1/docs/spec-guidance.md`
- Behavior entries in this catalog stay as short bullets ending with `Sources:` citations; `[uncertain]` is reserved for cases where source evidence cannot support a stronger claim. Sources: `v1/spec/completed/2026-05-22T04-09-01Z-v1-behavior-catalog/00-skeleton-commands-and-project-resolution.md`

## Commands and modes

### Command surface

- The shipped top-level subcommands are `run`, `init`, `config`, `log-server`, `cleanup`, `triage`, `review-feedback`, `plan`, `intent`, `prompt`, `prices`, and `help` (including `-h`/`--help` aliases to help output). Sources: `v1/src/cli.ts`
- Every subcommand recognizes `--help` and `-h` flags and prints command-specific help text, then exits 0 without running the command or forwarding the flag downstream. For pass-through commands (`prompt`, `prices`), the `--help`/`-h` flag takes precedence over prompt text or prices subcommand, never forwarded as data. Commands without dedicated help usage strings fall back to the global usage. Sources: `v1/src/cli.ts`
- Unknown subcommands exit non-zero and print usage, while parse-time argument errors also print usage with a command-specific error prefix. Sources: `v1/src/cli.ts`
- `review-feedback` requires a non-empty `<worktree-name>` and exits with usage when omitted, while `triage` accepts an optional worktree argument and otherwise runs a no-arg listing mode. Sources: `v1/src/cli.ts`, `v1/src/commands/triage.ts`
- `prices` is a two-operation command surface (`show` and `edit`) rather than one flat action, and missing/unknown prices subcommands print command-specific usage. Sources: `v1/src/commands/prices.ts`, `v1/src/commands/prices-show.ts`, `v1/src/commands/prices-edit.ts`
- `cleanup` exposes a `--dry-run` mode and requires execution from inside a registered project or it exits with a targeted registration error. Sources: `v1/src/cli.ts`, `v1/src/commands/cleanup.ts`

### Patch-mode run workflow

- `jarvis1 run` accepts `--max-iterations`, `--repo`, `--cwd`, and `--resume-review` around a required `<spec-path>`, then forwards those into run-mode options after validating numeric bounds for max iterations. `--resume-review` re-enters the post-completion review phase on an already-complete spec and enforces four preflight guards: review enabled (`modes.review.passes > 0`), effective `git: true`, implementation PR/remote branch exists, and spec has zero unchecked tasks; guard failures exit `1` with distinct error messages before agent spawn. Sources: `v1/src/cli.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- Default implementation runs are index-routed: the harness selects one unchecked linked subspec per agent iteration via `getActiveLinkedSubspecPath` and injects that subspec's path and body into the implementation prompt; agents execute the injected subspec rather than routing from `index.md`. Sources: `v1/src/modes/patch/completion.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/prompt.ts`, `prompts/patch/instructions.md`, `prompts/patch/rules.md`, `v1/docs/spec-guidance.md`, `v1/docs/run-loop.md`
- Non-index spec runs are blocked at preflight and never reach the agent loop: the harness prints a prompt offering to switch to a sibling `./index.md` (if one exists) or exit; the default/empty answer exits with code `0`. Sources: `v1/src/modes/patch/run.ts` (`resolveModeSpecificPreflight`)

### Patch-mode transient transport error retry

- Transient transport errors (connection reset, broken pipe, HTTP 502/503/504, etc.) are retried transparently within `runAgent` (`src/agents/spawn.ts`) at the spawn layer before callers see a result. Detection is via `isTransientSignal` (`src/agents/quota.ts`) on non-zero exits only (`exitCode === 0` always returns false). Retries are bounded to a fixed cap of **3 re-attempts (4 total spawns)** with escalating backoff (`[1s, 2s, 4s]` delay before re-attempts 1/2/3) and no agent advancement. If all attempts fail, the final error is returned as `kind: "error"` for normal mode-layer fallback/termination handling. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/quota.ts`, `v1/docs/quota-signals.md`, `v1/docs/agent-cli-failure-pipeline.md`
- An aborted invocation (timeout via `opts.signal`, iteration timeout, run timeout, or SIGINT) is never retried; the abort result is returned immediately. Per-iteration timeouts (idle, iteration, run) accrue across all retry attempts; the whole-iteration budget is not reset between spawns. Sources: `v1/src/agents/spawn.ts`
- Each transient re-attempt fires an optional `onTransientRetry` callback (added to `AgentRunOptions`) allowing modes to emit operator-facing diagnostics. Patch wires it to emit `transient transport error (exit N); retrying same agent (attempt A/CAP)` via harness stderr for operator visibility; this phrase shares no substring with quota strings (`quota exhausted; falling back` / `probable quota-like error`). Sources: `src/quota-harness-messages.ts` (`harnessTransientRetryLine`), `v1/src/modes/patch/iteration.ts` (`onTransientRetry` callback), `v1/src/agents/spawn.ts`
- Patch's `onSpawned` callback is made re-entry-safe for retry scenarios: any prior `descendantPollHandle` interval is cleared before assigning the new one (preventing leaked intervals on dead pids), and `watchdogPgid` is repointed to the live child. Sources: `v1/src/modes/patch/iteration.ts`

### Patch-mode review phase

- After implementation is complete (zero unchecked boxes) and `git: true`, a post-completion review phase runs when `modes.review.passes` is greater than 0 (default 1). The phase is skipped when `git: false`, `passes: 0`, or the run completed no implementation iterations. When review will run, the implementation-completion path defers PR readiness to the review phase (it does not `gh pr ready` early). Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- `jarvis1 run --resume-review <spec-path>` re-enters the post-completion review phase on an already-complete spec. Four preflight guards enforce: review enabled (exit 1), effective `git: true` (exit 1), remote branch existence (exit 1), and zero unchecked tasks (exit 1); each guard prints a distinct message. Execution uses the same review-phase path as normal completion, bypassing `implementationIterations > 0` gate only for review entry. Shrink phase is skipped. All review outcomes are preserved: baseline/final gate failure, blocker (exit 7), quota exhaustion (exit 2), idempotent ready PR. `--max-iterations` is accepted but has no behavioral effect (no implementation iterations run). Sources: `v1/src/cli.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- Plan and patch review share one v1 review runner (`v1/src/modes/review/`) with mode-specific adapters. Review agents resolve from `modes.review.agentOrder ?? modes.plan.agentOrder` (independent of `modes.patch.agentOrder`), while the review actuator and shrink agent resolve from `modes.patch.agentOrder`. Pass counts resolve via `resolveReviewPasses(cfg, --review-passes)`. This separation enables model tiering: operators assign faster/cheaper models to read-only review roles while keeping implementation-grade models on code-writing actuators. Tiering is operator guidance layered over the existing order-resolution structure; no new runtime selection logic was added. Sources: `v1/src/modes/review/run.ts`, `v1/src/modes/patch/review.ts`, `v1/src/modes/plan/review.ts`, `v1/src/config.ts`, `v1/docs/agents.md`, `v1/docs/config.md`
- Review phase flow is: baseline `bun run ready` (install → check:fix:unsafe → typecheck → test → check) → N debate cycles, each cycle = three read-only reviewer attempts (adversary → advocate → adjudicator, using registered role prompts) + injected actuator writing code from the verdict (using patch agent order). Reviewer prompts carry the completed spec tree plus a branch change summary (stat and changed paths via `BRANCH_DIFF`, not a full unified branch diff). Reviewer attempts are read-only on code; code edits are reverted after each reviewer role. Actuator is the only writer of code. Completed spec-tree edits are reverted for all roles including actuator; `verdict-patch.md` is preserved as the durable review verdict artifact. Non-empty changes are committed per role (`review: adversary`, `review: advocate`, `review: adjudicator`, `review: actuator`) and per actuator invocation; empty verdict produces no actuator commit. Prior cycle verdicts are passed as context to the next cycle's adversary. Sources: `v1/src/modes/review/run.ts`, `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/prompt.ts`, `v1/docs/run-loop.md`
- Verdict is a durable doc (`verdict-patch.md`) next to the executed spec, overwritten each cycle with the adjudicator's outcome-focused requirements (what must be true and why, not implementation details). Verdict is self-contained (actuator reads only the verdict, not prior role artifacts). Empty verdict (no content or whitespace-only) skips actuator invocation and produces no actuator commit via existing no-change path. Sources: `v1/src/modes/patch/review.ts`, `v1/src/modes/review/run.ts`
- Role-specific prompts are registered under `prompts/patch/review-*.md` (adversary, advocate, adjudicator) with self-contained verdict instructions; `BRANCH_DIFF` is a branch change summary, not a unified diff. Actuator uses the standard patch `patch.prompt.body` template adapted to the verdict as the task. Sources: `prompts/patch/review-adversary.md`, `prompts/patch/review-advocate.md`, `prompts/patch/review-adjudicator.md`, `v1/src/modes/patch/prompt.ts`
- A review blocker is signalled by the agent writing a `.jarvis-review-blocker` file at the repo root (not a `## Blocker` spec edit, which would be reverted). It stops the phase and exits `7`, with the blocker content posted as a PR comment and the sentinel consumed so it is never committed. Sources: `v1/src/modes/patch/review.ts`
- Quota exhaustion during any review role attempt triggers fallback to the next configured review agent; if all agents are exhausted, the cycle exits `2`. `model_config` exits `3`. Actuator runs with patch agent order and also respects quota fallback. Sources: `v1/src/modes/review/run.ts`, `v1/src/modes/patch/review.ts`
- Telemetry records review pass invocations with `patch_phase: "review"` and role-specific iteration counts so they are distinguishable from implementation iterations and role progression is traceable in `~/.jarvis/runs.jsonl`. Actuator invocations are recorded with agent name from the patch agent order. When an actuator terminal error occurs before the actuator records its own telemetry, the shared review runner records the failure against the adjudicator attempt context so agent/model metadata remains present. The run summary shows review attempts separately from implementation attempts while preserving correct totals. Sources: `v1/src/telemetry.ts`, `v1/src/modes/review/run.ts`, `v1/src/modes/patch/review.ts`, `v1/src/run-summary.ts`
- Review passes and verdict-actuator invocations use the same `DescendantTracker` orphan reaping as patch mode: track on spawn + interval, take a final snapshot after stopping the interval and before reap, then reap in each invocation's `finally`. The patch tracker is idle during review; overlap would be benign anyway because tracking is per-PID and identity-guarded. Reap failures are swallowed and never affect review outcome or exit code. Sources: `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/reap.ts`, `v1/docs/run-loop.md#orphan-process-reaping`

### Patch-mode completion `ready` gate

- After implementation is complete (zero unchecked boxes) and `git: true`, a completion-stage `ready` gate runs before shrink and review phases when at least one implementation iteration completed. The gate always runs the **`full`** tier harness-side via `runReadyAndCommit` (zero agent tokens), committing any `check:fix:unsafe` output. The gate is skipped when `git: false` or when no implementation iterations ran. Sources: `v1/src/modes/patch/run.ts`, `v1/src/ready-gate.ts`, `v1/docs/run-loop.md`
- On completion gate green: check:fix:unsafe output (if any) is committed, and the harness records a green result keyed to (1) HEAD sha (read via `git rev-parse HEAD` after the gate returns, capturing the post-commit state if `check:fix:unsafe` landed a commit) and (2) clean worktree verification. The run then proceeds to shrink → review (when configured) → `maybeMarkReady`. This completion gate is reached at most once per run (in `tryFinishSpecIfDone`, which early-returns whenever unchecked boxes remain). Sources: `v1/src/modes/patch/run.ts`, `v1/src/ready-gate.ts`
- Post-completion gates share `selectReadyTier(recordedGreen)`: when HEAD and porcelain match the recorded green carrier, shrink pre-gate, review baseline, and `maybeMarkReady` (completion-transition and per-iteration early-ready sites) each invoke `runReadyAndCommit` with **`fast`**; when the tree changed or no green was recorded, they use **`full`** and refresh the carrier on green. Review final **skips** `runReadyAndCommit` when the predicate holds (completion already ran **`full`**); otherwise runs **`full`** before `gh pr ready`. On the common path (green completion, no-op shrink, review makes no commits), exactly one **`full`** ready runs total. **`--resume-review`** has no in-run carrier: review baseline and final each use **`full`**. Sources: `v1/src/ready-gate.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/pr.ts`, `v1/docs/run-loop.md`
- Ready gate test-step serial retry: when the `bun run test` step fails with a genuine process exit code (not signal-derived or timeout), the gate runs the test suite serially (`bun test` without `--parallel`) exactly once before declaring the test step failed. If the serial run passes, the gate treats the test step as green and continues to remaining commands; if the serial run fails, the gate exits with the serial failure code. Non-test steps (`install`, `check:fix:unsafe`, `typecheck`, `check`) exit immediately on failure with no serial retry. Signal exits (SIGINT/SIGTERM, codes 130/143) and timeout exits (code 124) do not trigger serial retry — only genuine test-process failures do. This mirrors operator manual recovery from parallel-load flakes. Serial re-run accounts within the gate's deadline: if it exceeds the remaining budget, it is killed and the gate exits non-zero (fail-closed). Sources: `scripts/ready.ts` (`runReady`, `isGenuineTestFailure`, `isTestStep`), `v1/test/ready-script.test.ts`
- Blocker-validation suite-run serial retry: the base-ref test runner (`runBaseRefTests`, `v1/src/modes/patch/base-ref-test-runner.ts`) and snapshot-update retest runner (`runSnapshotUpdateRetest`, `v1/src/modes/patch/snapshot-update-retest-runner.ts`) each apply test-invocation-only serial retry on suite failure (non-zero `bun run test` exit), mirroring the ready gate's recovery pattern. When the parallel invocation exits non-zero, each runner re-runs `bun test` (no `--parallel`, same discovery, no path/filter args) exactly once in the same execution context (base-ref in the throwaway worktree before cleanup; snapshot in the agent working dir). If the serial run passes, the test is treated as green; if the serial run fails, the runner returns non-green. Non-test steps (git setup in base-ref, update-snapshots command in snapshot runner) exit immediately on failure with no serial retry. Each runner emits three stderr lines on parallel failure: a retry-starting line, a recovered line on parallel-red → serial-green, and a serial-still-failed line on parallel-red → serial-red. Runners accept an optional `runCommandFn` injectable parameter for test-invocation seaming (default: execFileSync). Sources: `v1/src/modes/patch/base-ref-test-runner.ts`, `v1/src/modes/patch/snapshot-update-retest-runner.ts`, `v1/test/base-ref-test-runner.test.ts`, `v1/test/snapshot-update-retest-runner.test.ts`
- Agent guidance serial retry (mid-work): `prompts/patch/rules.md` instructs agents, when `bun run test` fails during implementation iterations, to re-run the suite once serially (`bun test` without `--parallel`) before treating the failure as real or appending a `## Blocker`. Only a serially-reproducing failure grounds a blocker or stops the run; single parallel-load flakes are treated as non-deterministic noise and are recovered from without blocking. This mirrors the ready gate and blocker-validation harness-side serial retry, extending operator-like recovery logic to agent-executed test invocations mid-work. Guidance also instructs agents to skip `bun run test` when the iteration changed nothing under tested paths (no source files, test files, prompt fragments, or fixtures — only human-facing prose), avoiding flake exposure on docs-only subspecs with zero signal. Sources: `prompts/patch/rules.md` (revision 5), `v1/src/modes/patch/prompt.ts`, `v1/docs/spec-guidance.md`
- On completion gate red: the gate captures failure text and handles it per the loop-back completion behavior (specs `01-red-loopback-iteration.md` and `02-stuck-red-stop.md`); no green result is recorded. Shrink and review phases do not run on red; the run is handed off to loop-back logic. Sources: `v1/src/modes/patch/run.ts`

### Patch-mode fix-up iterations (red→green loop-back)

- When the completion `ready` gate fails (red), the harness launches a **fix-up iteration**: one agent invocation that receives the captured failure text prepended to the normal patch prompt. The agent sees both the `ready` failure and the completed spec, and can attempt root-cause fixes. Sources: `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/completion.ts`, `v1/docs/run-loop.md`
- Fix-up trigger: completion gate returns red; `CompletionLoopbackSignal` is set with the captured failure text. The fix-up iteration is invoked using `buildFixupPrompt()` which merges the failure text with normal patch rules.
- Fix-up post-iteration checks (in priority order): **blocker detection** (if any linked subspec gained a `## Blocker` section during fix-up, the run commits work, logs the blocker text to stderr, and exits 7); **spec completion** (if the spec still has unchecked boxes, fix-up counts as a regular implementation iteration and the main loop resumes); **completion retry** (if the spec remains complete, the completion gate is retried; if green, normal completion continues; if red, the loop repeats up to `maxIterations` limit). Sources: `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/completion.ts`
- Fix-up iterations do not include granular acceptance-criteria tracking because the spec is already complete. Any work is committed with `newlyChecked: []` and `checkedTotal: 0` in telemetry. Sources: `v1/src/modes/patch/run.ts`
- Fix-up iterations appear in run summary `implementation-iteration` counts. Exit code `7` (blocker detected during fix-up) takes precedence over exit code `5` (max iterations exhausted). Sources: `v1/src/modes/patch/run.ts`, `v1/src/run-summary.ts`

### Patch-mode stuck-red completion stop (exit 10)

- After each fix-up iteration, the completion gate is retried. The harness stops with exit code `10` (`ready-stuck-red`) — a recoverable stop indicating the issue persists and manual intervention is likely needed — in two scenarios: **(1) identical-failure stop**: the captured failure text is unchanged after normalization, no new work was ticked, and no new blocker was added; **(2) changing-failure bound**: the ready gate has returned red for N (3) consecutive fix-up iterations with no acceptance-criteria progress, and the failure text differs between iterations. Unchanged is determined by normalizing away known non-deterministic content: absolute worktree paths, durations/timings (e.g. `1234ms`, `12:34:56`), wall-clock dates, and deadline/timeout messaging. Sources: `v1/src/modes/patch/completion-pipeline.ts`, `v1/docs/run-loop.md`
- **Identical-failure stop**: The stuck-red stop fires when: (1) completion gate returns red, (2) captured failure text is unchanged post-normalization, (3) no new work was ticked (unchecked count is still 0), (4) no new blocker was added. The harness outputs "unchanged" language indicating the failure persists identically. Exit reason is `ready-stuck-red`. The harness outputs the captured `bun run ready failed:` text and a `jarvis1 triage <worktree-name>` pointer for operator recovery. Telemetry includes a record with `exitReason: "ready-stuck-red"`. Sources: `v1/src/modes/patch/completion-pipeline.ts:212-231`, `v1/docs/run-loop.md`
- **Changing-failure bound**: When the ready gate stays red across N consecutive fix-up iterations with no acceptance-criteria progress and the failure text differs each iteration (e.g., churning linter errors, flaky tests failing different ways), the harness stops with exit `10` rather than riding `maxIterations`. The harness outputs distinct language noting the gate stayed red for N iterations with no AC progress and the failure differed each pass. Reset semantics: the counter resets to 0 on a green gate or when acceptance-criteria progress is detected on the regular implementation path (via the `acProgressSinceLastGate` flag). N is fixed at 3, allowing 2 genuine fix-up attempts before the bound fires. Sources: `v1/src/modes/patch/completion-pipeline.ts:234-264`, `v1/src/modes/patch/iteration.ts:836-853`, `v1/docs/run-loop.md`
- If failure text differs after normalization between fix-up iterations (e.g. different line numbers, different test output) and is under the N-iteration bound, the loop continues; noise-only differences (timings, paths) are normalized away so they do not extend the loop. The comparison function `isReadyFailureUnchanged()` applies `normalizeReadyFailureText()` to both the previous and current failure texts before comparing equality. Sources: `v1/src/modes/patch/completion-pipeline.ts`, `v1/docs/run-loop.md`
- The review baseline gate's red→exit-1 path (`review.ts:583`) is now unreachable on the completion path because the completion gate ensures `ready` is green before shrink/review run. The review baseline gate remains in place as an unreachable backstop for non-completion paths. Sources: `v1/src/modes/patch/review.ts`, `v1/src/modes/patch/completion-pipeline.ts`

### Patch-mode post-completion shrink

- After implementation is complete (zero unchecked boxes), a clean worktree, and `git: true`, one shrink agent invocation runs when the run completed at least one implementation iteration and `modes.patch.shrink` is not configured to `"off"`. Shrink is skipped when `git: false`, when no implementation iterations ran, or when `modes.patch.shrink` is set to `"off"`. When shrink or review will run, per-subspec completion defers `maybeMarkReady` to the post-completion phases. Order: shrink (if enabled) → review (when configured) → `maybeMarkReady`. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- Shrink flow: pre-shrink gate uses `selectReadyTier` — **`fast`** when HEAD and porcelain match the recorded green carrier, **`full`** otherwise (refresh on green; failure logs warning, skips shrink) → one agent invocation with `patch.prompt.shrink` + `global.terse` (not `patch.rules`) → post-invocation spec-tree revert, out-of-scope revert, then detect surviving file changes. When no surviving changes remain, the phase exits early without contract validation and produces no commit. When changes survive, contract validation requires `bun run test` pass, no deleted scoped `*.test.ts`, no AC checkbox regression (a criterion checked pre-shrink must remain checked); contract miss or unsuccessful invocation discards all shrink changes without elevating run exit code. Single `shrink:` commit with attribution and PR footer refresh is produced only when changes survive contract validation. Sources: `v1/src/modes/patch/shrink.ts`, `v1/src/ready-gate.ts`, `prompts/patch/shrink.md`
- The `modes.patch.shrink` config field (string enum `"off" | "agent"`, default `"agent"`) controls whether the shrink phase runs. `"agent"` keeps the existing agent-shrink behavior; `"off"` skips the entire phase (no pre-shrink gate fires, no telemetry row is emitted). Invalid values fail config validation with a named error naming the field. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- Shrink scope is the accumulated set of non-spec paths touched during implementation iterations; edits outside that set are reverted post-invocation. Prompt carries a branch change summary for orientation, run-scoped unified diff (allowlisted files only in `RUN_SCOPED_DIFF`), and an explicit allowlist — never a full-branch unified diff. Sources: `v1/src/modes/patch/shrink.ts`, `v1/src/modes/patch/prompt.ts`, `prompts/patch/shrink.md`
- Telemetry records shrink with `patch_phase: "shrink"`; shrink is excluded from `patchIterationsCompletedForSummary` and run-summary `isImplementationAttempt` counts (like review). Sources: `v1/src/telemetry.ts`, `v1/src/modes/patch/run.ts`, `v1/src/run-summary.ts`

### Git and loop-only runs

- Effective `git` resolves per-run from the top-level `git` flag overlaid by the resolved project's `projects.<key>.git` override; `--repo`/`--cwd` and ad-hoc resolution all funnel through the same effective value. Sources: `v1/src/config.ts` (`effectiveGit`), `v1/src/modes/patch/run.ts`
- When effective `git` is `false`, patch mode runs "loop-only": no worktree is created, the agent's `cwd` is the resolved project root (or `--cwd <dir>` when supplied), and no per-subspec commit, push, draft-PR open, or ready-on-complete occurs. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- In loop-only mode completion is purely "zero unchecked boxes": the clean-tree requirement and exit `6` do not apply, and `worktreeSymlinks` is ignored. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- `--cwd <dir>` is only valid when effective `git` is `false` and must point at an existing directory; combining it with `git: true` exits `1`, and a missing `--cwd` directory exits `1`. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- With `git: true`, a resolved root that is not a `.git` checkout exits `1` before any agent runs, with guidance to set `"git": false` or pass `--repo` to a git checkout. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`

### Plan mode

- `jarvis1 plan` is a separate mode entrypoint with its own parser, usage text, and handler; `--help` exits `0` with plan-specific usage while parse errors (unknown flags, missing values, too many args, combining `--resume` + `--resume-draft`) exit `1` with targeted `plan:` messages. Sources: `v1/src/cli.ts`, `v1/src/commands/plan.ts`, `v1/src/commands/plan-args.ts`
- Plan-mode flag surface is `--review-passes`, `--repo`, `--cwd`, `--target-dir`, and `--resume`, with non-negative integer validation for review-pass counts. `--resume-draft` is still parsed but rejected with guidance (use `jarvis1 intent` then `jarvis1 plan <ready-intent>` for fresh work, or `--resume <index.md>` for post-draft review). The intent/refine phases — and the `--refine-turns` flag — were retired with the ready-intent flow; plan starts at draft and resume runs review passes only. Sources: `v1/src/cli.ts`, `v1/src/commands/plan.ts`, `v1/src/commands/plan-args.ts`
- The single positional argument is always a file path. Fresh runs require an existing ready-intent file (a non-existent path fails with operator guidance; there is no inline-text fallback). In `--resume` mode it is treated as a spec path (which need not exist relative to cwd, since the spec lives in the plan worktree). Sources: `v1/src/commands/plan-args.ts`
- `--resume` requires a path ending in `index.md` and derives plan identity from the parent spec directory basename (with timestamp prefix stripping for plan branch/worktree naming). Sources: `v1/src/commands/plan.ts`
- Fresh plan mode requires a ready-intent. The single positional argument must be an existing file under `<targetDir>/ready-intents/` with matching frontmatter `name:` and a `## Prerequisites` section; inline text, raw seeds, `wip-intents/` paths, and missing files are rejected with guidance to use `jarvis1 intent` first. Sources: `v1/src/commands/plan.ts`, `v1/src/commands/plan-args.ts`, `v1/docs/plan-mode.md`
- Fresh plan input is copied byte-for-byte to the generated spec directory as `intent.md`; with `commit: true`, the source ready-intent is deleted from the worktree after the draft phase succeeds and the write-boundary check passes (before the `plan: draft` commit is created) so the deletion is staged into the `plan: draft` commit, but deletion is skipped when the derived target is absent from the worktree base or resolves outside the worktree after path/symlink resolution; with `commit: false`, the source ready-intent is left untouched since the worktree is the live checkout and there is no spec PR to carry the deletion. Plan derives `<plan-name>` from the ready-intent frontmatter `name:`. Invalid `name:` or missing `## Prerequisites` fail before creating any branch/worktree/spec output. Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`
- Draft and review prompts both forbid self-referential deliverables: acceptance criteria must verify target state outside the active spec directory (code/tests/docs/operator behavior/generated evidence), so criteria that only grade active-spec prose are invalid even without saying "the spec." Sources: `prompts/plan/draft.md`, `prompts/plan/review-*.md`, `prompts/plan/review-actuator.md`
- Plan-mode spec authoring expects behavioral acceptance criteria for product specs: observable outcomes, not mandated files/modules/tables/shapes unless structure is the contract; harness subspecs may name internal structure when it is the contract. Draft and live review prompts (`plan.prompt.draft`, `plan.prompt.review.adversary`, `plan.prompt.review-actuator`) enforce the rule; `v1/docs/spec-guidance.md` is the durable operator doc. Sources: `prompts/plan/draft.md`, `prompts/plan/review-adversary.md`, `prompts/plan/review-actuator.md`, `v1/docs/spec-guidance.md`
- Fresh plan flows start at draft: jarvis runs draft and review (with optional `--review-passes`, default from `modes.review.passes`) in the same invocation for `commit: false`, or opens/updates the draft PR after `plan: draft` completion for `commit: true`, then continues through review and ready transition. Effective `git: false` forces the `commit: false` path even when `modes.plan.commit` or `projects.<key>.plan.commit` is `true`. Ready-intent `## Prerequisites` are validated and enforced in the draft phase (before spec generation): the draft agent reads the target repo and confirms each prerequisite is observable in committed code, tests, or docs; if all are confirmed, drafting proceeds; if any prerequisite cannot be cleanly confirmed, the agent appends a `## Blocker` to `intent.md`, writes no spec files, and plan exits non-zero; empty or bareword-`none` prerequisites skip the gate. If the draft succeeds, prerequisites become context for the generated spec and subsequent review passes. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`, `v1/docs/plan-mode.md`, `prompts/plan/draft.md`
- Draft behavior requires index generation plus numbered subspecs and treats blocker insertion in `intent.md` as a valid stop state; otherwise missing `index.md` or missing numbered subspecs fail validation. Sources: `v1/src/modes/plan/draft.ts`, `prompts/plan/draft.md`
- Draft validation order: blocker (if any) → index.md existence → numbered subspecs presence → per-subspec structural validation. Blocker check runs first so prerequisite gate failures short-circuit subsequent checks within `validateDraftOutput`. Per-subspec structural checks run after index/subspecs-existence validation and validate each generated `NN-*.md` against: heading exactness (near-miss acceptance/blocker headings fail), duplicate canonical sections (duplicate `## Acceptance criteria` or `## Blocker` headings fail), missing/empty acceptance section (zero parseable criteria under exact `## Acceptance criteria` heading fails), structural ACs (location/existence predicates produce non-blocking stderr warnings), and behavioral/preservation-AC anchor grounding (ACs containing preservation/continuation trigger verbs without test or source anchors produce non-blocking stderr warnings). Anchor-grounding trigger verbs are `preserved`, `unchanged`, `stays`, `remains`, `stops`, `continues` (case-insensitive, whole-word). Anchors are path-like references: a `*.test.ts` filename/path or a backtick span containing a path separator or source-file extension. Plain backtick spans without path shape do not count as anchors. Structural validation and anchor grounding run only at draft time; resume `plan: review N rM` passes do not re-validate subspecs. The `shared/spec-parser.ts` change is additive — duplicate detection, structural-AC classification, and anchor-grounding checks added as categorized warnings; first-occurrence ticking behavior preserved (patch-mode parsing unchanged). Sources: `v1/src/modes/plan/draft.ts`, `shared/spec-parser.ts`
- Review behavior snapshots current spec markdown into prompt context, forbids `intent.md` rewrites except blocker append, validates `index.md` still exists, and can skip committing when no changes were produced. Plan review routes through the shared review runner in `v1/src/modes/review/` with a plan adapter; review agents resolve from `modes.review.agentOrder ?? modes.plan.agentOrder` and cycle counts from `resolveReviewPasses(cfg, --review-passes)` (`modes.review.passes`, default `1`, where each cycle runs adversary → advocate → adjudicator → actuator). Plan reviewers (adversary/advocate/adjudicator) are read-only on the spec; any spec edits during reviewer roles are reverted by the harness. Per-role artifacts are stored as temporary files and injected into successor roles (e.g., adversary findings → advocate, advocate response → adjudicator). The adjudicator's verdict drives one review-actuator prompt invocation that receives `intent.md`, the generated spec files, spec guidance, and the verdict, then applies the verdict to `index.md`/subspec files under the existing plan write boundary; the actuator also rejects non-blocker `intent.md` rewrites. Verdict is persisted as `verdict-plan.md` in the spec folder, overwritten each cycle. Per-role commits are emitted with messages `review: <role>` for reviewer roles and `review: actuator` for the actuator. Empty verdicts skip actuator invocation and do not create an actuator commit. Sources: `v1/src/modes/plan/review.ts`, `v1/src/modes/review/run.ts`, `prompts/plan/review-*.md`, `prompts/plan/review-actuator.md`, `v1/src/commands/plan.ts`, `v1/src/config.ts`
- Plan prompts are intentionally data-delimited with sentinel delimiters (e.g., `<<<INTENT_BEGIN>>>`, `<<<INTENT_END>>>`) so intent/spec text is treated as content, not executable instructions. Template rendering is non-recursive: placeholders in the template source are substituted exactly once, and literal placeholder-looking text in injected values (e.g., `<SPEC_GUIDANCE>` appearing in intent) is preserved as data without recursive substitution. This allows spec-governance and prompt-documentation content to reference exact placeholder names. Sources: `v1/src/modes/plan/template-renderer.ts`, `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`, `v1/src/modes/plan/verdict-actuator.ts`, `v1/src/commands/plan.ts`
- Plan uses `modes.plan.agentOrder` and per-attempt quota classification like patch mode, but its fallback stderr is explicitly prefixed per agent as `plan: <agent>: <quota-fallback-line>` for phase-level diagnostics. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/emit-plan-quota-stderr.ts`, `v1/src/quota-harness-messages.ts`
- Plan exit semantics include `0` on successful completion, `2` on all-agents quota exhaustion, `3` on model configuration errors, `130` on SIGINT checkpoints, and `1` on blockers/validation/hard failures; completion may still print usage summary output when telemetry has agent attempts. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`
- Resume invocations track prior plan commit history to continue numbering (`plan: review <N>`) and append `r<n>` resume suffixes to resumed review/blocker commit subjects for later attribution and chronology. Effective `git: false` forces resume onto the external-spec/no-commit path instead of requiring `.worktree/plan-<name>` or `plan/<name>`. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/commits.ts`
- Plan `commit: true` mode creates a dedicated `plan/<name>` branch and `.worktree/plan-<name>` worktree (under the final name directly — no temporary-name rename), opens/updates a draft PR after the first `plan: draft` commit, rewrites PR header/footer on each plan commit, and attempts auto-ready transition only when an open PR is still draft. `ensureDraftPr` scopes to the current branch's open PR only (closed/unrelated PRs are not reused). Sources: `v1/src/commands/plan.ts`, `v1/src/worktree.ts`, `v1/src/modes/plan/pr.ts`, `v1/src/pr.ts`
- Plan `commit: true` automatic pre-commit failure cleanup: when a plan fails **before** the first `plan: draft` commit (draft agent errors, validation failures, draft-phase exceptions, or draft-commit failures), jarvis automatically removes the associated `.worktree/plan-<name>` directory and `plan/<name>` branch. Cleanup is local-only; a surviving remote `origin/plan/<name>` branch is expected when the failure occurs after push but before the draft commit succeeds. Resumable failure states are preserved: boundary blockers (where a `plan: blocker` commit exists) and draft/review-phase blockers (where `plan: draft` and draft PR exist) keep their worktrees and branches intact for `--resume`. SIGINT before the draft commit also preserves the worktree/branch for deliberate restart. Cleanup is gated to `commit: true`; `commit: false` runs reuse `project.root` with no plan worktree/branch, so cleanup never runs there. Sources: `v1/src/modes/plan/run.ts` (error-return paths with cleanup invocations), `v1/docs/plan-mode.md`
- On committed `--resume`/`--resume-draft`, if `.worktree/plan-<name>` is missing, jarvis best-effort fetches and auto-recreates it from local `plan/<name>` or `origin/plan/<name>` (logging recreate source), but it still enforces the later `origin` presence check and still fails with the original missing-worktree error when neither local nor remote branch exists. Sources: `v1/src/commands/plan.ts`, `v1/src/worktree.ts`
- Plan `commit: false` mode writes spec output to Jarvis-owned external spec roots and emits absolute-path next-step commands for later `jarvis1 run` execution instead of creating git commits, pushes, or PR transitions. Effective `git: false` is treated the same way: no plan worktree, branch, push, PR, or revert path. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/spec-paths.ts`, `v1/docs/plan-mode.md`
- On fresh `git: false` plan runs, name-collision checks come only from the external spec root; existing repo `spec/…`, `.worktree/plan-…`, and `plan/…` branch names do not rename the external spec. In git-disabled review, reviewer temp artifacts and reviewer-edit cleanup also stay in the external spec directory and avoid repo `git` cleanup calls. Sources: `v1/src/modes/plan/run.ts`, `v1/src/modes/plan/review.ts`, `v1/docs/plan-mode.md`
- Plan `commit: false` mode prints `Intent: <absolute-path-to-intent.md>` to stdout immediately after the external `intent.md` is written and before any later draft or review phase can fail. This ensures the operator retains the external intent artifact path even if a later phase fails. Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`
- Plan mode enforces a write boundary before each draft/review commit: agent writes must stay within the active spec directory (and, for `commit: false`, the external spec root). On a boundary violation, commit-mode plans revert the offending paths, append a boundary `## Blocker`, commit a `plan: blocker`, and exit `1`; no-commit plans append the blocker and exit `1` without reverting. In no-commit mode with effective `git: false`, the target-repo `git status` boundary probe is skipped; only the external spec-root boundary remains. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/boundary.ts`
- Plan `commit: false` mode preserves the named external spec directory and its `intent.md` on all later-phase failures (draft/review generic error, quota, model config, validation, boundary violation, blocker, interrupt): failure output prints a `Spec preserved at` breadcrumb naming the directory path so operators can inspect the artifact. The only exception is pre-`intent.md` write failure — in that case the abandoned spec directory is removed and no breadcrumb is printed (the operator has not yet received an `Intent:` path). Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`

### Intent mode

- `jarvis1 intent` is a separate mode entrypoint with its own parser, usage text, and handler; `--help` exits `0` with intent-specific usage while parse errors print targeted `intent:` messages. Sources: `v1/src/cli.ts`, `v1/src/commands/intent.ts`
- Intent mode supports both committed and no-commit routing based on `modes.plan.commit`. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- Fresh intent mode requires exactly one seed. The positional argument is treated as a file only when the path exists; otherwise it is treated as inline text. File seeds must live under `<targetDir>/wip-intents/`. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- Intent mode uses the same plan-root resolution as plan mode. Committed runs write authored intents to `<targetDir>/ready-intents/` in the target repo; no-commit runs write to an external Jarvis-managed directory `~/.jarvis/specs/<project-safe-id>/ready-intents/`. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- Running intent mode splits one seed into N behavior-level intents, writes only `<name>.md` files under `ready-intents/`, and enforces (with deterministic repair) matching `name:` frontmatter and a `## Prerequisites` section in each file: missing or mismatched `name:` is rewritten to the filename slug; missing `## Prerequisites` is appended as an empty section; malformed `## Prerequisites` bodies (non-bullet text) remain hard errors. Non-empty prerequisites are required to be one bullet line per prerequisite behavior. Never writes spec `index.md` files or numbered subspecs. Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`
- A single-behavior seed is valid and still runs the full flow, emitting exactly one authored intent. Sources: `v1/src/commands/intent.ts`, `v1/test/intent-command.test.ts`
- Intent-name collisions are hard errors: if `<targetDir>/ready-intents/<name>.md` (committed) or external `ready-intents/<name>.md` (no-commit) already exists, the run aborts without overwriting files and without opening a PR. Sources: `v1/src/commands/intent.ts`, `v1/test/intent-command.test.ts`
- Splitter output is staged, mechanically repaired (`name:` frontmatter and `## Prerequisites`), and validated before move/commit. Structural errors (bad filenames, duplicates, malformed prerequisites, no files) abort without partial `ready-intents/` writes or a PR. Sources: `v1/src/commands/intent.ts`, `v1/src/modes/plan/intent-split.ts`, `v1/test/intent-command.test.ts`
- Intent mode reuses the plan agent order and quota-fallback rules for the splitter step; quota exhaustion falls through to the next configured agent and terminal exhaustion exits with the shared all-agents-exhausted wording. Sources: `v1/src/commands/intent.ts`, `v1/src/modes/plan/intent-split.ts`, `v1/test/intent-command.test.ts`
- The raw seed in `wip-intents/` is left in place after fan-out. Sources: `v1/src/commands/intent.ts`, `v1/test/intent-command.test.ts`
- **Committed mode (`commit: true`):** Successful runs create a dedicated `intent/<name>` branch and `.worktree/intent-<name>` worktree, commit the `ready-intents/` split, and open or update a draft PR for operator review before any later `jarvis1 plan` runs. Sources: `v1/src/commands/intent.ts`, `v1/src/worktree.ts`, `v1/src/pr.ts`, `v1/docs/intent-mode.md`
- **No-commit mode (`commit: false`):** Successful runs write authored intents to the external Jarvis-owned directory, skip worktree/branch/commit/push/PR operations, and print absolute-path `jarvis1 plan --repo <project> <path>` next-step commands for each emitted intent. The splitter runs with `--add-dir` access to a temporary external staging directory. This mode enables intent splitting in isolated setups (non-git project roots or `git: false` configurations). Fallback to cursor/opencode agents writes no files and fails validation since they do not honor `--add-dir` (inherited `--add-dir` limitation; fix out of scope). Sources: `v1/src/commands/intent.ts`, `v1/docs/intent-mode.md`, `v1/test/intent-command.test.ts`

### Plan-mode flow matrix

Which phases actually run in a single invocation depends on the entry mode and the resolved `commit` flag. This consolidates the prose bullets above. Fresh plan flows require a ready-intent (`<targetDir>/ready-intents/<name>.md`) and skip intent authoring phases entirely:

| Entry mode | `commit` | Phases that run in one invocation | Stop / handoff |
| --- | --- | --- | --- |
| ready-intent (file arg) | `true` | copy `intent.md` -> draft -> `plan: draft` -> review -> PR handoff | exits `0`; operator merges PR then runs `jarvis1 run` on the generated spec |
| ready-intent (file arg) | `false` | copy `intent.md` -> draft -> review (into external spec root) | exits `0`; prints `jarvis1 run <indexPath>` next step |

Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`, `v1/docs/plan-mode.md`

- `--resume-draft` is rejected with guidance to use `jarvis1 plan <ready-intent>` for fresh work or `jarvis1 plan --resume <index.md>` for post-draft review. Sources: `v1/src/commands/plan.ts`
- `commit: true` plans run under a `plan/<name>` branch and `.worktree/plan-<name>` worktree where `<name>` is derived from the ready-intent frontmatter `name:`. Sources: `v1/src/commands/plan.ts`, `v1/docs/plan-mode.md`

### Prompt mode

- `jarvis1 prompt` is a single-pass one-shot agent invocation mode controlled by a required `<text>` positional argument and an optional `--repo` flag; `--cwd` is explicitly rejected as an error (prompt mode requires git). Sources: `v1/src/cli.ts`, `v1/src/modes/prompt/run.ts`
- Prompt-mode preflight gates include: `git: true` requirement (exit `1`), project registration (exit `1`), and GitHub CLI auth (`gh auth status`, exit `1`). Sources: `v1/src/modes/prompt/run.ts`
- Prompt mode uses `modes.prompt.agentOrder` for agent iteration; if `modes.prompt` is not defined in config, it defaults to a structuredClone of `modes.patch.agentOrder` at load time. Sources: `v1/src/config.ts`, `v1/src/modes/prompt/run.ts`
- Worktree creation names follow pattern `.worktree/<timestamp>-prompt-<nonce>/` on branch `<timestamp>-prompt-<nonce>` (UTC ISO8601 timestamp, 6-character random nonce suffix); the worktree is always created in the project root. Sources: `v1/src/modes/prompt/run.ts` (`iso8601DateTime`, `generateNonce`, `createPromptWorktree`)
- Prompt mode is strictly single-pass with per-agent fallback: agents are tried in `modes.prompt.agentOrder` order; `quota` and `model_config` advance to the next agent, generic `error` and timeout halt immediately, and iteration stops on success or chain exhaustion. Exit 2 only when every attempted agent returned quota; exit 3 when a non-quota fallthrough ended the chain without success. Weak-quota upgrades are always allowed (no progress gate). Sources: `v1/src/modes/prompt/run.ts`
- Prompt output handling differs by diff state: if the agent run produces no git diffs (`git status --porcelain` is empty), the agent's stdout is printed to the operator and the run exits `0` without any git/PR operations. If diffs exist, the prompt text is committed and a PR opened. Sources: `v1/src/modes/prompt/run.ts`
- When diffs exist, prompt mode commits with subject = first non-empty line of prompt text (ellipsized to ~72 chars), body = full prompt text + `Jarvis-Agent: <label>` trailer, then pushes and opens a draft PR with the prompt text as body + attribution footer. Sources: `v1/src/modes/prompt/run.ts`
- Prompt PR body is static (operator input only in the PR title/description): `<prompt-text>\n\n---\n\n🤖 Generated with [Claude Code](https://claude.com/claude-code)`. Sources: `v1/src/modes/prompt/run.ts`
- Prompt telemetry is written with namespace `<project-key>:prompt` (matching patch mode's `<project-key>:run` and plan mode's plan naming), mode field `"prompt"`, and one terminal row per command (intermediate fallback attempts are stderr-only). Terminal exit reasons include `success`, `all-agents-quota`, `agent-failure`, `watchdog-iteration-timeout`, and others matching patch-mode taxonomy. Chain exhaustion without success (mixed `model_config`/`quota`, all-`model_config`, or generic error) records `telemetryKind: "error"` and `exitReason: "agent-failure"`; all-quota exhaustion records `telemetryKind: "quota"` and `exitReason: "all-agents-quota"`. Sources: `v1/src/modes/prompt/run.ts` (`appendTelemetryLine`)
- Prompt mode exit codes mirror patch mode: `0` success, `1` error, `2` quota exhausted, `3` agent/model hard failure, `8` timeout, `9` worktree lock busy. Sources: `v1/src/modes/prompt/run.ts`
- Prompt mode always acquires and releases `.jarvis.lock` for the created worktree (failing with exit `9` if the lock is held by a live process), matching patch-mode lock semantics. Sources: `v1/src/modes/prompt/run.ts`, `v1/src/worktree-lock.ts`
- Prompt-mode invocations use the same `DescendantTracker` orphan reaping per fallback attempt: each attempt gets its own tracker, polls on spawn + interval while the agent runs, takes a final snapshot before reap, and reaps in that attempt's `finally`. Reap failures are swallowed and never affect the prompt exit code or reason. Sources: `v1/src/modes/prompt/run.ts`, `v1/src/modes/patch/reap.ts`, `v1/docs/run-loop.md`

## Spec authoring and implementation workflows

- New implementation specs are expected to be authored as index-routed trees (`index.md` + numbered subspec files) with checklist links from index into atomic subspec documents. Sources: `v1/docs/spec-guidance.md`
- The documented workflow requires spec-first sequencing: create a spec PR, merge spec files to `main`, and only then start implementation runs against that merged spec. Sources: `v1/docs/spec-guidance.md`
- `jarvis1 plan` can generate spec trees, but generated specs follow the same merge-first rule before `jarvis1 run` implementation work begins. Sources: `v1/docs/spec-guidance.md`, `v1/docs/workflows.md`
- External plan output (`modes.plan.commit: false`) produces Jarvis-owned spec trees written to a configured external spec root directory (not inside the target repo) with a required `repo:` binding so later `jarvis1 run` invocations can resolve the target checkout. Sources: `v1/src/modes/plan/spec-paths.ts`, `v1/docs/spec-guidance.md`, `v1/docs/config.md`
- For v2 phase-led execution (`v2/spec/v2-meta-index.md`), operator input should be a build brief sourced from the chosen phase line and matching `v2/docs/v2-build-order.md` section; `jarvis1 plan` is the drafting step, `jarvis1 run` is the implementation step, and phase completion is merged `v2/src` code rather than generated intent/spec artifacts. Sources: `v2/spec/v2-meta-index.md`, `v2/docs/v2-build-order.md`, `v1/docs/spec-guidance.md`

## Config and project resolution

### Config storage and bootstrap

- Jarvis stores state under `~/.jarvis/` with `config.json`, and configuration is auto-bootstrapped on first run rather than requiring manual initialization. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- The config defaults to schema version 2 with mode-specific agent order blocks (`modes.patch.agentOrder` and `modes.plan.agentOrder`) and project registry storage under `projects`. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- The config exposes behavior knobs beyond agent order (quota policy, timeouts, log server, telemetry, git toggle, worktree symlinks); see the [Configuration field reference](#configuration-field-reference) below for the full enumeration and defaults. Sources: `v1/src/config.ts`, `v1/docs/config.md`
- Each registered project may declare `siblings`: absolute paths passed to the agent as additional readable directories alongside the spec. Patch preflight errors with exit `1` if a configured sibling does not exist. Sources: `v1/src/config.ts`, `v1/src/modes/patch/run.ts`
- Invalid config structure is rejected with file-specific validation errors instead of partial best-effort reads. Sources: `v1/src/config.ts`
- `jarvis1 init` only registers repos under `~/Work` by deriving the project key from the path relative to that root, and it records `origin` only when `git remote get-url origin` yields a non-empty value. Re-registering the same name+root is idempotent; the same name pointing at a different root errors. Sources: `v1/src/commands/init.ts`, `v1/src/config.ts`

### Repository resolution order and matching

- Target-repo resolution order is `--repo` first, then spec `repo:` value, then spec-path-inside-registered-project, then ad-hoc parent walk for a `.git` checkout root, then unresolved prompt/error signaling. Sources: `v1/src/resolve-project.ts`, `v1/src/repo.ts`, `v1/docs/run-loop.md`
- For both `--repo` and non-absolute `repo:` values, matching first checks exact registered project key and then loose URL/slug equivalence via normalized `host/owner/repo` comparison. Sources: `v1/src/resolve-project.ts`, `v1/src/repo-url.ts`
- Legacy absolute-path `repo:` values are honored only as exact matches to a registered project root; non-matching absolute paths fall through to location-based resolution. Sources: `v1/src/resolve-project.ts`, `v1/docs/spec-guidance.md`, `v1/docs/run-loop.md`
- URL normalization intentionally lowercases host/owner/repo, strips protocol/user/trailing `.git`, interprets bare `owner/repo` as GitHub, and drops extra URL path segments when comparing loose matches. Sources: `v1/src/repo-url.ts`

### Ambiguity handling and operator prompts

- Multiple registered matches for `--repo` or spec `repo:` produce an explicit ambiguous result with candidate set rather than picking one silently. Sources: `v1/src/resolve-project.ts`
- In interactive mode, disambiguation prompts let operators choose by 1-based index or exact project key, with `q`/blank treated as cancellation. Sources: `v1/src/disambiguation-prompt.ts`
- In non-TTY mode, disambiguation does not prompt and instead emits candidates plus a rerun hint using `--repo <name>`. Sources: `v1/src/disambiguation-prompt.ts`

## Agent adapters, model selection, and quota fallback

### Roster and default order

- v1 recognizes exactly five adapter names (`claude`, `codex`, `cursor`, `opencode`, `aider`) and `createAgent()` instantiates the matching adapter class directly from that name/model pair. Sources: `v1/src/agents/types.ts`, `v1/src/agents/factory.ts`
- Default `modes.patch.agentOrder` and `modes.plan.agentOrder` include only three entries in this order: `claude` (`haiku`), `codex` (`gpt-5.4`), then `cursor` (`Composer 2.5`); `opencode` and `aider` are supported but opt-in via config edits. Sources: `v1/src/config.ts`, `v1/docs/agents.md`
- [v2 divergence] v1's combined `{agent, model}` per-mode `agentOrder` is intentionally **not** carried forward to v2. v2 splits the two axes: a per-machine **agent fallback order** (just agents) and a separate machine-independent **category→agent→model store** (categories: thinking/reviewing/executing), with a step naming a category and the model resolving per agent. No v1 migration — v1 keeps the combined order. Sources: `v2/docs/v2-architecture.md` (per-project config), `v2/docs/v2-vision.md` (Models separate from agents)
- Both patch and plan modes execute agents in their configured order and advance only when an agent result is classified as quota-related; if the active agent returns a non-quota hard error, the mode stops instead of trying later agents. Sources: `v1/src/modes/patch/run.ts`, `v1/src/commands/plan.ts`, `v1/src/agents/quota.ts`

### Adapter-specific behavior

- `claude` runs `claude -p --permission-mode acceptEdits --output-format json`, pipes the prompt on stdin, forwards `--add-dir` entries, and parses JSON response fields into displayed text, usage, and cost when present. On exit `0`, it first checks stdout for a verified quota error envelope (`is_error: true`, `api_error_status: 429`, quota message in `result`); when matched, it returns `kind: "quota"` with the full stdout JSON preserved in `stderr` diagnostics instead of parsing success fields. Sources: `v1/src/agents/claude.ts`, `v1/src/agents/claude-json.ts`, `v1/docs/agents.md`
- `codex` runs `codex exec --color never --sandbox workspace-write -c approval_policy="on-request"` with stdin prompt piping, appends a per-invocation marker to the prompt, and derives usage by correlating changed `~/.codex/sessions/*.jsonl` files; ambiguous or missing correlation is reported as unavailable instead of guessed. Codex `input_tokens` is normalized to fresh-only (cached-input subtracted) before costing to match the disjoint-bucket convention that `computeCost` assumes. Sources: `v1/src/agents/codex.ts`, `v1/src/agents/codex-session.ts`, `v1/docs/agents.md`
- `cursor` runs `cursor agent -p --output-format text --force --workspace <cwd> <prompt>`, and successful runs estimate token usage from prompt+stdout rather than CLI-reported counters. Sources: `v1/src/agents/cursor.ts`, `v1/src/agents/cursor-tokens.ts`, `v1/docs/agents.md`
- `opencode` runs `opencode run --dir <cwd> --model <provider/model> --format json <prompt>`, parses JSONL event output, uses summed `step_finish` token/cost fields when present, and falls back to estimator warnings when no clean `step_finish` data exists. Sources: `v1/src/agents/opencode.ts`, `v1/src/agents/token-estimation.ts`, `v1/docs/agents.md`
- `aider` runs with non-interactive flags including `--yes-always`, `--no-auto-commits`, `--no-git`, and `--no-show-model-warnings`, sets `BROWSER=false` in subprocess env, and always uses token estimation (or unavailable usage when estimation fails). Sources: `v1/src/agents/aider.ts`, `v1/src/agents/token-estimation.ts`, `v1/docs/aider-model-warnings.md`

### Model and pricing visibility

- Each configured agent entry carries its own model string, and each adapter emits attribution labels as either known friendly names, raw model strings, or `<agent> (default model)` when no explicit model is configured. Sources: `v1/src/config.ts`, `v1/src/agents/claude.ts`, `v1/src/agents/codex.ts`, `v1/src/agents/cursor.ts`, `v1/src/agents/opencode.ts`, `v1/src/agents/aider.ts`
- Pricing support is adapter-specific: Claude/Codex/Cursor/Opencode report `agentHasPricedModels=true` while Aider reports `false`; price-key resolution is delegated per adapter and may return `null` for unsupported/unpriced model values. Sources: `v1/src/agents/price-keys.ts`, `v1/src/agents/claude.ts`, `v1/src/agents/codex.ts`, `v1/src/agents/cursor.ts`, `v1/src/agents/opencode.ts`, `v1/src/agents/aider.ts`
- Exact usage/cost visibility is mixed by adapter: Claude and Opencode can return agent-sourced usage/cost, Codex computes cost from correlated session usage plus local price table, Cursor/Aider primarily produce estimated usage, and any estimator/session-correlation miss is surfaced via `usage_source: "unavailable"` plus warnings. Sources: `v1/src/agents/types.ts`, `v1/src/agents/claude.ts`, `v1/src/agents/codex.ts`, `v1/src/agents/cursor.ts`, `v1/src/agents/opencode.ts`, `v1/src/agents/aider.ts`, `v1/src/agents/codex-session.ts`
- Patch-mode harness emits one-time operator stderr notices when successful Cursor or Opencode runs still have unavailable usage (`token usage not available for this CLI version`) and forwards adapter warnings with `<agent>: <warning>` prefix. Sources: `v1/src/modes/patch/run.ts`

### Quota detection and fallback semantics

- Spawn classification order is model-configuration first, then strict quota pattern matching, then generic error; only non-zero exits can classify as quota/model-config at the shared spawn layer. The Claude adapter may reclassify exit-`0` stdout JSON into `kind: "quota"` before accepting `ok`. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/quota.ts`, `v1/src/agents/claude.ts`, `v1/src/agents/claude-json.ts`
- Quota and model-configuration classification is regex-driven per adapter, with shared base model-config patterns and extra adapter-specific additions for Opencode/Aider provider-local failures. Sources: `v1/src/agents/quota.ts`, `v1/docs/quota-signals.md`
- `quotaFallback: "lenient"` can upgrade `kind: "error"` into `kind: "quota"` only when the caller-provided guard allows it; patch mode passes that guard only for no-progress iterations, preventing weak quota upgrades after observable repo progress. Sources: `v1/src/agents/quota.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/quota-signals.md`
- Quota rotation and exhaustion stderr strings are shared constants: strict fallback uses `quota exhausted; falling back`, lenient upgraded fallback uses `probable quota-like error (exit N); falling back`, and terminal exhaustion uses `all agents quota-exhausted` (plan prefixes with `plan:` and may append phase suffixes). Sources: `v1/src/quota-harness-messages.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/plan/emit-plan-quota-stderr.ts`, `v1/src/commands/plan.ts`, `v1/docs/quota-signals.md`

### Patch invocation architecture

- Patch mode's per-iteration loop retains its own advancement semantics (head agent per iteration, with fallback on quota exhaustion). Starting with the shared-binding migration, patch now uses separable v1-owned binding methods for spawn and classification, distinct from the plan binding's coupled `invoke` method.
- The patch binding factory (`createPatchInvocationBinding`) exposes `spawn` and `classify` methods. `spawn` runs the agent with watchdog integration (onSpawned, lastOutputAtMs, abortKillGraceMs). `classify` applies quota fallback with a caller-supplied guard thunk (computed after the iteration body completes).
- The patch iteration loop calls `binding.spawn()` to run the agent, then executes the iteration body (checking acceptance criteria, detecting file edits, etc.), then calls `binding.classify(result, noIterationProgress)` with a guard computed from the iteration results.
- Patch keeps its own iteration-driven loop and does not use the shared executor (`executeWithQuotaFallback`). Its per-iteration telemetry, stderr messages (quota fallback and exhaustion), and exit codes remain unchanged.
- The separable spawn/classify seam exists to serve paths (review, shrink) that need custom logic between spawn and classification; patch is the primary consumer driving that separation. Sources: `v1/src/modes/patch/patch-invocation-binding.ts`, `v1/src/modes/patch/run.ts`, `v1/docs/agents.md`

### Abort and process lifecycle

- All adapters execute via a shared spawn wrapper that launches the CLI in a detached process group, normalizes env with `PWD=<agent cwd>` and no `OLDPWD`, and buffers stdout/stderr until stream close + process close before final classification. Sources: `v1/src/agents/spawn.ts`, `v1/docs/agents.md`
- Patch-mode Ctrl-C handling aborts the current iteration controller and surfaces `interrupted`; agent subprocess abort handling then sends `SIGTERM` to the process group first and escalates to `SIGKILL` after a grace timeout. Sources: `v1/src/modes/patch/run.ts`, `v1/src/agents/spawn.ts`
- Aborted agent runs resolve as `kind: "error"` with `exitCode: -1` and `stderr` prefixed `aborted: <reason>`, so aborts are operator-visible as explicit harness-side failures rather than silent termination. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/types.ts`
- Patch mode enforces two timeouts that both surface as exit `8`: a per-iteration timeout (`iterationTimeoutMs`, default 30 minutes) and an optional whole-run timeout (`runTimeoutMs`). On iteration timeout a watchdog `SIGTERM`s the agent process group and escalates to `SIGKILL` after a grace period (5s), in addition to aborting the iteration controller; telemetry distinguishes `watchdog-iteration-timeout` from `iteration-timeout` and records the watchdog pgid plus stall diagnostics (`last_output_age_ms`, `watchdog_descendants_alive`) snapshotted at watchdog fire. Sources: `v1/src/modes/patch/run.ts`, `v1/src/agents/spawn.ts`
- An optional idle-output watchdog (`idleOutputTimeoutMs`, unset by default) aborts the iteration if the agent produces no stdout/stderr for the configured span, resetting the bound on every output chunk. Whichever timeout fires first (idle or wall-clock) aborts the iteration. Idle abort returns exit `8` with `exitReason: "watchdog-idle-timeout"` (distinct from `watchdog-iteration-timeout`) and **is not classified as quota**, so no agent fallback is triggered. Idle abort behavior mirrors wall-clock timeout: when pgid is known, a `[watchdog]` line is logged and the process group is killed; when pgid is unavailable, telemetry still records `last_output_age_ms` but omits `watchdog_pgid` and `watchdog_descendants_alive`. Sources: `v1/src/modes/patch/run.ts`, `v1/docs/run-loop.md`
- On normal agent completion with exit code `0` and no abort reason, the harness best-effort reaps in-group stragglers via `process.kill(-pgid, "SIGKILL")` from a `child.on("exit")` handler. **Deadlock rationale**: the reap runs on `exit` rather than on the close branch because `close` fires only after stdout/stderr stream teardown; a straggler that inherited the agent's stdio pipes holds them open indefinitely, preventing teardown and causing settlement (which waits for stream end) to deadlock. The `exit` event fires independent of pipe state, so killing the group closes inherited pipes and allows settlement to proceed. The reap is non-fatal: a kill error (including `ESRCH` on a clean close where the agent left no descendant) is swallowed and does not affect the settled result kind or exit code. Reaping is POSIX-only (it relies on `-pgid` for process-group targeting). Only in-group descendants are targeted; a process that left the agent's group (e.g., started its own session) is out of scope and is not killed. Reaping does not run when `code !== 0`, on the error-settle, quota, model-config, or `child.on("error")` paths; abort and timeout paths have their own group-kill logic. Sources: `v1/src/agents/spawn.ts`, `v1/docs/run-loop.md`
- Agent descendants that leave the agent's process group (e.g. via `POSIX::setsid()`) and re-parent to init (PPID=1) escape the in-group straggler reap above. macOS does not expose process environments to an unprivileged `ps`, so Jarvis tracks these orphans by PID instead of an env marker: while an agent runs, it samples the process table on a fixed interval and records every descendant PID (transitive `ppid`, plus processes sharing the agent's `pgid`), capturing escapees while their lineage is intact. At iteration end (settle, abort, timeout) and at finalize (SIGINT and direct `process.exit`) it SIGKILLs recorded descendants that are still alive, skipping any PID whose start time (`lstart`) changed to avoid killing a recycled PID, and never the harness's own process. Reaping is best-effort and non-fatal; it reads only `pid`/`ppid`/`pgid`/start time, so no process environments or arguments are logged or stored. Sources: `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/reap.ts`, `v1/docs/run-loop.md#orphan-process-reaping`

## Git/GitHub behavior

### Worktrees and locks

- Patch runs derive the worktree directory and branch name from the parent directory name of the resolved spec path, and create/reuse `.worktree/<spec-name>` plus branch `<spec-name>` (including recreating a missing local branch from `origin/<spec-name>` when available). Sources: `v1/src/worktree.ts`
- If `jarvis1 run` is invoked from inside a checkout already on branch `<spec-name>`, worktree creation is skipped and the current checkout is reused as the agent working directory. Sources: `v1/src/worktree.ts`
- New patch branches are based on `gh repo view --json defaultBranchRef` (via `getBaseBranch`), while failures to `git fetch origin` are tolerated and do not stop worktree setup. Sources: `v1/src/worktree.ts`, `v1/src/gh.ts`
- Plan mode uses a separate namespace: `.worktree/plan-<name>` on branch `plan/<name>`, with an explicit hard error when the plan worktree path already exists. Sources: `v1/src/worktree.ts`
- `review-feedback` auto-materializes a missing `.worktree/<worktree-name>` when `git: true`, creating the worktree from `origin/<worktree-name>` if remote-only or from the existing local branch otherwise; if neither exists it errors `no local or remote branch named <name>; cannot create worktree`. With `git: false` the legacy `unknown worktree "<name>"` error is preserved. Plan worktrees (`plan-*`) are rejected before this check. Sources: `v1/src/commands/review-feedback.ts`, `v1/src/worktree.ts`
- Patch and review-feedback flows serialize per-worktree execution with `.jarvis.lock`; if an existing lock PID is still alive, the command exits with code `9` and stderr `worktree is in use by process <pid> (started at <timestamp>)`. Sources: `v1/src/worktree-lock.ts`, `v1/src/modes/patch/run.ts`, `v1/src/commands/review-feedback.ts`
- Stale lock recovery is automatic: when a lock file exists but its PID is dead, jarvis replaces the lock with the current process and records a harness log line about recovering a stale lock. Sources: `v1/src/worktree-lock.ts`, `v1/src/modes/patch/run.ts`
- `.jarvis.lock` exclusion is enforced best-effort through worktree-local `info/exclude` so normal `git add -A` commit paths do not stage lock files. Sources: `v1/src/worktree-lock.ts`
- Patch-mode run teardown always attempts to release `.jarvis.lock` for the active worktree once preflight marked it as acquired. Sources: `v1/src/modes/patch/run.ts`, `v1/src/worktree-lock.ts`

### Branches and commits

- Patch subspec completion commits are created by jarvis (not agent git automation) with subject equal to subspec H1, body first line `Spec: <relative subspec path>`, and embedded `## Acceptance criteria` section body copied from the subspec file. Sources: `v1/src/modes/patch/subspec.ts`
- Completing a subspec also flips the corresponding linked checklist entry in that subspec directory's `index.md` from `[ ]` to `[x]` before commit creation. Sources: `v1/src/modes/patch/subspec.ts`
- Progress and blocker iterations are committed as `WIP:` subjects with `Spec: <relative subspec path>` in the body, and blocker variants append a `## Blocker` section in commit message content. Sources: `v1/src/modes/patch/subspec.ts`
- All harness-authored commit shapes append `Jarvis-Agent: <label>` trailer when the agent label is non-empty; empty labels omit the trailer line entirely. Sources: `v1/src/commit-trailer.ts`, `v1/src/modes/patch/subspec.ts`, `v1/src/modes/patch/pr.ts`
- Push behavior is two-phase: first branch push uses `git push -u origin <current-branch>` and later pushes use plain `git push` once upstream tracking exists. Sources: `v1/src/worktree.ts`, `v1/src/modes/patch/run.ts`

### PR and GitHub CLI mediation

- GitHub connectivity/auth is preflight-gated through `gh auth status`; failures stop patch and review-feedback flows with surfaced stderr guidance rather than continuing without GitHub operations. Sources: `v1/src/gh.ts`, `v1/src/modes/patch/run.ts`, `v1/src/commands/review-feedback.ts`
- Base-branch discovery for new worktree branches is mediated by `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` and errors are surfaced as `failed to detect base branch: ...`. Sources: `v1/src/gh.ts`, `v1/src/worktree.ts`
- Draft PR creation is gh-mediated and idempotent per open branch PR: `gh pr view` filters to `OPEN` only, and `gh pr create --draft --base <base> --head <branch> --title <title> --body <body>` is called only when no open PR exists. Sources: `v1/src/pr.ts`
- Closed/merged PRs on the same branch are intentionally ignored by existence checks, so branch reuse can open a new draft PR instead of binding to historical PR state. Sources: `v1/src/pr.ts`
- Transient git/gh network errors are retried transparently within the `runGhCommand` chokepoint (`src/gh.ts`) — used for `gh auth status`, `gh repo view`, `gh pr comment`, and review-feedback calls — before callers see a result. Detection is via `isTransientNetworkError` (`src/agents/quota.ts`) on non-zero exits only (`exitCode === 0` always returns false). Retries are bounded to a fixed cap of **2 re-attempts (3 total invocations)** with a **1-second backoff** between attempts (network transients benefit from brief pause). The classifier matches `sharedTransportPatterns` (agent-spawn errors like connection reset, 502/503/504) ∪ harness-scoped git/gh phrasings (`TLS handshake timeout`, `could not resolve host`, `timed out`, `SSL_ERROR`, `the remote end hung up unexpectedly`). Sleep is injectable for tests. Permanent gh failures (not-authenticated, 404, branch-protection `BLOCKED`) do not match any pattern and fast-fail with exactly one invocation. Each re-attempt emits `OP: transient network error; retrying (attempt A/CAP)` to stderr by default (defaults to `process.stderr.write()` when no override is provided), operator-distinguishable from quota strings and the agent transient line; the callback is injectable for tests. Sources: `v1/src/gh.ts`, `v1/src/agents/quota.ts`, `v1/src/quota-harness-messages.ts`, `v1/docs/quota-signals.md`
- Transient errors on sync `git push` and direct `gh pr ready` shell-outs are also retried with the same classifier and policy as `runGhCommand` but via sync `withSyncTransientRetry` wrapper. `git push` is invoked via `pushCurrent` (`v1/src/worktree.ts`); `gh pr ready` is invoked directly in four sites (`v1/src/modes/patch/pr.ts`, `v1/src/modes/plan/pr.ts`, and two sites in `v1/src/modes/patch/review.ts`). Error classification uses the error's captured `stderr` buffer with exitCode = `.status ?? -1` (so thrown errors never read as exit 0). Transient-classified errors retry up to the same cap (2 re-attempts, 3 total attempts) with **1-second backoff**; permanent failures fast-fail after exactly one attempt. `gh pr ready` has an additional success guard: if a retry fails with stderr matching "already ready" or "not a draft", the failure is treated as success (lost-ack case where the PR was already flipped before the ack timed out). The error message from permanent failures is preserved so caller try/catch behavior is unchanged. Each re-attempt emits `OP: transient network error; retrying (attempt A/CAP)` to stderr by default (defaults to `process.stderr.write()` when no override is provided), with the callback injectable for tests via `onRetry`. Sleep is injectable for tests via a `sleepSync` seam. Sources: `v1/src/gh.ts`, `v1/src/worktree.ts`, `v1/src/modes/patch/pr.ts`, `v1/src/modes/plan/pr.ts`, `v1/src/modes/patch/review.ts`
- Shared PR narrative module: patch and plan modes both use a shared PR body generation and rewrite module (`v1/src/pr-shared.ts`) that consolidates sentinel extraction/validation, narrative marking, and rewrite logic previously duplicated across modes. The module supports two narrative modes via per-mode `prNarrative` config (`modes.patch.prNarrative`, `modes.plan.prNarrative`): `template` (default) builds narrative deterministically from spec index subspec titles and branch commits, while `agent` invokes the model. Both modes preserve human edits inside the narrative markers on rewrite. Sources: `v1/src/pr-shared.ts`, `v1/src/modes/patch/pr.ts`, `v1/src/modes/plan/pr.ts`
- Patch-mode draft PR creation (not just rewrite) now honors `prNarrative`: under `template`, the narrative is built from the spec index and commits deterministically; under `agent`, the mode invokes the agent to generate narrative with a short description followed by a `Decisions:` section, wrapped in literal `<<<PR_DESCRIPTION_BEGIN>>>` and `<<<PR_DESCRIPTION_END>>>` sentinels. The harness extracts only content between the sentinels; absent or malformed sentinels or extracted content lacking `Decisions:` yield no narrative. Sources: `v1/src/modes/patch/pr.ts`, `v1/src/modes/patch/run.ts`
- Patch mode rewrites the PR body once at completion (after the green completion ready gate, before shrink/review phases) via `gh pr edit <branch> --body-file -`, preserving any human-edited narrative inside the markers from draft creation. The draft PR is created on the first subspec completion with narrative determined by `prNarrative` config. The completion-time rewrite regenerates narrative: under `template`, from the spec index and commits; under `agent`, when empty and an agent is available (otherwise preserving prior machine-owned narrative as-is). Header and attribution footer are regenerated at completion-time rewrite. On failure, the rewrite is logged as a warning and does not abort the run. Sources: `v1/src/pr-shared.ts`, `v1/src/modes/patch/pr.ts`, `v1/src/modes/patch/run.ts`
- Plan-mode draft PR creation and body refresh honor `prNarrative`: under `template`, the narrative is built from the spec index and commits deterministically (does not require intent content); under `agent`, the mode invokes the head agent of `modes.plan.agentOrder` to author narrative with short description + `Decisions:` section, wrapped in `<<<PR_DESCRIPTION_BEGIN>>>` and `<<<PR_DESCRIPTION_END>>>` sentinels, extracted identically to patch mode. The draft creation path (`ensureDraftPr`) respects `prNarrative` the same as the rewrite path. Sources: `v1/src/pr-shared.ts`, `v1/src/modes/plan/pr.ts`, `v1/src/commands/plan.ts`
- Plan mode rewrites existing PR bodies via `gh pr edit`, preserving human-edited narrative inside the markers. Under `template`, the narrative is regenerated each rewrite from the spec index and commits, independent of intent content. Under `agent`, narrative regeneration occurs only when empty and an agent + intent content are available; on regeneration, the agent output is treated identically to draft creation (extract only content between sentinels; absent/malformed sentinels or missing `Decisions:` preserve prior machine-owned narrative as-is). Header (with `targetDir`-aware title and file pointers) and attribution footer are regenerated each rewrite. Sources: `v1/src/pr-shared.ts`, `v1/src/modes/plan/pr.ts`, `v1/src/commands/plan.ts`
- Patch-mode draft-to-ready transition requires an existing open PR. `maybeMarkReady` uses `selectReadyTier`: **`fast`** when HEAD and porcelain match the recorded green carrier, **`full`** otherwise (refresh on green), then `gh pr ready`. Review final skips ready on the same predicate and calls `gh pr ready` directly. Sources: `v1/src/modes/patch/pr.ts`, `v1/src/modes/patch/review.ts`, `v1/src/ready-gate.ts`, `v1/docs/run-loop.md`
- Plan-mode ready transition is PR-state aware: no-op when no open PR or already ready, and only draft PRs run `bun run ready` (committing any `check:fix:unsafe` output) followed by `gh pr ready <branch>`. Sources: `v1/src/modes/plan/pr.ts`, `v1/src/ready-gate.ts`

### Attribution and PR footer behavior

- Patch PR attribution is derived from `git log <base>..HEAD` and includes only commits whose first non-empty body line starts with `Spec:`, excluding commits without that prefix from per-commit attribution bullets. Sources: `v1/src/pr.ts`
- Per-commit attribution bullets render as `- <short sha> <subject> — <label>`, where missing trailers map to `unknown` and multiple `Jarvis-Agent` trailers are joined with `,`. Sources: `v1/src/pr.ts`
- Footer summary line is first-seen deduped (`Written by <Label A>, <Label B> through Jarvis.`) and omitted when no labelled commits exist; the entire footer is omitted when no qualifying subspec commits are present. Sources: `v1/src/pr.ts`
- Patch PR body rewrites preserve only content between `<!-- jarvis:narrative:start -->` and `<!-- jarvis:narrative:end -->`; header and footer are regenerated each rewrite and manual edits outside narrative markers are not sticky. Sources: `v1/src/pr.ts`, `v1/src/modes/patch/pr.ts`
- Plan PR body rewrites preserve only content between `<!-- jarvis:narrative:start -->` and `<!-- jarvis:narrative:end -->`; header and footer are regenerated each rewrite and manual edits outside narrative markers are not sticky. Plan mode mirrors patch mode's narrative preservation semantics. Sources: `v1/src/modes/plan/pr.ts`, `v1/src/commands/plan.ts`
- Plan-mode attribution collapses consecutive plan meta-commits into a single summary bullet, while subspec commits remain individually listed, and both still contribute to the deduped `Written by ... through Jarvis.` summary ordering by first appearance. Sources: `v1/src/modes/plan/pr.ts`
- Cross-reference: plan-mode collapsed attribution wording has a fixed label that can be lossy relative to grouped commit variants; see `## Behaviors with uncertain intent`. Sources: `v1/src/modes/plan/pr.ts`

## Filesystem, logging, telemetry, and other side effects

- `run` and `plan` both run a mandatory log-server reachability preflight (default `http://127.0.0.1:4310/logs`) after repo resolution and before agent work; failures print a specific `jarvis1: log server unreachable at <url>. Start it with \`jarvis1 log-server\` or update config.` banner plus error detail and exit `1`. (`run` runs this inside `runSharedPreflight`;`plan` runs it via `enterMode`/`runModeLogPreflight`.) Sources:`v1/src/modes/shared-entry.ts`,`v1/src/mode-entry.ts`,`v1/src/log-server-preflight.ts`

Sources: `v1/src/modes/patch/run.ts`, `v1/src/config.ts` (`openSessionLog`), `v1/src/commands/plan.ts`

## Completion, blockers, exit codes, and failure handling

### Patch mode

- Patch spec completion is checkbox-driven: parser counts unchecked GitHub-task items, and a spec with zero task items is malformed (`MalformedSpecError`) rather than complete. Sources: `v1/src/modes/patch/completion.ts`, `shared/spec-parser.ts`
- For index-routed runs, the harness resolves the active linked subspec with `getActiveLinkedSubspecPath`, inlines that subspec's full body between `<<<ACTIVE_SUBSPEC_*>>>` delimiters in the implementation prompt, and omits sibling subspec bodies, index checklist prose, and full spec-tree dumps; when no linked unchecked subspec exists, the active-subspec block is omitted and iteration logic falls back to top-level checklist progress only. Sources: `v1/src/modes/patch/completion.ts`, `v1/src/modes/patch/run.ts`, `v1/src/modes/patch/prompt.ts`, `prompts/patch/instructions.md`
- Implementation prompts preload bounded repo guidance from `AGENTS.md` and root `CLAUDE.md` under the registered target repo root (`project.root`), omitting each file silently when absent; the prompt does not instruct agents to discover repo guidance on their own. Sources: `v1/src/modes/patch/prompt.ts`, `v1/src/modes/patch/run.ts`, `prompts/patch/instructions.md`
- Review verdict actuator and completion fix-up iterations share migrated `patch.prompt.body` without repo-guidance or active-subspec blocks; the verdict or ready-failure preamble carries the task. Sources: `v1/src/modes/patch/prompt.ts`, `v1/src/modes/patch/run.ts`, `prompts/patch/instructions.md`
- If the active subspec has no exact `## Acceptance criteria` checklist items, patch run stops with exit `1` and prints parser-warning details when near-miss headings (wrong case/level) were detected. Sources: `v1/src/modes/patch/run.ts`, `shared/spec-parser.ts`
- Blocker detection is exact-header based (`## Blocker`): pre-existing blocker body causes immediate blocked exit `7`, and newly added blocker body during an iteration also exits `7` (with WIP blocker commit/push in git mode before exiting). Sources: `shared/spec-parser.ts`, `v1/src/modes/patch/run.ts`
- Blocker claim validation: when a newly added blocker body contains pre-existing-failure language (e.g., "pre-existing", "preexisting", "unrelated", "baseline", "not caused by", "not related to", "already fail"), the run validates the claim against the base ref before committing and exiting 7. If the base ref validates green (cited failures do not reproduce), the blocker is rejected: the `## Blocker` section is stripped from the subspec, a distinct rejection telemetry event is emitted, and the iteration loop continues (no exit 7, no blocker commit). Per-subspec rejection is bounded to 2 consecutive rejections; after the bound is hit, further matching claim blockers stand (exit 7) instead of re-validating. If the base ref validates red, validation fails, the seam is absent, or git is disabled, a secondary snapshot-update re-test gate runs in the agent worktree (only when not already rejected by base-ref and not past bound): update-snapshots pass followed by re-test; if re-test is green (failures were outdated snapshots), the blocker is rejected (stripped, `blocker-rejected` telemetry with `exitReason: "snapshot-churn"` emitted, updated snapshots left dirty for normal commit, loop continues); if re-test is red, seam absent/throws, or git disabled, the blocker stands (exit 7 as today). The base-ref test run is injected via an optional async seam (`opts.runBaseRefTests?: (baseRef: string) => Promise<boolean>`, true = green); the snapshot-update re-test runner is injected via an optional async seam (`opts.runSnapshotUpdateRetest?: () => Promise<boolean>`, true = green after update+retest). When no base-ref seam is provided, a default implementation runs the target `bun run test` in a throwaway git worktree detached at the local merge-base of the agent branch and its base branch (resolved locally from git config or defaulting to `main`), with serial-retry applied to the test invocation only: on non-zero parallel `bun run test` exit, the runner re-runs the test serially (`bun test` without `--parallel`) exactly once in the same throwaway worktree before cleanup; if the serial run passes, the base is treated as green; if the serial run fails or discovers zero test files, the base is treated as non-green (fail-safe). Non-test steps (git setup, merge-base resolution) exit immediately on failure with no serial re-run. The base-ref runner emits three stderr lines on parallel test failure: a retry-starting line, a recovered line on parallel-red → serial-green, and a serial-still-failed line on parallel-red → serial-red. The runner leaves the agent worktree untouched and removes the temporary worktree on every exit path (even if the test throws). When no snapshot seam is provided, fail-safe serial-retry is applied: on non-zero parallel re-test exit following a successful update, the runner re-runs the test serially (`bun test` without `--parallel`) exactly once in the agent working dir; if the serial run passes, the re-test is treated as green; if the serial run fails or discovers zero test files, the re-test is treated as non-green. Non-test steps (update-snapshots command failure) exit immediately with no serial re-run. The snapshot runner also emits three stderr lines on parallel re-test failure. The base-ref resolution uses `git merge-base` which is offline (no network calls), so validation works under `skipGhCheck`/offline conditions; the base branch name is resolved locally first (from git tracking config) before falling back to `"main"`. Sources: `shared/spec-parser.ts`, `v1/src/modes/patch/iteration.ts`, `v1/src/modes/patch/base-ref-test-runner.ts`, `v1/src/modes/patch/snapshot-update-retest-runner.ts`, `v1/src/modes/patch/run.ts`, `v1/src/telemetry.ts`
- Spec checklists can be complete while run still exits `6` when git worktree state blocks completion (dirty/unpushed state surfaced via `worktreeCompletionBlocker` guidance and `jarvis1 triage` hint). Sources: `v1/src/modes/patch/run.ts`, `v1/src/worktree.ts`
- Exit reasons are mapped from run codes in patch mode as: `0` criteria complete, `1` error, `2` quota exhausted, `3` agent/model hard failure, `4` no progress, `5` max iterations, `6` dirty worktree/completion blocker, `7` blocked, `8` timeout, `9` worktree lock busy, and `130` SIGINT. Sources: `v1/src/modes/patch/run.ts`
- The patch run summary's `exit reason:` line includes the numeric exit code alongside the reason word (e.g., `exit reason: quota-exhausted (exit code 2)`), composed at the `mapExitCodeToReason` call sites in `run.ts` when the exit code is available; the plan summary's `exit reason:` line is unchanged (no numeric code added). Sources: `v1/src/modes/patch/run.ts`, `v1/src/run-summary.ts`
- Exit `4` (no progress) on clean runs with a resolvable active subspec prints a diagnostic listing unticked acceptance criteria from that subspec to guide recovery; this diagnostic fires only on the clean-run-but-unticked path, not on other stop conditions such as dirty-worktree or model-config failures. The guidance message explains that ticking satisfied criteria and rerunning will complete the subspec. Top-level checklist runs with no linked subspec fall back to the generic no-progress message. Sources: `v1/src/modes/patch/run.ts`
- Agent-failure pipeline classifies non-zero exits in strict order (`model_config` before strict quota before generic error), merges stderr+stdout into diagnostics on errors, and only allows weak/lenient quota upgrades in mode-controlled no-progress contexts. Sources: `v1/src/agents/spawn.ts`, `v1/src/agents/quota.ts`, `v1/docs/agent-cli-failure-pipeline.md`, `v1/src/modes/patch/run.ts`
- Exit `6` (dirty worktree) on edited-but-unticked iterations now retries a bounded number of times: an agent iteration that edits files but checks no new acceptance criteria on the same active subspec triggers a loopback instead of immediate exit 6. The run loops back for up to 2 consecutive edited-but-unticked iterations on the same active subspec before exiting 6; if acceptance criteria progress occurs or the active subspec changes, the counter resets to 0. Retries consume normal iterations and count against `maxIterations`. Acceptance criteria ticked in the working tree but absent from committed HEAD are committed at iteration start as progress and re-evaluated for completion; this prevents deadlock when a prior run ticked criteria but stopped before committing. The harness never auto-ticks acceptance criteria; the retry only declines to give up after one turn. Sources: `v1/src/modes/patch/iteration.ts`, `v1/src/modes/patch/subspec.ts`
- Patch-mode fallback policy differs by error class: strict quota rotates to next configured agent, model-config fails fast with no fallback, and non-quota errors only rotate under lenient weak-quota rules; otherwise run exits `3`. Sources: `v1/src/modes/patch/run.ts`, `v1/src/agents/quota.ts`
- Patch rules require the agent to tick every confirmed-satisfied acceptance criterion as a mandatory final step of each iteration. When acceptance criteria are already left `- [ ]` on entry but their underlying work is already complete, the agent must re-verify and then tick; never report "already done" without ticking. This rule prevents silent no-progress exits when criteria remain unchecked despite completed work. Ticking stays restricted to genuinely-satisfied criteria (no speculative ticking), and the agent owns all tick decisions; the harness never auto-ticks acceptance criteria. Only the top-level `index.md` checkbox is auto-flipped by the harness when all acceptance criteria in a subspec are checked. Sources: `prompts/patch/rules.md`

### Plan mode completion

- Plan mode completion is spec-driven: the draft phase produces spec output, and the review phase validates that `index.md` exists and completion is signaled by zero review-pass changes or explicit blocker insertion in `intent.md`. Sources: `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`
- Plan exit semantics include `0` on successful completion, `2` on all-agents quota exhaustion, `3` on model configuration errors, `130` on SIGINT checkpoints, and `1` on blockers/validation/hard failures. Sources: `v1/src/commands/plan.ts`
- Plan mode blocker behavior: blocker insertion in `intent.md` during the draft or a review pass stops the run with exit `1`, and blocker content is preserved across phases. Sources: `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`
- With `commit: false`, the draft, review, and verdict-actuator phases run with write access to the external spec directory, allowing agents to write `index.md`/subspecs and append `## Blocker` sections to `intent.md`. Only claude and codex receive this access as `--add-dir` flags and honor it (`--permission-mode acceptEdits` and `--sandbox workspace-write` respectively); cursor and opencode never receive the directory; aider receives it as a positional argument but cannot write external files. Non-default `modes.plan.agentOrder` on cursor, opencode, or aider cannot write the external tree. Sources: `v1/src/commands/plan.ts`, `v1/src/modes/plan/draft.ts`, `v1/src/modes/plan/review.ts`, `v1/src/modes/plan/verdict-actuator.ts`, `v1/src/modes/review/run.ts`, `v1/docs/plan-mode.md`

## Test execution and development workflows

- Root package.json exposes runnable test commands: `test` (`bun test --parallel`, invoked as `bun run test`), `test:v1` (`bun test ./v1/`), `test:v2` (`bun test ./v2/`), and `test:shared` (`bun test ./shared/`). Each scoped slice targets its exact owner root with a trailing slash to prevent fuzzy substring filtering. Sources: `package.json`, `bunfig.toml`, `test/test-slices.test.ts`
- Patch-mode agent iterations and shrink contract validation use `bun run test` for the full-repo aggregate (same command as the ready gate's test phase). Scoped slices remain for targeted runs only. Sources: `AGENTS.md`, `v1/src/modes/patch/shrink.ts`, `scripts/ready.ts`
- The 30-second timeout for all test runs is inherited from `bunfig.toml` (`[test] timeout = 30000`) and applies to every slice invocation (aggregate, `test:v1`, `test:v2`, `test:shared`); no per-script `--timeout` flag is needed or added. Sources: `bunfig.toml`
- Test file ownership is enforced by disjoint-roots: v1 tests live under `v1/test/`, v2 tests co-locate next to v2 source under `v2/`, and shared-owned tests live under `shared/`. v1/v2 tests may import `shared/**` runtime code; this is coverage, not ownership violation. - Agent-spawn safety preload (`test/setup-fake-agents.ts`) is repo-wide infrastructure loaded globally via `bunfig.toml` preload for all test slice runs, preventing accidental real-agent-CLI spawns under any slice invocation. Sources: `bunfig.toml`, `test/setup-fake-agents.ts`
- `bun run ready` reaches the test phase via `bun run test` (the aggregate command) and does not use scoped slices; the ready pipeline order (install → check:fix:unsafe → typecheck → test → check) is enforced by regression tests. Sources: `scripts/ready.ts`, `v1/test/ready-script.test.ts`
- Test-only DI seams added during test suite determinism refactoring: `v2/src/write.ts` and `v2/src/write-loop.ts` accept optional `withExternalWorktree` parameters (test-only, default to real implementation) for dependency injection in unit tests.
