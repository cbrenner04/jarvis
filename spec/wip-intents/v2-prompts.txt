Decide how v2 should treat prompts as first-class implementation artifacts. This is a follow-on v2 architecture intent seeded from `v2-catalog.txt` and `v2-vision.md`'s "English is code" framing. It should land after the v1 behavior catalog, because the behavior catalog tells us what prompts currently *do*, while this intent decides how exact prompt text should be inventoried, reviewed, and carried forward.

Goal: produce a concrete prompt-governance design for v2, with enough detail that later v2 implementation specs know where prompts live, how prompt changes are reviewed, how prompt behavior is tested, and whether v1 shares, snapshots, or ignores the new prompt artifacts. The output is a design doc, not a broad prompt rewrite.

Why this matters:

- Jarvis behavior is heavily shaped by English instructions sent to agents.
- v1 has prompts split across Markdown templates, inline TypeScript string construction, injected rules, generated handoff text, and agent-specific wrapping.
- v2 should not bury those instructions inside unrelated control-flow code. If prompts are code, they need stable ownership, reviewability, and tests where tests make sense.
- v1 must stay reliable while v2 is built. Any shared prompt strategy must not accidentally destabilize the `jarvis1` daily-driver.

Primary questions to resolve:

- Should exact prompt strings be cataloged as a separate artifact from the behavior catalog?
- Should prompts live in a shared top-level directory (for example `prompts/`) that both `v1/` and `v2/` can read, or should prompts belong separately to each version?
- If prompts are shared, does `jarvis1` consume ongoing prompt improvements, or does v1 pin a frozen prompt snapshot so its behavior stays stable?
- If prompts are v2-only, when does extraction happen: before v2 architecture work, as part of the first v2 operation, or incrementally as each operation is implemented?
- What counts as a prompt artifact: only text sent to agent CLIs, or also injected rules, placeholders, generated next-step instructions, command suggestions, and agent adapter wrappers?
- What review standard applies to prompt changes? For example: snapshot tests for rendered prompts, behavior tests for prompt assembly, line-by-line PR review, or explicit changelog notes for behavior-affecting wording.

Initial scope:

- Inventory every v1 prompt surface by purpose and lifecycle, not by implementation file:
  - patch/implement prompt and injected patch rules,
  - plan refine prompt,
  - plan name-only prompt,
  - plan draft prompt,
  - plan review prompt,
  - disambiguation and confirmation text that asks the human to choose a path,
  - generated next-step/handoff text when it effectively instructs a future human or agent action,
  - agent-specific prompt transport or wrapping, including prompt markers used for telemetry correlation.
- Classify each surface as one of:
  - **agent instruction**: text whose wording directly shapes agent behavior,
  - **human instruction**: text that tells the terminal user or PR reviewer what to do next,
  - **protocol marker**: machine-readable text included in prompts or outputs for correlation, validation, or boundaries,
  - **data wrapper**: delimiters, placeholders, or framing that protect user/repo/spec content from being interpreted as higher-priority instructions.
- Propose a target prompt layout. Consider at least:
  - `v2/prompts/` owned only by v2,
  - repo-root `prompts/` shared by `v1/` and `v2/`,
  - `v1/prompts/` frozen plus `v2/prompts/` evolved separately,
  - a hybrid where shared rules live at root but operation-specific prompts live under each version.
- Propose a prompt rendering contract: how prompts are assembled, how placeholders are typed/validated, how user-provided content is delimited, and how prompt-injection protections are represented.
- Propose a review and testing standard. Prompt diffs should be reviewable like code; rendered prompt snapshots or focused tests should protect meaningful behavior without making harmless wording edits painful.
- Identify what, if anything, should change in v1 immediately. The default bias is no v1 prompt rewrites unless extraction or testing is needed to make the v2 handoff safe.
- Produce follow-on implementation intents if the design chooses extraction, shared directories, snapshots, or prompt renderer changes.

Expected output:

- A design document at `v2/spec/prompts.md` (working name) that includes:
  - prompt inventory,
  - recommended directory/layout decision,
  - v1 sharing/snapshot decision,
  - prompt artifact taxonomy,
  - rendering and placeholder rules,
  - review/testing expectations,
  - migration sequence,
  - unresolved risks or tradeoffs.
- If the design recommends prompt extraction before v2 architecture work, draft one or more follow-on intents under `v2/spec/wip-intents/` for that extraction. Keep those implementation intents atomic and testable.
- If the design recommends deferring extraction, state exactly what the first v2 implementation intent must do so prompt handling does not become an afterthought.

Review flow:

- Open this design as a draft PR.
- Use PR review comments as the main iteration mechanism.
- Keep the first pass concrete enough to debate decisions, not just a list of possibilities.

Relationship to the behavior catalog:

- `v2-catalog.txt` catalogs user-observable behavior and prompt *effects*.
- This intent catalogs and governs exact prompt artifacts.
- Do not duplicate the behavior catalog. Reference it when needed, but keep this document focused on prompt ownership, rendering, testing, and migration.

Out of scope:

- Rewriting v1 prompts for style without a behavior reason.
- Implementing the full v2 architecture.
- Implementing a new prompt renderer unless the accepted design says that must happen immediately.
- Deciding which v1 behaviors v2 keeps or drops.
- Duplicating the behavior catalog. This intent concerns prompt artifacts and prompt governance, not every user-facing behavior.
- Adding broad agent e2e tests. Prefer rendered prompt tests, placeholder validation tests, and small behavior-focused tests unless there is a specific high-risk path.
