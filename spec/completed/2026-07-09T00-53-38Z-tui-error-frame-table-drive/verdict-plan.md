1. **Preserve concurrent/correlation coverage — must be an explicit decision + acceptance criterion, not a task-checklist hint.**
   Several of the 9 source tests (e.g. "list and wait correlated error frames reject," "steering correlated error frames reject") don't just assert that method/code pair X maps to `TuiDaemonRpcError` — they assert the client correctly demultiplexes concurrent in-flight requests on a shared connection by request id, rejecting only the correlated one. A flat one-row-per-pair table with a single request per test collapses that into isolated single-request assertions, silently dropping the concurrency/correlation property while every stated AC ("13 pairs reject as `TuiDaemonRpcError`") still passes.

   The current draft only gestures at this in the task checklist ("the minimum number of loops needed to keep multi-request-id setups like `withFixedUuid` correct") — that's non-binding. The spec's own intent explicitly puts "dropping coverage for any method/code pair" out of scope, and its verification section requires every dropped test to be named alongside its surviving owner. A surviving owner that lost the concurrency property is not a true owner of that coverage.

   **Required fix:** Add a decision stating that rows originating from a shared-connection/multiplexed-request source test retain their concurrent-request setup (multiple requests issued on one connection, asserting only the correlated one rejects) — only the per-pair assertion body is factored into the table, not the connection/request structure. Add a corresponding acceptance criterion that this concurrency/correlation behavior is preserved, not flattened, for the affected pairs (at minimum the `list`/`wait` pair and the `pause`/`resume`/`kill` steering pairs). This ensures the "surviving owner" language in the verification section is actually true for these rows.
