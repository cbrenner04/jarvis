## The bug that was waiting on the first command

The session's first command — a v2 `implement` on the already-planned `blocked-run` spec —
returned run id `f9d556ed` and exit 0. `f9d556ed` was **the run from three hours earlier**, the
one the P0 seed was written about. `jarvis run log` showed no new events; `run list` showed it
terminal; nothing had been invoked.

`prepareWorkflowStep` resolves a step's run by `(project, branch)` and short-circuits any
`completed` row. The implement branch defaults to the spec directory basename, so **the state
store, not the spec, decided the work was done**. Combined with the false-`done` P0 — which let a
run reach `completed` with 0/5 criteria ticked — a spec that had once lied about finishing became
*permanently unrunnable* through v2, and every retry silently replayed the lie. Seeded as #1501,
planned, and shipped as #1513 the same session.

That is the whole session's pattern, stated once: **a terminal status asserted without the
evidence that would substantiate it** — and, here, then trusted.

## What the harness got wrong

- **Three of five implement runs reported `completed` with the work uncommitted and no PR.** Two
  were the P0 reproducing. The third was my misread — see below.
- **A run id going terminal does not mean the workflow is done.** `jarvis run wait <id>` returns
  when *that* run finishes, but the workflow continues under a *new* run id (shrink, then
  publication). Twice I concluded "the run dropped the work" while an agent was still live in the
  worktree. This is seed `workflow-completes-before-its-review-step` (#1488), previously filed as
  P5 backlog and **operator-confirmed** as such. That was wrong: it is the most operator-
  misleading behavior left, and I have promoted it to P1.
- **No v2 run can gate its own work.** v2 worktrees live at `~/.jarvis/worktrees/`, outside the
  repo, so bun's `node_modules` up-walk never finds the project's. `bun run typecheck` exits
  **127** in one. Agents there cannot run the tests `AGENTS.md` tells them to run before ticking
  criteria — which is a mechanism for the next bullet. Seeded (#1510).
- **Agents tick criteria on untested behavior.** #1512 arrived with all five criteria ticked and
  zero tests; the test I added then showed one *ticked* criterion was not actually satisfied
  (`completionCommitError` did not name the paths on the workflow path). #1511 the same. Seeded
  (#1515): a subspec that changes runtime behavior should carry a criterion naming a test that
  fails pre-fix — the one spec that did is the one that caught its own seed.
- **An agent silently mangled non-ASCII.** The #1509 run rewrote `['’]` → `['']` in every claude
  quota-detection pattern. The regex still compiles; the suite stayed green; a quota-exhausted
  claude would have settled `ok`. Caught by reading the diff, which is not a gate. Seeded (#1510).
- **A `blocked` run records no cost.** 13m35s of claude work behind #1508, and `runs.jsonl` wrote
  no `cost_usd` and no `usage`. Blocked is an *encouraged* outcome, so the sheets systematically
  under-report the honest stops. Seeded (#1515).
