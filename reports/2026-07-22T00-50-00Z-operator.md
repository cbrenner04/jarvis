The plan step writes criteria asserting *the feature works*. The gate requires *every changed guard
pinned in both directions*. Nothing bridges them, so an implementer who satisfies the written
criteria has done what was asked and still fails. Recovery each time was the operator hand-adding
the missing criterion — nine times.

Two sub-patterns, both worth knowing:

- **Naming one guard gets exactly that guard covered.** Three specs stalled a second time on the
  *same guard shape one layer up* (`write-loop` → `ready-finalize`; `stale-dispatch` →
  `daemon-lifecycle` → `daemon-entrypoint`). Pointwise naming loses to a large diff.
- **Optional-field spreads need key-absence assertions.** Inverting `x === undefined ? {} : {x}`
  yields a *present-but-undefined key*, which a value assertion cannot distinguish from absence.

Seed: `plan-specs-omit-both-direction-guard-coverage` (#1928). It explicitly rules out weakening the
gate, which has been correct in every observed case.

Each fix adds code; the added code adds guards; the new guards are the next stall. The final one is

injection.

**State:** CI green, full v2 suite passing, both named race layers now covered, diff reviewed. Draft
only because the mutation gate failed.

**Not merged deliberately.** This change replaces the daemon socket and dispatch path the harness
itself runs on. Force-merging a blast-radius change of that size past a genuine gate failure, at
session end, without operator confirmation, risks the next session starting on broken dispatch.
The earlier merge-over-gate (#1908) was justified because that mutation was *bogus*; this one is
real.

**Options, in recommended order:**

1. Land `plan-specs-omit-both-direction-guard-coverage` (#1928) first, then re-run this spec once.
   The systemic fix is exactly the missing input, and this spec is its best test case.
2. Merge #1941 over the gate after an operator diff review, accepting the uncovered timing bound.
3. Re-run with clock injection added to the AC — a fifth cycle, ~20 minutes, no guarantee the next
   added code does not introduce the next guard.

## Runbook corrections (2)

- **#1916 — the quiescence check was wrong.** The bullet said "no `bun` process under
  `lsof +D <worktree>`". `bun` only appears in the test/gate phase; the *agent* write phase runs
  `codex-aar`/`claude`/`cursor-agent`. Seven worktrees read "0 bun" while every one had a live
  `codex-aar` writing in it — the exact wrong conclusion the entry exists to prevent.
- **#1929 — do not poll `lsof +D`.** It walks the worktree recursively. Polling it across every
  worktree every 30s put two `lsof` processes at 25% and 14% CPU, above every agent they were
  measuring. Use it one-shot; count agent processes to wait.

## Concurrency finding

Running **7 implements concurrently** was comfortable: load average ~4, 4 `codex` + 4 `bun`, total
CPU well under saturation. The "throttle to 1–2 implement runs" folklore did not hold on this
machine — the measurement tooling cost more than the extra runs did. Fan-out is limited by the
*daemon revision guard*, not CPU: any merge touching `v2/src/**` makes the daemon stale, and a stale
daemon cannot bounce while runs are live, so dispatch serializes behind a fully idle fleet.
