## Verdict — refinements required

**1. The shared rules text must be mode-neutral; the `## Blocker` clause as written is false for two consumers.**
`DEFAULT_WRITE_STEP_RULES` is consumed by four write-step builders. Plan-draft and intent-split inject it as an appended `## Step completion` section outside the placeholder mechanism, so any sentence added to the constant ships into those prompts too. In plan draft the blocker lands in `intent.md`, not "the spec"; in intent split there is no spec at all. The spec's supporting claim that "the semantics are the same for every write step" does not hold for this clause. Refine so the shared constant states only what is true for every consumer (e.g. "record the blocker where your mode's rules require") and put the patch-scoped binding — when you append `## Blocker`, emit `blocked` — where patch rules already live (`prompts/patch/rules.md` §Stop already owns the `## Blocker` obligation and exit-7 behavior but names no token). This preserves the spec's anti-duplication decision without shipping a false sentence.

**2. Define all four tokens, not just two.** The acceptance criteria require the text to *name* four tokens but *define* only `progress` and `blocked`. The originating incident was an agent that finished subspec `00` with `01` unstarted — the live ambiguity there was `done` vs `progress`, and an implementer can satisfy every current AC while leaving that ambiguity intact. The runtime split is real and asymmetric (`progress` re-iterates and skips contracts; `done`/`no-work` run the artifact contract and end the loop), so the rules text must define `done` and `no-work` as well.

**3. Resolve `patch.prompt.shrink` on its merits.** The decision "leave shrink unchanged — it is a hidden non-token pass" is factually wrong: the shrink step inherits `stepRules` from the spread implement step and is run through the same `executeWriteLoop`/`runStep` terminal-token parse. `prompts/patch/shrink.md` declares no `STEP_RULES`, so it has the identical defect. Either fix it in the same change or state a true reason for deferring it. Do not leave the false rationale in the ledger.

**4. Pin the placement of `<STEP_RULES>`.** The rule governs the *final line* of output, and `patch/instructions.md` currently ends with the `<PATCH_RULES>` block. "Carries a `<STEP_RULES>` token" is too weak — the AC should pin that it renders last.

**5. Correct the verification scope and the revision question.** `prompts/**` is root-level and consumed through the `shared/prompts` registry, so the gate is a full `bun run test`, not `test:v2`. On revisions: bumping the two patch artifact templates is owed (their bodies change); changing the constant alters a placeholder *value* and a builder-appended section, not any artifact body, so no bump is owed for plan/intent — but their rendered output does change, so the spec must cover refreshing the affected prompt snapshot fixtures.

**6. Trim AC 4 and the problem statement.** AC 4 bundles an observable ("existing tests stay green") with a design constraint already stated in AC 1 — drop the tail. The problem statement's "the agent sees the tokens nowhere" should acknowledge the `write.token-reprompt` fallback, so an implementer doesn't believe they're fixing a total blackout.

**Scope:** stays one subspec. This is a single reviewable unit with focused verification; do not split.
