## The fan-out regression, found and fixed

[#2577](https://github.com/cbrenner04/jarvis/pull/2577) opened red: `daemon-pipeline-resume.test.ts` — `"resume returns after admission before async continuation runs"` — failed 3/3 on the branch and passed on `main`. Revert-bisect isolated it to `pipeline-execution.ts`, and subspec 01 scopes resume explicitly **out**, so it read as unintended fallout.

It was not a product regression. Instrumenting the walk showed the stage dispatched normally and then hung forever inside `dispatchPipelineStage` at `await wait(entryRunId)`. The cause was the test double:

```ts
let settleFn: (() => void) | undefined;
const factory = createBindingFactory(({ cwd }) => new Promise((resolve) => { settleFn = () => …; }));
return { factory, settle: () => settleFn?.() };
```

`settleFn` is only assigned **when the binding is invoked**, so a `settle()` that lands before the write step starts is silently discarded and the promise never resolves. The test asserts the stage is still `pending` and *then* settles — it depends on the continuation starting in that window. `main` passed on timing luck; the concurrent-dispatch change moved invocation past the `settle()` call and the signal was dropped. Latching the double (record the request, release on invocation) makes it order-independent: green 3/3, and the whole gate green.

## Two inert mutation directives, recorded not shipped

Applying all four `@mutate` directives by hand: the two on branch-scoped artifact lookup kill correctly; the two on concurrency are **inert** and leave `pipeline-execution.test.ts` at 73 pass / 0 fail. The task arrays are built with `.map()`, which starts every promise eagerly, so awaiting them serially changes nothing.

Making them real needs lazy thunks with the concurrency in the awaiting line. That was prototyped and works — but the serialized form then *deadlocked* the fixture rather than failing it, so the criteria were unticked with a `## Blocker` proposing bounded waits in the fixtures.

**That diagnosis was wrong, and the correction matters.** The serialized form deadlocks *because of* the `awaitFanOutPeerRow` bug below: a serialized leader cannot dispatch the peer, so the peer spins forever. Adding bounded waits to the fixtures would have converted a real product hang into a tidy test failure and hidden it. Fix the spin and the pins fail honestly. The Blocker on the branch has been corrected on the PR.

Also recorded: subspec 00 decided to "drop `sharedStageArtifacts` carry-forward into suffix `runAuthoredStages`", but the implementation keeps passing it and gates it internally. Equivalent in effect, covered by a working mutation pin, but not what the decision says.

## The deadlock that a single hand-gate missed

After the resume fix the whole gate ran green locally, so #2577 went ready — and CI killed `pipeline-end-to-end.sandbox-unrunnable.test.ts` at its 3-minute budget. It reproduces: **1 run in 3** on the branch hangs, while `main` is 4/4 green in ~2s. My clean hand-gate was the lucky two-thirds.

Concurrent sibling dispatch can deadlock a real end-to-end pipeline. That is a harder failure than the inert pins, and it is the reason the branch is back to draft. The lesson worth carrying: for a concurrency change, one green run of the affected file proves nothing — run it repeatedly before calling it green.

**Root cause, found:** `awaitFanOutPeerRow` spins on `await Promise.resolve()`, a *microtask* yield, so the queue never drains and timers and I/O never run — 5M iterations in 114 ms with a `setTimeout(…, 0)` that never fires. Every non-leader fan-out branch parks there. A macrotask yield takes the e2e file to 8/8 green; I **did not commit it**, because two deterministic deadlocks sit behind it (leader row already `succeeded`, or `failed`/`skipped` — both on the daemon-restart recovery path) and the yield would turn a loud 100%-CPU wedge into silently pending pipelines under a green suite. Full remediation, plus a double-settlement defect and `Promise.all` swallowing sibling errors, is recorded on #2577 and at the top of the queue.

## Friction (not seeded)

- `jarvis run list` gives no hint that a settled row has a live successor step. Diagnosing the false
  completion required reading `run log` timestamps against `telemetry.jsonl` to notice `639c40a6`
  started at the millisecond `eabc39a7` finished.
- Managed worktrees have no `node_modules` of their own for a hand gate; the operator borrows the
  primary checkout's by symlink. Jarvis creates one itself during a run, so this only bites on
  salvage.
- `test:v2` in a managed worktree needs the sandbox off (`mkdtemp` under `~/.jarvis`), consistent
  with the existing note about socket tests.
