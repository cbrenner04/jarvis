## Verdict: Redesign required (blocking)

1. **`renderStepPrompt` signature must generalize to a placeholder map, not a fixed `{specPath, stepRules}` tuple.** Verified: `plan/draft.md` requires `WORKDIR!, NAME!, INTENT!, SPEC_GUIDANCE!` and `patch/instructions.md` requires `SPEC_PATH!, SIBLINGS_BLOCK!, REPO_GUIDANCE!, ACTIVE_SUBSPEC_PATH!, ACTIVE_SUBSPEC_BODY!, PATCH_RULES!` — none of these are satisfiable by a signature hardcoded to `specPath`/`stepRules`. `renderTemplateWithDeclarations` throws `missing_value` on any unsatisfied required placeholder, so the current design cannot render a non-write prompt id at all, which directly contradicts the intent's stated goal ("presets can reuse `plan.*`/`patch.*` artifacts without new code paths"). The spec must change the decision so `renderStepPrompt` takes `(promptId, placeholders: Record<string, string>)` or equivalent, with each write-step call site responsible for constructing its own placeholder map.

2. **AC #2 is currently unimplementable and must be rewritten to match the corrected signature.** As drafted, the example of rendering `plan.prompt.draft` through a write step's fixed placeholder set would throw, not succeed. The acceptance criterion must be restated against the generalized signature so it's actually achievable and testable.

3. **The always-injected `PRINCIPLES` placeholder is a write-specific assumption baked into a general-purpose function and must be removed from `renderStepPrompt` itself.** Once the signature takes a caller-supplied placeholder map, write-step call sites remain responsible for including `PRINCIPLES` in the map they build; `renderStepPrompt` should not hardcode injecting it for every promptId.

4. **Documentation updates section must be corrected.** `v2/docs/prompts.md` documents `write.execute` as the fixed, sole prompt for write steps. This subspec changes that documented contract, so per repo convention (any spec changing existing functionality/documented behavior must update the relevant doc), the "Documentation updates: None" claim is wrong. The spec must identify `v2/docs/prompts.md` (and any other doc stating the write-step-prompt-id contract) as requiring an update, and describe what the updated behavior is.

5. **Error-surfacing behavior for an unknown/incompatible `promptId` needs an explicit decision.** The spec should state whether a registry lookup failure or a placeholder/template mismatch at a non-default `promptId` propagates as an uncaught error or maps into a `WriteLoopOutcomeKind`-style outcome, so behavior is deterministic and testable rather than left implicit.

6. **Minor, non-blocking:** consider adding a one-line acknowledgment that no current caller constructs a step with a non-default `promptId` yet (per the intent's stated out-of-scope items — TUI picker and new prompt bodies are excluded), so reviewers understand the AC's test is the sole proof of the mechanism working, without requiring new scope to wire a real consumer.
