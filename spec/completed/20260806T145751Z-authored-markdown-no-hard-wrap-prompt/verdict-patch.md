## Verdict: required outcomes

**Upheld — the branch changes v2 production prompt assembly, and neither the spec nor the docs say so.**

Before this branch, `v2/src/execution/write-prompt.ts` composed no fragments at all: it rendered the step artifact alone. The branch adds global-fragment discovery to it, so **every** v2 step prompt rendered through that path now carries `global.documentation`, `global.naming`, `global.terse`, and `global.no-hard-wrap` — including `patch.prompt.body` (the primary v2 implement prompt), `patch.prompt.shrink`, `patch.prompt.review-actuator`, `implement.prompt.review.critic`, `write.mutation-repair`, and `write.ready-repair`, none of which the spec mentions. The subspec's decision "rely on `assemblePromptForStep` global-fragment discovery — rules out manual per-step wiring" was factually wrong for v2: no such discovery existed on this path, and the branch hand-rolled a partial copy of it instead. The behavior change is defensible (the ACs were unsatisfiable otherwise, and the added rules are ones v2 should have been carrying), but shipping it as an unstated side effect of a fragment-registration spec is not.

1. **Record the corrected premise.** The subspec Decisions must state what actually changed: v2's step renderer previously composed nothing, now composes global fragments for all step prompts it renders. A reader of the spec should not have to diff the branch to learn that v2 implement prompts gained three unrelated global rules.

2. **Update the v2 durable docs in this subspec.** `v2/docs/v2-architecture.md` states the layering contract ("global fragments → behavior fragments → the step's task text") as designed; v2 now implements the global half of it on the write path and not the behavior half. Prompt and operator-facing semantics changed, so the durable v2 prompt home must say which fragments v2 step prompts carry and which they do not. `global.documentation` requires this in the same subspec, not a follow-up.

3. **Pin the broadened behavior where it matters most.** The new tests cover `write.execute`, `plan.prompt.draft`, and `patch.prompt.shrink`. Nothing asserts that `patch.prompt.body` — the prompt this harness actually implements with — now carries the globals. That is the highest-value assertion and its absence is why the widening could ship quietly. Add coverage for it.

4. **Guard the new executable code by inversion.** `globalFragmentBodies` is new production logic (global/kind filter, `remove` exclusion, `order` sort). The subspec's mutation checkpoint targets prompt frontmatter only, on the assumption that no executable code changed — that assumption no longer holds. The repo rule for mixed code work applies: a mutation checkpoint must name the real guard in `write-prompt.ts` such that inverting it turns a named test red.

5. **Do not leave the shared/v2 divergence silent.** `plan.prompt.draft` now renders two different ways: `shared/prompts/plan-draft.ts` (via `assemblePromptForStep`) includes behavior fragments `plan.decisions-ledger` / `plan.defer-to-consumer` and honors `metadata.add`; the v2 path includes neither. One prompt id with two renderings is a defect waiting to be discovered by whichever consumer is wrong. Converging on `assemblePromptForStep` is the correct end state — the behavior-fragment omission exists only to avoid duplicating `write.principles`, which a `remove` declaration on `write.execute` solves — but the blast radius exceeds this subspec. Either converge here, or record the divergence and the `metadata.add` gap explicitly as a decision in the subspec and seed a follow-up intent. Silence is not acceptable.

**Not required.** The `write.mutation-directive-reprompt` path bypasses fragment composition entirely — real, but fragment-free before this branch too, so out of scope; seed it. Placeholder-scanning of assembled templates is a pre-existing v1/v2-shared property, not caused here. `registry.txt` file ordering is cosmetic; layering comes from `order:` frontmatter and is test-pinned. The vacuous `plan.prompt.review@r7` revision assertion (no fixture resolves to that key) predates this branch — worth its own intent, not this one. Fixture pruning: no policy exists.
