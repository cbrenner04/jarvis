## Verdict

**Required outcome 1 — Close the workflow-vs-workflow (and workflow-vs-bare) double-claim hole.**

Subspec 01's own stated goal is "a workflow start must not be able to double-claim a worktree already claimed by another live run or queued entry for the same `(project, branch)`." The current implementation only checks `store.hasQueuedRun` and `checkWorktreeClaimed(_registry, ...)` before starting a workflow, but never calls `_registry.claim(...)` for the workflow's ownership key. That means once a workflow start proceeds, its worktree is invisible to `_registry`/`checkWorktreeClaimed` — a second workflow start (or a bare write-loop start) for the same `(project, branch)` will not see it as claimed and can proceed concurrently. This is a live double-claim, not a deferred concern; the subspec text doesn't scope it out. Fix: workflow starts must register their claim in `_registry` (and release it appropriately) so subsequent starts — bare or workflow — are correctly blocked for the duration of the run. Add coverage for a live *workflow* run blocking a subsequent bare or workflow start on the same key (the existing tests only cover the reverse direction).

**Required outcome 2 — Define and enforce behavior when a workflow's first step is `review-debate`.**

Subspec 00 defines `onFirstRunCreated`/`onStepRunCreated` as firing once the step's run row is "durably created." `review-debate` steps do not persist a durable run row — `executeWorkflow` synthesizes a `runId` for reporting only, per its own existing deferred-scope note. Nothing in subspecs 00–02 restricts `steps[0]` to non-`review-debate` behaviors, so `start({ steps: [reviewDebateStep, ...] })` currently returns a `runId` that `list`/`kill`/`pause` cannot resolve, violating the stated durable-row contract. Fix one of: (a) reject a workflow start whose first step is `review-debate` with a clear error, or (b) explicitly define and implement what `start` returns in that case consistent with the non-durable nature of that step. Either way this must be covered by a test — it's currently untested and unhandled.

No action required on the other two adversary points: collapsing pre-step-0 failures into the existing error path matches the spec's explicit decision (not a deviation), and the mixed key-space (`activeRuns` keyed by ownership-string for write-loop vs. by runId for workflow) is a documented, working design choice per subspec 02 — worth a clarifying comment but not a functional defect requiring a fix here.
