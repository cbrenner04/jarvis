## Observations

- **Root-caused and fixed a recurring CI `Test (v2)` hang that predated this session.** PR #1068 hit a CI timeout-kill (`v2 "agent" test run timed out or was killed`, the bounded 300s `AGENT_MODE_TIMEOUT_MS` guard from an earlier fix, PR #1061) on two consecutive CI runs, wedging at the identical spot (`tui-daemon-client.test.ts`) both times — a file untouched by that PR's diff, ruling out anything the PR itself introduced. Swept every real-Unix-socket test file for `connectIpcClient()` calls lacking a bounded timeout; found `connectSocket()` in `v2/src/ipc/client.ts` had **zero timeout on the connection-establishment step itself** — the earlier fix (PR #1061) only ever bounded `nextFrame()` reads *after* a connection succeeded, never the initial connect. Two test call sites (`tui-daemon-client.test.ts`, `tui-log-tail-client.test.ts`) hit exactly this gap via a deliberately-unreachable socket path. Added a 5s connect-timeout (PR #1075); confirmed fixed by two subsequent clean CI runs (#1074, #1076) with no recurrence. This was a genuinely different bug from the one PR #1061 fixed, not a re-flake of the same issue.
- **A real test-design bug slipped through an implementing agent's own review pass.** PR #1068's `daemon-queue-promotion.test.ts` tried to simulate "a queued run whose key is claimed by a live run" by calling the `start` RPC twice with the same key — but `start` rejects an already-claimed key outright (whether live or queued) before ever reaching the queuing/promotion logic, per the spec's own decisions. Two automated `jarvis1 run` retries did not fix this (the second retry just re-ran the ready gate with no new agent iteration, since acceptance criteria were already marked complete). Hand-fixed by constructing the blocked-queued-row state directly via `stateStore.createRun`, bypassing the guarded RPC layer — mirroring an existing test's pattern of poking state below the RPC boundary. Verified with the full local `bun run ready` gate (green) before manual-finalize admin-merge.
- **Intent-split granularity gap, confirmed but out of scope to fix this session.** The `memory-watermark-admission-and-queued-status` intent bundled a zero-risk additive primitive (memory-watermark config/reader) with behavior-changing production logic (removing the global single-in-flight admission guard) in one 3-subspec spec — the operator noted this in retrospect as a case where a same-agent refine turn after intent-split (a step `jarvis1 intent` currently does not run — confirmed via `v1/docs/intent-mode.md`: intent mode does not run refine, splits once and hands off to operator review) might have caught the split-worthiness earlier. Judged not worth a seed given v2's evolving concurrency model handles this more structurally going forward.
- **Test architecture in `v2/src/daemon/daemon.ts` forces real-socket integration testing for pure control-flow logic.** Admission/claim/promotion logic (`promoteQueuedRun`, the `worktree_claimed` check) lived as closures inside `createRunControlHandlers`, with no standalone export — so testing FIFO ordering or a claim-conflict check required a real Unix domain socket server + IPC client round trip. This directly contributed to both the recurring CI hang (more real-socket tests accumulating against a fixed CI timeout budget) and the test-design bug above (reasoning about a real async socket state machine is harder than reasoning about a pure function). Seeded (`daemon-admission-logic-unit-testable`) and fully landed this session: both `promoteQueuedRun` and the `worktree_claimed` check are now standalone exported functions, unit-tested directly with no socket involved.
- **Plan-mode dependency ordering caught a real prerequisite gap.** `concurrent-run-execution`'s plan blocked cleanly on its first attempt: its intent assumed daemon changes were needed, but `memory-watermark-admission-and-queued-status` (a listed prerequisite) hadn't merged yet. Abandoned the draft cleanly (ready-intent file preserved, no orphaned worktree) and resequenced. On re-plan (after the dependency landed), investigation found the daemon already executed admitted runs concurrently — the intent's premise had partially been overtaken by other Phase 7 work; the subspec correctly pivoted to regression-coverage-only, explicitly flagged up front.
