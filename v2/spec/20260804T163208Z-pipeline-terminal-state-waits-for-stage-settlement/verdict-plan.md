## Verdict: required refinements

1. **Define deferral in terms of actionable unsettled work, not guard reorder alone.** Decisions and the task checklist must state that fan-out suffix aggregation defers terminal `failed`/`rejected` only while **actionable** sibling work remains: live `running`, or unsatisfied non-skipped stages whose branch predecessors are satisfied (matching the intent’s reachable-gate definition). A naive precedence swap without this rule breaks post-settlement mixed-branch rejection: a terminally rejected branch can still leave dead-branch `pending` rows that would incorrectly beat `rejected` if every `anyPending` counts. The spec must require settlement-first precedence on actionable signals, with terminally failed/rejected branches treated as settled for deferral even when branch completion flags remain false.

2. **Add a preservation acceptance criterion for mixed-branch rejection.** Intent and decisions say `running` wins over both `failed` and `rejected` while sibling work continues; the spec already cites `"mixed branch failure and success names the failed branchKey while the sibling still reaches terminal success"` as a preservation AC but omits the symmetric rejection case. `"mixed branch rejection and success names the rejected branchKey without aborting the sibling"` is directly threatened by naive reorder and must be cited as a stays-green preservation AC per spec guidance for behavior-preserving work.

3. **Close the intent coverage gap for `rejected` + `running`.** Acceptance criteria must explicitly require that failed-plus-running fan-out rows derive `running` **and** that the same settlement-first rule applies when one branch is `rejected` and a sibling workflow stage is `running` — via a new row-seed regression AC or an explicit citation of a pinning test. Intent’s “running over failed or rejected” decision must not rely only on prose.

4. **Clarify mutation-checkpoint scope for aggregation changes.** The mutation AC and task checklist must cover each **new or moved** suffix guard condition (including any actionable-pending logic), not only a pure reorder of existing `anyRejected`/`anyFailed`/`anyRunning` returns. Each linked `// @mutate` directive must invert a real production condition that the named pinning tests exercise.

5. **Require reconciling contradictory documentation.** The documentation task must explicitly require updating `v2/docs/daemon-host.md` where it currently states terminal states take precedence over approval boundaries — that sentence contradicts settlement-first fan-out behavior (failed branch + sibling reachable gate). Doc updates should record the operator-visible rule: aggregate state and `pipeline_wait` stay non-terminal while actionable sibling work or reachable gates remain; terminal `failed`/`rejected` only after full branch settlement.

These refinements align with spec guidance (failing-test ACs for runtime behavior, refactor ACs that cite tests by name, mutation checkpoints on real guards, and `v1-behaviors.md` / daemon docs for behavior changes) without widening scope beyond fan-out suffix settlement-first terminality.
