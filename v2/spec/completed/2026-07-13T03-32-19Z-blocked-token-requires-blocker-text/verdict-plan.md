## Verdict — refinement required

The spec's core shape is sound (verify the `blocked` token's artifact; one cheap re-prompt; a distinct terminal outcome that does not route to `inspect_spec`). All of it survives. The following gaps must be closed before this draft is implementable.

### Required refinements

1. **Operator-error precedence is unhandled — the highest risk of shipping a red AC.** `composeRunOperatorError` (`v2/src/daemon/run-operator-error.ts`) special-cases `outcomeKind === "invalid_token"` *before* consulting `RESUMABLE_TERMINALS`; without that branch a `paused` run reports as `resumable_pause`. A `paused` run carrying the new outcome kind falls straight through to `resumable_pause` and subspec 01's first acceptance criterion cannot pass. The spec must state that the new reason is a member of the closed `RUN_OPERATOR_ERROR_REASONS` list and that the precedence path recognizes the new outcome kind, and must carry an AC for it.

2. **Blocker detection must name the correct canonical, and unification is its own subspec.** `extractBlockerSection` in `v2/src/execution/write.ts` is a verbatim duplicate of the (currently private) `extractBlockerBody` in `shared/spec-parser.ts`. `shared/` is the version-agnostic home per the repo layout rules, so the shared one is canonical and write.ts's copy is what gets deleted — the draft's decision has this inverted. This unification touches three call sites (shared export, write.ts's copy + `hasGenuineBlocker`, plan-draft's existing gate), is independently implementable, and its whole contract is "existing tests stay green." Split it out as its own subspec, landed first, linked from the index. Every original task and acceptance outcome must appear exactly once across the resulting subspecs.

3. **Presence of a `## Blocker` is not evidence the agent wrote one.** `appendBlockerToSpec` (`v2/src/execution/write-loop.ts`) writes a `## Blocker` section itself on `contract_miss`, so any spec that took a contract miss in an earlier iteration already carries a non-empty blocker on disk; a stale operator-authored blocker has the same effect. A presence-only check accepts both and silently reproduces the bug this spec exists to fix. The spec needs a decision on the baseline (a before/after comparison in the shape of the existing `hasGenuineBlocker`), plus an AC pinning it.

4. **Pin which file the contract reads.** "The spec tree carries a `## Blocker`" is not a location. The mechanism is fine — the contract can close over its paths lexically like every existing one — but *which* file is operator-observable and must be stated (the resolved spec file the blocker append already targets is the likely answer; say so rather than leaving it to the implementer).

5. **Pin the loop `kind` and exit code.** `kind` is load-bearing: commit/publish gate on `kind === "complete"`, and the workflow runner returns early for any non-complete kind. The `paused` decision already implies mirroring `invalid_token` (`invocation_failure` + `paused` + exit 2), but the doc-updates section promises an exit-code row with no decision behind it. State it.

6. **Rename the contract and fix a false acceptance criterion.** Plan-draft already declares a gate named `plan.draft.blocker` whose polarity is the *inverse* of the new one (it fails when a genuine blocker exists; the new one passes). Same word, opposite meaning — rename the new contract. Subspec 00's last AC ("steps that declare no blocker contract (intent-split, plan-draft)") is literally false for plan-draft and must be corrected.

7. **The plan-draft deferral's stated reason is wrong.** Plan-draft strands runs *today* by the identical short-circuit mechanism, so "pin when one of those flavors strands a run" is a false premise. Scoping plan-draft out remains defensible — its blocker home is `intent.md` and its gate means the opposite thing — but the deferral must carry that reason.

8. **Re-prompt plumbing collisions.** The write loop emits a `token_reprompt` log event unconditionally whenever the `reprompt` field is set, before the outcome branch — a blocker re-prompt reusing that field is logged as a token re-prompt. Address it. Relatedly: the blocker parser matches the exact literal heading, so the re-prompt text must quote it or the second miss is near-guaranteed; and the spec must say in one sentence *which* response text the rejected result carries.

9. **Scope resume out explicitly.** The spec asserts `nextAction: "resume"` as the recovery but never verifies it, and says nothing about what a resumed run does differently — leaving a reject → resume → reject loop unaddressed. Resume for `paused` runs already has known limits for non-workflow runs, and `invalid_token` carries the same pre-existing hazard. The right move is a decision that resume semantics are unchanged and out of scope, and that the new outcome mirrors `invalid_token`'s exactly — not new resume machinery.

10. **The new outcome kind's type-level and mapping surface.** The persisted `OutcomeKind` union has no runtime validator, so adding a member there is type-only and needs no store round-trip test or persistence doc row. The real work is the operator-error reason list and the attempt→invocation mapping switch, which currently falls through to `undefined` for unrecognized kinds. One AC, not a subspec. Note this outcome is *not* a `WriteLoopOutcomeKind`, so it likely does not touch that validated set — say which vocabulary it joins.

### Not upheld

- An AC asserting the rejected run leaves work uncommitted would restate the existing `kind !== "complete"` gate. If included at all, it must be the citation form the spec guidance prescribes for preservation criteria, not a new prose claim.

### Rationale

Findings 1, 3, and 5 are the ones that make this spec typecheck and still fail its own acceptance criteria — the operator-error precedence branch and the loop-`kind` gate are both invisible from the spec's current text but decide whether the feature works at all. Findings 2 and 6 are correctness-of-record problems: the draft names the wrong canonical parser and asserts something about plan-draft that the code disproves, and this repo's guidance is explicit that a decision must name the plausible wrong alternative it rules out — a decision resting on a false premise rules out nothing. Findings 4, 8, and 9 are the "deferral over invented precision" rule applied in reverse: the spec promises operator-observable behavior (a file location, an exit-code row, a resume recovery) without pinning it, which is the deferral this repo's guidance requires be made explicit or made concrete. The split in finding 2 is a genuine seam, not prose compression: it is independently testable against existing tests and removes a duplicate definition before the new contract is built on top of it.
