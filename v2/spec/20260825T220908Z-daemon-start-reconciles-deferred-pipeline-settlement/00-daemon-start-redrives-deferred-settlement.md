# Daemon start re-drives deferred stage settlement

## Problem

A stage settles through the live entry-run boundary. When the daemon dies between its entry run reaching a durable terminal status and that boundary being delivered, the row stays `running` with `failureDetail: { code: "settlement_deferred", reason: "entry_run_still_live" }` forever: `recoverContinuablePipelines` admits a pipeline only when `isPipelineContinuable` holds, and that predicate needs derived state `pending` (or pending terminal settlement), while a pipeline carrying a stale `running` row derives `running`. Nothing revisits the row, the successor never dispatches, and terminal publication never fires — observed 2026-08-16 on pipeline `aede4177`, whose implement entry run `b35b61dd` was durably `completed` and not live while the stage still read `running`. The pipeline read `running` for as long as it did because only a daemon restart re-drives a deferred marker; a live daemon that already missed delivering the live boundary event has no other trigger to revisit the row, so it stays wedged until the process bounces.

`continuePipeline` already re-settles such a row once it is entered (`v2/src/daemon/pipeline-execution.test.ts` — `re-settles a deferred running stage when continuePipeline runs after the linked entry run terminals`). The gap is selection, not settlement.

## Decision ledger

- Admit the sweep through `recoverContinuablePipelines`'s existing per-pipeline filter (`if (!isPipelineContinuable(pipeline) && !hasRedrivableDeferredSettlement(store, pipeline, reconciledEntryRunIds)) continue;`); rules out a second startup pass in `startDaemonRuntime`, which would need its own ordering against orphan-pipeline settlement and reconciled-run resume. The filter runs first, exactly as today; the owner-liveness skip that follows it is unchanged and still applies to whatever the filter admits.
- Scope the sweep to rows still `running` and carrying the `settlement_deferred`/`entry_run_still_live` marker; rules out re-driving every `running` row whose linked entry run happens to read terminal. A row a prior daemon start already settled `interrupted` is out of reach by construction.
- A stage whose linked entry run id is a member of *this same start's* `reconcileOrphanedRuns` result is excluded from the redrive and left to `recoverReconciledRuns`. The deferred marker's natural companion state is an entry run that was itself live and got orphaned by the same daemon death; pre-IPC reconciliation terminalizes that run (`killed`/`interrupted`) before the continuation sweep runs, so by sweep time it reads "terminal, not live" with nothing to distinguish it from a genuinely-finished run. Admitting it would fail the stage and skip its successor while `recoverReconciledRuns` independently resumes that same run moments later with no pipeline loop watching it — replacing today's honest `interrupted` landing with a composed failure plus an orphaned resumed run. Rules out treating "not live" as sufficient evidence of durable settlement; the intent's "still live" acceptance criterion cannot catch this case because nothing is live once pre-IPC reconciliation has run.
- `redrivableDeferredSettlementEntryRunId` lives in `v2/src/daemon/pipeline-stage-dispatch.ts`, beside the code that writes the marker, and derives the entry-run id via the existing `settlementLinkedEntryRunId` accessor rather than reading `failureDetail.entryRunId` — the same accessor `dispatchPipelineStage`'s re-settle path already uses, so the new predicate and settlement can never disagree about which run they're judging. This rules out restating the marker shape in `pipeline-execution.ts`. The reconciled-run-id exclusion is restart-batch-specific, so it lives in `hasRedrivableDeferredSettlement` (`pipeline-execution.ts`) rather than in the dispatch-module predicate. The `pipeline-resume-drives-deferred-settlement` ready-intent consumes `redrivableDeferredSettlementEntryRunId` later.
- A marker row whose linked entry run row is absent counts as redrivable and settles through the ordinary non-`completed` path, landing the generic `harness_failure`/`retryable: false` detail `failureDetailForEntryRun` already falls back to for any vanished-run settlement. Accepted as-is, not separately pinned here: the shape is identical to that existing fallback, already exercised by `pipeline-stage-dispatch.test.ts`. Rules out reading an absent row as still-live and wedging the stage forever.
- The new predicate carries no pipeline status/context preamble: `continuePipeline` already refuses `missing_context` and `claimPipelineContinuation` already refuses a non-claimable pipeline; rules out duplicated admission guards that would each need their own inversion coverage.
- Successful settlement clears the row's deferred `failureDetail`; rules out a `succeeded` row that still reports a settlement failure to `pipeline list`.
- Tests drive their `wait` stub (and any predicate fixture asserting a "durable" rollup) through `rollupWorkflowRunStatus` over seeded sibling step-run rows — the same mechanism `waitForWorkflowEntryRun` uses in production — rather than a fixed literal or the entry row's own `status` field read in isolation. A run row with no authored step rows rolls up to a non-`completed` status, so a fixture that stamps the entry row `completed` with no step rows would pass a state production would reject; seeding the sibling rows is what makes "settles from the durable entry-run row" a claim the fixture actually proves.
- `pipeline_resume` is untouched here — the operator verb for an already-up daemon is the sibling `pipeline-resume-drives-deferred-settlement` intent.
