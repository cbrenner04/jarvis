# Three-bucket top-level ordering

Authoritative for implement runs: acceptance criteria, documentation updates, and material decisions in this file supersede `intent.md` where they differ.

## Problem

`orderPipelineNodes` (`v2/src/tui/tui-monitor-pipeline-tree.ts`) splits top-level rows into two buckets: non-terminal by `createdAt` ascending, then terminal by finish ascending. A pipeline parked at a gate for days ranks inline with running work. The terminal block puts the oldest finish nearest the tree and pushes the newest toward the bottom of the pane. Terminality is read off `finishedAtMs !== null`, so a terminal-state item with no finish stamp is bucketed as active, and the `?? 0` fallback in the terminal comparison is unreachable epoch coercion.

## Decision ledger

- Top-level rank is running (0) → gated (1) → terminal (2), painted in that order. Rules out the current two-bucket active/terminal split.
- Terminality comes from the item's derived state (`isPipelineTerminal(snapshot.state)`), not from `finishedAtMs !== null`. Rules out keeping finish-timestamp classification, which buckets a finishless terminal with running work.
- Gated means derived pipeline state `awaiting-approval`. Rules out re-deriving the gate by scanning stage records for `awaiting`.
- Running is "neither terminal nor gated", so `pending` pipelines ride in the running bucket. Rules out a fourth bucket for admitted-but-not-yet-running work. This definition supersedes `v2/spec/seeds/tui-unified-work-tree.md`'s "any live/active member" running definition (see Tasks) — the two disagreed on where `pending` lands.
- Running and gated buckets both sort `createdAt` ascending, oldest highest. Rules out newest-first for live work and rules out leaving the gated bucket in snapshot order (merged multi-socket snapshot order is arbitrary).
- Fixture invariant for the running/gated pinning test: every gated pipeline's `createdAt` must precede the earliest running pipeline's `createdAt`. Pre-fix code sorts running and gated together by `createdAt` ascending, so only this relationship makes pre-fix output (gated first) diverge from post-fix output (running first); the reverse relationship makes the two outputs coincide and the regression — and the guard mutation — hollow.
- Terminal bucket sorts `finishedAtMs ?? createdAt` descending. Rules out the `?? 0` epoch coercion and the current oldest-finish-first order.
- The `createdAt` fallback is a comparator key only; no rendered elapsed or finish cell changes. It is a defensive default, not a scenario the daemon's own derivation produces: `derivePipelineFinishedAtMs` (`v2/src/daemon/pipeline-observation.ts:159`) always backfills a terminal snapshot's `finishedAtMs` from `terminalPublicationSucceededAt` → max stage `endedAt` → `createdAt`. The reachable path is the wire boundary: `parsePipelineList` (`v2/src/tui/tui-daemon-client.ts`) casts the `pipeline_list` payload to `PipelineSnapshot[]` with no per-field runtime validation, so a stale client against a mismatched daemon, or a malformed payload, can hand the tree builder a terminal snapshot with `finishedAtMs: null`. No display-side invention of a finish time. Drop any attribution to the `pipeline-terminal-timestamps` seed — that seed covers run `finishedAtMs`, stage `endedAt`, and approval `decidedAt`, not pipeline-level finish, and cannot produce or repair this case.
- Consequence, stated plainly: a finishless terminal ordered by `createdAt` sits higher among terminals than its true finish would place it, roughly by its own duration. Strictly better than the current `?? 0` epoch coercion, but not "sorts near its true peers."
- The comparator key is `{ rank: "running" | "gated" | "terminal", createdAt, finishedAtMs }` — an explicit `rank` field, not separate `running`/`gated` booleans with terminal inferred by exclusion (a `{running: true, gated: true}` shape has no defined rank). A pipeline-node key deriver reads `snapshot.state` through `isPipelineTerminal` / `=== "awaiting-approval"`; a generic key comparator ranks then tiebreaks, so non-pipeline top-level items can reuse it by supplying the same key shape rather than reading `PipelineSnapshot` fields directly.
- Equal-key ties (duplicate pipeline ids from merged multi-socket snapshots, or same-millisecond `createdAt`/`finishedAtMs`) resolve by stable sort, preserving merge order — no explicit tiebreak field needed.
- Deferred to first consumer: how a non-pipeline top-level item derives its `rank` key — pin when a caller adds one.
- Ordering is asserted through `flattenMonitorPipelineTree` output, not rendered ink (`v2/docs/test-writing.md` § TUI test strategy). Rules out an ink-frame assertion that goes local-green / CI-red.
- Initial selection (`firstSelectableNodeId` → `monitorSelectableNodeIds(state)[0]`) is order-derived, so it changes as a consequence of the reorder — e.g. on an all-terminal tree, initial selection now lands on the newest-finish pipeline instead of the oldest. This is a genuine behavior change the reorder causes, not something preserved by it; document it, don't fold it into a preservation claim.
- Out of scope: unattributed-segment membership, retention, and selection; ordering of stages and runs within a pipeline. The unattributed-segment retention sentence in `v1-behaviors.md` (actives by earliest `createdAt`, terminals oldest-finish-first) stays as written and now contradicts the tree's newest-finish-first order — a known, temporary inconsistency that the queued `tui-unified-work-tree` work resolves by deleting the segment. Note it in documentation; don't fix it here.

## Prerequisites

- `buildMonitorPipelineTreeJoin` builds top-level pipeline nodes from merged daemon `pipeline_list` snapshots (`v2/src/tui/tui-monitor-pipeline-tree.ts`).
- `PipelineSnapshot` carries `state`, `createdAt`, and `finishedAtMs` (`v2/src/daemon/pipeline-observation.ts`).
- `awaiting-approval` is a `PipelineDerivedState` value produced by `derivePipelineState`; `isPipelineTerminal` classifies the terminal set (`v2/src/daemon/pipeline-execution.ts`).
- `flattenMonitorPipelineTree` emits the whole tree, and `monitorSelectableNodeIds` derives from that full flatten, so *selectability* is not truncated by pane height. Painted rows are a different story: `monitorLeftPaneTreeRows` (`v2/src/tui/tui-monitor-lines.ts:530`) slices painted rows to the viewport, so a reorder changes which rows are on-screen at a given scroll offset, not just their relative order — this is why the reorder's blast radius reaches every test that asserts painted-row identity against an overflow fixture.

## Tasks

- In `v2/src/tui/tui-monitor-pipeline-tree.ts`, import `isPipelineTerminal` and `PipelineDerivedState` from `v2/src/daemon/pipeline-execution.ts`, then replace `orderPipelineNodes`/`isTerminalPipelineNode` with:
  - `type TopLevelOrderKey = { rank: "running" | "gated" | "terminal"; createdAt: number; finishedAtMs: number | null }`
  - `const GATED_PIPELINE_STATE: PipelineDerivedState = "awaiting-approval";`
  - `pipelineNodeOrderKey(node)`: terminal via `isPipelineTerminal(state)`; else gated via `state === GATED_PIPELINE_STATE` (this condition is the guard-mutation anchor); else running.
  - `compareTopLevelOrderKeys(a, b)`: rank order `running < gated < terminal`, then `createdAt` ascending for running/gated, `return (b.finishedAtMs ?? b.createdAt) - (a.finishedAtMs ?? a.createdAt);` for terminal (this line is the keystone-mutation anchor).
  - `orderPipelineNodes` maps nodes to `{ node, key }`, sorts with `compareTopLevelOrderKeys`, unwraps — `Array.prototype.sort` is stable, so equal keys preserve merge order.
- In `v2/src/tui/tui-monitor-pipeline-tree.test.ts`, replace `orders active pipelines above terminals by createdAt then finishedAtMs` with the three titled regressions, preserving its coverage:
  - `top-level rows order running before gated before terminal`: two running (`createdAt` 1000, 2000), two `awaiting-approval` gated (`createdAt` 100, 500 — both earlier than every running `createdAt`, per the fixture invariant), one terminal. Assert painted order `[running-1000, running-2000, gated-100, gated-500, terminal]` — covers running-internal and gated-internal `createdAt` ascending order plus the rank boundary.
  - `terminal rows order newest finish first`: two `succeeded` snapshots with distinct `finishedAtMs`; assert the newer one paints first.
  - `a finishless terminal row sorts by createdAt among terminals`: a hand-built terminal-state snapshot with `finishedAtMs: null`, landing between two finish-stamped terminals by its `createdAt`; comment that this is a defensive-fallback fixture (see Decision ledger), not one the daemon's own derivation produces.
  - Place the guard `// @mutate` (mutating `state === GATED_PIPELINE_STATE` to `false`, collapsing gated into running) inside `top-level rows order running before gated before terminal`, and the keystone `// @mutate` (swapping `a`/`b` in the terminal subtraction to revert to ascending) inside `terminal rows order newest finish first`.
