# Live PR body updates and per-commit attribution

repo: git@github.com:cbrenner04/jarvis.git

Today Jarvis writes the draft PR body once, when it opens the draft, and
appends a single attribution footer naming the agent that produced the
*first* commit (`ensureDraftPr` in `src/pr.ts`, called from
`src/modes/patch/run.ts`). Two problems:

1. **Stale body.** The PR description never updates after the draft is
   created, so as more subspecs land the body drifts further from the
   actual state of the branch. Reviewers landing on the PR mid-run see
   a description that doesn't match the index.
2. **Single-agent attribution.** The footer reflects only the agent
   that opened the draft, but a multi-iteration run will frequently
   switch agents (quota exhaustion, fallback order, manual restarts).
   Later contributions are invisible in the PR.

This spec addresses both: the PR body becomes a deterministic header +
checklist mirror of `index.md` plus a preserved/regenerated narrative
section, refreshed after every subspec commit; and attribution is
sourced from per-commit `Jarvis-Agent` git trailers rendered as a
per-commit list plus a deduped summary line.

## Decisions

- **Update cadence.** The PR body is rewritten after every successful
  subspec commit (the same code path that today calls `ensureDraftPr`
  once on the first subspec commit). WIP commits do **not** trigger a
  rewrite — they are noisy and would churn the PR. The first subspec
  commit still creates the draft PR; subsequent subspec commits update
  its body in place via `gh pr edit`.
- **Body shape (option 1c, hybrid).** The body has three sections,
  rebuilt from scratch on every update:
  1. **Deterministic header**, generated by jarvis from `index.md`:
     - H1 from `index.md`.
     - A "Progress" line: `N of M subspecs complete`.
     - The mirrored index checklist (each `- [ ]` / `- [x]` linked
       subspec line copied verbatim from `index.md`, preserving the
       link text and target).
  2. **Narrative section** (preserved/regenerated). The first time the
     body is built (i.e. the draft-PR-creation path), jarvis asks the
     active agent to produce a short summary of the spec via the
     existing `bodyGenerator` mechanism. On subsequent updates jarvis
     extracts the existing narrative from the live PR body (between
     two stable HTML-comment markers, see "Markers" below) and reuses
     it verbatim. If the markers are missing (legacy PRs, manual
     edits), the narrative section is omitted on this update; it will
     repopulate on the next draft-PR creation. The narrative is never
     regenerated on update, only on initial create.
  3. **Attribution footer**, generated by jarvis from `git log`
     trailers on the PR branch (see "Attribution" below).
- **Markers.** Jarvis brackets the narrative section with stable
  HTML-comment markers so subsequent updates can find and preserve it
  without disturbing manual reviewer edits elsewhere:

  ```
  <!-- jarvis:narrative:start -->
  …agent-authored summary…
  <!-- jarvis:narrative:end -->
  ```

  Reviewers may edit text *inside* the markers; jarvis preserves
  whatever lives between them. Reviewers may *not* expect edits to the
  deterministic header or footer to survive — those are rewritten on
  every update. This trade-off is documented in
  `docs/worktrees-and-commits.md`.
- **Attribution source: git trailers.** Every commit jarvis creates
  (subspec commits *and* `WIP:` commits) gains a
  `Jarvis-Agent: <attributionLabel>` trailer in the commit message.
  Stamping WIP commits keeps the data shape uniform even though the PR
  body only renders subspec commits. The trailer value is exactly
  `agent.attributionLabel()`.
- **Attribution rendering (option 2c).** The footer has two parts:
  1. **Per-commit list**, in chronological order, one bullet per
     subspec commit on the PR branch:

     ```
     - <short sha> <commit subject> — <agent label>
     ```

     Subspec commits are identified by their first body line starting
     with `Spec: ` (matching `commitSubspec`). Commits without a
     `Jarvis-Agent` trailer are listed with `unknown` as the label
     (covers legacy/in-flight PRs created before this change).
  2. **Deduped summary line**, preserving first-appearance order:

     ```
     Written by <Label A>, <Label B>, <Label C> through Jarvis.
     ```

     If only one unique label is present, the line collapses to the
     existing format: `Written by <Label> through Jarvis.`. If no
     trailers are found at all, the summary line is omitted (the
     per-commit list is still rendered with `unknown` labels).
- **Failure mode: warn and continue.** A failed `gh pr edit` (network,
  rate-limit, permissions) emits a `harness` warning to stderr and the
  iteration continues. The next successful subspec commit's body
  rewrite naturally heals the description, since the body is rebuilt
  from scratch each time. No persisted retry queue, no "dirty" state
  to track.
- **Backward compat.** PRs created before this change have no
  `Jarvis-Agent` trailers on existing commits and no narrative
  markers. The first post-upgrade update will:
  - Render the deterministic header (always works).
  - Omit the narrative section (no markers to preserve from).
  - Render the per-commit list with `unknown` for pre-upgrade commits
    and proper labels for post-upgrade commits.
  Old PRs are not retroactively rewritten outside their normal update
  cadence.
- **Ready-for-review transition unchanged.** `maybeMarkReady` in
  `src/modes/patch/pr.ts` continues to mark the PR ready when every
  linked subspec checkbox in `index.md` is checked. No change.
- **Scope cuts.**
  - No per-author `Co-Authored-By` trailer. The attribution stays in
    the PR body. (We can revisit if reviewers want git-blame-level
    attribution.)
  - No configurable trailer name or footer format.
  - No env-var or config flag to disable updates or attribution.
  - No update on WIP commits, even though they carry trailers.
  - No backfill of trailers onto pre-upgrade commits.
  - No protection against reviewer edits to the deterministic header
    or footer — those are rewritten.
