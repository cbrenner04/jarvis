## Verdict: refine before implement

The core design holds — three-bucket rank (running → gated → terminal), terminality from derived state rather than `finishedAtMs !== null`, terminals newest-finish-first. That is consistent with how `tui-monitor-lines.ts` already classifies terminality (`TERMINAL_PIPELINE_STATES`), and the work stays one module boundary and commit-sized. **No split is warranted.** But the spec understates blast radius, leaves one criterion unfalsifiable, conflicts with a queued sibling seed, and leaves two mutation anchors unspecified.

### Blocking refinements

1. **Name the third test file in the blast radius.** The reorder breaks order-sensitive assertions in `v2/src/tui/tui-monitor-lines.test.ts`, which the spec never mentions. Its `overflowPaneMonitorFixture` is all-`succeeded` with `finishedAtMs` ascending by index, so the new order reverses the painted sequence. Three tests must be repaired: `retains every full-flatten tree row id while painted tree rows stay within the pane budget` and `leftPaneTreeScrollOffset shifts painted tree rows without trimming monitorSelectableNodeIds` (both `toEqual` against the fixture array or a slice of it), and `resolves pipeline detail for off-pane tree row selection` (which picks `pipelines[maxVisibleRows]` as an off-pane element; under the new order that element is painted, so the off-pane pick must be re-derived, not just flipped). Add these to Tasks and to the preservation criterion. A spec that lands with an unlisted test file broken strands the implement run.

2. **Pin the fixture's timestamp relationship for the running/gated criterion.** Pre-fix code sorts running and gated together by `createdAt` ascending. The regression fails pre-fix — and the rank-collapse mutation goes red — only when the gated pipeline's `createdAt` precedes the running pipeline's. Choose it the other way and pre-fix order already equals post-fix order: the suite stays green and completion refuses the checkpoint as hollow. State the constraint as a decision, not as an implementer's inference.

3. **Fix the finishless-terminal premise.** `derivePipelineFinishedAtMs` (`v2/src/daemon/pipeline-observation.ts:159`) falls back `terminalPublicationSucceededAt` → max stage `endedAt` → `pipeline.createdAt` for every terminal state, so the daemon projection cannot emit a terminal snapshot with a null finish. The criterion as written pins a case reachable only by hand-constructing a snapshot. Either state honestly that this is a defensive fallback and cite the actual ingress that admits an absent/invalid field (`parsePipelineList` in `v2/src/tui/tui-daemon-client.ts` casts the wire payload without validation), or drop the criterion and keep the `?? createdAt` fallback as an unpinned safety default. Also drop the attribution to the `pipeline-terminal-timestamps` seed — that seed covers run `finishedAtMs`, stage `endedAt`, and approval `decidedAt`, and cannot produce or repair a finishless *pipeline*. The spec guidance's reachability rule applies: a premise about a forbidden condition needs a cited path by which it occurs on the base.

4. **Reconcile with the queued sibling that owns the same decisions.** `v2/spec/seeds/tui-unified-work-tree.md` carries the identical ordering decisions ("running items … → pipelines awaiting a gate … → terminal items (finish timestamp descending)"), the identical finishless-`createdAt` rule, and an AC pinning all three; `v2/spec/tui-command-center-brief.md` row 2 still tracks `running→gated→terminal order` as seeded. Worse, the two definitions of *running* disagree: the seed says "any live/active member," this spec says "neither terminal nor gated," so `pending` — a real `PipelineDerivedState` value — lands in different buckets under each. Add a task that prunes the now-superseded ordering decisions and AC from that seed, updates the tracker row, and states which `running` definition survives. This is exactly the same-seam-siblings failure the repo rule warns about.

5. **Name both `@mutate` anchors concretely.** Both checkpoint criteria promise "a uniquely occurring anchor" without saying what it is. A rank function's `return 0;` / `return 1;` lines recur and refuse as *several occurrences*, blocking completion. Specify the actual single-occurrence line each directive targets (the gated-rank expression; the terminal comparison line), and confirm each directive sits inside its pinning test body.

### Required corrections

6. **The preservation criterion asserts a falsehood.** Initial selection is order-derived — `firstSelectableNodeId` returns `monitorSelectableNodeIds(state)[0]`, the first flattened tree row — so on an all-terminal tree initial selection moves from oldest finish to newest. Selection is not "unchanged by the reorder." Remove selection from the preservation claim and record the new initial-selection behavior in the `v1-behaviors.md` documentation criterion. Separately, tests whose expectations are *rewritten* to newest-finish-first are behavior-change evidence, not preservation; keep the "stays green" claim scoped to the invariants that genuinely do not change (membership, retention, expansion).

7. **The comparator key set is internally inconsistent.** The declared keys are `running`, `gated`, `finishedAtMs`, `createdAt`, with no terminal key — so terminality is only inferable as "neither," and `{running: true, gated: true}` has no defined rank. Make the key set express the three states unambiguously.

8. **Preserve the coverage the folded test carries.** `orders active pipelines above terminals by createdAt then finishedAtMs` is the only existing pin on running-bucket `createdAt` ascending, and it pins two active pipelines. Folding it into three tests that each pin a single running pipeline silently drops that assertion, plus gated-bucket internal ordering and the "`pending` rides in the running bucket" decision. Every acceptance outcome the superseded test carries must survive somewhere in the replacements.

9. **Correct the pane prerequisite.** The claim that "the left pane flattens the whole tree and scrolls a viewport over it, so top-level order is not truncated by pane height" is only half true: `monitorLeftPaneTreeRows` slices painted rows to the viewport (`v2/src/tui/tui-monitor-lines.ts:530`); it is *selectability* that spans the full flatten. This misreading is what hid the blast radius in item 1.

10. **State tie behavior.** Merged multi-socket snapshots can carry duplicate pipeline ids, and the spec should say what happens on equal sort keys (stable sort preserves merge order) rather than leaving determinism implicit.

11. **Tighten the documentation criteria.** § Observe of the operator runbook describes the left pane in more than one place — name the paragraph the change lands in. And `v2/docs/v1-behaviors.md:615` will describe the unattributed segment as sorting terminals oldest-finish-first directly alongside a tree that now sorts newest-first; record that as a known temporary inconsistency the unified-work-tree work resolves, rather than leaving two contradictory sentences unexplained.

12. **Acknowledge the placement consequence.** A finishless terminal ordered by `createdAt` sits systematically higher among terminals than its true finish would place it, by roughly its own duration. That is strictly better than the current epoch coercion, but it should appear as an accepted consequence rather than an implied "sorts near its peers."
