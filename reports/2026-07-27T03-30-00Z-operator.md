## The session's main finding

**The kill design that failed four times shipped, by deleting the discriminant rather than fixing
it.** Every prior attempt gated `run kill` on a *stall* signal, and each failed for one structural
reason: every signal tried coincides with the run terminating, so no `(live ∧ reapable)` state is
ever observable by a real kill. One attempt (#1760) was a faithful implementation that was a
runtime no-op, proven by 8 trials × 200 macrotask kill-polls → zero reaps.

The rewrite (#2192) dropped the stall discriminant entirely: **authorization is liveness**, the same
predicate the write-loop path already uses. One `AbortController` per workflow invocation, injected
daemon-side onto the steps handed to `executeWorkflow` — it cannot come from the caller because
steps cross IPC as JSON. The plan's decisive acceptance criterion asserts the injected signal
actually aborts the in-flight step, which is exactly the check #1760 passed vacuously.

## Second finding: a shipped durability guarantee that never engages

`workflow-steps-commit-each-progress-iteration` shipped in-flight iteration commits so a mid-run
kill leaves prior commits on the branch. **It has never engaged on an implement run.**
`write-loop.ts:396` commits only when the agent returns `result.kind === "progress"`; an agent that
finishes returns `done`. Five run rows examined: every one consumed exactly one iteration, settled
`outcomeKind: "done"`, produced zero `iteration_commit` records.

Realized cost, three times this session: a killed run lost its entire worktree. `9c61a90e` lost 9
files, detach lost 10 files twice. Seed: `write-iteration-commits-never-engage` (#2198). The seed
names the coverage shape that let it ship — verification must observe a *killed* run, because a
completed run commits anyway and "commits exist after success" stays green against dead code.

## Capacity: the throttle was wrong

The "~2 concurrent implements" rule was over-broad. On 18 cores, load averaged ~3.0 with two live
runs, because the agent write phase is network-bound; only the ready gate saturates (default
`floor(parallelism / 2)` = 9 workers). The real constraint is concurrent **gates**, a minority of an
implement's wall clock. `JARVIS_TEST_CONCURRENCY` is honored and — unlike `JARVIS_READY_TIER` —
is *not* stomped by `ready-finalize.ts:177`, so the daemon was restarted with it at 4.

Note the daemon restart is gated on total quiescence, so this lever is only reachable in the gaps
between runs. That friction is recorded, not seeded.
