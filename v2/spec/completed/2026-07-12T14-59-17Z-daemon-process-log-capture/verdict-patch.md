## Verdict — refinements required

1. **Real capture and append-across-restart must be actually verified.** Every new test drives `startDaemon` with a `socketProber` that always returns `false`, so `startDaemon` always fails readiness and no live child process ever runs or writes to the log fd. The "writes to logPath" test only checks the file exists; the "appends" test pre-seeds content and confirms it's untouched by a failed start — neither exercises a real child writing through the inherited fd or a real restart appending after a prior daemon's output. This leaves the two most safety-critical acceptance criteria — "output written by the child after detach is readable in the file" and "the prior daemon's output is still present alongside the new daemon's" — ticked without evidence. Add coverage that spawns an actual short-lived child (e.g. a trivial `bun -e "console.log(...)"` process) wired to the opened log fd, waits for it to exit, and reads the file back to confirm both fresh-write and append-after-restart behavior.

2. **Remove the unrelated change in `v2/src/execution/workflow-runner.ts`.** Dropping `project, branch` from a destructure in `runStandardReviewStep` is outside this subspec's scope (daemon lifecycle, paths, CLI, docs). Revert it, or if it's a genuine unrelated fix, split it out of this branch — per repo convention, changes must stay within the active subspec's scope.

3. **Move the new log/rotation tests into the correct `describe` block.** The five new tests (log capture, directory-missing throw, rotation, append, no-logPath default) are nested under `describe("getDaemonStatus", ...)` even though they all exercise `startDaemon` options. Relocate them under the `startDaemon` describe block for accurate grouping.

4. **Add a test for the unwritable-path throw, not just missing-directory.** The acceptance criterion covers both "directory does not exist" and "cannot be opened for writing" as one bullet; only the missing-directory case has a test. Add a permission-denied (or otherwise unwritable) case to confirm the throw path is actually exercised, not just present in code.

Rationale: item 1 is required because AC verification must demonstrate the behavior it claims, not merely that a code path exists — ticking safety-critical ACs on tests that never run a real child understates risk in exactly the post-mortem scenario this spec exists to cover. Items 2–4 are scope and coverage-completeness issues consistent with this repo's "keep changes minimal and within scope" and "AC only ticked once actually satisfied" rules.
