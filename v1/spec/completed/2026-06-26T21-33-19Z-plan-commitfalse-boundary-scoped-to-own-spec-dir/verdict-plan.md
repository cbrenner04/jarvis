## Verdict

The mechanical fix (removing the racing sibling enumeration) is sound and the false-positive it eliminates is real. The spec must not ship as written, however: it frames a genuine loss of coverage as lossless and tests an untouched check as if it were the replacement. Required refinements:

1. **Record the dropped guarantee as an explicit, accepted tradeoff.** Removing `assertNoCommitExternalSpecBoundary` eliminates the *only* check that ever inspects external storage (`~/.jarvis/specs/<proj>/`). After removal, a `commit:false` plan that writes a rogue sibling into external storage is caught by nothing. The Decisions section currently implies this is fully covered by the surviving worktree/repo check — it is not. Add a load-bearing decision stating plainly that external-storage rogue-sibling *detection is removed*, that no concurrency-safe replacement exists without per-write attribution (a rogue sibling and a concurrent legitimate sibling are byte-identical signals at the external root, which is the root cause of the bug), and that the severity is low because the blast radius is Jarvis-owned scratch storage, never the user's target repo. This is the honest reason "scope → remove" is correct rather than a workaround.

2. **Fix AC #3's overclaim.** The surviving guard (`assertTargetRepoPlanBoundary`) flags only `spec/`-prefixed paths in the target checkout; it does not catch arbitrary out-of-own-dir writes (e.g., to `src/`), and it never inspects external storage. AC #3 currently asserts that a `commit:false` plan "writes into the worktree/repo checkout outside its own spec dir still trips the boundary violation" — this overstates what survives. Narrow it to the actual surviving contract (writes under `spec/` in the target checkout still trip) and drop any implication that external-storage escapes remain guarded.

3. **Correct the "isolated worktree" framing.** For `commit:false`, the plan runs against the shared live checkout (`project.root`), not a per-plan worktree; the isolation is the external spec *dir*, not a worktree. Fix the Problem section so the safety argument does not rest on worktree isolation that does not exist on this path.

4. **Make the cleanup precise and honest:**
   - State that the sibling-enumeration test coverage is *dropped*, not replaced — silent removal reads as "still covered."
   - Explicitly scope removal to the `preExistingSiblings` snapshot only; keep `externalSpecRoot`, which remains load-bearing (dir creation, collision detection, preserved-spec breadcrumb). Guard against an over-eager implementer removing both.
   - Name the specific no-commit call site to change (the draft/review no-commit branch) and confirm the `commit:true` `assertPlanWriteBoundary` call site is untouched, rather than a plural "call sites" that invites collateral edits.

5. **Keep the docs coherent.** The `plan-mode.md` rewrite must not merely soften the sibling sentence — it must re-explain *why* concurrent no-commit plans coexist now that the guard is gone (coexistence holds precisely because the external check no longer enumerates siblings). The `v1-behaviors.md` entry must record the new behavior — including the dropped detection — as the v1 parity baseline, per the rule that any change to existing functionality updates that catalog.

**Rationale:** The quality bar requires specs to be honest ledgers — decisions must name the wrong alternative they rule out and must not present a coverage drop as preservation. Acceptance criteria must verify the behavior that actually survives, not a check the change leaves untouched (an AC that tests an unrelated guard is the same defect class as paraphrasing untested behavior). None of this changes the code direction — the removal is correct — but the spec's decision record, AC #3, framing, and docs must stop claiming a safety net that no longer exists.
