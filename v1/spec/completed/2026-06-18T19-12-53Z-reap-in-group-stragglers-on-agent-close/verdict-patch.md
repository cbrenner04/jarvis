# Verdict — `reap-in-group-stragglers-on-agent-close`

The shipped behavior is correct and the PR is the right size. During implementation the obvious approach — reaping inside the success branch before final settlement, exactly as the spec instructed — was found to deadlock: a straggler that inherits the agent's stdout/stderr pipes holds them open, so the stream-end conditions gating settlement never fire and the run hangs. The code correctly routed around this by moving the reap to a process `exit` handler, which fires independent of pipe teardown; killing the group then closes the inherited pipes and lets settlement proceed. That is the right fix and must stand. The defect is that this discovery never propagated back into the spec, the acceptance criteria, or the durable docs, which still describe the abandoned design — and one acceptance criterion is ticked while being literally false against the shipped code. The following must be corrected.

## Required outcomes

1. **Durable docs and spec must describe the mechanism that actually shipped.** The subspec Behavior/Tasks sections, AC#1, `v1/docs/run-loop.md`, and `v2/docs/v1-behaviors.md` all locate the reap at the "close branch / success branch (spawn.ts:79–80)." The reap actually runs in a separate process `exit` handler, not in the settlement/close branch. A v2 reader following the catalog citation to that line finds only `settle()` and concludes the catalog is stale. Align all four artifacts to the `exit`-handler mechanism. The prompt's opening rule is explicit: when the mechanism changes, the durable docs must be aligned in the same subspec, not deferred.

2. **Capture the deadlock rationale in the docs, not only the code comment.** The choice to reap on `exit` rather than at settlement is non-obvious and load-bearing: a future maintainer who "simplifies" it back into the success branch reintroduces the hang. The implementation comment already explains why; that reasoning (straggler inherits the pipes → close/settlement would deadlock → `exit` fires independent of pipe teardown) must also live in the durable doc entry so the constraint survives independent of the code comment.

3. **Reconcile the `code === undefined` claim — the code and the artifacts must agree, and AC#1 must be true before it is ticked.** Settlement classifies both `code === 0` and `code === undefined` as `ok`, but the shipped reap guard is `code === 0` only; the `undefined` case does not reap. AC#1, the Behavior section, and both doc entries assert that `code === undefined` *also* reaps, and AC#1 is checked `[x]`. That criterion is unsatisfied for the half it claims. Resolve the contradiction in one direction: either the docs/spec/AC are corrected to state the reap fires on `code === 0` (with a brief note on why the `undefined` case does not arise on the `exit` event — Node delivers `null`, not `undefined`, on signal termination there), or the guard is widened to match the documented behavior. Do not leave a ticked criterion describing behavior the code does not implement.

4. **The kill-failure test must actually pin the contract it names.** AC#3 requires that a kill failure during the reap leaves the settled result kind and exit code unchanged. The current test runs a bare `exit 0` binary with no descendant and asserts only `result.kind === "ok"` — an assertion that holds on any clean exit whether or not the reap path executes, so the test would still pass if the entire reap handler were deleted. Strengthen it so it fails when the reap path is removed: assert that the stubbed kill was actually invoked (e.g., a call counter), so the test demonstrates the reap ran, threw, and was swallowed without altering the result. The global `process.kill` stub with `finally` restore is an acceptable mechanism (no new public/option surface); only its assertion strength is deficient.

## Out of scope — no action required

- **`realpathSync(cwd)` in the new tests.** This matches the established convention in the pre-existing tests in the same file; consistency is the right call, not a defect.
- **Error-path / quota / `child.on("error")` stragglers are not reaped.** This is the spec's intended boundary (success branch only; abort and timeout already group-kill), correctly implemented. The docs already enumerate the excluded paths. An additional "failed agents still leak stragglers" sentence is optional polish, not required.
- **A dedicated abort-with-straggler interaction test.** The `exit` handler is guarded by `abortReason === null`, so it provably no-ops on any abort/timeout; the interaction is safe by construction and the existing abort/timeout suite is unchanged. AC#4 is satisfiable without a new test.
- **Enumerating D-state / uninterruptible-sleep edge cases in the comment, or a "must not delay settlement" timing clause.** `process.kill` is non-blocking and the iteration watchdog backstops pathological cases; this is speculative precision about a non-risk.
