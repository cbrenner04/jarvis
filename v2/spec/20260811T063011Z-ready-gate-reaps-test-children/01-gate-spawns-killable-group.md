# 01 - Gate and required-integration invocations spawn in a killable group bound to run termination

Module boundary: execution (`v2/src/execution/ready-finalize.ts`, `v2/src/execution/write-loop.ts`).

`createDefaultRunReadyGate` calls `runner.runAsync("bun", ["run", "ready"], worktreePath, { maxBuffer, env })` with no `signal` and no `processGroup`, and `createDefaultRunRequiredIntegration` passes even less. Terminating a run (kill, abandon, iteration timeout, or settlement after daemon loss) unwinds the harness while the gate's `bun test` tree keeps running — observed surviving for days and starving the machine. This subspec binds both invocations to the run's termination signal in process-group mode, and makes sure a kill mid-gate doesn't get misclassified as a real gate failure. Recording the spawned group id on the run row is `02`.

## Decisions

- Call-time signature, not construction-time closures: `ReadyGate` and the required-integration runner type both widen from `(worktreePath, baseRef) => Promise<void>` to `(worktreePath, baseRef, options?: { signal?: AbortSignal }) => Promise<void>`. `createDefaultRunReadyGate`/`createDefaultRunRequiredIntegration` read `options?.signal` and pass it straight through to `runner.runAsync(..., { signal, processGroup: {} })`. `ReadyFinalizeInput` gains `signal?: AbortSignal`, and the finalizer returned by `createReadyFinalizer` passes `input.signal` as the third argument to both invocations. This is bounded: it touches the two default-gate bodies, the two exported function types, and `ReadyFinalizeInput` — not every seam mock, since the added parameter is optional and existing mocks in `ready-finalize.test.ts` that ignore a third argument keep compiling.
- The run's existing termination `AbortSignal` (`WriteLoopInput.signal`, aborted by the daemon's per-run `abortController` on kill/abandon) is the binding, not a new controller. `runReadyFinalizer` in `write-loop.ts` passes `args.signal` into the `finalInput` object it builds for `readyFinalizer(finalInput)` — `args.signal` is already reachable there today (`WriteLoopInput["signal"]`), so no new plumbing is needed to get the signal to this call site.
- Group mode's `maxBuffer` is not honored: `shared/subprocess.ts`'s `runGroupMode` path buffers stdout/stderr unbounded regardless of `maxBuffer`, unlike the default `execFile` path. This subspec accepts unbounded output capture for both invocations rather than extending group mode with a cap — gate output volume is bounded in practice by the test suite's own output, and the shared runner's capture behavior is out of this subspec's module boundary. `maxBuffer` is dropped from the "preserved options" claim; the preservation criterion instead pins command, args, cwd, and `env`.
- Abort-caused rejection must not read as a real gate failure. When `runner.runAsync` rejects because the run's signal fired (group killed, not a genuine test failure), `createDefaultRunReadyGate`/`createDefaultRunRequiredIntegration`'s catch checks `signal?.aborted` (the same signal passed to `runAsync`) before wrapping into `ReadyGateError`; when aborted, it rethrows the underlying error unwrapped instead. `publishWithReadyRepair` in `write-loop.ts` gains a check immediately after gate-failure classification: `if (isActiveReadyGateFailure(outcome) && args.signal?.aborted) return buildReadyRepairPublishResult(outcome, iterationsConsumed)` — this reuses the existing "not an active failure" return shape (same as a timed-out gate) so the repair loop (`runReadyGateRepairLoop`, which spends real agent iterations) is never entered once the run is aborted. The caller in `write-loop.ts` (~line 1779) already routes any returned failure to `finishLoop(..., "progress", ..., true)` when `args.signal?.aborted`, so the terminal status of a run killed mid-gate is unaffected by this subspec — this decision only stops the repair loop from doing wasted/unsafe work against a terminated worktree in between.
- Scope is the spawn options, the abort/classification guard, and the reap regression: test selection, `JARVIS_READY_TEST_SCOPE` derivation, and repair behavior for genuine (non-abort) failures are untouched.

## Task checklist

- [ ] Widen `ReadyGate` and the required-integration runner type with an optional third `{ signal?: AbortSignal }` parameter; widen `ReadyFinalizeInput` with `signal?: AbortSignal`; thread `input.signal` from the returned finalizer into both invocations.
- [ ] Pass `signal` and `processGroup: {}` in both `createDefaultRunReadyGate` and `createDefaultRunRequiredIntegration`, keeping command, args, cwd, and `env` unchanged; drop `maxBuffer` from both calls.
- [ ] In both invocations' catch blocks, check `signal?.aborted` before classifying as `ReadyGateError`; rethrow unwrapped when aborted.
- [ ] Thread `args.signal` from `runReadyFinalizer` (`write-loop.ts`) into the `finalInput` passed to the finalizer.
- [ ] Add the `args.signal?.aborted` short-circuit in `publishWithReadyRepair` immediately after gate-failure classification, before the repair-allowset/repair-loop path.
- [ ] New integration regression `v2/src/execution/write-loop-ready-gate-reap.sandbox-unrunnable.test.ts`: drive a run to a gate that spawns a real, long-lived child process group, abort the run's signal, and assert the group is gone.
- [ ] Unit tests in `v2/src/execution/ready-finalize.test.ts` asserting the spawn options (`signal`, `processGroup`, no `maxBuffer`) for both invocations, and that an abort-caused rejection from each invocation is not wrapped in `ReadyGateError`.
- [ ] Unit test in `v2/src/execution/write-loop.test.ts` (or the sibling repair-loop test file) asserting that an aborted signal short-circuits `publishWithReadyRepair` before any repair iteration runs.

## Acceptance criteria

- [ ] Terminating a run whose ready gate is mid-flight leaves no surviving test descendant: a new `v2/src/execution/write-loop-ready-gate-reap.sandbox-unrunnable.test.ts` drives a run to a gate spawning a real process group, aborts the run signal, and polls `process.kill(-pgid, 0)` until it throws `ESRCH` (bounded deadline, not a single immediate check, so the SIGTERM→SIGKILL escalation has room to complete) — it fails against the pre-fix code, where the group survives past the deadline. The fixture's child ignores SIGTERM (or sleeps past the grace window) so the assertion actually exercises the SIGKILL escalation rather than passing on a lucky SIGTERM exit.
- [ ] The gate and the required-integration invocation each spawn in group mode bound to the run's termination signal, asserted from the spawn options captured by a mock `AsyncSubprocessRunner` for both invocations in `v2/src/execution/ready-finalize.test.ts`.
- [ ] A gate that completes normally is unaffected: the existing `v2/src/execution/ready-finalize.test.ts` `createReadyFinalizer` tests stay green, including `runs the ready gate then flips the draft PR on green`, `overrides inherited JARVIS_READY_TIER=fast with full in the gate's child env`, `carries the ready gate command, exit code, and combined output`, and `runs required integration scope after ready gate and before flip`.
- [ ] A gate that fails because it was killed by an aborted run signal is not classified as `ready_gate_failed` and never enters agent repair: a new test in `v2/src/execution/write-loop.test.ts` — `an aborted signal short-circuits ready-gate repair without spending an iteration` — drives `publishWithReadyRepair` with a mock gate that rejects while `args.signal.aborted` is true, and asserts `runReadyRepairIteration`/the repair loop is never invoked; it fails against the pre-fix code, which would classify the rejection as `ReadyGateError` and enter repair.
- [ ] Dropping the run signal turns the binding assertion red: replacing the gate's `signal` option with `undefined` leaves the gate unbound from run termination. `v2/src/execution/ready-finalize.test.ts` — `spawns the ready gate in group mode bound to the run signal`; Mutation checkpoint: the captured spawn options no longer carry the run's signal.
- [ ] Dropping the required-integration invocation's binding turns its own assertion red, independent of the gate's. `v2/src/execution/ready-finalize.test.ts` — `spawns required integration in group mode bound to the run signal`; Mutation checkpoint: replacing the required-integration invocation's `signal` option with `undefined` leaves that spawn unbound while the gate's spawn (previous checkpoint) stays bound.
- [ ] Reverting the gate's spawn options to baseline (`{ maxBuffer, env }` — no `signal`, no `processGroup`) turns the reap regression red. `v2/src/execution/write-loop-ready-gate-reap.sandbox-unrunnable.test.ts` — `terminating a run mid-gate kills the ready gate process group`; Keystone checkpoint: a surviving revert means the group-mode spawn is inert.
- [ ] `bun run typecheck`, `bun run test:v2`, and `bun run test:integration:v2` pass.
