## Refine turn 1

### Machine check

### Root cause

The failing spec at `~/.jarvis/specs/genomics-stream/lab-systems-testing-evidence-scanner/index.md` was generated by `jarvis plan` against the registered project `genomics-stream`. The plan command injects a `repo:` line into the generated `index.md` via `injectRepoLineIntoIndex` in `src/commands/plan.ts:2402`, which prefers the project's `origin` URL but **falls back to `project.key`** when no origin is configured:

```ts
const repoValue = project.origin ?? project.key;
// ...
lines.splice(1, 0, `repo: ${repoValue}`);
```

The `genomics-stream` project in `~/.jarvis/config.json` does not have an `origin` set (likely because the target directory is not a git repo, or `jarvis init` didn't detect one), so plan mode wrote `repo: genomics-stream` into the spec.

At `jarvis run` time, `resolveProject` in `src/resolve-project.ts:55` processes the spec's `repo:` value. For a non-absolute value (line 83), it calls `normalizeRepoUrl(repoValue)`. `normalizeRepoUrl` in `src/repo-url.ts:18` requires either a `owner/repo` slug pattern or a full URL with at least `host/owner/repo` (three path parts). A bare token like `genomics-stream` has no `/`, so `normalizeRepoUrl` returns `undefined`, and the resolver errors out with `unrecognized \`repo:\` value: genomics-stream` (line 88).

### Asymmetry in the existing resolver

`resolveProject` already accepts a bare registered project key when it arrives via `--repo`. In `resolveFromFlag` (line 166), the flag value is first matched against `projects.find((p) => p.key === trimmed)` before URL/slug normalization. The spec `repo:` path (Step 2) skips this name-match entirely and only tries URL/slug normalization. Plan mode's own fallback (key) is therefore inconsistent with what the run-time resolver accepts from a spec.

This is the core bug: **plan mode writes values that `jarvis run` cannot read back.**

### Fix options (for the drafter)

There are two reasonable directions; both should be considered, and the spec should pick one (or do both).

1. **Resolver accepts registered project keys from spec `repo:` (preferred, fixes existing broken specs in place).**
   - In `resolveProject` Step 2, before calling `normalizeRepoUrl`, try `projects.find((p) => p.key === repoValue)` and resolve to that project (source: `spec-repo`, mode: `registered`) if matched.
   - Matches symmetry with `--repo <name|path|url>`. README/docs already say `--repo` accepts a name; this brings spec `repo:` to parity.
   - Portability caveat: project keys are local to one user's `~/.jarvis/config.json`. Documented behavior should call this out and continue to recommend URL/slug for portable specs. For no-commit specs that live in Jarvis-owned storage and are inherently single-machine, accepting a key is fine.

2. **Plan mode stops emitting bare keys; emit nothing when no origin is known.**
   - Change `injectRepoLineIntoIndex` so that when `project.origin` is undefined, it does **not** fall back to the key. Either skip injection or compute a best-effort origin (e.g. try `git -C <root> remote get-url origin` at plan time).
   - Cleaner for portability but does not repair existing broken specs already on disk.

Doing **both** is best: fix the resolver so existing specs run, and fix plan mode so future specs are portable when an origin exists.

### Resolution-order placement

If accepting keys in Step 2: place the name-match **before** the absolute-path branch (line 69 of `resolve-project.ts`) so that a key never accidentally matches an absolute path. Concretely, the new order inside Step 2 should be:

1. Registered project key match.
2. Absolute path → exact-root match (existing legacy behavior).
3. URL/slug → `normalizeRepoUrl` + loose origin match.

Project keys are constrained by the existing config schema to non-empty strings; the only collision risk is if a user registers a project whose key happens to be a valid `owner/repo` slug. That should still resolve to the registered project (name beats URL match), matching `--repo`'s precedence.

### Scope boundaries

- **In scope:** Make spec `repo: <registered-key>` resolve when the key matches a project in `~/.jarvis/config.json`. Update tests in `src/resolve-project.test.ts` (or equivalent). Update `docs/spec-guidance.md`, `docs/run-loop.md`, and the README sections that enumerate accepted `repo:` forms to document the new accepted form.
- **Out of scope:** Re-running `jarvis init` for `genomics-stream` to back-fill an origin URL. The fix should make the existing spec on disk work as-is. Changing `--repo` flag behavior. Migrating other registered projects. Reworking how plan mode chooses what to write (this could be a follow-up subspec but is not required for the bug fix).

### One additional load-bearing point: there are TWO spec-repo failure paths, not one

Turn 2 said to reuse `formatUnknownRepoError` at "the spec-repo URL/slug failure at line 88." Re-reading Step 2 in full, that's incomplete. Step 2's URL/slug `else` branch (lines 83–110) has **two** ways to not resolve:

1. **`normalizeRepoUrl` returns undefined** (line 85) → currently returns `kind: "error"` with the bare message (line 88). This is what the reported bug hits.
2. **`normalizeRepoUrl` succeeds but `matches.length === 0`** (the implicit fall-through at line 109) → currently falls through to Steps 3–5 (path-based resolution, then prompt/error). It does *not* return an error here.

These are different shapes and the drafter must decide whether the new registered-key check changes either fall-through. The recommended behavior:

- **Path 1 (current bug):** After the new registered-key match at the top of the Step 2 block fails AND `normalizeRepoUrl` returns undefined, return `kind: "error"` with `formatUnknownRepoError(repoValue, projects)` (lead-in adapted for `repo:`). This replaces the bare line-88 error and gives the user the registered-keys list. This is what subspec 1 must do to make the failing command resolve.
- **Path 2 (no-matches fall-through):** Leave as-is. A spec with `repo: https://github.com/owner/somerepo` where no registered project's origin matches should continue to fall through to Steps 3–5 so an ad-hoc git-checkout walk can still find a checkout. Do not convert this into an error; that would regress unregistered-but-on-disk repos. The new key check sits *before* `normalizeRepoUrl`, so it does not affect this branch.

Spelled out, the new Step 2 control flow (subspec 1 target) is:

```ts
if (opts.specRepo !== undefined && opts.specRepo.trim() !== "") {
  const repoValue = opts.specRepo.trim();

  // (a) NEW: registered project key match.
  const byName = projects.find((p) => p.key === repoValue);
  if (byName !== undefined) {
    return { kind: "ok", resolved: { project: byName, mode: "registered", source: "spec-repo" } };
  }

  // (b) Existing: absolute path → exact-root match (legacy).
  if (isAbsolute(repoValue)) {
    // unchanged
  } else {
    // (c) Existing: URL/slug.
    const normalized = normalizeRepoUrl(repoValue);
    if (normalized === undefined) {
      // CHANGED: use formatUnknownRepoError so the user sees registered keys.
      return { kind: "error", message: formatUnknownRepoError(repoValue, projects) };
    }
    // Existing match logic; matches.length === 0 still falls through to Steps 3–5.
  }
}
```

That is the minimum change set. Anything more (e.g. erroring on the no-matches fall-through, or adding a key check inside the absolute-path branch) is out of scope for subspec 1.
