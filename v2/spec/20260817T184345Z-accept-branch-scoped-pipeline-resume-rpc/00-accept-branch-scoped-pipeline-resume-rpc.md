# 00 - Accept branch-scoped pipeline resume RPCs

## Problem

`handlePipelineResumeHandler` reads only `pipelineId` and always calls `resumePipeline(..., { detachContinuation: true })`. The branch-scoped admission that landed in `resumePipeline` has no wire caller, so an operator cannot resume one failed fan-out branch over IPC: on a pipeline whose siblings sit at `awaiting` gates, the unscoped path derives `awaiting-approval` and returns `resumed` after claiming ownership, without reopening or dispatching the failed branch.

## Decision ledger

- `branchKey` is an optional field on the existing `pipeline_resume` params object, forwarded to `resumePipeline`'s `options.branchKey`. Rules out a second RPC method and rules out breaking unscoped callers.
- A supplied `branchKey` that is not a string, or is blank after trimming, refuses `invalid_params` at the handler before `resumePipeline` runs. Rules out forwarding a blank key so it lands as the library's `branch_not_found`, which reads as "that branch is gone" for what is a malformed request, and rules out collapsing a malformed key into unscoped whole-pipeline resume.
- The non-string rejection exists because a non-string `branchKey` faults inside `resumePipeline`'s admission (`branchKey.trim()` throws on non-strings): the guard prevents an unhandled handler fault, not just a nicer error message. Rules out relaxing the guard for message-quality reasons in a later slice.
- Whitespace-only keys are `invalid_params` at the handler, not `branch_not_found` from the library. Rules out `" "` meaning two different things depending on which layer answers.
- `trim()` is used only to test blankness; a non-blank key with surrounding whitespace forwards unchanged (untrimmed) to `resumePipeline`. Rules out the handler silently normalizing a key that downstream branch matching compares exactly.
- An unknown-but-non-blank `branchKey` (no matching branch on the pipeline) passes handler validation and reaches `resumePipeline`, which returns a `refused` result with reason `branch_not_found` — not `invalid_params`. Rules out the handler pre-checking branch existence and duplicating the library's admission logic.
- `branchKey: "default"` forwards unchanged; the library's existing `"default"`-aliases-omission handling stays the single home for that rule. Rules out a second alias check in the handler.
- Responses keep the existing envelope (`{ kind: "response", result: <ResumePipelineOutcome> }`); branch-scoped refusals pass through with their `branchKey`, `stageId`, and `status` detail as the library produced them. Rules out a parallel branch-only response shape and rules out re-wrapping refusals as RPC `error` frames.
- `detachContinuation: true` is unchanged for branch-scoped requests, so the handler still resolves after admission rather than after continuation. Rules out awaiting branch continuation on the scoped path only.
- Retirement (`daemon_superseded`) and missing/empty `pipelineId` (`invalid_params`) checks run before branch-key validation, pinned by a retiring-daemon-plus-malformed-branch-key case in the malformed-key test. Rules out a retiring daemon answering a branch-key validation error instead of `daemon_superseded`.
- CLI plumbing stays out of slice (`jarvis pipeline resume` keeps its current arguments); the TUI daemon-client's resume params type and branch-node behavior are likewise unchanged. `v2/spec/ready-intents/expose-branch-scoped-pipeline-resume-cli.md` owns the CLI surface. Rules out absorbing either operator surface into this PR.

## Task checklist

- Add a named fan-out pipeline definition (`intent` → `gate` → `plan` → `implement`, matching `pipeline-execution.test.ts`'s `FAN_OUT_PIPELINE_DEFINITION` shape) and a production-shaped fixture to `v2/src/daemon/daemon-pipeline-resume.test.ts` against the real state store: a succeeded intent stage with three `downstreamInputs`, branch rows at every post-split position including the gate, `default` post-split rows `skipped`, the target branch's gate `approved` and plan `failed`, and two sibling branches at their own `awaiting` gates.
- Add a branch-aware `resolveStage` stub that reads the `branchKey` `resolveStage` is called with and stamps it onto each dispatched step, mirroring `pipeline-execution.test.ts`'s branch-scope `dispatchLog` pattern, so the dispatch log is branch-attributable.

- Add in-body `// @mutate` directives for the keystone (forwarded branch scope) and each added validation guard on real production lines.
- Update `v2/docs/daemon-host.md` and `v2/docs/v1-behaviors.md`, correcting the existing statements that `pipeline_resume` does not accept a branch key.

## Implementer notes

- Keep the validation condition on one physical line so both mutation directives quote unique single-line text, for example `if (params.branchKey !== undefined && (typeof params.branchKey !== "string" || params.branchKey.trim() === "")) {`, and keep the forwarded scope on one call line so the keystone directive is stable.
- `daemon-pipeline-resume.test.ts` runs against a real `openStateStore`; build branch rows with `StateStore.createPipelineStageBranch`. Mirror `pipeline-execution.test.ts`'s `describe("resumePipeline branch scope", …)` fixture (`setupBranchResumeFixture`: one branch row per stage at every post-split position, default rows `skipped`, per-branch gate/plan/implement statuses) — build the same row shape against the real store instead of porting its in-memory fake.
- Name the pipeline definition (`intent` → `gate` → `plan` → `implement`, matching `pipeline-execution.test.ts`'s `FAN_OUT_PIPELINE_DEFINITION`) so the stage following the replayed one is fixed and the quiescence point doesn't move.
- Branch admission derives its boundary from the lowest position carrying both a `default` row and a branch row, so the fixture needs a branch row at the gate position too, and the post-split `default` rows must be `skipped`.
- Use the pin file's existing quiescence pattern for the async-dispatch assertion: `controllableBindingFactory`/`settle()` for the branch's dispatched step, `waitFor(...)` on the row's terminal status, then `flushBackgroundRuns()` — the same sequence used in `resume returns after admission before async continuation runs`.
- The pin file's existing `resolveStage` fakes are keyed only by `stageIndex` and ignore `branchKey`; the new tests need a fake that reads `deps?.branchKey` (the 5th `resolveStage` argument) and stamps it onto the returned step, mirroring `pipeline-execution.test.ts`'s `dispatchLog` pattern, so dispatched steps are branch-attributable.
- Add no test-only inversion hooks; every directive must mutate the real handler guard.
