## Verdict — minor test-fidelity gaps, no blocking defects

Both raised concerns are valid but narrow: they weaken the *proof* the render-level test provides, not the shipped behavior. No re-implementation is required. Two follow-up outcomes are required before this can be considered done:

1. **Document why the render-level test reconstructs the display instead of capturing the real rendered element.** The fake `inkRender` in `tui-ink-monitor.test.tsx` ignores the element `openInkMonitor` actually passes and instead calls `createMonitorDisplay` directly, unlike the precedent seam in `tui-log-follow-entry.test.tsx` which pushes the real element. This is a reasonable choice (walking the real tree would invoke `MonitorSessionRoot`'s `useState`/`useInput` outside a reconciler and throw), but it's undocumented, so a future reader would assume this test proves what `openInkMonitor` renders when it actually proves `createMonitorDisplay` colors correctly plus a separate assertion that `renderFn` is called. Add a short comment at the fake-capture definition stating this constraint and what the test does and does not prove.

2. **Note that the `Box`-wrapped row-layout path is untested.** `loadInkUi` with an injected fake `inkRender` never supplies `Box`, so `renderSegmentRow`'s real-Ink branch (used in production) never runs in this suite — only the `Fragment` fallback does. The "row text renders identically to today" acceptance criterion is therefore verified only on the fallback path, not the actual `jarvis tui` code path. Add a one-line note (in the subspec or next to the relevant test) scoping the "no spacing change" guarantee to the tested `Fragment` path and flagging the `Box` path as an inherited, pre-existing gap in the `loadInkUi(inkRender)` test seam — not something this subspec is expected to newly solve with heavier render infrastructure.

Both are documentation/comment additions clarifying the actual scope of test coverage; no test infra rewrite (e.g., `react-test-renderer`) is required for this subspec.
