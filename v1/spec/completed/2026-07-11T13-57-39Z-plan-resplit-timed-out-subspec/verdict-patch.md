Verdict: three required outcomes.

1. **Checkpoint-safety guard must check the correct receipt path.** `assertRecoveryCheckpointSafe` currently hardcodes `join(projectRoot, ".git", "jarvis", "iteration-timeout-checkpoint.json")`, but the receipt actually lives at the patch worktree's linked git-dir (resolved via `git rev-parse --git-path jarvis/iteration-timeout-checkpoint.json`, scoped to that worktree), per `timeout-checkpoint.ts` and `v1/docs/run-loop.md`. As written, the guard can never find a real receipt once the worktree has been removed but the checkpoint file survives — precisely the case the spec's "pending timeout-checkpoint receipt" refusal AC exists to catch. Fix so the guard resolves the actual receipt path and correctly refuses recovery when a pending/malformed/mismatched receipt exists.

2. **Replacement count must be verified as newly-created files, not inferred from total sibling count.** `validateRecoveryReconciliation` counts all `NN-*.md` siblings excluding only the old file's basename. In a tree with ≥2 preexisting completed subspecs, this check passes even if drafting produced zero new replacement files. This doesn't actually enforce the spec's "two or more independently testable... sibling subspecs" requirement. Fix so the check verifies at least two files were newly added by this recovery draft (e.g., diff the sibling set before/after drafting), not just that the post-draft count is ≥2.

3. **Blockers appended by the agent during drafting must be observable by validation.** In `run.ts`, `intent.md` is force-restored to its original content immediately after drafting and before `validateDraftOutput` runs. Since blocker detection (`hasGenuineBlocker`/`detectBlocker`) reads `intent.md` from disk, any `## Blocker` the agent wrote is destroyed before it can be seen — recovery drafting failures can only ever surface as generic validation/reconciliation errors, never the agent's actual blocker reason. This breaks the spec's documented blocker path. Fix so blocker detection happens before `intent.md` is overwritten, or the blocker content is captured/diffed prior to restoration.

Rationale: findings 1 and 3 are correctness bugs that silently defeat two explicit acceptance criteria (checkpoint-safety refusal and blocker surfacing on drafting failure); finding 2 leaves the replacement-count AC unenforced in a realistic case (recovering in a tree with existing completed neighbors). All three must be fixed before acceptance. The dead ternary in `plan-args.ts` and the missing `stripNonContractIndexLines` call in the recovery path are minor/cosmetic and do not block acceptance, but should be cleaned up while in the area.
