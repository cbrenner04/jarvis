## Verdict: Required Refinements

1. **Post-merge trunk safety net.** The spec must state explicitly what happens on `push` to `main` (this repo's trunk-only push trigger): it must always run the full `bun run test`, regardless of changed paths. Rationale: scoping trunk pushes the same as feature-branch PRs removes the safety net that catches two independently-scoped, individually-safe PRs combining to break something neither touched alone. This is a load-bearing decision the current draft leaves as an accidental byproduct of base-SHA plumbing rather than a stated choice.

2. **Fail-safe catch-all for unmatched paths.** Add an explicit decision: any changed path that does not match `v1/**`, `v2/**`, `shared/**`, or a recognized root-tooling pattern must trigger the full suite. As written, a diff like a root-level `README.md` change (not `package.json`, not `tsconfig*.json`, not under `.github/workflows/**` or `scripts/**`) falls through every existing rule with no defined outcome. The intent's own "never skip a surface by mistake" principle requires a fail-safe default, not just the two narrower escape hatches already listed.

3. **Merge-base/diff mechanics must be pinned down.** Per spec guidance, harness subspecs should name exact mechanisms when structure is the contract — and git diff/ref resolution is exactly that kind of contract here. The spec must specify: which diff form is used (two-dot vs three-dot) and against which refs for `pull_request` vs `push`; and that an all-zeros base SHA (`0000...`, which GitHub sends for a new branch's first push or certain force-push cases) is treated as unresolvable and falls through to the full suite, same as any other unresolvable-base case.

4. **Explicit job/workflow structure decision.** The spec must decide and state whether scoping is implemented as one job with conditional steps or as separate filtered jobs, and why. This has real consequences for branch-protection required-status-checks (a required check whose job is skipped can block merges indefinitely). A single job with conditional steps — preserving one stable job name regardless of which scripts run — should be the stated default unless the spec gives a different structure with an explicit branch-protection-compatible rationale.

5. **Testable classification logic.** At least one acceptance criterion must be verifiable via `bun run test`/`bun run typecheck` rather than only by observing live GitHub Actions runs, consistent with how this repo normally gates subspec completion. The spec should call for extracting the changed-path → scripts-to-run classification into a unit-testable function/script with its own test file (inputs: changed paths + base-SHA resolvability; output: which scoped scripts to run), and add acceptance criteria against that unit, not only against live CI behavior.

6. **Explicit combined-surface acceptance criterion.** Add an acceptance criterion covering a diff that touches both `v1/**` and `v2/**` (no `shared/**`): it must run both `test:v1` and `test:v2` (and `test:integration:v2` per the existing v2-coverage rule). The per-surface decisions are only implicitly non-exclusive; this case should be exercised directly rather than left inferred from the `shared/**` case.

Not required, but recommended as low-cost additions during refinement (not blocking): a one-line rationale for why `test:shared` itself is never invoked (shared changes must satisfy both consumers, not its own suite), and a one-line note flagging the `bun run test` ⊇ `test:v2` + `test:integration:v2` equivalence as a known, pre-existing assumption this spec relies on but does not re-verify. Documentation location (runbook vs. AGENTS.md) is fine as drafted — no change needed.
