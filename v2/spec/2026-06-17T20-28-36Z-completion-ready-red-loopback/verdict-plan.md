# Verdict — Refinements Required

The spec's core design decision — loop a red completion `ready` back into one counted, `maxIterations`-bounded fix-up iteration rather than exiting `1` on finished work — is sound and consistent with the intent. Uphold it. The loop-back vs. error decision, the red→green progress test, and the recoverable-stop-with-pointer direction all stand. But the spec under-specifies five mechanisms that are this spec's own first-consumer responsibility, contains one correctness gap behind an acceptance criterion, and bundles independent changes. The following refinements are required before this draft is ready.

## Must-fix (load-bearing; refine in place)

1. **Pin the new exit code as a concrete value, not a negative description.** The exit-code space `0–9` and `130` are fully assigned; "not `4`, not `1`" leaves no value to emit or to write into the stop-conditions table. This spec is the first (and only) consumer of the new stuck-red stop, so the integer and its reason string must be pinned here — this is not deferrable to a later caller. Add an acceptance criterion asserting the specific code and reason. The doc task that says "write its new exit-code row" cannot be satisfied without it.

2. **Specify how the captured `ready` failure becomes the fix-up iteration's task.** The iteration loop short-circuits to the completion path *before* any prompt is built whenever zero boxes are unchecked, and the only prompt-construction path today reads an unchecked spec task. Feeding free-text `ready` output as "the next task" requires a prompt path that does not exist. The spec must define how the captured text reaches the agent and how the zero-unchecked short-circuit is bypassed for a fix-up iteration. This is the central new mechanism and is currently asserted, not designed.

3. **Define the "unchanged `ready` failure" comparison contract.** The captured failure text embeds non-deterministic content (timings, durations, deadline messaging, absolute paths). A raw equality test would almost never report "unchanged," so the stuck-red stop would rarely fire and the run would burn to `maxIterations` instead. Since "changed body = progress, unchanged = stop" is the pivot the recoverable stop depends on, the spec must define the normalization/comparison rule (or explicitly defer it to first consumer with the standard inline marker). Treating "changes between iterations" as trivial is the gap.

4. **Reconcile blocker/dirty detection with full completion — AC 6 currently sits behind an unreachable path.** The `## Blocker` (exit `7`) detection in the iteration loop is gated on an active linked subspec resolving, but at full completion no unchecked subspec link exists, so that resolution returns nothing and the in-iteration blocker check does not run as written. (The dirty-worktree exit-`6` path is separate and does fire at completion.) The spec promises blocker/dirty precedence over the stuck-red stop (AC 6) but does not establish that the blocker path executes during a fix-up iteration. The spec must specify how a `## Blocker` added during the fix-up iteration is detected, or AC 6's exit-`7` guarantee is unfounded. This is a correctness gap, not a doc nit.

5. **Specify telemetry / run-summary treatment for the new iteration shape and stop.** The run summary derives implementation-iteration counts from per-invocation telemetry keyed on checkbox/completion logic that will not naturally fire for a fix-up iteration where all boxes are already ticked. The intent's "counts against `maxIterations`" has no telemetry anchor in the spec. Per harness-subspec convention, name the telemetry rows that are the contract: the fix-up iteration's record, the red→green proceed, and the stuck-red stop's reason. Without this, "counts as an iteration" and the new stop are unobservable in telemetry and the summary will misreport.

6. **Split the subspec into independently reviewable changes and update `index.md`.** The single subspec bundles three separable concerns: (a) introducing the completion `ready` gate and reconciling it with the shrink and review `ready` invocations; (b) the loop-back iteration, `maxIterations` accounting, and suppression of the checkbox-delta no-progress stop; (c) the new exit code, stuck-red stop reason, message, worktree pointer, and telemetry. Each is independently testable; together with tests this approaches the reviewability warning threshold. Split into at least two atomic subspecs and route them from the index.

## Refine for accuracy and scope (prose/boundary fixes)

7. **Re-ground the Problem section and Decisions 1–2 on the real post-completion `ready` control flow.** Today the *first* `ready` at completion is the shrink pre-gate, which on red **warns and skips shrink** rather than exiting; the review baseline gate is the first that **hard-exits `1`**; and `maybeMarkReady` runs `ready` again on the no-shrink/no-review branch. The spec narrates as if review baseline is the first and only relevant gate. The design (a new gate before both phases) survives this correction, but the prose must name shrink's warn-and-skip-on-red behavior, identify review baseline as the first hard-`1`, and enumerate the full set of post-completion `ready` invocations (shrink pre-gate, review baseline, review final, `maybeMarkReady`) stating which the new gate makes redundant. Restate Decision 1's hole accordingly.

8. **Specify the capture mechanism relative to the existing throw-with-prefix behavior.** The shared ready helper *throws* the failure as an `Error` prefixed `bun run ready failed:\n…`; the spec wants to *capture* it and pins that exact prompt text as if it arrives clean. State whether the completion gate catches that Error (and how it derives the prompt text from it) or uses a capture-only variant. Drop the "no `check:fix` commit on the red path" statement as a design property — it is inherent to the helper (red throws before the commit path), not something this spec introduces.

9. **Scope the green-path "unchanged" claim and reconcile AC 8 with the task list.** Inserting a gate before shrink adds a `ready` invocation (cost, wall-clock, and a possible extra `check:fix` commit), so AC 7's blanket "behavior is unchanged" is too strong: scope it to operator-visible completion semantics (`spec complete`, PR URL, draft→ready). AC 8 ("no completion-path run exits `1` solely because `ready` was red") is global, but the task list only mentions adjusting the review baseline gate; since shrink already swallows red and review baseline exits `1`, either narrow AC 8 to the reconciled gates or add the relevant gate work to the task list so the global claim is actually satisfiable.

10. **Split AC 4 into separately verifiable criteria and tidy boundaries.** AC 4 bundles five conditions (still-red AND no-checkbox AND no-blocker AND unchanged-failure AND specific stderr content) into one checkbox; separate the "stop fires under these conditions" assertion from the "stderr names the captured failure + worktree path + triage command" assertion. Draw the out-of-scope boundary against shrink explicitly, given the gate-ordering change touches shrink's relationship to `ready`. Optionally flag in `index.md` that this is an existing-behavior change.

## Rejected (do not act on)

- The claim that the spec's premise rests on wrong code: rejected. The design routes red through a *new* pre-shrink gate, so it does not depend on "review baseline runs first"; only the prose (item 7) needs correction.
- The claim that the spec should have blocked on a missing prerequisite: rejected. The prerequisite-confirmation gate is plan-draft machinery against the target repo, not an adjudication concern for a harness spec, and the spec correctly made the new gate an explicit first task and decision rather than silently absorbing it. The legitimate residue is the atomicity/scope concern, addressed by item 6.

The loop-back decision and its recoverable-stop direction are upheld; none of the above changes that approach. They close the first-consumer specification gaps, fix one acceptance criterion resting on an unreachable code path, correct the control-flow prose, and split the change to a reviewable size.
