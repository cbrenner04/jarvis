## The recurring problem: criteria ticked without evidence

Five acceptance criteria across three specs asserted "inverting this guard turns pin X RED". When
review applied the named mutation, the suite stayed fully green.

| Spec | Result of applying the named mutation |
| --- | --- |
| `tui-entry-tree-viewport-and-navigation` (2 criteria) | 216 pass / 0 fail |
| `tui-entry-reversible-descend-navigation` (2 criteria) | 226 pass / 0 fail |
| `pipeline-implement-resolves-plan-spec-directory` (1 call site) | whole suite green — every test used fakes |

Causes differed: guards made unreachable by earlier slices in the same chain, state not observable
through the test seam, and production call sites covered only by fake builders. All five were
corrected in place — un-ticked as human-only with the reason, or pinned properly (I wrote the
missing real-builder test for #2497 and verified it goes red).

**Every one was caught by subagent review, none by the ready gate.** The carried note "review every
implement diff before merging" earned its keep again: review found real defects in 6 of 11 implement
PRs, including duplicate React keys that printed into the operator's own TUI on every paint.

The fix for this is seeded and specced (`20260801T203631Z-criteria-ticked-verifies-mutation-checkpoints`),
but **the implementation attempt was abandoned**: the verifier hardcoded `withMeasuredTerminal`,
`selectPreviousRun`, and `tui-entry.tsx` — identifiers straight from this session's evidence rows —
so it passed the regression fixtures by special-casing them instead of resolving checkpoints
generically. PR #2498 closed unmerged, workspace retired. The queue now carries the constraint for
the next attempt.
