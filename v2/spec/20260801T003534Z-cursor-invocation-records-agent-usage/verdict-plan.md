## Verdict — required refinements

1. **With-usage `cost_source` on telemetry rows** — The subspec decides to leave `cost_usd` and `cost_source` unset on `InvocationOk` when parsed usage is present, but `execute.ts` maps unset `cost_source` to `"unavailable"` on `invocation_completed` rows. That contradicts the intent’s usage-before-cost framing and diverges from opencode finalize, which sets `cost_source: "no-price"` when usage is agent-sourced but cost is absent. The spec must choose and pin the row-level outcome: either finalize sets explicit provenance for the with-usage branch (e.g. `cost_usd: null` + `cost_source: "no-price"`) or the intent Behavior section and AC #1 must state that telemetry rows carry `cost_source: "unavailable"` while usage is agent-sourced. AC #1’s “no `cost_usd`/`cost_source` on `InvocationOk`” does not cover the telemetry contract operators actually read.

2. **Present-but-empty `usage` frames** — `parseCursorJsonOutput` can return `usage` as an object with all-null token fields when the frame carries a non-null but empty/unparseable `usage` block. Gating on `parsed.usage !== undefined` will still record `usage_source: "agent"`. The spec must decide whether that is intended provenance (“agent reported a usage block, fields unparseable”) and say so in Decisions; AC #1’s “non-null mapped token fields” should be scoped to fixture-backed happy-path evidence, not a general guarantee.

3. **No-usage warnings** — Opencode no-usage finalize emits a warning; claude no-result warns. The subspec is silent on whether cursor no-usage should warn, omit warnings, or follow another precedent. Add an explicit decision (including “do not warn” if that is the choice) so implementers do not inherit behavior by accident and noisy per-invocation warnings on expected older-CLI paths are a conscious tradeoff.

4. **Documentation coverage** — `v2/docs/shared-invocation.md` is the canonical per-agent finalize contract (opencode’s `usage_source` / `cost_source` branches are spelled out there); its cursor paragraph still describes text-only spawn with no usage finalize behavior and must be in Documentation updates. `v2/docs/v1-behaviors.md` updates should name the stale lines that claim cursor finalize is text-only (`:394`) and that cursor “primarily produces estimated usage” (`:403`), per spec guidance that behavior-changing specs must update that catalog with concrete before/after statements.

5. **Multiple terminal `result` frames (out-of-scope note)** — The prerequisite parser overwrites usage from the last `result` frame, so a later bare `result` clears parsed usage. That is parser behavior, not finalize scope. A brief out-of-scope note in Decisions or Tasks prevents this subspec being blamed for that edge case; optional but low-cost.

**Not required:** Dropping “all-null `usage`” from binding-level AC #2 is correct — opencode finalize omits `usage` on the no-usage path and `execute.ts` supplies the all-null object at telemetry mapping. Intent AC #2’s row-level wording is slightly misaligned but does not block this subspec. Guard-inversion on `!== undefined` vs `!== null` is already covered by AC #2; naming that mutation in a pinning comment is optional polish, not a coverage gap. No split — single subspec remains appropriately sized.
