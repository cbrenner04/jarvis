## Verdict: Required Refinements

**1. Kill/pause for workflow-started runs is unaddressed and must be pinned explicitly.**

`executeWorkflow` has no abort/pause signal parameter today — only the bare write-loop path threads `AbortController`/pause-`AbortController` signals into execution. The spec's current task checklist only covers cleanup-on-settle, never the live kill/pause path, and no acceptance criterion exercises kill/pause against a workflow-started run. Shipping this silently means workflow starts can't be killed or paused, with no error and no test catching it — worse than stating the gap. The spec must add a decision + acceptance criterion covering one of: (a) `executeWorkflow` gains abort/pause signal plumbing, threaded per the intent's "no new pause/resume/abort semantics" boundary, or (b) kill/pause against a workflow-started run explicitly returns `run_not_active` (or equivalent), stated as a deferred-to-first-consumer limitation rather than left unstated. Per this repo's "deferral over invented precision" rule, option (b) is acceptable but must be written down, not implied.

**2. `activeRuns`' single-runId-per-ownership-key tracking goes stale as a workflow advances through steps, and the spec must state the scoping decision.**

The daemon's `activeRuns` map stores one fixed `runId` per ownership key at spawn time; `killHandler`/`pauseHandler` only act on an exact match against that stored id. Each workflow step gets its own runId internally, so once a workflow advances past step 0, the daemon's bookkeeping no longer matches the step actually running. This compounds finding 1 and is currently unaddressed. The spec needs an explicit decision on scope: e.g., kill/pause (if supported at all per finding 1) applies to the whole workflow keyed by the first step's runId, with later steps' distinct runids explicitly out of matching scope — or some other stated resolution. This cannot be resolved silently during implementation.

**3. The synchronous `{ runId }` return for a workflow start has no implementation hook and the spec must decide how it's obtained.**

The bare path can return `{ runId }` synchronously because the daemon itself calls `store.createRun(...)` before fire-and-forget dispatch. `executeWorkflow` creates each step's run row internally, mid-execution, with no callback or return channel exposing the first step's run id before the whole `executeWorkflow` promise settles. The spec's "Dispatch is fire-and-forget... Success response stays `{ runId }`" decision assumes this by analogy to the bare path without verifying `executeWorkflow`'s actual signature supports it. The spec must add a concrete decision for how the daemon obtains the first step's runId synchronously (e.g., a new callback/hook on `executeWorkflow`'s input contract, or restructuring so the daemon pre-creates the first run row itself before invoking `executeWorkflow` for the remaining steps) — this is a signature-level gap, not an implementation detail, and needs to be named in the subspec's decisions and reflected in the task checklist.

**Rationale:** All three gaps are load-bearing per this repo's decision-ledger standard — each names a concrete alternative (silent breakage vs. stated limitation vs. real plumbing) that a competent implementer could resolve wrong or inconsistently absent a stated decision. The intent's own boundary ("No new pause/resume/abort semantics beyond what `executeWorkflow` already defines") means the spec cannot invent new abort semantics from scratch, but it equally cannot ignore that the existing daemon kill/pause surface silently stops working for workflow starts — the spec must state which of these is true and pin it, per the "deferred to first consumer" convention already used elsewhere in the draft (e.g., the memory-headroom queuing deferral).
