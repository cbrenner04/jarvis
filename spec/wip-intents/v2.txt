Split the repo into top-level `v1/` and `v2/` directories so that v1 keeps running unchanged while v2 is built alongside it. This is step 1 of the v2 rewrite — see `v2-vision.md` (sibling of this file; will live at `v2/spec/wip-intents/v2-vision.md` after this change) for the broader context, principles, and architectural constraints. Do not re-derive that here.

Goal: after this change, running `jarvis` (and every CLI subcommand) behaves identically to today, but all of v1's source, tests, specs, and v1-specific tooling live under `v1/`. A sibling `v2/` directory exists with its own `spec/` (containing this intent and the vision doc, migrated as part of this change) and room for src/test to land later. The repo root becomes workspace and repo-wide glue: CI workflows, root README, root `.gitignore`, root `package.json`, root `bun.lock`, shared `node_modules`, and the root `bin/jarvis` shim needed for existing installs to keep resolving. Once v2 reaches parity, deleting `v1/` is one move.

What needs to happen, at a high level:

- Move `src/`, `test/`, `spec/`, and any other v1-only directories/files into `v1/`.
- Create `v2/` with at least `v2/spec/wip-intents/` populated by migrating this file and `v2-vision.md` into it. No v2 source code yet.
- Keep the `jarvis` CLI entrypoint working from the repo root unchanged — binary name, subcommands, flags, stdout/stderr, exit codes all identical. Keep the root package `bin` field pointing at `bin/jarvis`, and update that shim to run the v1 CLI explicitly (for example `../v1/src/cli.ts` instead of `../src/cli.ts`). Existing symlinks to `bin/jarvis` must keep working.
- Convert root `package.json` into a Bun workspace root for `v1/` and `v2/`, while preserving the familiar root command surface. Root `bun run typecheck`, `bun test`, `bun run check`, and `bun run ready` should still work and validate v1 after the move.
- Keep `bun.lock` and `node_modules` at the repo root as shared workspace state. Do not create a v1-local lockfile unless Bun requires it; if it does, document why.
- Split tooling config conservatively: root owns workspace/repo-wide config and delegating scripts; v1 owns v1-specific compiler/test/lint inputs if those configs need to move with v1 source. v2 should not get source/test tooling yet beyond whatever minimal workspace metadata is needed for the empty `v2/spec/` tree.
- CI and GitHub workflows continue to pass against v1 from its new location. Prefer path/script updates over workflow redesign; if workflows already call root scripts, keep that contract.
- Update any cross-references in v1's existing specs that point at old paths (e.g. `src/modes/patch/pr.ts` → `v1/src/modes/patch/pr.ts`), or explicitly grandfather them if updating them is risky.
- This change is purely structural. No behavior changes, no deletions of "probably unused" code, no renames.

Implementation shape:

- Do the relocation as a single big-bang structural move. This repo is currently personal-use enough that staged directory moves would add overhead without reducing meaningful risk.
- This is not the moment to introduce `jarvis1`; that rename is the next intent (`v2-rename-binary.txt`).
- The verification bar is the existing gate plus a small manual CLI smoke test: `bun run typecheck`, `bun test`, `bun run check`, `bun run ready`, `bin/jarvis help`, and one harmless config/read-only subcommand. Do not add broad e2e coverage as part of this split unless the move reveals a specific regression that cannot be covered with existing tests.

Out of scope:

- Any v2 source code or scaffolding beyond the migrated `v2/spec/` tree.
- Cataloging v1 behaviors (next intent — see `v2-catalog.txt`).
- Dropping unused v1 code.
- Renaming `run`/`patch` to `implement` (v2-only concern).
- Touching agent adapters' external contracts.
