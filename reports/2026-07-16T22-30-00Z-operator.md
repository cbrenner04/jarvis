## 3. The headline: a green gate certified a command that could never run

The cleanup anchor was implemented twice, by two different models, and rejected twice. **Neither rejection was caught by any gate.** Both required subagent diff review. This is the single most decision-relevant finding of the session.

### Attempt 1 — codex, PR #1672

`v2/src/commands/cleanup.ts:49` called:

```ts
["pr", "view", "--head", candidate.branch, "--json", "state", "-q", ".state"]
```

`--head` is a `gh pr list` flag. `gh pr view` takes the branch positionally (`gh pr view [<number> | <url> | <branch>]`). Every invocation exits non-zero → `runAsync` rejects → `hasMergedPr`'s `catch { return false }` swallows it → `eligible()` is always false → **discovery always returns `[]`**.

`jarvis cleanup` was a **permanent no-op**. The fail-closed direction is correct, which is exactly why it is silent: the operator runs `cleanup --dry-run`, sees an empty preview, and concludes nothing is retireable — the precise problem the spec exists to fix.

It shipped with **7/7 acceptance criteria ticked and a green gate**, because the test that existed to prove eligibility works (`cleanup.test.ts:15`) was:

```ts
if (command === "gh") return "MERGED\n";
```

Matches the command *name*; never inspects argv. Answers `MERGED` to a call that cannot run.

### Attempt 2 — claude, PR #1675

Re-run from scratch on a stronger model. It fixed the flag (`["pr","view",branch,"--json","state","-q",".state"]` — verified correct against `gh pr view --help`). Its test suite was **100% vacuous — strictly worse**.

Every test passes a fabricated registry (`{ testproj: { root: "/path/to/repo" } }`) while `discoverWorktreeCandidates` reads the **real** `~/.jarvis/worktrees/<projectKey>`. That path does not exist → zero candidates → early return. The `isMergedPr` and `listRunsFromDaemon` mocks are never invoked. The two guard tests assert `toContain("no merged worktrees to remove")` — the *zero-candidates* string — so they pass with the guards deleted.

**Demonstrated, not inferred:** restoring the original `--head` bug *and* stubbing `checkWorktreeEligibility` to `return { candidate, eligible: true }` (every guard removed) still yields **7 pass / 0 fail**.

The vacuous suite masked two further defects, both of which any test reaching the subprocess layer would have caught instantly:

- **The command can never succeed.** `removeWorktree` is `rmSync(path, {recursive, force})` with no `git worktree remove` and no `git worktree prune` anywhere in the diff. The registration in `.git/worktrees/` survives, so git still considers the branch checked out, and the subsequent `git branch -d` → `-D` fallback **both fail** (`cannot delete branch 'x' used by worktree at …`, reproduced live). Every eligible worktree ends half-mutated: directory deleted, branch orphaned, stale registration left behind, exit 1 — and not idempotent on re-run. Strictly worse than a no-op.
- **Daemon-down fails open.** `cli.ts:~498` wraps the daemon call in `catch { return [] }`, so an unreachable daemon yields zero non-terminal and zero live runs → **eligible**. "Ownership inspection unavailable" is exactly the case the spec says must fail closed; here it reads as blanket permission. Concrete: daemon crashes while a run holds a worktree, PR is merged, `jarvis cleanup` deletes it out from under recovery.

### Root cause — the code shape, not the model

`discoverWorktreeCandidates` resolves `~/.jarvis` internally and accepts **no injectable root**. There is no seam to test against, so the only way to make the suite green is to mock around the thing under test. Two independent models did exactly that, in two different ways, and both ticked the fail-before criterion.

**A third run repeats this.** That is why I stopped at two rather than spending another ~$4 and 25 minutes.

Two contributing spec defects, both of which must be fixed before this spec is re-run:

- **AC #5** required "regression coverage … that fails against the pre-change code and passes after implementation." The second half is true; **nothing verifies the first half**. It is a claim the agent grades itself on, and a permissive mock is cheaper than a real assertion.
- **AC #6** required `bun run typecheck`, `test:v2`, `test:integration:v2` — but **not `bun run check`**. Both agents ticked all criteria honestly while biome was red. The ready gate enforces `check`; the criteria never did. This is a systematic gap: any spec written this way can be fully satisfied and still red-gate.

Seeded: `agent-authored-subprocess-mocks-assert-nothing-about-argv` (#1673, amended with the second instance and the test-seam decision in #1676).

## 4. The reviewed plan path is unusable

`plan --review-passes 1 --review-behavior light` produced, **3 for 3**, a PR containing `.jarvis-plan-stage/` and no spec. Controlled comparison — same ready-intent, same agent, review flags the only difference:

| path | runStatus | spec dir | staging dir |
|---|---|---|---|
| `--review-passes 1 --review-behavior light` | `killed` | none | still populated 25 min after exit |
| plain `plan` | `completed` | landed at `v2/spec/<ts>-<name>/` | consumed |

Two distinct defects, one trigger. Both seeded in #1670.

**(a) Landing never resumes** — `reviewed-plan-workflows-never-land-their-spec`. The landing layer is *already generic*: `publication-landing.ts:5` defines `intent-stage | plan-tree | none` and `landPublication` dispatches all three (`landPlanTree` is what plain `plan` uses successfully). Only the review step's **resumption hook** is intent-shaped — `landReviewedIntentOutput` (`workflow-runner.ts:1575`) and `finishReviewedIntentLanding` (`:1606`) both take `Extract<PublicationLanding, { kind: "intent-stage" }>`, and both call sites guard `if (landing?.kind === "intent-stage")` (`:1834`, `:1986`). A deferred `plan-tree` landing has no resumption path. Review is review — this is an accident of `intent-reviewed` shipping first, not a design. Fix is to generalize the hook to call the existing `landPublication`, not to add a second plan-shaped hook that can drift the same way.

**(b) False `killed`** — `a-non-durable-review-step-rolls-up-as-killed`. `workflow-runner.ts:1980` deliberately gives generic review steps no run row:

```ts
// Only reviewed-intent workflows carry a durable post-review checkpoint; generic review
// steps stay non-durable (no run row, fresh synthesized run ID each dispatch).
```

…while `workflow-run-status-rollup.ts:39` returns `"killed"` for any step with no run row. So **every reviewed plan reports `killed` by construction**, on success, while its own log ends `boundary_committed / completed` then `loop_finished / complete`. The rollup already skips `review-debate` steps for what looks like this exact reason; the generic review step never got the same treatment. Cost: `killed` is a terminal failure status, so it sends the operator hunting for lost agent work and a daemon restart that never happened. It cost this session real time before I read the rollup.

**Workaround in force:** drive plans with plain `jarvis run workflow plan`. Verified twice (cleanup, promotion) plus once on claude (triage).

## 5. Other findings, all seeded

- **`a-daemon-lost-run-row-deadlocks-the-daemon`** (#1665). A durable row that is non-terminal *and* absent from memory is refused by **both** guards at once: `daemon stop` → `DaemonStopRefusedError: active durable runs: df8ec8f8…`, and `run kill` → `run_not_active`. `run list` shows it `in-progress` / `not-live`; its spec had already merged and archived. Because the harness *requires* a daemon restart after every v2 code merge (stale snapshot), **one stranded row wedges the daemon and every subsequent v2 merge**. Startup reconciliation would clear it — but reaching startup requires the stop the orphan forbids. Both guards are individually correct; neither owns the case where the row is non-terminal but the process is gone. `run list` already knows (`not-live`); nothing acts on it.

- **`ready-gate-tier-is-not-configurable`** (#1670). `ready-finalize.ts:54`:

  ```ts
  env: { ...process.env, JARVIS_READY_TIER: "full" },
  ```

  Spread *then* literal — the operator's value is overwritten, not inherited, so `export JARVIS_READY_TIER=…` silently does nothing. Measured: a two-file markdown plan spec cost ~15 min wall clock, ~13 of it gate (~85%). Every workflow pays the worst-case gate identically, and the aggregate suite is also the one suite CI never runs. This is the dominant wall-clock cost of v2 and the top throughput lever available.

- **Publication failed silently, twice.** Both the triage plan and the cleanup implement committed locally, pushed nothing, and opened no PR. `jarvis run resume` reported `resumed` and changed **nothing** — row byte-identical, no new events. Both hand-published (`git push` by hand worked first try, so the push mechanism is fine). Worth noting Wave 1's guard (#1658) behaved **correctly** here: it recorded `completion_commit_failed` rather than claiming success without PR evidence. The detection works; the recovery path does not.

- **Wave 1's repair loop works — observed firing for real.** On the codex cleanup run: `ready_gate_repair { attempt: 1, gateExitCode: 1 }` → fresh `iteration_started` → `boundary_committed / completed`. The red gate was handed back to the agent instead of stranding the run. This is the first independent confirmation that #1654 does what it claims.

- **`jarvis1 cleanup` is blind to v2 — confirmed live.** Reported "no merged worktrees to remove" with **26 abandoned v2 worktrees on disk** under `~/.jarvis/worktrees/`. Hand-reclaimed 30 → 3. This is exactly the gap the (unlanded) anchor addresses, and it recurs every session until it lands.

- **`worktree_claimed` on a re-run.** After tearing down a worktree, the next `implement` on the same branch returned `worktree_claimed: Worktree already claimed`. Re-invoking cleared it, as the runbook documents. Non-blocking but a wasted cycle.

- **`unknown_run` on workflow start.** One `implement` invocation returned `unknown_run: Run 6b80f80d… not found` — the CLI got back a run id the daemon does not have. Not reproduced; not seeded for lack of evidence. Flagging in case it recurs.

## 8. Recommendations

Ranked by leverage.

1. **Do not re-run the cleanup spec as written.** Fix the spec first, or attempt 3 fails like 1 and 2:
   - give `discoverWorktreeCandidates` an **injectable root** so the suite can be honest;
   - add `bun run check` to the acceptance criteria;
   - replace the self-graded "fails against pre-change code" criterion with something mechanically checkable, or have the harness run new tests against the base tree and require red.
2. **`promotion-consumes-its-input` is the better anchor** — its spec already demands baseline-failing tests, symlink-escape coverage, and real-path comparison on both sides. It was in flight at close; check it before re-planning anything.
3. **Fix reviewed-plan landing.** Cheap (generalize one hook to the existing `landPublication`) and it restores review to every plan in the repo. Currently review is effectively off, silently.
4. **Fix the rollup's `killed`.** One line of intent, high operator-confusion cost.
5. **Make the gate tier configurable.** ~85% of v2 wall-clock is a gate that CI never runs. Biggest throughput lever available.
6. **The daemon deadlock is a latent session-killer.** It did not block this session only because every merge was markdown. The first v2 code merge that needs a restart will hit it.
