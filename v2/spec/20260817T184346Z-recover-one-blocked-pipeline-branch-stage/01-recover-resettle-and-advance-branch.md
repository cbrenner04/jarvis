# 01 - Recover, re-settle, and advance only the target branch

## Problem

An admitted recovery target is inert: nothing invokes `recoverPlanStage` on it, re-settles the branch's failed stage row from the attempt, or advances that branch. `reopenFailedPipeline` alone hands the row back to fresh dispatch, which redrafts and discards the operator's correction.

## Decision ledger

- Recovery captures the entry run id (`workflowInvocationId`) and worktree path from the resolved failed row before any mutation; the attempt runs against that capture, not against a re-read of the row, because `reopenFailedPipeline` nulls `workflow_invocation_id` and the row must stay readable until settlement.
- Recovery claims durable stage admission (`claimPipelineStageAdmission`) before running the attempt and refuses `stage_claimed` — a remap of the store's existing `claim_lost` outcome — when the claim is held; rules out a concurrent `dispatchPipelineStage` mutating a row recovery is mid-attempt on.
- The attempt (the injected seam, defaulting to `recoverPlanStage`) runs directly against the captured entry run and worktree with no prior row mutation: the target row's `failed` status, `failureDetail`, and linkage stay exactly as resolution found them until the attempt's outcome is known. `recoverPlanStage`'s own run-shaped admission (populated staging, `blocked` status, Git mode, operator-blocker, staged validity — see `00`) runs first and can still refuse; rules out reopen-first ordering, which would null those fields before that admission has run, discarding the operator-facing diagnostics the intent's "settles with its reason" depends on, and stranding the row's linkage if the process crashes mid-attempt.
- Settlement reads the attempt's own outcome, never `wait(entryRunId)` — a successful recovery leaves the write run `blocked` (pinned by `v2/src/execution/workflow-runner.test.ts` test `recovers an operator-edited plan stage through publication without redrafting`), so the shared rollup would settle the stage `failed` on every success — and the success predicate is `outcome.ok && outcome.kind === "complete"`, not `outcome.ok` alone: `recoverPlanStage` also returns `ok: true` for a non-`complete` workflow result and for `kind: "completion_commit_failed"` (nothing was committed in either case), and settling those `succeeded` would ship the success-shaped no-op the intent rules out.
- Only a successful attempt (`ok: true`, `kind: "complete"`) reopens the branch (`reopenFailedPipeline` — the only primitive that clears the branch's `skipped` suffix and requires the `failed` row to still exist), immediately relinks the reopened row `running` to the captured entry run, and settles it `succeeded`; this confines the relinked-`running` window to the success path, where the row is about to be overwritten with the real artifact anyway.
- A refused or failed attempt (an `ok: false` admission refusal, a non-`complete` workflow result, or `completion_commit_failed`) never reopens; it settles the still-`failed` target row in place (`updateStage`, which patches by `(pipelineId, stageId, branchKey)` with no status precondition) with the attempt's own reason in `failureDetail`, continues nothing, and leaves the row `failed` and admissible for another correction without a fresh resolution walk.
- A succeeded settlement's artifact is built by the same private `stageArtifactFromEntryRun` helper (`pipeline-stage-dispatch.ts`) ordinary settlement uses, from the entry run's own `specPath`, `downstreamInputs` (when present), `prNumber`, and `prUrl` (when present); a recovered plan run never opened a PR, so its run row carries no `prNumber`/`prUrl` and the helper naturally omits them — rules out a recovery-only artifact shape the downstream `approve-plan` gate cannot consume, and is proven by comparing the recovered artifact's field set against an ordinarily-settled plan stage artifact's.
- Success continues via `continuePipeline(pipelineId, deps, branchKey)`, scoped to the target branch; for the `full-review`-shaped fixture the plan stage's successor is the `approve-plan` gate, so continuation moves that gate row to `awaiting` and dispatches nothing further — rules out unscoped continuation, which would walk sibling branches whose gates the operator has not decided, and rules out asserting a downstream workflow stage dispatches when the real successor is a gate.
- The attempt seam is injected (defaulting to `recoverPlanStage`) so the daemon can layer its worktree claim and log sink; rules out this module reaching into the daemon's ownership registry.
- Out of slice: a concurrent continuation adopting the relinked `running` row mid-attempt. Durable stage admission gates `dispatchPipelineStage`, not `advanceWorkflowStage`'s adopt path, and a pipeline has one live continuation owner.
- Out of slice: a leaked `pipeline_stage_admission` claim after a crash mid-attempt. The claim has no stale-holder sweep and `releasePipelineStageAdmission` refuses any non-holder, so a crash between claim and release leaves the branch permanently `stage_claimed`-refused; operator disposition is to identify and delete the leaked `pipeline_stage_admission` row for `(pipelineId, stageId, branchKey)` directly, the same manual recourse a leaked claim from ordinary dispatch already requires. An automatic stale-claim sweep is a separate, deferred piece of work.

## Implementer notes

- Reproduce the blocked shape the way `v2/src/execution/workflow-runner.test.ts`'s `recoverPlanStage` suite does (real Git worktree, staged tree, seeded `blocked` run with a `contract_miss` attempt and a `contract_miss_detail` log record), then attach it to durable pipeline rows.
- Inject `resolveStage` to return the plan stage's write and review steps so the test does not depend on the project registry or machine config; give the write step a binding factory that records invocations, so "no redraft" is asserted, not assumed.
- Capture the entry run id and worktree path from the failed row *before* running the attempt, not just before `reopenFailedPipeline` — the attempt itself never reopens the row, so the capture is what the attempt runs against regardless of outcome.
- For the `completion_commit_failed` case, inject the attempt seam directly (bypass the real `recoverPlanStage`) to return `{ ok: true, kind: "completion_commit_failed", completionCommitError: "..." }` deterministically rather than staging uncommittable filesystem state.
- `adoptAndSettlePipelineStage` is not the settlement path here: it waits on the entry-run rollup, which stays non-`completed` after a successful recovery.
